# Recipient-controlled coordination notifications

`notify_agent` delivers a discretionary coordination notice, not a review, task, challenge or assignment event. Review requests are submitted to the existing frozen shared review queue and claimed by an eligible reviewer; agents should not notify individual named reviewers to request work. No reviewer polling or fan-out is required.

A registered agent may call `get_notification_preferences` for its current durable policy, `set_notification_sender_block` to block/unblock a project-qualified sender, or `set_notification_mute` to mute/unmute discretionary notices. Set `senderProjectName` to the sender's project for cross-project blocks; omit it for this project. The recipient's policy lives in the destination project's Git ledger, separate from assignments, and works while the agent is unassigned. Per-sender blocks take precedence over general mute. Existing pending notifications remain visible; changing preferences never silently acknowledges or deletes them. Blocks are reversible.

Sender block keys use the canonical registered project name, **not** a selected checkout. `Jarvis` and `Jarvis::registered-worktree` represent the same project for preference writes, source verification and delivery decisions; aliases of the destination are local. Unknown or malformed selectors must fail project verification, never be interpreted as arbitrary new sender identities. The original operation UUID remains stable across aliases.

When blocked, the destination ledger atomically records an immutable suppression decision under the original operation UUID, **without adding a notification**. The response exposes `notificationDelivery.status = Blocked` and the recipient-selected `autoReply` (if any), or a generic block indication. The autoreply is a direct tool result, never a reverse notification. When allowed, the response exposes `status = Delivered` and the durable notification UUID. Replaying the same UUID preserves the original outcome and reply even after preferences change; a new UUID sees current settings. Concurrent sends and preference changes serialize through the ordinary Git ledger CAS path. This prevents accumulating hidden inbox notices, although each unique attempted blocked send necessarily has a durable decision receipt for replay safety.

Autoreplies are optional plaintext, at most 512 UTF-8 bytes, without control characters. Each recipient may store at most 32 explicit sender blocks; this bounds preference-record size and policy evaluation. Only the specifically selected autoreply is visible to a blocked sender. These tools follow the project's existing explicit agent-ID and authenticated-user access model: that model does not cryptographically bind a ChatGPT conversation to a particular agent identity, so no stronger per-agent identity assurance is claimed by this feature.

The shared reviewer queue and canonical review/assignment/challenge state are unchanged by notification blocks. Do not use a different operation ID or agent recipient to work around a `Blocked` response.

Deployment/role rollout: the repository's `Jarvis/AGENTS.md` is project-scoped, not an account-global policy. The integration owner must attach the reviewer-pool-only coordination instruction to applicable persistent reviewer/worker/Lead roles or workspace-wide instructions for Jarvis, Wayfold, Favn and other registered projects. Keep canonical review events exempt from discretionary notification suppression; do not assume this repository's instructions propagate automatically.
