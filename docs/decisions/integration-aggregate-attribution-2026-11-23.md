# Aggregate source inclusion is not a constituent publication

## Decision

A managed integration publication has exactly one canonical completion receipt, attributed to the original publisher and operation. When a reviewed aggregate already includes separately reviewed constituent sources, another target push or a synthetic v1 receipt is not evidence of the constituents' publication. Use a distinct disposition: `IncludedInAggregate`, with all original constituent publication fields still blank.

The original independent aggregate reviewer can explicitly attest an exact task-bound constituent submission through `record_aggregate_inclusion`. This is a Git-write-authorized ledger transaction, **not** a source publication. It does not complete tasks, change reviews, accept a work-composition unit, unblock queues, or implicitly activate the reviewer’s unrelated Ready assignment. Older readers that recognize only Pending/Integrated cannot dispatch or accept the new status; strict historical schema readers may reject affected task reads until updated. Deploy compatible readers before separately authorizing any production attribution. The original aggregate v1 receipt and source refs remain unchanged.

## Evidence and validation

The request binds the constituent task/submission, caller's stable operation UUID, aggregate task/submission, aggregate original completion UUID, exact independent Accepted review decision operation UUIDs, final reviewed aggregate tree, and an explicit list of per-path corrections if necessary. The correction locator may be a shared review as evidence of a changed path; that never creates a task-bound integration for an unbound/shared review. Neither a summary document, owner assertion, bare ancestry, nor a review ID without its exact decision operation is sufficient.

The operation independently verifies the ledger project, epoch and original transaction receipts, immutable Accepted review decisions (allowing acknowledgement but not replacement), exact remote review and integration refs, original Pending submission and aggregate v1 completion. The aggregate reviewer must be independent of both constituent and aggregate authors. The constituent decision and Pending submission precede the aggregate decision. The reviewed constituent commit must be an ancestor of the reviewed aggregate. The exact Git tree delta relative to the constituent's reviewed base is checked path-by-path, including file mode, object ID, and deletions, against the aggregate tree, the original published integration commit, and the observed current target. A later independently Accepted correction may explain a different final entry only when its exact source is in the aggregate ancestry, its decision predates the aggregate decision, and its own reviewed delta establishes that entry. Duplicate, unrelated, redundant and missing corrections fail closed; an empty or reverted constituent delta is not inclusion.

The observed remote target must retain the original publication lineage and the validated constituent path entries at the time of attribution. This is historical evidence, not a continuing guarantee against subsequent target edits or an independent external target CAS. The ledger CAS revalidates the full proof when replanning; it atomically sets only the constituent disposition and creates `records/integration-attributions/<task>/<submission>.json`. The immutable record contains project/ledger/epoch, actor, operation, original publication locator, constituent and aggregate commit identities, reviewed tree, observed target, and exact typed evidence. Stable operation replay returns the original ledger result; a changed request under the same UUID is rejected. A new operation cannot overwrite the record. Pending-intent reconciliation requires the exact original request and both entity effects. Reads expose verified historical records separately from actual integration receipts.
