# Trusted-writer managed integration acceptance — decision, 2026-11-21

**Decision:** Under the human Operator-approved trust model, Jarvis's authorized operator/client Git and canonical-ledger writer is trusted. Inputs, review and source identity, target effects, state transitions, concurrency, replay and uncertain outcomes must still be verified. No separate signing key, GitHub App publisher, remote service or competing journal is required to unblock managed acceptance. This is a design decision, not a merge, deployment, scheduler activation or Git-host permission change.

## Boundaries verified in the accepted HOLD ancestry

- The supported external MCP/OrchestrationApi exposes typed `SubmitIntegration`, `CompleteIntegration`, and `CompositionAcceptIntegrated` commands. These do not accept caller-supplied ledger-file planners or publication receipt bodies. `ReviewWorkflow.completeIntegration` constructs its canonical request using the original operation UUID and pending submission, and calls `LedgerStore.publishIntegrationTarget` before storing the resulting receipt.
- The publisher reads the immediate remote T, rejects an already-published proposed tip and an incorrect mechanical merge first parent, performs an ordinary bounded **non-force** push, then reads back the target. An unknown remote effect is `OutcomeUnknown` and **must not be replayed** under a fresh UUID or an assumed failed push. A lost ledger CAS after push is not proof the push failed.
- `LedgerStore.transact` remains an intentionally general *in-process* ledger primitive used by legitimate workflow, WorkComposition and WQ02 writers. No raw arbitrary transaction/planner is exposed through the supported MCP command surface. This API scoping does not make arbitrary same-privilege code safe. A nominal F# visibility change is not a security boundary.
- The managed acceptance adapter checks the immutable originating `CompleteIntegration` operation and canonical request, original historical receipt, Accepted independent review/source and exact managed ref binding, project/ledger/target, v1 mechanism/operation ID and remote Git ancestry. For genuine clean diverged I=(T,S), it checks original first parent T and mechanically identical conflict-free merge tree. It is read-only.
- WorkComposition accepted graph CAS and the frozen WQ02 stage release share this verifier in the same original project Git ledger transaction. A normal `CompositionMutate.Accept` without it is rejected. A stale competing CAS or UUID replay never silently retries remote publication.
- Managed blank publication fields/pre-v1-looking direct completions remain fail-closed: no authenticated historical rollout anchor or documented exception exists. Separate branch-only historical workflows are unchanged.

## Explicit adversarial limit

The preserved disposable bare-Git two-clone experiment sets B, accepted source S and independent advance U; a privileged actor externally force-rewrites U to S and directly manufactures a canonical `CompleteIntegration` operation with plausible `VerifiedNonForceGitPush/v1` fields through generic `LedgerStore.transact`. Under the approved model this actor has **already bypassed the trust boundary** by combining arbitrary ledger writes with target writes. Consumer consistency checks cannot distinguish perfectly fabricated old history from a true trusted publisher execution. The fixture intentionally demonstrates that limitation rather than declaring an impossible local proof or suppressing the observation. Ordinary supported typed MCP operations cannot supply this forged planner/receipt, but bugs or compromised privileged clients remain real risks.

An independent authenticated publisher or GitHub App, stronger remote branch/force-push protections, and principal separation across **all** canonical ledger, graph, queue and target writes can be pursued as optional defense-in-depth, subject to separate authorization. None is this task's prerequisite. No invented cryptographic issuer or journal is installed.
