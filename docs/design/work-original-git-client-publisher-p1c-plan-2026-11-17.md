## 1. Decision

**Use the existing typed `IOriginalGitPublisherAuthority.PublishCas` as the future authenticated execution boundary at the lowest original Git publication seams.** It must own both durable operation admission and the *actual remote ref mutation*. Do not add a `mayPush`/`isFenced` client guard whose success is followed by an ordinary client `git push`: it cannot exclude unchanged stale clients, and it has a check/push race. The publisher must be the only principal whose credential or host-side transport can advance **all** protected original project/account/source-effect refs. The client continues constructing original Git commit trees and opaque original receipt bytes; it receives a typed authoritative CAS result or an unresolved effect, never a reusable push permit. The accepted P1a gateway design remains controlling; P1c should compose with its publisher journal, executor, and trusted inventory rather than building a second client-side backend.

Do not switch the old pathways off until the operator explicitly authorizes and verifies **remote exclusion**, including previously deployed clients with still-valid old credentials. An opt-in client wrapper can improve new-client behavior, but is **not** an all-client fence. Maintain default-off compatibility with **ordinary current Git behavior exactly**; production old Git ledgers remain authoritative.

## 3. Existing contract to reuse; missing facts

`Server/OriginalGitPublisherAdmission.fs:11–93` already supplies `OriginalGitRefPurpose`, `OriginalGitPublisherTarget` (account/project/ledger/epoch/canonical repository/fingerprint/exact ref), `OriginalGitPublisherIdentity` (publisher/device/protocol/credential generation), `OriginalGitPublisherCas` (original UUID, request SHA, expected/new OIDs, optional source-effect operation UUID), `OriginalGitPublisherCasReceipt`, `OriginalGitPublisherFailure` (including `Fenced`, `ReusedOperationId` and `OutcomeUnknown`), `OriginalGitPublisherFenceRequest`, `OriginalGitPublisherBarrierReceipt` and `IOriginalGitPublisherAuthority`. `validateCasAgainstTrustedInventory` and `validateFenceRequestAgainstTrustedInventory` (:211–250) check supplied typed records against a supplied inventory; **no authenticated production inventory or publisher implementation is registered by this P0 contract**.

Proposed smallest enabled-path adapter:

1. **Host-selected, default-disabled, typed publication port** internal to the original writer boundary; use the existing authority types. A host-owned authenticated publisher connection selects the allowed remote and derives publisher identity, device, credential generation and ledger/ref registry independently. `LedgerBinding`/`AccountBinding` and `SourceEffectScope` hashes are useful *consistency inputs*, not trust roots or evidence of every credential channel. Bind the validated exact ref and immutable repository identity before sending an operation; never accept an actor, Git URL, agent label, or caller-built “trusted inventory” as authority.
2. **Client proposal remains local and content-addressed.** Preserve existing Git tree/commit construction, source object checks, original intent/request canonicalization, original Git operation record and original result hashes. Submit to the authority a canonical envelope with the expected remote OID (or absent), proposed commit OID (or absent for guarded delete), operation UUID, original request SHA, fixed target purpose and explicit source-effect identity. The publisher returns the outcome of its own ref CAS; *client must not perform a second direct push after success*.
3. **Object delivery is a required, currently unimplemented part of the seam.** A local commit SHA by itself is insufficient if the publisher cannot read the object. Authenticate a bounded Git pack/bundle or content-addressed upload into a publisher-controlled **non-ref-mutating quarantine**; validate object type/OID, tree/commit provenance, parent ancestry and size. Only the publisher may move the intended protected ref. Do **not** stage via an unprotected branch, API ref creation, or client push to a “temporary” remote ref: that would reintroduce a write channel. Exact transfer and remote host design require separate review/lease.
4. **One server serialization and durable journal domain.** Key each effect by authenticated subject, original UUID, canonical digest, physical (`repository,ref`), epoch, exact expected/proposed OIDs and kind. Persist durable `Prepared` before any remote effect. Run actual remote CAS under the same publication/barrier serialization lane. Return an exact durable `Applied`, `StaleRemoteHead`, `Fenced`, or `Unknown` receipt; an uncertain push is held in `RecoveryHold` with no fresh UUID and no speculative retry. Identical replay returns the same journaled outcome; changed digest/target/identity/device/epoch is `ReusedOperationId` / authority error. A remote head alone is not proof of which operation won.
5. **Preserve legacy public result types.** Keep `LedgerWrite.Operation`, `CurrentHead`, `AlreadyApplied` and `AccountWrite.Receipt`/`CurrentHead`/`AlreadyApplied` from the same canonical Git records; do not synthesize or reserialize `OriginalResultJson`, `OriginalResultHash`, `RequestHash`, `AccountOperationReceipt.OriginalResultJson`, `ResultSha256` or `Sequence` from the new publisher receipt. The publisher receipt is *additional transport evidence* tied to the old durable operation. Map typed unknown effects to old `LedgerFailure.OutcomeUnknown` or `AccountOutcomeUnknown` **without turning “unknown” into a confirmed conflict or success**; preserve operation identity for same-UUID reconciliation. Keep detailed publisher refusal discoverable through a typed diagnostic instead of silently changing an original receipt.
6. **Already-applied legacy receipts are not admission bypasses.** In default-off mode, honor current early replay semantics exactly. In enabled mode, a local `findApplied`/`readReceipt` may return the original immutable receipt *only after* authoritative phase/identity check confirms this is a pure read of a genuinely prior operation, not a new source ref effect or publication. Barrier-pending or unknown replays that might publish remain blocked. No planner-only guard.
7. **No second production Work database or client-wide SDK.** Reuse P1a publisher store/executor and eventual single authenticated server SQLite transaction authority; do not replace the unrelated FeedbackStore. Keep the small adapter private to the existing F# publication leaf functions, with explicit named per-purpose policy rather than an extensible generic Git mutator for clients.

### Source-ref operation identity and ordering gap

`publishReviewRef`, `publishIntegrationRef`, and `deleteReservedReviewRef` currently receive `binding + ref + OID` but **no caller-stable source-effect UUID**. Their `ReviewWorkflow` parents do have a stable *ledger* action `operationId`, while a source ref publication and subsequent ledger CAS are **different physical effects**. A single publisher UUID must not be reused for both distinct envelopes (strict operation-reuse checks would reject it).

A future narrowly reviewed signature/context change must carry a **durable, deterministic, domain-separated stage identity** (parent original operation UUID, stage kind, exact managed ref, intended OID, canonical request digest) established **before the first side effect**, with one stable publisher effect UUID per stage. Bind that effect to the same original action and journal lineage; do not use `Guid.NewGuid()` per attempt or infer authorization merely from the deterministic hash. The exact field/link representation is an interface decision for P1b/P1c review; current `OriginalGitPublisherCas` carries `SourceEffectOperationId` but does **not** by itself authenticate parent ledger-action linkage or provide a durable source-effect reinspection method. Add the minimal necessary typed correlation/reinspection mechanism with a reviewed contract change, or retain NO-GO; never overload an unrelated ID silently.

Preserve order: inspect source/accepted review → durable source-effect prepare → publisher-only create-only ref CAS → authoritative ref verification → original ledger CAS. If latter loses, keep the source orphan and its immutable evidence (as `ReviewWorkflow.fs:3418–3420,3469–3471` already intend); deletion, if independently authorized later, is separately journaled with exact expected SHA. Replays inspect both journaled stage and canonical ledger outcome without a second source publish. Do not mistake `AlreadyAbsent` after an unauthenticated read for remote fence evidence.

### Initialization and provenance gap

`LedgerStore.initialize` and `AccountCapacityLedger.initialize` have no per-attempt caller UUID. The approved caller consent/first-creation rule and account auto-init are not interchangeable. Under an enabled publisher, introduce a separate explicitly authorized bootstrap operation with stable identity, exact absent-ref lease, a trust-bound original ledger/project/account ID and durable recoverable receipt before ref creation; require full verification of retry/conflict after lost response. Until such contract exists, **do not route enabled initialization to a fresh anonymous publisher operation**. The default-off initialization functions stay unchanged.

Source OIDs may originate from registered worktrees, but `sourceRepositoryIdentity` and approved URL checks are not independent credentials/remote rule proof. `LedgerStore.validate` (`LedgerStore.fs:511–529`) and account `validate` (`AccountCapacityLedger.fs:389–402`) compare local Git remote URLs to locally approved values. `LedgerStore.inspectRemotePolicy` (:531–582) explicitly reports hosted policy as unknown. No source scan establishes the authorized repository inventory, installed client population, canonical repository+ref uniqueness across remotes, or actual GitHub rules/bypass permissions. These remain explicit blockers.

## 4. Required atomicity, concurrency and recovery semantics

**Physical identity and ref coverage.** Trusted inventory must enumerate each actual original project repository and account repository, ledger ID/epoch, canonical repository identity, exact approved fetch/push transport, host/credential generation and every mutable ref class. This includes dynamically created review/integration refs, their deletes, alternate branches/tags, API ref endpoints and alternate protocols. Detect duplicate (`canonical repository,ref`) with inconsistent scope; reject mismatched project/account/epoch/fingerprint, aliased name on two devices, missing ref registration, unauthorized wildcard or unknown admin bypass. No claim that a library regex captures the full host namespace.

**Exact Git semantics.** Project CAS remains a nonforce fast-forward update from the fetched current original parent; account CAS remains an exact-old-head lease, never an unconditional update. Review/integration refs are create-only even if another existing value would be a fast-forward; deletion requires exact OID and authorization. Publisher must independently verify proposed commit object and **old head** at effect time. A generic `git update-ref new old` alone would not enforce all historical nonforce/ancestry rules; add that verification in the same serializing domain. Reads/fetch caches remain read-only, including when fenced.

**Account and project are physically separate Git authorities.** Do not claim a SQLite transaction makes a multi-remote Git update atomic. Record one global `FencePending` / monotonic barrier epoch before exposing any individual project/account fence as positive; stop new admission for all in-scope refs, drain or reconcile every in-flight prepared effect, then independently confirm every host rule, head, original pending-intent/source-effect high water and account/project ledger epoch. A partial fence stays **nonpositive and fail-closed**; C3 must not promote on partial evidence. During cancellation, disconnect, delayed response, server restart, restored stale backup or Git divergence, retain `Unknown`/`RecoveryHold` until independently reconciled. The old and new authorities must not both have live write credentials to a supposedly protected ref.

**Original pending-intent and source-effect high water are separate from Git ledger sequence.** `LegacyDirectWriterFence.inspectHighWater` (`LegacyDirectWriterFence.fs:115–133`) explicitly returns Unknown for the original pending journal, source-effect journal and client protocol population, even when it knows project `NextSequence - 1`. `SourceEffectJournal` is host-local and incomplete; it cannot certify historical uninstrumented source activity. Need source-attested import of every relevant original pending UUID/hash, in-flight remote effect and source-effect route through the all-client authority. Missing continuity, disconnected clients, unreviewed process trees, unobserved effect, or lost journal means no positive barrier.

**Remote exclusion is a separate independent proof.** An unchanged stale client with a valid legacy PAT/SSH credential must be rejected *by the enforcing remote* after the fence; it cannot be expected to install this adapter. Required operator-reviewed host plan: deny old Git/API/SSH/Actions/admin bypass, protect refs and their creation/deletion, restrict only the private publisher credential, inventory alternate URLs and direct filesystem access, and independently verify the exact host policies. A disposable bare-Git pre-receive hook proves only disposable receive-pack rejection; it cannot prove GitHub.com is configured, nor exclude bare-repo filesystem writers. Existing hosted audit has not supplied this proof. No GitHub Actions.

**Default-off old paths.** When feature is disabled, call the original `git push` and confirmation/retry paths as before, with the same OID, refspec, remote, output errors, opaque receipts, `AlreadyApplied`/`AlreadyAbsent`, and order of source ref versus ledger CAS. No new auth request, pending operation, SQL write, network call, UUID, false fence result, or migrated identity requirement may affect normal legacy operation. Current optional `LegacyWriterProtocolFence`/`LegacyDirectWriterFence` remains a separate default-off command guard; it is neither removed nor treated as proof.

## 7. Precise remaining blockers / questions for Lead and operator

1. **Trusted repository+ref inventory:** actual account and each project repository ID, ledger ID/epoch, approved host/push endpoint, every dynamic managed ref/alternate ref or tag, and authoritative head/ancestry. Current local `binding` or URL hash cannot prove full coverage.
2. **Host enforcement and credentials:** full list of old clients/devices, PAT, SSH/deploy keys, GitHub Apps, admin/Actions/API/bypass roles, alternate Git transports and direct filesystem writers; evidence that all stale direct publishers are denied while only the authenticated publisher can mutate.
3. **Object-upload mechanism:** verified quarantine/object transfer to the publisher without creation of a client-writable bypass ref, preserving Git object provenance and fast-forward/lease constraints.
4. **Durable original effect lineage:** all-client old pending intents (operation ID/digest) and source-effect journals, independent high-water/uncertain effects, complete original source route coverage and retry/reconciliation rules; current local WQ03 journal cannot attest it.
5. **Bootstrap/stage identity contract:** durable operation ID for project/account initialization and exact parent/stage identities for review/integration/create/delete effects; per-effect reinspection/readback required across crash and lost response.
6. **Cross-repository barrier implementation:** one serialized publisher admission/barrier domain, monotonic epoch, independent confirmation of all protected heads and no mixed old/new writers, explicit fail-closed partial/unknown states.
7. **Activation decision:** reviewed P1b fixture plus P1c implementation (future), independent actual-host negative/positive proof, then operator-approved recredential/provision/fence and finally separately reviewed C3 cutover. None of these approvals is presumed here.

**Conclusion:** the smallest coherent original-client compatibility seam is **typed publisher-owned CAS at the eight leaf remote-push sites, with caller-stable source-effect correlation and exactly preserved legacy default-off receipts**. That code cannot honestly yield an all-client fence without authenticated remote exclusion, object delivery, and complete old pending/source-effect high-water. Until those proofs and independent authorizations exist, keep existing Git clients and ledgers operating normally and the migration **HARD NO-GO**.
