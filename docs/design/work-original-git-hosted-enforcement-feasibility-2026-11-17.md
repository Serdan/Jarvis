## 1. Executive decision

A single authenticated GitHub App can plausibly be the *only admitted writer of protected branches and tags* when GitHub rulesets and account/repository permissions are correctly provisioned. GitHub documents branch/tag **restrict creations, restrict updates, restrict deletions**, and GitHub App bypass actors. Its installation token supports HTTP Git and REST/GraphQL with explicit repository permissions. This provides a promising **remote** protection layer—unlike a local client pre-push check—but it neither establishes complete coverage of *all* Git refs and credentials nor serializes a multi-repository original-Git CAS/barrier with the Work host's durable state.

**Current observed source repository is not remotely fenced:** `https://github.com/Serdan/Jarvis.git` (GitHub repository ID `720501829`, public, owner `Serdan`) reports **zero repository rulesets** from `GET /repos/Serdan/Jarvis/rulesets?includes_parents=true` (response `[]`). `GET /repos/Serdan/Jarvis/branches/jarvis-orchestration` reported `protected: false`, head `9d63c2227c3af349533bcba1f946fcf1b0c1e2f7` during inspection. The current working tree's `origin` fetch and push URL both resolve to the above GitHub URL. This is an *observed source/project branch*, not proof that every configured Jarvis project or account ledger lives there. The account branch `jarvis-account-admission` returned **404 in this repository**; its authoritative remote may be elsewhere. The connector's branch-protection detail read returned **403 Resource not accessible by integration**; do not interpret that permission failure as no additional protection on uninspected branches.

Therefore **no all-ref, all-credential remote exclusion exists in evidence**. Even if a later ruleset protects `jarvis-orchestration`, a positive witness additionally requires (a) all protected original project/account/source-effect refs and transport routes, (b) an independently administered sole privileged publisher identity, (c) verified denial of unchanged stale clients at the GitHub host, and (d) durable publication/barrier linearization and unknown-effect reconciliation. Never fabricate `AllOriginalClientsQuiesced` from clean heads, source-protocol version, local journals, or a synthetic fixture.

## 3. Documented GitHub.com controls and their precise limits

**Branch/tag rulesets.** GitHub rulesets can target branches and tags, and `restrict creations`, `restrict updates` and `restrict deletions` so only configured bypass actors can mutate matching refs. Bypass may name a GitHub App; a bypass is an explicit privileged writer, not a universal ban on all actors. Rulesets are available for public repositories on Free and for private repos on paid eligible plans. Admins or actors with edit-rules permission may alter/disable them; bypass auditing and parent organization policies must be inspected independently. Classic branch-protection rules may also apply, layering restrictions. A response with no rulesets does not enumerate classic protection. [GitHub: available rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets), [about rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets), [REST rules API](https://docs.github.com/en/rest/repos/rules).

**Target pattern completeness.** GitHub documents `fnmatch` with `File::FNM_PATHNAME`: `*` does **not** match `/`; for arbitrary nesting use carefully validated `**/*`-style patterns or an explicit platform "all branches" target. An innocuous `jarvis-review/*` does not cover the multiple nested components present in original managed review refs. Audit concrete zero/one/many-level names, new branch creation, tag names, exclusions, special refs, and updated future ref grammars. The pattern must cover any original-authority-bearing ref that a stale client could publish, not only today's existing refs. [GitHub: creating rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository).

**Push rulesets are not a blanket sole-writer switch.** GitHub's push rulesets are largely based on changed file paths, extensions, path lengths and file sizes across a repository/fork network. They do not substitute for branch/tag actor-based create/update/delete restrictions, nor establish a universal CAS/barrier hook. [GitHub: about rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets).

**GitHub App identity and token scope.** A GitHub App installation token works with REST/GraphQL, and with Git over HTTPS when the App has Contents permission; installation tokens expire after one hour and can be limited to a subset of the App's granted repositories/permissions. A *dedicated* publisher App with Contents write limited to the authority repositories is a plausible single bypass actor. Its private key and ephemeral tokens must exist only in the server publisher boundary; an App token passed back to clients is a shared remote bypass. The 1-hour lifetime is credential hygiene, **not** a barrier, proof of isolation, or instantaneous revocation of already minted tokens. [GitHub: authenticating as an App installation](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation).

**Alternate API/ref namespaces.** The Git references API exposes create/update/delete using Contents write. The create endpoint documents any fully qualified `refs/.../...` with at least two slashes as its syntactic input; list-matching without a prefix can include notes/stashes. GitHub's documented **branch/tag** rulesets do not promise protection of every generic `refs/*` namespace. This is a real *coverage proof gap* for arbitrary future effects or nonbranch ref writes—not proof that a particular undocumented ref push succeeds in the inspected repository. Do not claim full-channel exclusion from branch patterns alone. Revoke or restrict all nonpublisher *repository write permissions*, or obtain independent host evidence that all permitted nonbranch ref operations are denied. An old owner-level token with unrestricted repository write permission is not made globally incapable of every ref write merely because two branch/tag rulesets were set. GitHub's REST ref-update `force=false` guarantees fast-forward only, **not an exact expected-old-OID CAS**; publisher must use a correct lease/atomic ref update and independently verify the actual result. [GitHub: Git reference REST endpoints](https://docs.github.com/en/rest/git/refs).

**Actions, admin and transport.** GitHub Actions mints a per-job `GITHUB_TOKEN` as a GitHub App installation token; permissions can authorize repository mutations. A stale workflow, a stored PAT/App token, SSH deploy key or administrator-controlled automation may have a distinct write route. Audit effective actor/bypass at the GitHub host, not the hostname or method string alone. An administrator who can edit or disable rulesets is an *out-of-band trust principal*, never a technically excluded writer. [GitHub: GITHUB_TOKEN](https://docs.github.com/en/actions/concepts/security/github_token), [GitHub: deploy keys](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/reviewing-your-deploy-keys), [GitHub: REST rules](https://docs.github.com/en/rest/repos/rules).

**No custom GitHub.com receive hook in evidence.** GitHub documents user-defined pre-receive hooks for **GitHub Enterprise Server appliances**, not as a deployable custom hook for a github.com repository. Thus a GitHub.com ruleset cannot be assumed to evaluate the Jarvis original operation UUID/digest, an authenticated pending-effect high-water or a SQLite barrier at Git receive time. That logic belongs to the exclusive publisher, backed by host-enforced credential/ref exclusion. [GitHub Enterprise Server: pre-receive hooks](https://docs.github.com/en/enterprise-server@3.21/admin/enforcing-policies/enforcing-policy-with-pre-receive-hooks/about-pre-receive-hooks).

## 4. Candidate A — sole-App GitHub.com publisher (conditional design, not GO)

**Provisioning is a separate operator-approved and independently reviewed operation.** Prefer isolating original authority refs in repositories where comprehensive publisher-only restrictions will not break ordinary human source branch work; otherwise human normal development and unrestricted main/source branch writes are an explicit operational conflict. Inventory physical `(GitHub repository ID, full ref)`, immutable ledger identity/epoch and approved push endpoint first. For each actual repository, define effective *active* create/update/delete rulesets with a dedicated GitHub App as the only bypass on every original-authority branch/tag, including new/deeply nested refs. Require privilege and repository access audits: no stale client may possess the publisher private key/installation token, and no other effective owner, classic PAT, deploy key, App, Actions job or admin bypass can write any original authority ref or evade the publisher by switching ref namespace. Existing administrators remain explicitly trusted policy operators, not claimed excluded actors. Site-specific API+Git transport negative tests on disposable repositories are necessary: there is no independent observed positive enforcement yet.

The **only** mutating original-Git request must be handled by an authenticated server publisher deriving account/project/device identity from trusted session/registry, binding canonical repository/ref/epoch, stable operation UUID/digest, exact old/new OIDs, and credential generation. Reuse the proposed single authoritative Work SQLite transaction domain (after its *own* approved cutover), not a second independent general orchestration service or the unrelated FeedbackStore. The publisher holds one serialized admission lane across *all* account, project and source-effect authorities. It durably records Prepare/InFlight/Applied/Rejected/Unknown plus global `Active -> FencePending -> Fenced` or `RecoveryHold` state. Every Git effect is executed **by the publisher**, not authorized for a client-side follow-on push. Exact remote CAS/lease, response/readback and receipt recording are a journaled external effect, **not** one atomic SQLite+Git transaction.

A barrier first commits global `FencePending` before granting any further admissions, then drains or reconciles all previously admitted in-flight effects. A push issued before the barrier may still complete after the request; it must remain inside the publisher serialization/unknown-effect accounting and prevent a positive barrier receipt. A stale clone's direct push is denied by **pre-existing effective remote permissions/rules**, not by the barrier's client-readable boolean. On process restart or lost response, leave `Unknown/RecoveryHold` until reconciled; if original old-client effects were never journaled, remote matching heads alone cannot recover their high-water. Persisted server-state loss and stale backup restore must keep external effects fenced pending explicit Recovery.

**Required proof before an affirmative statement:** from two independent stale clients with still-valid credentials, demonstrate remote rejection across the protected project and account refs, nested review/integration creation/deletion, alternate branch/tag and any allowed other refs, both Git protocols and ref APIs, Actions and privileged paths; verify the publisher App alone may publish; race publisher CAS vs global fence; inject disconnect after remote advancement and before receipt; restart and recover with an uncertain head; independently reread exact auth/rulesets/ref state *before* and *after* the barrier. Missing scopes, stale ruleset evidence, unknown token holders, unaccounted effects or a mutable administrative bypass outside the trusted operator boundary => **HARD NO-GO**.

**Operational footprint:** GitHub remains the bare-object host, so no new Git object server or custom SSH service on the cheap droplet. The existing server gains one small serialized publisher process/queue, SQLite journal transactions, protected credential storage, token refresh roughly hourly and Git/HTTPS/API round trips per original mutation. Remote API latency, token/rate limits and Git outages can dominate; batching, safe retry and effect reconciliation must be measured. No host cost, bandwidth, rate, write-latency or plan-fee figure was independently benchmarked here. Creation of special repositories/rulesets or a paid private-repo tier may have administrative/subscription cost.

## 5. Candidate B — direct bare-Git receive-pack gate (conditional fallback, not approved)

GitHub-only *with fully revoked/reduced old write grants and correctly scoped rulesets* is not shown categorically impossible; therefore no new remote topology is mandated by this audit. **If** operator/host inspection demonstrates that an extant valid writer or required generic ref namespace cannot be excluded by GitHub.com's actual rules/permissions, a minimal controlled bare-Git alternative exists: on the existing droplet, host the already-needed original account and project bare repositories behind a **single publisher-owned receive-pack boundary**, with a restrictive SSH forced command or equivalent authenticated transport, no general shell/bare-repository filesystem access to stale clients, host-level deny-by-default credentials and a pre-receive rejection path for all unadmitted writes. The privileged local publisher serializes exact Git `update-ref`/lease with the same durable SQLite operation/barrier journal; all remote Git clients without publisher authority are rejected, independently of their Jarvis version. A hook accepting a caller-provided "permit" push option or environment variable is **not** authoritative; protect the OS credential/transport instead. Separate backup/restore of repos, audit, quotas, host patching and remote availability are mandatory. Disposable hooks prove only that normal remote pushes are denied, not that clients with filesystem/root access cannot bypass.

| Criterion | GitHub.com sole-App candidate | Bare receive-pack alternative |
| --- | --- | --- |
| Remote denial of old direct writers | Conditional on exact per-repository rulesets and credential/repository permissions, independently tested | Conditional on exclusive SSH/OS credentials, repository ACLs, hooks/transport and no alternate filesystem write path |
| Dynamic nested branch/tag refs | Potentially coverable through complete active target sets; `*` alone misses nested slashes | Explicit `refs/*` deny-by-default gate under the publisher's policy |
| Arbitrary generic refs | **Not proven** covered by GitHub branch/tag rulesets; permission removal or host-specific evidence required | Can reject every ref namespace at server receive boundary, subject to OS access control |
| UUID/epoch/high-water and barrier vs push | Must be implemented by exclusive app publisher + SQLite journal; GitHub rulesets cannot enforce arbitrary Jarvis state | Can share one local serialized update-ref authority + journal; still requires crash and external-effect reconciliation |
| Admin/bypass principal | GitHub owner/repo/ruleset administrators and App custody must be trusted and inventoried | Droplet root/SSH/service operators must be trusted and inventoried |
| Cheap droplet burden | Lower server operations; GitHub hosts repo storage, API/token/rate and network latency | Higher: durable Git objects, disk/inodes, bandwidth, backups, SSH service hardening, availability and recovery |

Do not deploy either choice from this document. In particular, a bare test remote does not prove hosted GitHub exclusion; moving the authoritative original refs would itself require a separate migration/compatibility and rollback plan.

**Present verdict (2026-11-17): HARD NO-GO.** Hosted sole-App enforcement is *technically plausible under a constrained, independently proved ref and credential topology*, but no such topology is verified; the actual inspected Jarvis source ledger branch is unprotected. The evidence neither proves an all-channel GitHub.com guarantee nor mandates a bare-host migration without further host-specific investigation.
