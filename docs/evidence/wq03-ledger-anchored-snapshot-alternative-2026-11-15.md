**Date:** 2026-11-15. **Agent:** Worker 2. **Canonical task:** `wq03-wip-host-protection-proof`, task-spec revision seq 3673.

## Alternative design that can preserve the guarantees

**Authority:** Use a *single* canonical append-only ledger head with host-enforced no-force/no-delete (or independently durable WORM anchor), not a mutable source branch. Each published ledger commit must **atomically contain** (a) canonical `SourceHandoff` receipt + high-water/claim transition and (b) the complete self-contained Git snapshot bundle as a Git blob, not only a 40-char source SHA or a link to source objects in a different repository. The bundle is content-addressed and cryptographically bound to repository identity, source base, predecessor snapshot hash, work/task/lineage ID, stage, claim generation, launch UUID, original operation UUID/request hash, immutable snapshot SHA, bytes/hash, approved remote, and test evidence. Verify that the bundle contains its full closure, that reconstruction into a completely new repo yields the exact commit/tree, and that base/predecessor ancestry holds.

**Submission sequence:** (1) trusted host broker pre-journals each *original* source-mutating process, push, retry, and identity/scope before dispatch; unknown is not terminal. (2) Source worker builds only in a separate generation sandbox without reusable remote-push credentials. (3) Supervisor must authoritatively quiesce and terminalize all prior generation processes and outbound Git effects; any lost original push receipt, ambiguous process exit or delayed retry durably sets `SourceRecoveryBlocked` before release, and retains old claim/token/UUID evidence. (4) Freeze the worktree, check cleanliness and ancestry, create/verify a self-contained bundle and reconstruct it in an independent checkout. (5) Broker publishes exact immutable bundle bytes + canonical handoff receipt in **one ledger CAS commit**, keyed by original stable UUID and canonical hash. If ledger reply is lost, reread the verified head and look up *that exact UUID/hash*; matching applied receipt is idempotent, mismatch is fatal, absence is **not** proof that an external source push/job is terminal. (6) Only after successful canonical CAS and all job/push terminal fences release old launch/token and permit a new FIFO claim. (7) Successor uses a newly provisioned **separate Git repository or storage-isolated generation worktree** reconstructed from the trusted bundle; compare SHA/tree, bind new claim+agent UUID+session to ledger generation, and reject old-session mutations at both ledger and physical effect boundary. Do not rely on a linked worktree sharing mutable refs, alternates or object store with an unfenced old writer.

**Threat counterexamples:** Content addressing protects *what A means*, not who can delete an anchor or issue a late remote side effect. A delayed original `git push --force` to the source target can still change that remote after A is snapshotted. A still-running process can write local files in its old worktree; if new generation reuses the same path, common Git store, credentials or OS privileges, it can contaminate B. A broad Git token that can force `jarvis-orchestration` can erase A from current reachability; `git gc` can then prune it. A fresh clone cannot rely on locally remembered high-water. Neither `git ls-remote`, a clean HEAD, ledger `NotFoundAtVerifiedHead`, cancellation request nor timeout proves the original effect cannot later land. This is why source isolation and terminal host/remote barriers are independent of ledger integrity.

## Minimum operator actions and tested implementation track

1. **No policy-free claim.** Before implementing the alternative, pick the durable trusted anchor: ideally the existing `refs/heads/jarvis-orchestration` **if** its update semantics can be proven append-only/no-force/no-delete and host credential isolation can be safely applied without disrupting the production ledger. Otherwise use an operator-controlled independent append-only/WORM snapshot store, with authenticated immutable object versions and lifecycle retention. A new ref/store must avoid a non-atomic two-ref commit: stage blob first in durable store, then CAS its hash into canonical ledger; pending unreferenced blobs need retention during uncertainty.
2. **Explicit operator authorization** is required to change GitHub protections/permissions or deploy broker credentials. Inventory actual source-worker, broker, scheduled-host, recovery and admin/GitHub App/deploy/PAT identities and effective bypass for `jarvis-orchestration`, `jarvis-wip/**`, and protected target branches; inspect applicable ruleset ID/version, legacy branch protection and inherited policies. Ensure worker credentials are *read-only* to source/ledger anchors and cannot invoke an omnipotent CLI or inherit an admin token; broker is a separate audited principal with the minimum append-only capability. A GitHub ruleset's `restrict updates` with a bypass list may let the bypass actor modify refs, so do not call that alone immutable. Test actual same-effective identities and no-force/no-delete behavior. See GitHub documentation: https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets and https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches .
3. **Retain/attest** reachable snapshot bytes and ledger/backup anchor across full unfinished task, all outstanding original operation IDs, stalled launches and RecoveryBlocked periods (potentially unbounded until explicit terminal/operator reconciliation). Define deletion only after an independently verified terminal + successor/closure high-water. Run two independent fresh-clone fetches *after* representative host maintenance, backups/restore and long-horizon expiry controls. Git's reachable-object GC semantics alone are not host-specific SLA: https://git-scm.com/docs/git-gc .
4. **Separate reviewable implementation track** (not this task): bounded bundle producer and parser with size/resource limits and complete object closure; one-commit ledger snapshot+receipt CAS; host broker predispatch journal and effect terminalization/recovery; per-generation isolated repo and no inherited push token; trusted no-bypass process/remote fences; explicit durable `SourceRecoveryBlocked` transition; exact original UUID/hash lost-ack recovery; crash and two-clone adversarial tests in .NET 11 Release, followed by task-bound frozen independent review and explicit operator cutover decision.
5. Required negative tests: old process running after clean HEAD; original remote push delayed beyond a missing receipt; untrusted old agent tries ledger CAS from stale generation; out-of-band source ref overwritten/deleted/forced; a second client races snapshot publish; ledger ref force/delete attempted with *every effective credential* and denied; fresh clone after retention/GC; same UUID different hash; new checkout cannot access old worktree, common object store, alternate, network credentials or old session; source lineage cannot be upgraded from ordinary `PublishStage`/replay. A missing evidence result is **Blocked**, not success.

**Recommendation:** The self-contained ledger-anchored snapshot approach is architecturally viable **only with a protected/recoverable ledger trust anchor, genuinely fenced old jobs and pushes, no-bypass host credentials, independent generation storage, and proven retention**. It may reduce the need for one GitHub immutable rule per WIP generation, but **cannot replace all host/credential policy**. Until those are proven and separately reviewed, retain existing `verifySourceExternalEffectsAndRefProtection` rejection and keep source succession, Scheduler, deployment and migration disabled.
