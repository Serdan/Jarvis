# Feature: Develop Telos with Telos

- **Identity:** `telos.feature.self-development`
- **Systems:** [Intent](../systems/intent.md), [Work](../systems/work.md), [Execution](../systems/execution.md), [Evidence](../systems/evidence.md)
- **Status:** Proposed enduring Feature contract

## Desired behavior

Telos should be capable of using its ordinary engineering mechanisms on its **own repository**. This is a credibility test of the product, not special permission to bypass the checks it applies to other projects.

With the Operator's intended change and the applicable Telos contracts, the system can identify a coherent implementation slice, authorize an isolated source owner, execute and test a candidate, request a genuinely independent frozen-source review, reconcile requested changes and advance accepted source through the established integration boundary. It should record evidence and report which requirement the resulting source now satisfies.

Self-development must not imply that Telos can approve its own new permissions, bypass existing deployment gates, mutate its running orchestration authority merely by writing a design document, or treat an agent's confidence as a release decision. Changes to scheduling and durable authority deserve the same exact-source and unknown-effect handling as other sensitive work.

## Observable satisfaction

For one nontrivial Telos feature change, a complete trace exists from the **current Feature criterion and approved Work**, through bounded implementation and actual tests, independent review, exact source integration and a current conformance judgement. A requested correction produces a real subsequent candidate and review rather than rewriting acceptance history. The Operator can inspect the sequence without relying on a single giant chat transcript.

**Not implied:** that the current Jarvis implementation already self-hosts, that every future self-change is safe to deploy automatically, or that producing this specification constitutes accepted implementation.
