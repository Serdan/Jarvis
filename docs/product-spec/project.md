# Project: Telos

- **Identity:** `telos`
- **Kind:** Project — enduring product purpose and engineering intent
- **Status:** Proposed specification experiment; not deployed or ledger-authoritative

## Why Telos exists

Telos turns a person's desired software outcomes into sustained, verifiable engineering progress. The Operator should be able to express what a product must do, delegate ordinary technical decisions, and see whether the result actually meets that intent—without manually coordinating a fleet of agent chats, writing a complete task plan, or treating passing tests as a substitute for the product promise.

Telos is an **execution and coordination system**, not the visual client itself. Servitor is the intended visual interface, but Telos must be useful through other authenticated clients and tool surfaces. It should support the Operator's own projects and, as a meaningful proof of its maturity, engineering work on Telos itself.

## Product promise

The effective meaning of a Project, its Systems and Features survives the individual Work items used to build them. Telos maintains that meaning as a natural-language, versioned contract. When the Operator changes intent or implementation evidence reveals a discrepancy, Telos identifies the affected obligations and helps move the real implementation toward the new contract. Neither a completed task nor a persuasive agent report silently rewrites the desired behavior.

Telos should organize the next useful Work, run eligible bounded Activities on authorized resources, obtain independently meaningful evidence, and carry the outcome through review and integration where applicable. Work may be planned, implemented, tested, investigated, reviewed, corrected, integrated and verified by different short-lived executions. The product must remember the objective, what was actually established, and what remains missing between those executions.

When progress toward an objective is constrained, Telos must represent the actual missing dependency, resource, evidence or authorization and make the next eligible action discoverable. It should preserve accountability for reaching the outcome without manufacturing work to fill idle capacity, crossing project boundaries or bypassing authority. A genuine unresolved dependency must remain explicit; progress is established by changed state and evidence, not an executor's narrative.

## Engineering intent and tradeoffs

- **Correct behavior over ceremonial compliance.** Tests, review and evidence matter because they establish relevant claims; producing documents, passing checks or closing tasks is not the objective by itself.
- **Initiative within purpose.** Telos should permit autonomous decisions and reversible, attributable candidate work inside granted scope. Extra approval is for consequential scope, permissions or external effects, not every local engineering judgment.
- **Proportional verification.** A disposable code experiment needs less assurance than integration into protected main, deployment, credentials or an irreversible external action. Unknown evidence is not success, and verification must not become an infinite prerequisite generator.
- **Long-term coherence.** Prefer existing abstractions, meaningful invariants and usable architecture over one-off fixes. Avoid speculative frameworks, arbitrary microtasks and excessive instruction text.
- **Parallel progress without chaos.** Independent safe Work should progress concurrently within actual resource and budget limits. Correct source ownership, capacity accounting and execution deduplication matter more than nominal agent utilization.
- **Durable continuity and truthful status.** Source identities, decisions, evidence, checkpoints and uncertain effects must survive ordinary interruptions. If a backup is stale, Telos must explain what it cannot safely reconstruct instead of guessing.
- **Human authority where it matters.** The Operator controls intent, budgets and reserved actions. Intelligence proposes and implements within delegated authority; review, integration and release decisions have their own explicit rules.

## Boundaries

Telos must not assume that accessing a repository, tool, browser, project or device grants unlimited authority over it. Project scope, resource access, approved operations and current source lineage must be enforced by the authoritative runtime, not merely requested in a model prompt. A requested feature is not permission to deploy it.

Telos is not intended to be a universal formal specification language, a second source-control system, a monolithic chat transcript, or a system that requires a continuously active conversational supervisor to coordinate execution. It should not require Servitor to run, and Servitor must not become a competing scheduler or source of truth.

## What would demonstrate the Project promise

An Operator can describe a Feature in ordinary language. Telos develops an actionable, authorized path to a working implementation, supports independent correction and verification, and reports which criteria currently have valid evidence and which remain unknown. The Operator can change that Feature midstream and see only the genuinely affected obligations re-evaluated; unrelated work continues. After interruption, Telos resumes from durable state without duplicating a submitted external effect or mistaking old evidence for current acceptance.

Finally, Telos should use this same mechanism on its own codebase: produce a bounded change, establish source-pinned evidence, pass an independent review and integration process, and report the actual result. This is a project-level proof, not a claim that the present implementation has already achieved it.
