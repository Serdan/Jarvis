# Canonical project-capacity role and assignment projection

Status: default-off isolated source adapter, no launch permission, runtime registration, occupancy completeness, cap activation or deployment. Source baseline: d091424227a34358e1d1a3d3fa1b06c2259e40de (origin/main, Chat-first integrated).

## Contract

Use the already authenticated and authorized project launch host; the actor label in a command or LedgerIntent is journal provenance, not authentication. This module has no credential issuer, identity mapping from an actor label, or independently authenticated sender. The host must bind the exact attributed target to the actual dispatch request (including effect ID and source), freeze the expected assignment tuple once for the original operation and bind those assertions to the complete LedgerIntent. Do not recompute the expectations on retries. Never derive target identity from arbitrary browser script arguments.

CanonicalProjectCapacityRoleBinding.projectAt takes that target, exact expected project/ledger/epoch, target agent, task, attempt, assignment generation, role, role-definition version and agent-role-config version, plus the verified snapshot supplied by the admission transaction. It uses ReviewWorkflow.getAgentWorkingTurnAt and getTaskAt and RoleInstructions.resolveAtKnownAgent, comparing path identities and focused task/attempt owner, lifecycle, phase and generation. It builds the witness from decoded canonical values, not from the assertions. It additionally rejects duplicate/noncanonical nested currentAssignment keys (the existing outer entity decoder does not recursively reject duplicates). Role attachments and definitions are canonical role records, not name prefixes or caller-supplied roles. One role is supported by the present reservation seam; zero or multiple roles deny rather than select a preferred role or undercount a ceiling. The witness includes project/ledger/epoch, snapshot commit, canonical role blob, config and role versions and exact assignment identity. Role changes or assignment recovery invalidate the prior expected tuple on the next snapshot. This is evidence of assignment and role only, not provider/session ownership, launch eligibility or capacity availability.

Invoke projection, policy readForRole, inventory validation and admission planner inside the *same* LedgerStore CAS callback, on its snapshot. On every retry all reads must repeat; no live fetch or cached witness is allowed. A historical witness has historical provenance only. Use the derived role/version/generation in the reservation planner, and preserve the full tuple and evidence boundary in the eventual journal contract. A committed receipt, including AlreadyApplied on a replay where the callback does not run, is never authority to send. This module performs no mutation or external effect.

## Unsupported paths and missing inputs

At baseline, Client/SignalR/Client.fs beginAttributedLaunch already reads getAgentWorkingTurnAt inside its ledger transaction but stores only target, task ID, assignment snapshot, script path/digest and launch ID. It does not bind attempt, assignment generation, role/config version or policy/admission on the same CAS. BrowserRunInNewTabCommand carries TargetAgentId option, not that full frozen assignment tuple. The new module must not be treated as a positive admission path until the authenticated host and journal bind these missing inputs and the inventory/admission owner composes the same transaction. The legacy disabled-mode path remains unchanged; NegativeOnly continues to deny launches.

Unattributed BrowserRunInNewTab, BrowserExecuteFile, BrowserExecuteJs and persisted scheduled scripts without an exact attributed assignment identity cannot produce this witness. Likewise, registered but taskless agents (including taskless reviewer or Lead sessions) lack the required canonical task/attempt generation; the adapter denies, not guesses an assignment or supplies a synthetic generation. A native scheduler target can use this projection only if the actual dispatch is bound to a canonical registered target and exact assignment tuple under existing authenticated project authority. No scheduler host integration or generic sender coverage is asserted. Ephemeral Work identities are not legacy registered task attempts and require a separate explicitly scoped authority. These restrictions concern the future role-capacity domain, not changes to existing launch behavior.

The isolated tests use the existing disposable Git fixture, actual canonical registration/role/assignment writers and independent clones. They cover correct snapshot/role blob identity, missing attribution/assignment, wrong project/ledger/epoch/role/version/owner, ambiguous role attachment and nested focus, role changes, recovery generation changes, original receipt replay, and a barrier-controlled competing recovery during the reservation transaction. The fixture composes the existing policy and disposable admission planners on one snapshot. Its host actor/target and initial occupancy are test fixtures only: it does not establish real host authorization, a real occupancy issuer, production reservation persistence or a universal send fence. No shared project file, live sender or production configuration is modified.
