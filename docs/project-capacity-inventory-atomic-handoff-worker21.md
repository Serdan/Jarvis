# Capacity and inventory transaction handoff

Source base: independently accepted capacity seam `e3430a0806c77078344b23d17095971a5fe2edde`. This branch is a new, unreviewed composition on that base, not an integration or live admission boundary.

## Contract for inventory owner and runtime

Call `planReservation binding snapshot actor operation effect role roleVersion generation` only from the same `LedgerStore.transact` planner that reads and validates the canonical inventory baseline and fence at that exact snapshot. Combine its returned file changes with the inventory changes in that callback. Abort on unknown, incomplete, invalid or stale inventory; don't treat a caller boolean as evidence. Every retry must reread and recompute both pieces from the new snapshot. A read before the transaction cannot establish this property. The transaction intent must bind the operation, effect, owner, role, role version, generation, inventory identity and fence and every other input that affects admission; the same operation ID must never represent different inputs. Keep effect and operation stable across retries. Do not invoke external effects in the callback. Existing `reserve` keeps its original intent and semantics and does not itself validate inventory.

LedgerStore.fs 2827-2853 on the base documents and implements recomputation for each fetched tip. A matching operation receipt returns before the callback: replay means the transaction was applied, not that the fence remains fresh or that dispatch is authorized. The caller must use the appropriate durable receipt and separately revalidate dispatch authority; uncertain external effects must not be replayed. Transaction changes must have unique paths, valid expected blob OIDs and fit ledger limits. This helper cannot itself prove the integrity or completeness of the inventory owner's evidence, nor enforce the host's intent construction. Review the composed caller and its tests before any use.

## Evidence boundaries

The accepted capacity file's disposable state has project, ledger and epoch, total limit, role limits and entries with effect, reservation operation, owner, role, role version, generation and Held/Dispatching/Excluded status. Its count includes every non-Excluded entry across all roles, including Dispatching; Excluded does not count. Role caps are optional and apply only to matching role. Missing or malformed state fails closed. Initialization is test-only: there is no production-proven initial baseline, freshness timestamp, canonical role authorization, recovery exclusion proof or trusted enumeration of other writers. Generation is caller supplied, not independently verified against canonical ownership. Consequently neither this state nor the helper alone proves complete project-wide occupancy or fresh authority.

W23 prototype `38e235e4f9f8324bfa10040e80d45787b6de0440`, `docs/scheduler/project-scoped-planner-preparation.md`, requires same project/ledger/epoch/head and observation freshness on policy and occupancy, complete sessions and reservations, and holds unknown capacity kinds. It is advisory and the host must prove completeness, including uncertain in-flight effects; worker/reviewer materialization cannot silently omit other roles. W19 preparation `4e72f45c65a1c601d976db9cc2e4fda60e8c1f3d`, `Client/AutomationNativeRuntimeHost.fs`, refreshes verified input at wake and treats its preflight pair as a witness, not a transaction fence. Neither prototype establishes same-CAS inventory validation. These are source pins, not claims of integrated or independently accepted behavior.
