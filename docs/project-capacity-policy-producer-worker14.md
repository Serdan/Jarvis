# Project capacity policy handoff

This supersedes the mandatory-cap contract of the original accepted policy producer. Operator decision 2026-11-25: project-wide and per-role caps are independently configurable and off by default. The component remains unregistered, default-off and grants no production admission.

## Representation

The policy lives at `records/project-capacity-policy/policy.json`, bound to project ID, ledger ID and epoch. Schema 2 has a positive monotonic revision, required `Total` (JSON null for disabled, positive integer for enabled), and required `Roles` (object mapping only enabled canonical role IDs to positive integers; empty is valid). Missing fields, duplicate keys, unknown schemas/fields, invalid values, malformed identities or unknown configured role IDs fail closed. Unlisted *canonical* roles have no role cap in schema 2. Role identity is resolved from the same project ledger snapshot, not inferred from agent names or a cap entry.

Absence of the whole record is represented as revision zero with both dimensions disabled, no blob ID. An expected positive revision with no record is a failure, not a default; an expected zero revision with an existing record also fails. After initial creation, disabling caps writes a new positive revision rather than deleting the record. The policy producer does not delete records; readers must use an authenticated snapshot, not fall back to zero after an error.

Schema 1 configured total and role limits are preserved exactly on read. Schema 1 still denies unlisted roles (its original conservative behavior); an explicit schema 2 update is required to adopt the new unlisted-canonical-role semantics. The predecessor is parsed and validated before replacing it. The existing schema-1 API remains for isolated legacy callers/property tests, validates canonical role identities, and cannot read or replace a schema-2 record; new consumers must use the optional API. No live migration is performed.

## Scheduler contract

`readCurrentOptional binding snapshot` returns `OptionalPolicy * string option` or a ledger failure. It reads only the caller-pinned verified snapshot, uses the same parser and canonical configured-role checks as the exact-revision API, and returns the actual revision and blob identity. Absent record means revision zero and disabled limits; malformed or unavailable records are errors, not absence. The scheduler must hold on a policy read error. For legacy schema 1, preserve the existing unlisted-role denial; for schema 2, an unlisted canonical role has no cap. Canonical target role/assignment identity remains the scheduler's responsibility.

The two independent optional limits apply only to scheduled resumes: compare current canonical Working counts for the project and the relevant role against enabled limits. Manual launches bypass capacity, even if policy or count data is unavailable. Both limits are disabled by default. No account census, external occupancy, strict reservation or attested-drain prerequisites are required. Capacity is a restriction, not permission; unrelated dispatch and STOP gates still apply. Read policy and counts from the same verified snapshot, and recheck as required by the scheduler's dispatch contract. The producer itself is not a dispatch gate.

`readOptionalForRole binding snapshot expectedRevision role` remains the exact-revision compatibility API, including revision zero for absence. It validates the canonical target role and retains schema-1 unlisted-role denial. For update CAS, read the current policy on each retry and compare the exact expected revision; never fetch a newer head inside a callback.

`updateOptional binding actor operation expectedRevision total roles` uses the existing authenticated ledger CAS, with `None`/empty map for disabled dimensions. It replaces the complete policy at the next revision, including explicit removal. Revision zero is create-only. The request binds the complete replacement and expected revision. A repeated identical operation returns its original receipt (not proof of current policy); reuse with changed inputs fails. Schema-1 compatibility calls retain their original intent serialization and cannot downgrade schema 2.

Property fixtures for both APIs must register canonical role records on their disposable ledger, then test absent/default, independent limits, explicit removal, schema-1 preservation, stale revision, unknown roles, identity mismatch, malformed data, competing writers and replay. No production registration, callsite changes, deployment, restart, activation or uncertain-effect retry is included.
