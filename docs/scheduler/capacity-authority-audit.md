# Native Scheduler account capacity and admission authority audit

**Date:** 2026-11-21. **Task:** `scheduler-native-capacity-authority-audit-20261121` (Worker 1, assignment generation 1). **Scope:** architecture-only, source base `d702352ef705f9991ac1cb14dc15a13cce78aa44`, one new document; no runtime changes, migrations, launches or activation.

## Decision

**Reuse the account Git compare-and-swap (CAS) mechanism, not the meaning of its WQ07 tokens.** WQ07 already has trusted account/ledger/epoch/remote bindings, one account ref, immutable request-hashed operation receipts, bounded compare-and-swap publication, lost-ACK reconciliation and terminal-proof-based release. Its `Held` token means one **Work Queue launch** admitted under a specific WQ02 project/role, not one authenticated native ChatGPT Worker/Reviewer session. In particular it has one `MaxConcurrentAgents` integer, not verified worker and reviewer pools, and no complete native browser-session or account-project roster. Treating `Tokens=[]` or `MaxConcurrentAgents` as native free capacity is unsound.

Native Phase 1 is a **pure, accepted planner**, not an admission authority (commit `34facab5db97b2f238d2415c8f7ae6b59866b754`, `scripts/jarvis-ledger-planner.mjs` and `docs/scheduler/phase-1-ledger-planner.md`). The frozen Phase 2 default-off adapter (commit `8ed32fd8c9f8be19afda677cc3a28bba4f4e835e`, review `d6f2a9b178c14d66ac76cf127e0aab93` underway) expressly reports `completeness.projects=false` and `accountCapacity.complete=false`, with null limits/sessions/reservations: `scripts/jarvis-phase2-snapshot-adapter.mjs:476-530` and `docs/scheduler/phase-2-snapshot-adapter.md`. It has not been integrated into `main`, and its synthetic Git fixtures do not authenticate production membership or sessions.

**Smallest coherent path:** provision a trusted, complete account/project membership and capacity policy; extend the *same* account Git CAS head with a separately typed native admission namespace and one reservation/session reconciliation adapter. Preserve WQ07 behavior and fence simultaneous legacy/native writers until coexistence is proven. Use the existing project Git CAS for worker assignment and reviewer claims, and a durable exclusive original-send fence before any browser effect. A new DB, Manager agent, second account capacity ledger, live scheduler service, or generalized distributed transaction framework is not justified.

## Minimum trusted data contract

1. **Root account authority and complete roster.** Pin the authenticated account subject to immutable `accountId` (UUID), account ledger ID/epoch and exact approved account Git fetch/push authority; do not derive from the workspace name, browser tab, caller-provided URL or device connection. A versioned, operator-approved **complete** roster binds every allowed `projectId` UUID to a unique canonical `projectName` alias, project `ledgerId`, epoch, approved Git remote fingerprint, canonical project ref and approved limits. A roster update is itself an account CAS operation with version/receipt; invalid/missing/duplicate/unknown project, stale epoch, absent approval or incomplete enumeration globally **holds** dispatch. An existing host-supplied dashboard registry is a model for the fields, not proof of the authentication boundary. Membership completeness must be proven at the account root, not asserted by arbitrary clients.
2. **Policy is not occupancy.** Publish authenticated account `configuredLimits.worker` and `configuredLimits.reviewer` and explicit per-project worker/reviewer quotas, all versioned in the account CAS head. Zero is a valid intentional limit (hard hold); missing, negative, contradictory or unverifiable limits must not default to zero sessions or positive availability. Denote a project with no authorized quota as held. The old WQ07 `MaxConcurrentAgents` cannot be split into these limits by guessing.
3. **Canonical native occupancy.** Store an append-only-audited reservation/session state indexed by one immutable dispatch key and scoped to `(accountId, projectId, projectLedgerId, projectEpoch, kind)`. Worker identity is `(taskId, attemptId, assignmentGeneration, ownerAgentId, source repository/ref/base/target/lease proof)`. Reviewer identity is `(reviewId, review version, immutable reviewedHeadOid/reviewRef, chosen and authenticated Reviewer agentId at claim)`. Bind account operation UUID, effect/launch ID, session/provider ID if actually verified, project CAS operation UUID, source snapshot heads, actor and monotonic event generation. Keep exact immutable receipts and terminal tombstones; never erase idempotency history to make space. A stable Phase-1 emitted `idempotencyKey` must map uniquely to canonical UUID identities; aliases may not create a second launch for the same canonical attempt/review.
4. **Capacity projection cannot double count.** One dispatch occupies one slot continuously from durable `Reserved` through `Dispatching`, `Submitted` or `Uncertain`. If credible session evidence exists, transfer that slot atomically at the account head into `Active`/`Unknown` session occupancy, retaining a terminal reservation tombstone with the same idempotency key. Otherwise keep the nonterminal reservation counted. Do **not** expose both a live reservation and the same live session as two independent slots to Phase 1; it currently counts each. Active/Unknown sessions always count; only positively proven terminal sessions do not. The per-project capacity arrays must be the exact account snapshot subsets from the **same head**, not independently sampled approximations.
5. **Session provenance.** A browser submission success, tab registration/closure, client last-seen, agent `ActiveSessionId`, or account Git absence is not sufficient to claim all sessions. Require a trusted provider/session ingress with coverage for every allowed client/dispatch or retain the durable `Uncertain` reservation instead; no automatic release for lack of evidence. Authenticated device identity can identify an observer, not replace provider effect identity. If provider completion cannot be authenticated, use an auditable, explicit operator reconciliation path for exceptional release, never idle-time expiration.

## Bounded reserve / dispatch / terminal protocol

**A. Read and plan (no effects).** Verify approved complete account/project roster, account CAS head/epoch, each project ledger head/epoch, all required task/agent/source/review/Challenge records, complete source lease and frozen review-source proof, capacity policy, session coverage and limits. Reject clock regression, expired/unparseable observations and unknown statuses. Run unchanged accepted `planLedger(snapshot, nowUtc)`. Its deterministic ranking (worker priority/project/task, reviewer created sequence/project/review) is the default fairness order, with no LLM decision.

**B. Account admission is the linearization point.** One account-head CAS selects the first eligible candidate under the current complete verified candidate order and per-kind **account and project** quotas, rechecking account state and immutable dispatch key before granting a reservation. A competing client must re-read/replan on a proven non-fast-forward loss. Two different operation UUIDs for the same canonical candidate fail uniqueness, while an exact original UUID+payload replays its immutable receipt. A changed payload or mismatched account/project/role/source cannot replay. A stale or incomplete global snapshot **never** wins; a winning account CAS is only a credit reservation, not permission to send a browser command. This serializes credit consumption and yields deterministic fairness for the *same verified snapshot*. There is no global atomic read across independent project Git remotes, so do not claim stronger real-time fairness.

**C. Project pre-send fence.** Re-read the current project head and prove exact account reservation, ownership/generation, source lease or immutable review source. For workers, permit only the canonical Ready/Queued owner and the original generation; for reviews, resolve an eligible authenticated Reviewer agent, then win existing `claimBranchReview` with expected version/Unclaimed and associate the original reservation. Record one exclusive create-only **native send intent/claim** in project Git CAS keyed by dispatch identity and account reservation, with original browser effect UUID/host binding, before any external send. A different client/operation cannot inherit a prior send claim after a lost ACK. If the project CAS definitively loses, write a no-effect/abort tombstone and release only after independently verified project absence/terminal proof; if either Git outcome is uncertain, **retain the account slot** and original IDs. Do not recreate a new candidate or claim after an uncertain project write.

**D. Effect boundary.** Reconfirm original account/project receipts and fresh identity; persist `Dispatching` and durable original-send evidence, then call browser/provider at most once. Immediately record `Submitted` with authenticated effect/session metadata, or `Uncertain` if send or ACK is not provably pre-effect. A deterministic prestart failure may abort only with typed, independently proven no-send evidence. Never treat an exception, timeout, lost client connection, browser restart or missing tab as proof no effect occurred; no duplicate send/rearm on restart. Reconciliation uses original operation IDs and immutable Git receipts, not new UUIDs. Native project send fence can reuse WQ11/WQ03 one-shot design principles without treating their Work Queue records as native state.

**E. Verified release.** Keep slot through session activity and any unknown effect. Free it in account CAS only upon a verified original project *terminal/no-send* receipt and trusted provider/session terminal or audited explicit operator reconciliation bound to the same project/dispatch/generation. A canonical Worker yield/completion or Reviewer verdict is useful project lifecycle evidence but alone does not prove the backend provider session stopped. Release checks original account reservation, role, exact project authority/source/ref, session/effect identity and immutable terminal operation; terminal receipt is idempotent and capacity is freed **once**. Restart/reconnect/owner change/stale terminal/unknown Git push preserve occupancy. Project tombstone and account release remain two CAS operations: intermediate uncertainty consumes capacity.

**Coexistence/migration guard:** Keep native writes default-off. The minimal implementation should use the **existing verified account Git remote and one CAS ref/head**, with a versioned namespaced native record plus unchanged WQ07 records/receipts. Review a narrow schema/transaction extension rather than reusing WQ07 `Held` tokens or standing up a second ledger. Before native admission, prove zero unclassified WQ07 live tokens and fence competing WQ07 writers (or explicitly implement and test joint accounting on the same CAS head). Merely creating a separate native ref while WQ07 may still allocate from the same physical account would be a second competing authority and is **not** safe. Activation/migration needs independent review and operator permission.

## Required negative-space test matrix (all disposable authorities)

| Case | Expected result |
| --- | --- |
| Two projects, two client clones, worker cap=1, simultaneous distinct requests | Exactly one account CAS reservation; loser holds/replans, no second browser send |
| Two schedulers, same worker attempt N or review/version, different operation UUIDs; exact UUID replay | One immutable key, one send intent; exact replay returns original receipt, changed semantic payload fails |
| Account cap available but project quota 0; both quotas full; worker and reviewer separate pools | Deterministic fail closed for affected pool/project; no unrelated cap consumed |
| Missing/stale/incomplete roster; foreign project; duplicate projectName/ID; epoch or remote mismatch | Account-wide hold; no invented sessions or project subset; no dispatch |
| Working/Unknown agent with null provider session; stale idle/last-seen; client disconnected | Occupied/Unknown or contradiction hold, not idle inference |
| Reservation won, project claim loses or ACK lost; original no-send fence ambiguous | Token retained until verified project terminal/no-effect receipt; no fresh candidate/send |
| Browser send accepted, ACK lost; restart, re-register, new device and clock rollback | One original effect, `Uncertain` occupancy, no replay or timed auto-release |
| Reviewer A/B claim same frozen review/version; source rewritten/stale ref | Existing project CAS has one winner; failed/mismatched claims cannot launch; account reconciliation preserves evidence |
| Genuine terminal plus verified provider end, duplicate release, foreign terminal, stale generation | One receipt-backed release; replay idempotent; foreign/stale proof refused |
| WQ07 `Held` token during native activation; migration Frozen/Preparing; account remote unavailable | No concurrent unaccounted admission; no silent migration or empty-capacity inference |
| Two head updates on account/project, unseen third project or session, non-monotonic observation | No overbooking; hold on incomplete or unverifiable global snapshot; honest non-atomic project-read boundary |

Tests must include real disposable bare Git remotes, two independent clones, deterministic CAS interleavings (including accepted-push/lost-ACK and rejected-push), clock/restart simulations and a fake browser with precise before-send vs after-send faults. Assert actual process exits, immutable receipt lineage and absence of external sends, not only high-level planner output. No production launch is needed for these fixtures.

## Prioritized, bounded implementation tasks

1. **P0: authenticated account roster and capacity snapshot authority.** Establish the operator-approved account-ID ↔ authenticated subject binding; versioned complete project ID/ledger ID/epoch/remote roster; account+project worker/reviewer policies (including zero), verified session coverage or explicit Unknown; provenance of observed heads/time. Feed the Phase-2 normalized adapter without manufacturing completeness. This is the currently missing authority and is a hard gate.
2. **P0: one account CAS native namespace.** Refactor/extend WQ07's existing trust-bound CAS/receipt machinery under the same account head (preserve its migration rules) to record native reservations, monotonic status, canonical idempotency/uniqueness, kind/project quotas, active/unknown session occupancy, terminal tombstones and original-op replay. Test WQ07 coexistence denial, concurrent-client fairness, unknown push and capacity transfer exactly once. No independent account ref or SQLite.
3. **P0: thin project/effect bridge and terminal verifier.** Reuse canonical Ready assignment/lease and shared review claim CAS plus original-send pre-effect fence; persist browser effect Unknown/Submitted with durable replay fencing; provide trusted terminal/session reconciliation. Prove release and denied-claim abort for both workers and reviewers.
4. **P1: integration-ready projection and operator dry run.** Once 1-3 have separate acceptance and accepted Phase 1 is integrated, replace Phase 2's deliberate capacity/membership holes with independently verified fields. Run an operator-authorized **one-pass dry run** returning candidate, reservation and expected fence/hold only, with zero effects. Do not turn on periodic scheduling without explicit cutover approval.

**Proportionality:** One account Git CAS writer/receipt abstraction and a thin native project/browser adapter suffice in principle. An additional storage engine, persistent LLM manager, generic distributed workflow platform, or separate replacement for Jarvis task/review/Challenge ledgers would add coordination risk rather than fix the missing evidence. The irreducible work is authentication/completeness of the global roster/session inventory, one atomic account slot decision, and an effect-terminal proof path. Until those are real, native dispatch stays off.
