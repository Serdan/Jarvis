# Native Scheduler account configuration and reservation boundary (default-off)

The Operator's 2026-11-24 architecture correction supersedes the separate signed roster and Scheduler-specific authentication design. The Scheduler is an internal consumer of the existing authenticated Jarvis client, existing configured account/project bindings and authorized Git operations. There is no Scheduler signer, second subject registry, approval key, or per-dispatch approval. Neither account/project identifiers nor an observation constitute a credential. The enclosing authenticated client is responsible for obtaining the complete configured bindings and enforcing its normal permissions; no external endpoint is added here.

## Canonical account state

The existing account admission ref (refs/heads/jarvis-account-admission) stores native/scheduler-roster-policy-v1.json and native/scheduler-reservations-v1.json. SetNativeSchedulerRosterPolicy pins the previous policy version, exact account head, operation UUID, actor and typed policy. The operation CAS writes the policy, immutable receipt and ordinary StateVersion/NextSequence increment together; WQ07 migration phase, legacy tokens, configuration version and capacity remain unchanged. Native quotas are separate Worker/Reviewer pools at account and project level; zero is a limit, not evidence of free capacity. Legacy Held occupancy still fences native reservations.

Current policy must match the complete configured account/project identity set, including ledger UUIDs, epochs, unique aliases, exact remotes and canonical project refs. Each project is fetched in a fresh private bare repository; object history redirects and replacement objects cannot supply positive proof. The isolated proof keeps normal client Git/SSH credential access, while stripping metadata/environment overrides and using an empty template. The fetched canonical ledger header and advertised ref must match the ordinary LedgerStore verified read. A re-fetched changed account head fails closed. Independent project Git reads are not a globally atomic snapshot; fresh exact observations are required again for each reservation CAS.

The original v1 JSON format with historical authenticatedSubject, signerPublicKeySha256 and signatureBase64 fields is parsed as configuration, never as an independent authentication mechanism. Read verification hashes and checks the original stored bytes and canonical receipt, exact predecessor and changed paths. Later configuration updates use the reduced DTO. Historical commits/receipts are neither deleted nor rewritten. Unrelated WQ07 migration witnesses are not Scheduler signing and are unchanged.

## Internal producer API for Worker 16

All functions below are assembly-internal, not an externally callable permission boundary. Modules are Client.AccountCapacityLedger.AccountCapacityLedger and Client.NativeSchedulerAccountReservation.NativeSchedulerAccountReservation.

- setNativeRosterPolicy (b: AccountBinding) (projects: LedgerBinding array) (update: NativeRosterUpdate)
- readNativeRosterPolicy (b: AccountBinding) (projects: LedgerBinding array)
- reserve b projects (coverage: NativeAccountCoverage) operationId actor (candidate: NativeDispatchCandidate)
- readVerified b projects coverage
- verifyReviewerClaim (binding: LedgerBinding) (snapshot: LedgerSnapshot) (candidate: NativeDispatchCandidate) : Result<unit, AccountFailure>
- readOriginal b projects coverage (locator: NativeOriginalReservationLocator)
- transition b projects coverage operationId actor locator toStatus projectFenceOid providerSessionId
- release b projects coverage (verifier: INativeTerminalVerifier) operationId actor (locator: NativeTerminalLocator)

NativeRosterUpdate contains SchemaVersion, OperationId, Actor, PreviousVersion, ExpectedAccountHead and Policy (no signer or subject). NativeAccountCoverage contains AccountHead, ProjectHeads and ObservedAtUtc only; construct it from the successful current verified configured policy read, never from a claimed membership flag or provider status. The project head must be verified by the existing LedgerStore before calling verifyReviewerClaim; the shared helper checks exact project/ledger/epoch, active snapshot, review claim operation and immutable origin, review ref/head/version, canonical reviewer assignment and current Reviewer role through RoleInstructions.resolveAt. The reservation path calls this same helper. No duplicate writer or authorization route.

The original reservation locator carries ReservationOperationId, ReservationRequestSha256, Candidate, ExpectedGeneration, ExpectedProjectFenceOid and ExpectedProviderSessionId. readOriginal returns AccountHead, ReservationOrigin, ReservationParent, ReservationReceipt, CurrentReservation and VerifiedProjectHeads. It revalidates the immutable reserve receipt, predecessor state and exact append, candidate identity, current generation/fence/session, and the original project tuple in the current complete verified project heads. A legitimate roster update that retains the original project does not lose its receipt. Removed or replaced original lineage makes original context and mutations unavailable, but the historical record still consumes account credit. Transition and terminal release recheck original receipt/lineage within their CAS. NativeTerminalLocator adds ReservationRequestSha256 and ExpectedGeneration to the existing original dispatch/reservation/effect/terminal IDs. Unknown, Uncertain, Submitted and all other non-Released states retain occupancy; exact UUID replay returns its immutable result, never another send authorization.

A terminal callback alone is not proof: the accepted terminal contract still checks the canonical project terminal operation, exact original session, receipt/blob and Git ancestry. An actual verified-no-send issuer and operator reconciliation path must be coordinated with the distinct project/effect consumer lease; the historical Stage B fake no-send proof cannot release a real reservation. No fabricated terminal, automatic timeout release or per-dispatch human signature is introduced. Until genuine evidence exists, hold the reservation. Policy reads do not authorize launches and are not claims of complete provider session occupancy. Default-off runtime activation and independent review remain outside this producer implementation.

## Original-bound no-send release (source-only; issuer composition pending)

The distinct internal account operation is `releaseNoSend b projects coverage operationId actor (locator: NativeNoSendLocator)`. It shares the original reservation receipt/context validation, current configured coverage and account CAS with the existing terminal path. It never creates or requires a provider session. Only Reserved/generation 1 without a fence or Dispatching with its exact fence and no session can qualify; Submitted, Uncertain, Active, Unknown and Released do not. No-send operation IDs are subject to the same historical uniqueness rule as terminal IDs.

The project issuer owns the send-exclusion transition. In one verified project CAS of kind `NativeVerifiedNoSend`, it must exclusively create the original worker/reviewer fence tombstone before any send fence exists or CAS the exact HeldBeforeSend fence into a terminal tombstone before any send authorization. All launch/send paths must reject this terminal fence permanently. It must also create the immutable evidence path `noSendEvidencePath operationId` (records/native-scheduler/no-send/{operationId:N}.json). Both paths contain the exact bytes returned by `serializeNoSendEvidence (evidence: NativeNoSendEvidence)`, also used as the canonical project operation RequestJson. `noSendFencePath candidate` derives the exact worker/reviewer fence identity; reuse it rather than duplicating path logic.

NativeNoSendEvidence fields: SchemaVersion=1, State="VerifiedNoSend", AccountId, AccountLedgerId, AccountEpoch, ReservationOrigin (original reserve commit), CanonicalKey, Original (entire NativeOriginalReservationLocator, including receipt hash, candidate/dispatch/effect, generation, fence OID, empty session), NoSendOperationId (Guid). NativeNoSendLocator fields: Original, NoSendOperationId, ProjectHead (fresh verified current head), NoSendOrigin (immutable project operation commit), EvidenceBlobOid. The consumer verifies exact receipt intent, operation origin and both terminal blobs at origin and current verified head, plus original-fence ancestry where present. Missing/mismatched/deleted evidence is denied. This is not a new credential or approval system. The account consumer does not itself issue the project cancellation; no operational release is authorized until the genuine issuer and consumer are independently reviewed together. Test-only fake no-send and generic observations remain invalid.
