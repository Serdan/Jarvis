# Native project effect exclusion: isolated CAS contract

Scope: source-only preparation at base `08994560914ac473c4c9d935bf584c0e3cc7b3cb`. This module is not registered in the running Client, does not authorize an external action, and does not release account capacity. It deliberately does not claim account proof from the unaccepted W12 implementation or production wiring from W16.

## Invariant and ordering

All participants contend on the same canonical project ledger ref and same original effect key. A verified account reservation alone is not send authority. A missing project fence alone is not a no-send result.

| Current project state | Claim | Begin send | Exclusion |
| --- | --- | --- | --- |
| Absent | Commit original HeldBeforeSend + immutable launch intent/args | Denied | Commit original-bound tombstone + immutable evidence |
| Exact original HeldBeforeSend, unchanged from verified claim origin | Denied | Commit Dispatching | Commit original-bound tombstone + immutable evidence |
| Dispatching, terminal, uncertain, unknown, malformed or any other occupied state | Denied | Denied | Denied |
| VerifiedNoSend | Denied | Denied | Only exact operation replay; never another transition |

The one winning commit provides the ordering. A caller must never send from a cached claim result, an applied-operation replay, a stale proof, or uncertain publication. The begin-send commit must be fresh and acknowledged by the canonical Git transaction, before the original provider call. A failed or uncertain send cannot be converted back to HeldBeforeSend. No rollback from Dispatching is supported here.

## Composition contract

- W12 is the owner of authenticated original reservation resolution. Read the actual current original context, candidate, immutable reservation receipt and its origin, account ledger/epoch, status/generation, and current verified project heads. Exclusion is allowed only from an explicitly no-session pre-send account state; unknown/submitted/active/uncertain stays occupied. Revalidate during the project CAS plan. Do not accept a caller boolean, absent intent, browser observation, timeout, closure or fake provider session as proof. The original project fence, if account-recorded, must be the same verified claim origin as the transition witness. The pre-fence case must establish the tombstone on the very key used by ingress.
- W16 is the owner of the authenticated project claim and the provider callsite. Use `checkClaim` within the existing claim/intent/arguments transaction. Use `planBeginSend` within a distinct request-hashed transaction on that same project ref, binding the original claim, effect and exact argument evidence; call the provider only if the transaction reports fresh success (`AlreadyApplied = false`) and all other existing transport and account checks succeed. Every native send route must pass this transition. A read-only original intent is not send permission.
- `planExclusion` is a project transaction planner. The enclosing authenticated caller constructs the existing W12 typed account evidence from verified context. The `NativeVerifiedNoSend` intent request is a separate version-1 envelope with exactly four fields: `schemaVersion: 1`, `expectedProjectHead` (verified pre-mutation project head), `predecessor` (either `{"kind":"BeforeClaim"}` or `{"kind":"ExactHeldFence","claimOperationId":...,"claimRequestSha256":...,"claimOrigin":...,"claimBlobOid":...}`), and `evidence` (the existing W12 NativeNoSendEvidence JSON object, unchanged). The planner parses the envelope once, rejects duplicate fields, verifies identity/operation/account locator locally, and derives the change from that request. Explicit head/predecessor arguments are consistency assertions. The raw nested evidence object, not the envelope, is written to both the canonical fence and `records/native-scheduler/no-send/{operationId:N}.json`. Keep the serializer's exact compact account evidence bytes. For a held predecessor, verify the claim operation ID, request hash, origin commit and unchanged original fence blob; actor and all original identity fields must agree. No other project record is overwritten. Preserve immutable original launch intent and argument paths.
- Three distinct cases: A = actual absence and account Reserved generation 1, empty account fence; B = exact HeldBeforeSend while account remains Reserved generation 1, empty account fence; C = exact HeldBeforeSend with a recorded matching original claim origin and later account generation. B does not invent an account recording. A stale BeforeClaim request cannot be rebound to B even at a refreshed head. A fresh B request uses a new operation ID and exact held predecessor while preserving the account locator. A recorded account fence must match the held claim origin, and no provider session is permitted. Exact account generation/receipt authentication remains W12/runtime responsibility; any concurrent change requires revalidation or reconciliation, never evidence rewriting.
- The current isolated source validates the existing worker fence key and the matching observed W12/W16 reviewer draft key; use the accepted common account-side key helper directly at composition, not a new parallel key. A distinct attempt/review claim has a distinct key. Reopening an excluded key under a different dispatch or reservation UUID is forbidden.
- W12 consumer coordination (not implemented in this lease): retain exact serialized typed account evidence comparison at both immutable blob paths at origin and current verified head. Parse the canonical operation envelope's `request` **string** as JSON; verify the nested account evidence against the independently reconstructed expected account locator and the request-bound local predecessor/head against the actual receipt (the verified original operation's `OriginalResultJson.changes` fence `beforeOid`, null for A or exact claim blob for B/C; the verified origin's parent and held claim origin/hash/blob). Use `LedgerStore.verifyIntegrationOperationIntent` on the reconstructed full request, **not** raw string equality with the canonical nested request. LedgerStore recursively canonicalizes JSON key order. Do not use the canonicalized nested evidence as the original blob bytes; compare the actual bytes separately. W12 draft ea25c158 verifies the previous account-evidence-only intent and requires this coordinated adjustment. Release remains an account CAS against the original receipt, generation and exact current occupancy; never rely on capacity already being released.

## Evidence boundary

The standalone test harness uses real disposable project Git remotes and two clones, with fixture original context (not an authenticated account reservation). It exercises same-key preclaim exclusion, exact held-fence exclusion before and after account fence recording, stale preclaim request rebinding, embedded identity/operation mismatches, begin-send consumption, stale and duplicate rejection, operation replay, immutable origin/blob evidence, successor key isolation, foreign fence path, wrong claim hash, changed assignment generation, unknown fence rejection and simultaneous two-clone CAS conflicts. No actual provider call or account release occurs. Composed tests using accepted W12 authority, W16 ingress, exact release evidence, real worker and reviewer claims and all send paths are required before any enablement. The old Stage B fake effect/no-send helper is not the producer.

The independent account/host source and operational acceptance remain prerequisites; this module alone is not proof of end-to-end scheduler dispatch or safe live activation.
