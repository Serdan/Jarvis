# Work queues and ephemeral agent executions

**Status:** Proposed architecture specification; design reference, not implemented or deployed. This branch is a Lead correction draft, not the frozen original under independent review.
**Revision basis:** `e737c2da901ae4073f7ecc066781f428020ffdd1` (frozen review `d4fbb56e2d4c451eab1ef23c281dc647`).
**Date:** 2026-11-15
**Scope:** Jarvis per-project coordination, Git-backed work ledger, agent roles, queue dispatch, resumable execution, reviews, integration, challenges, Manager, and migration.
**Authority:** This document proposes a future replacement for the persistent agent-assignment portions of docs/specs/orthogonal-agent-state.md and the current Manager/reviewer launch convention. Existing APIs and live ledger semantics remain authoritative until a separately reviewed, operator-approved cutover.

## 1. Decision

Jarvis manages **durable, prioritized work with task-addressed communication** and **ephemeral executions**, not durable assignments or conversations to named worker IDs.

The desired autonomous loop is intentionally simple: **Lead prioritizes the actionable work queue; Manager launches as many role sessions as verified demand and capacity allow; each Worker atomically claims the highest-priority currently feasible eligible task while preserving already-admitted launch credits; the result and any question to the operator are recorded against the task.** Review and integration reuse the same pattern with their own queues. Manager dispatches capacity, not task ownership. The operator primarily sees *what work needs attention*, not which numbered worker was allocated.

- Tasks, frozen reviews, integrations, planning requests, and challenge follow-ups can publish actionable items to project-scoped work queues.
- Role subscriptions determine which queues a newly launched execution is expected to consume. A role does not imply a permanently active session or perpetual work item.
- Manager uses queue availability and **one account-wide maximum concurrent agent-execution limit** to launch disposable sessions with explicit roles. Each launched session atomically claims **one** eligible work item; Manager does not bind tasks to worker IDs in advance. The scheduler launches Manager with its role already assigned only when capacity permits; it does not need a model session merely to discover full capacity.
- Every claimed item has an immutable checkpoint history, latest continuation instructions, and an explicit terminal transition. Any compatible session can continue it on a later activation.
- Yielding unfinished work atomically persists a checkpoint and releases its claim. Completing a stage advances the work to its next explicit queue or terminal state. Blocking frees its execution slot while retaining a durable dependency.
- Existing agent IDs currently overload three incidental functions: a serialized execution slot (semaphore), a task focus, and an agent-addressed inbox. Separate global capacity and task claims from agent identity: each newly spawned **execution/session gets one generated UUID as its agent ID**, while role and transient `Worker N` display labels are independent. Work questions/replies belong to tasks; **the already-implemented one-shot response alerts continue addressing the exact agent ID**. A persistent numbered Worker N identity is not required.
- Agent UUID is a **required per-launch/session routing and audit handle**, not a security principal or task ownership key. It is generated at launch, never reused by another session and becomes historical after terminalization; resuming a task in a new session gets a new UUID. All agents running under the owner's account still have the same account permissions. Do not implement agent-ID-based permissions, role ACLs, or anti-impersonation mechanisms. Future contributors receive permissions at the authenticated account level.
- Reuse the existing `queue_response_alert` / `get_response_alerts` / `clear_response_alert` mechanism for session-targeted STOP instructions. A stalled agent UUID receives a `STOP` response alert, while ordinary questions, decisions and progress conversations remain attached to the durable task. Do not create a second session-control message bus or repurpose task conversations as alerts.

The role responsibilities are:

| Role | Responsibility |
| --- | --- |
| Manager | Reserve capacity from the one account-wide execution pool against eligible unreserved demand, then dispatch sessions with explicit roles; never prioritize or preassign a worker |
| Lead | Triage incoming work and operator decisions; prioritize and mark work ready; no worker selection or per-worker assignment maintenance |
| Worker | Claim highest-priority feasible eligible implementation work atomically, keeping other in-flight credits matchable; read durable task conversation/source, implement, checkpoint, ask operator, yield, block or submit completion |
| Reviewer | Claim frozen independent review work, record findings and decision |
| Integrator | Claim accepted integration work, validate and integrate **exact reviewed source**, record immutable evidence and completion |

A review, integration, or planning item needs no artificial implementation task merely to obtain a checkpoint.

## 2. Explicitly retained boundaries

1. Each project's canonical Git orphan ledger remains the sole source of truth for **its tasks, reviews, queues and conversations**. A separate account-scoped Git-backed admission ledger is the sole source of truth for the **shared global agent-capacity semaphore** across projects/devices. This is not a second authority for task state and introduces no database, external message bus or server-resident mutable workflow database.
2. Source branches, Git worktrees, immutable review refs and integration evidence remain distinct from orchestration state. An agent's conversation is never the durable work record.
3. The server continues exposing operations over the owner's authenticated account and the existing client project binding. Queue subscriptions and claim generations are coordination tools, not new permission boundaries.
4. The workflow does **not** infer acceptance from task completion, merge from review acceptance, or task closure from integration. Domain transitions remain explicit and independently auditable.
5. No persistent worker assignment, exclusive reviewer identity, or dedicated Integrator task is required. The scheduler launches a Manager role instance, and Manager launches Lead/Worker/Reviewer/Integrator role instances. The client derives transient per-role display labels such as `Worker 1` and `Worker 2` for simultaneous executions; numbers may be reused after termination and never serve as task/inbox addresses. Each execution retains an opaque immutable ID for historical attribution. Role subscriptions and instructions are versioned configuration for the launched role, not a membership list of named workers.
6. Browser tabs can be closed immediately after a confirmed one-shot submission; tab lifetime is not evidence that a model session ended. An uncertain submission must not be blindly repeated.
7. New work-queue plumbing is not permission to deploy, restart the live server/client, enable the Manager schedule, or launch unattended agent sessions. Those are separate rollout operations.

## 3. Vocabulary and durable objects

**Task** — Durable unit of requested work with canonical specification and lifecycle. It may produce multiple implementation stages and reviews; it is not owned perpetually by a worker ID.

**Work item** — One actionable stage or event, referencing its authoritative subject (task, review, integration candidate, challenge, or planning event). It is placed in exactly one queue and has one current claim at most. A Claimed item is presented as **Active** work while its execution is live; this is a derived task/work-status projection, not an independent task-lifecycle write.

**Queue** — Project-scoped index of work items eligible for a type of role. Standard queues initially: planning, implementation, review, integration, and challenge-triage. Queues are not authorization boundaries.

**Subscription** — Persistent role configuration listing queues and, optionally, selection policy. An agent can inspect or claim subscribed queues as a matter of cooperative protocol; the account's actual tool permissions are unchanged.

**Agent UUID** — A generated, globally unique UUID assigned to exactly one new Jarvis agent execution/session at launch, associated with its stable `launchId`, project and role. This is the exact recipient ID for the existing response-alert queue and the handle for last-seen, control/stop observations and history. It is **not** the provider's opaque conversation/session ID, a worker slot, a role name, a task claim, or a security principal. Every successor session receives a fresh UUID, even when it resumes the same task or reuses a display label such as `Worker 2`.

**Launch** — A bounded, journaled role-assigned session execution, including taskless Manager and zero-claim NoWork cases, with a stable opaque launch ID, **one generated agent UUID**, version/generation, account-global token and project-local dispatch/demand record. A verified project terminal receipt fences later claims and dispatches before the account-global token is released or transferred. A launch claims at most one work item during its lifetime. Predispatch cancellation, NoWork, normal Manager completion and error have explicit launch-level terminal outcomes, without fabricating work items.

**Activation** — One execution of a role that has claimed an item, identified by an opaque activation ID and claim generation, bound to its originating launch. It checkpoints while running and terminates through explicit yield, stage-complete, block or verified stalled-lease recovery. An activation is not a task or a persistent worker assignment; terminal activation and launch events are committed together where applicable. Its first-class liveness state can be **Running**, **Stalled** (lease expired but not reclaimed), or terminal **Reclaimed**.

**Claim** — Exclusive, current reservation of one work item by one activation, protected by the ledger's atomic compare-and-swap and a monotonically increasing claim generation. The generation is a stale-write coordination guard, not an identity or security check.

**Checkpoint** — Immutable progress evidence linked to the work item and activation; readable independently of any earlier ChatGPT session.

**Dependency** — A canonical condition/challenge that keeps a work item blocked until its specified release rule is satisfied.

**Global capacity slot** — One account-scoped concurrent **logical agent-execution** budget reservation, allocated to a launch regardless of role or project, not a named agent ID. Lead, Manager, Worker, Reviewer and Integrator all consume the same pool. The scheduler itself is a non-agent control-plane timer and consumes no slot. The slot is a semaphore token recorded across devices in one authoritative account-scoped admission ledger and released only by the evidence policy defined in section 8.

**Work conversation** — An append-only, subject-addressed exchange linked to the durable task (or another canonical review/integration/planning subject) with operator/agent messages, questions, answers, decisions, and references to challenge conditions. Messages are independent of whichever session currently claims the work; the conversation is not a second task specification or an alternate permission channel.

Agent display should primarily report Active and Stalled work, prioritized queued work, pending launches and blocked work. Agent UUIDs are the underlying execution identities and exact alert destinations; client-generated role numbers are display-only. The old Waiting/NeedsWork/Parked roster distinction is removed. For ephemeral execution labels, Ready is a confirmed pending dispatch, Working is activity within its lease, Stalled is an expired but unreclaimed execution, and Reclaimed/Terminated are historical terminal outcomes; Idle requires no persistent agent roster. Blocked belongs to a work item, not an agent. The canonical Task lifecycle remains Open/InProgress/Closed/etc.; task-level Active and Stalled are derived from claimed work stages, never separately writable Task states.

The `agentId` in a new activation is the **immutable UUID of the originating launch's execution** and must match that launch's registered agent UUID. The optional display label or historical legacy Worker N name is descriptive. New launches create/register a fresh UUID before any alert or tool response is routed, without requiring pre-registered numbered workers. The next execution resuming the same work receives a different agent UUID. Agent UUID, claim generation and work version are coordination and attribution data; none proves the caller's authenticated identity or creates permissions.

Launch records hold stable launch ID, **one registered agent UUID**, role/configuration version, eligible queues, versioned demand reservation, account-global capacity reservation ID, journaled browser dispatch state, optional one activation, server-witnessed lastSeen/lease-generation records (coalesced updates), STOP-alert enqueue/terminal receipts and terminal/uncertain/stalled-recovery evidence. The launch-to-agent UUID mapping is immutable and one-to-one; existing response-alert records remain addressed to that exact registered agent ID. The **account-scoped capacity ledger** is the sole authority for the global semaphore across all projects and devices. Each project's existing Git orphan ledger remains the sole authority for its tasks, reviews, challenges and queue demand; the account ledger contains no task specifications, review verdicts or duplicated queue state. Both use the existing Git-backed CAS/journal machinery, not a new database. Reserving global capacity and project demand is a two-ledger, idempotent admission protocol: obtain the global token first, then register project demand with the SAME launch ID, stable project operation ID and generated agent UUID. A project-demand CAS failure **before any project launch record exists** must commit an abort-only project launch tombstone before the global token may be released; an ambiguous demand write retains the token until the original operation outcome has been reconciled and the terminal tombstone or normal project terminal receipt has been durably verified. Never free a token based on an absent launch at one snapshot head. This cannot be presented as a fictitious cross-repository atomic transaction. A process-local Manager journal is a side-effect journal, not the cross-device reservation authority. The exact record representation is fixed in Phase A.

Work items are durably keyed by a deterministic identity derived from project, queue, authoritative subject, and the exact event/stage generation that made work available. Replaying the same event creates no second item. A new revision or ChangesRequested decision creates a new stage generation where necessary, without rewriting or erasing old events.

A task's implementation attempt can remain as the stable **work-stage** record spanning several activations, but it has no permanent ownerAgentId. Historical owner and assignment records are retained as audit provenance, not as current scheduling authority.

**Source-writer lineage:** Canonical key project + source repository + task + target ref + explicitly selected lineage ID. Every mutable implementation stage carries lineage, stage generation, pinned base, and current continuation SHA. Within a lineage, exactly one source-writing stage may be actionable or claimed; independent review items may coexist. ClaimNextWork checks both item version and lineage generation/claim in one CAS. Different lineages require an explicit branching/merge policy.

## 5. Source-of-truth and queue publication

- A work item points to canonical data; it does not duplicate task specifications, review findings/decisions, accepted source hashes, or integration receipts as alternative authority.
- A domain change producing work (task intake, Lead readiness decision, frozen review submission, review verdict, challenge satisfaction) publishes or updates the corresponding item **in the same Git-ledger transaction**, or uses a deterministic reconciler that rechecks the source and commits the missing projection before exposing availability. Queue/attention indexes have per-domain producer high-water marks and per-shard coverage marks checked against the verified Git ledger snapshot; a one-time migration coverage marker does not prove ongoing coverage.
- If a projection is missing, stale, partial, behind its latest producer high-water mark, or unverified, the system must not advertise a healthy empty queue or silently invent eligibility. Query the canonical source, repair the derived index with CAS, or report incomplete coverage. Manager must not reserve launches and ClaimNextWork must not return normal NoWork on unverified index coverage.
- In-memory queue counts and sharded indexes accelerate Manager reads but never authorize a claim. ClaimNextWork revalidates item state, subject state, dependencies, version and claim in the authoritative ledger.
- Queue creation is domain-specific and explicit. This design is not a general event bus, scriptable rule engine, or automatic approval system.

The initial producers are:

| Canonical event | Queue item |
| --- | --- |
| New task requiring triage or priority change | planning |
| Lead marks implementation stage actionable | implementation |
| Worker submits a new exact frozen review | review |
| Review returns ChangesRequested | join or create the single current correction stage for the matching source-writer lineage and generation; keep all review findings; stale verdicts go to Lead triage |
| Review is explicitly Accepted and integration is required by task policy and exact target/source are valid | one integration item pinned to review ID, frozen SHA and target |
| Pending challenge condition requires triage/action | challenge-triage or a queue specifically configured for that condition |
| Blocking dependency becomes satisfied | Existing blocked work item becomes Available; no duplicate item |

Task completion without review, acceptance without integration, and non-code work are valid policy variants; the Lead selects workflow requirements in the task specification/queue metadata. The queue mechanism must not force all tasks through review or merge.

## 6. Subscriptions, prioritization and fairness

A role subscribes to one or more queue IDs and carries versioned instructions in project configuration, independently of any numbered agent registry. The scheduler creates a Manager launch with role=Manager; Manager creates child launches with role=Lead/Worker/Reviewer/Integrator and a pinned role configuration version. The client automatically numbers concurrently visible executions sharing a role, for display only. Changing the configuration affects future launches/claims, not existing activations. Default role subscriptions: Lead to planning, Worker to implementation, Reviewer to review, Integrator to integration. Manager is a scheduled control-plane actor, not a permanent queue claim.

Queue selection is deterministic at one verified ledger snapshot: highest priority **feasible claim** first (lower numeric priorityRank if retaining the current convention), then older enqueue sequence, then stable item ID. Feasibility includes claim-generation/source-lineage checks **and preserving an injective compatible demand-credit matching for other in-flight launches**; a candidate that strands an already admitted compatible launch is not eligible for this claim. If multiple queue subscriptions exist, configured queue weights/priority are explicit. Starvation prevention can be added after measuring contention; do not hide ordering behind agent-ID names.

Lead prioritizes **work**, not people. New tasks and operator requests enter the planning queue until Lead records priority, dependencies, readiness, and the appropriate work type. Manager only observes verified eligible demand and capacity; it cannot implicitly decide which tasks are more important. Each Worker selects the highest-priority **feasible** implementation work using the canonical ordering and globally rematched outstanding demand credits under one project CAS, independent of its label. Lead may defer or reprioritize an item without assigning a named worker. A worker that finishes one activation does not acquire a preferred claim on the next one.

A role subscription is expected behavior, not access control. The current owner account remains able to invoke the same Jarvis operations under any agent label.

## 7. Claim, checkpoint and terminal state machine

Work item states:

~~~text
Available --atomic claim--> Claimed
Claimed   --checkpoint-->   Claimed
Claimed   --yield-------->  Available
Claimed   --block-------->  Blocked
Blocked   --wake--------->  Available
Claimed   --finish-stage->  Completed (+ optional next queue item)
Available/Blocked --cancel-> Cancelled
~~~

A finished stage is not necessarily a finished task. For example, implementation completion can produce an available frozen review item; the implementation item is Completed while the task remains InProgress.

**Launch state machine (including no-claim executions):**

~~~text
GlobalReservedNoProject --successful project admission CAS--> Reserved
GlobalReservedNoProject --abort-only project CAS--> TerminalPendingRelease (unbound admission tombstone)
Reserved --confirmed browser submit--> Submitted --observed/claim--> Running
Reserved --definite pre-submit cancellation/failure--> TerminalPendingRelease
Submitted/Running --TerminalizeLaunch(NoWork | ManagerFinished | Cancelled | Error)--> TerminalPendingRelease
Running + work claim --YieldWork/CompleteWork/BlockWork--> TerminalPendingRelease
Running(Manager) --PrepareManagerHandoff--> TerminalPreparedHandoff (project fenced)
TerminalPreparedHandoff --global CAS decides Swapped--> FinalizeProjectHandoff + child DispatchPending
TerminalPreparedHandoff --global CAS decides Aborted--> FinalizeProjectAbort + Manager TerminalPendingRelease
FinalizedProjectHandoff + valid child demand --> child DispatchPending / Manager Terminal(Handoff)
FinalizedProjectHandoff + cancelled child --> child TerminalPendingRelease (child owns token)
TerminalPendingRelease --verified account token release--> Terminal
Any ambiguous unverified side effect --> RecoveryNeeded (token held; no presumed terminal)
~~~

**Unbound admission abort (C01):** After the account-global `ReserveGlobalAgentSlot` has reserved one token but **before any project launch is registered**, a project-demand CAS can lose to another Manager. The stable project-admission operation ID and project Git CAS distinguish a definite recorded rejection from a missing/lost response. `AbortUnboundProjectAdmission(project, launchId, agentUUID, originalProjectAdmissionOperationId, expectedProjectHead, operationId)` is an **idempotent project-ledger CAS** which creates a minimal **abort-only terminal launch tombstone** bound to the same launch ID, agent UUID, original admission operation ID, verified original failure/settled outcome, and immutable abort receipt. It reserves no demand, creates no task/activation, and authorizes no browser submit. The tombstone permanently fences a delayed or replayed project admission using that launch ID: both the original admission and the tombstone must CAS-check the same launch-ID absence/version at the authoritative project head; a late old Git push based on a pre-tombstone head cannot win. If the original project admission might have committed or still has an unverified network outcome, **do not infer failure from record absence**; first recover its exact operation receipt and canonical head, or retain the account token as RecoveryNeeded until the competing project CAS can be conclusively serialized. After independently verifying the project abort tombstone, the normal account-ledger `ReleaseGlobalAgentSlot` CAS releases exactly one matching launch token using that terminal proof. A duplicate abort, original admission replay, client crash or two-client race cannot create a live project launch after its token was released. The same process covers scheduler-created taskless Manager admission failures. No per-agent special permission check is involved.

**TerminalizeLaunch** is the idempotent project-ledger terminal operation for a launch **without an active work claim**: Manager after dispatching children, Manager after demand disappears, zero-claim Worker/Reviewer NoWork, predispatch cancellation and verified error. It requires stable launch ID, expected launch version/generation, canonical reason, caller-stable operation ID and any relevant journal receipts. The project Git CAS writes one immutable terminal receipt and fences all future dispatch/ClaimNextWork/work-scoped mutations by that launch. Competing NoWork/cancel/handoff/normal-finish outcomes resolve to exactly one receipt. Normal taskless Manager calls TerminalizeLaunch(ManagerFinished) on turn completion; a reconciling client may invoke it only with positive termination evidence, never time, prose or tab closure.

For claimed Worker's terminal YieldWork/CompleteWork/BlockWork, the same project CAS must also terminalize its originating launch; there is no separate unfenced release path. **Only after verifying the project launch terminal receipt OR the C01 unbound project abort-only tombstone** may ReleaseGlobalAgentSlot use an account-ledger CAS to release that launch's token, exactly once. Every account release matches the current token owner (Manager or child), original launch ID, terminal receipt and its replay-safe operation ID; a failed response does not permit another release under a new ID. A pending release continues consuming global capacity until confirmed; Manager's children retain their independent tokens. Manager handoff follows the separate ordered protocol in section 8.

**ClaimNextWork** selects one eligible item for a specified current launch ID and caller-stable operation ID, allocates a fresh activation ID, increments claimGeneration and atomically updates the work item, activation, launch's one-claim marker and its demand reservation within one Git transaction. Competing clients must produce at most one winner. A loser rereads the queue only after its own original operation outcome is definitively known; it never assumes an ambiguous claim failed. A launch with any previous successful claim can never claim again, even after that activation yields or completes. The return includes canonical subject, frozen source/spec context where relevant, latest checkpoint, claim generation, exact ledger snapshot, and the workflow continuation requirements. If the result is lost after possible commit, the caller MUST query its exact operation receipt and/or immutable launch-claim mapping and replay the same operation ID/payload before ever issuing a different claim. An unknown outcome is not a NoWork response.

**CheckpointWork** appends immutable summary, nextAction and optional evidence/source SHA while preserving Claimed. Replays with the same operation ID and arguments return one receipt; different arguments for the same operation ID are invalid.

**YieldWork** is a *terminal operation for that activation and its originating launch*: atomically writes a final checkpoint, marks the activation/launch Yielded, releases the item claim, commits the project-side logical terminal receipt, and makes unfinished work Available. The matching account-global capacity token remains reserved until the independently verified project terminal receipt is released by account CAS. A separately configured strict provider-session capacity budget can remain reserved until its own host-terminal evidence. The next worker can have any label or session ID. No extra task reassignment or ownership transfer is needed. Old activations and launches are not silently resumed. For source-writing work, normal yield requires an independently retrievable, immutable continuation commit (plus repository and ref provenance) verified reachable from the configured remote BEFORE this transaction. A dirty/unpublished worktree cannot be silently yielded into the available queue. Non-source work may have no source commit. A failed source snapshot or unresolved mutating job leaves the work claimed or explicitly blocked with a durable dependency; it never advertises recoverability it cannot prove.

**CompleteWork** writes a final checkpoint, terminates both activation and originating launch, transitions this stage to Completed, and records any explicit next-stage item(s). Required source/frozen-review evidence must already be durably reachable and verified. It must not implicitly close a task, approve a review, or merge code.

**BlockWork** writes a checkpoint and dependencies, terminates the activation and originating launch, and leaves the item Blocked with no active claim. When dependencies are satisfied, the original item is requeued once with its existing checkpoint history. If a mutating job or dirty source prevents safe release of an execution/worktree, the blocking transition must represent that dependency and retain the necessary execution/workspace fence until positive handoff or verified termination.

A session may make several checkpoints before it yields. A claim is not released merely because a browser tab closes, a session ID changes, an elapsed-time threshold passes **without the specified atomic lease-recovery transaction**, an agent returns a prose message, or a review verdict is written. Work completion and provider-session termination are separate facts. A terminal Jarvis launch receipt fences future claims and work-scoped mutations for that launch; it is positive *logical* execution termination evidence, not proof that the browser/provider process has exited. When strict physical-session concurrency is required, retain capacity until independent host-terminal evidence or explicit recovery; do not relabel a Jarvis yield as a provider-process exit.

Every work-scoped mutation compares the latest work version and claim generation. An obsolete activation cannot publish new checkpoints, yield, or complete an item after its claim was explicitly released. This is coordination against stale work, **not** an agent-ID permission check; account-level Git/file tools retain their existing permissions.

## 8. Manager execution and capacity

Manager's only required scheduling decision for normal queue work is:

~~~text
unreservedEligibleDemand = count(unique eligible work generations left unmatched by verified live compatible demand-credit matching)
freeGlobalCapacity = maxConcurrentAgents - globallyReservedActiveAndUncertainLaunches
launchCount = min(unreservedEligibleDemand, freeGlobalCapacity,
                  remainingDispatchBudget)
~~~

**One global limit, no role quotas.** The owner-account configuration exposes `maxConcurrentAgents` as the one authoritative cap across **all roles, projects and devices**. A Manager, Lead, Worker, Reviewer or Integrator execution counts equally. There are no permanent Worker 1-5/Reviewer 1-3 reservations, role-specific ceilings or automatic role guarantees. The scheduler is a control-plane timer, not an agent execution, and consumes no capacity. In-flight, submitted, observed and uncertain launches all hold one global capacity token until verified terminal release/recovery. An unclaimed launch demand credit covers one compatible unique eligible work generation for demand accounting, without preassigning a task to that worker; repeated Manager passes cannot double-count still-available work. Manager reservation and demand coverage are CAS checked across devices, not merely protected by local journals. Reservations may conservatively suppress dispatch on temporary uncertainty, but never permit over-capacity launches.

**Demand-credit matching contract.** For a project at verified ledger snapshot S, let L be live, unclaimed launches whose demand credit is active and U the Available work generations. A canonical injective matching M maps every launch in L to a **distinct** generation in U compatible with that launch's role/queue subscriptions and current subject eligibility. These generation identities are internal demand accounting, **not a Worker N task assignment**; a worker still chooses among claimable work by priority. Every new launch reservation uses a bounded deterministic augmenting/rematching operation under one project Git CAS to prove a matching exists for L plus the new launch. A credit that cannot be matched is not an eligible dispatch reservation.

**Claim and rematch ordering.** `ClaimNextWork(Li)` scans the worker's priority-ordered eligible items and chooses the first candidate X for which there is a compatible injective matching for **all other still-live unclaimed launches** against U excluding X. Within one Git CAS it claims X, consumes Li's credit, and rewrites every affected credit in that matching. It cannot commit by updating only Li's previous generation. If Li was originally credited B but claims A, the other A-credited compatible launch is rematched to B **before** any new Manager pass can see B as uncovered. If roles overlap but a competing launch is eligible only for A, a worker eligible for A+B must take B first when taking A would strand the A-only launch. This is the highest-priority **feasible** claim, not an advance Manager assignment. All matching and rebalancing revalidate verified index coverage; incomplete or stale matching returns a retry/incomplete state, never an invented NoWork or license to launch.

**Changing demand after admission.** Cancellation, supersession, blocking, queue subscription reconfiguration and priority/eligibility changes recompute affected credits in the same canonical Git transaction as their domain projection or fence availability until deterministic reconciliation. A launch that can no longer be matched is marked `DemandInvalidatedPendingTerminal`, cannot claim another item, and retains its account-global capacity token until a verified NoWork/cancel terminal receipt. It cannot be counted as coverage for unrelated work or silently rebound to a task outside its subscriptions. Manager computes uncovered work only from verified matching plus fenced invalidated launch states and never reserves a second credit on already covered demand. Two-client CAS contention, lost replies and concurrent priority changes replay the same mapping or re-read; they do not commit partial rematches.

The account-global capacity ledger is the only authority for `globallyReservedActiveAndUncertainLaunches`; project ledgers are the only authority for source work and the queue. Cross-ledger admission must use idempotent operation receipts and compensating release/reconciliation, rather than claim imaginary atomicity. **The global invariant is `0 <= globallyReservedActiveAndUncertainLaunches <= maxConcurrentAgents`**, including Manager's own reservation. `maxConcurrentAgents` configuration and token reservations share **one account-ledger CAS/version domain**. A request to reduce the configured limit below active/uncertain token occupancy is rejected with an explicit occupied count. A reduction still at or above occupancy or an increase commits against the same CAS head as competing reservations; the scheduler revalidates on the actual reserve. No token is evicted on resize, no timeout frees uncertain activity, and no drain-only state is introduced initially. By default, this counts active/uncertain Jarvis execution sessions, not dormant historical ChatGPT conversation tabs. One-claim-per-launch fencing makes a logically terminated execution ineligible for further work. A separately configured hard ceiling on physically alive provider sessions would require independent host-exit evidence and is **not** implied by this logical global limit.

For each launch:

1. Read a verified consistent project work/claim/launch snapshot and account-global capacity snapshot. If coverage, client activity, or global admission evidence is incomplete, suppress launch and report why. Global free capacity must be reserved by CAS before any new browser side effect.
2. Acquire one account-global capacity token for a child launch with a stable launch ID, fresh agent UUID and requested role, then reserve one project demand credit for that launch against the unique eligible work-generation set. The steps span two canonical ledger scopes: after definitive project-demand rejection, commit and independently verify an **abort-only project launch tombstone** under the original launch ID before releasing that exact global token; after unknown outcome, retain the token while reconciling the same project operation and its possible late Git commit. A negative read is not an abort receipt. The demand credit participates in the canonical compatible injective matching above; it is not a task assignment and does not prescribe what the worker claims. Manager never binds a task to Worker N. Eligibility changes must atomically rematch or fence invalidated live credits before further dispatch. All reservations are idempotent by launch ID.
3. Dispatch one ChatGPT bootstrap for project + **assigned role and pinned role configuration version** + eligible queue(s) + launchId, using the existing one-shot submission semantics. The newly created execution gets an opaque unique ID. The client automatically labels simultaneous role instances (`Worker 1`, `Worker 2`) solely for display. Close the temporary browser tab once submission is positively confirmed.
4. The newly started Worker reads its role instructions and invokes ClaimNextWork with its launch ID, preserving/recovering the caller-stable operation ID across an uncertain result. **The Worker claims the highest-priority feasible queue item** under the remaining-live-launch matching contract, regardless of which generation previously credited its own launch. The claim CAS consumes its credit and rematches **all** other affected live credits atomically with the chosen item; if the matching cannot be verified, it fails closed for recovery rather than causing a new Manager dispatch. If the queue has emptied, it records a canonical NoWork terminal launch outcome, releases its demand/capacity reservations, and ends; Manager must not spin or keep launching because of the stale count.
5. When the claim succeeds, its activation becomes Working and its launch records that its lifetime one-claim allowance is exhausted. Session checkpoints and final outcomes are canonical work mutations. Yield, CompleteWork and BlockWork terminalize this activation/launch; the same launch cannot claim again. A verified project terminal receipt followed by idempotent account-ledger ReleaseGlobalAgentSlot CAS frees **one global capacity token**. Manager's last-slot handoff is the ordered project-fence-then-global-swap protocol below, never a fictitious cross-ledger atomic commit. If an outcome is ambiguous, keep the global token reserved and reconcile exact project/account receipts rather than overlaunch; never treat tab closure as terminal evidence.
6. A submitted-but-unobserved or uncertain browser launch still consumes reserved capacity until positively reconciled. No retry of an ambiguous submit.

The Manager must not launch merely because a Worker/Reviewer/Integrator/Lead ID is registered or subscribed. It must not infer taskless reviewer availability from a parked/unparked agent field. No browser tab is a proxy for claim/session state.

### Scheduler preflight and Manager handoff

The recurring scheduler is intentionally lightweight: it checks the account-global capacity ledger **before** opening a ChatGPT session. If `freeGlobalCapacity == 0`, it **does not launch Manager**, does not recurse or manufacture new role work, and records only a bounded deferred tick. A global-capacity release/verified recovery wakes a coalesced scheduling check; a periodic heartbeat remains a fallback so work is not stranded if an event is missed. Even at full capacity, non-agent diagnostics can surface active/uncertain launch receipts, reconcile definitively terminal evidence and report RecoveryNeeded to the operator; they **cannot** free a token on timeout alone or spawn an otherwise uncounted Manager. A scheduler read is only an optimization: the authoritative pre-browser reservation must CAS against the latest global capacity head, or fail cleanly if another project/device won the last slot. The scheduler pins role=Manager and the role configuration version in its launch; Manager then creates the child launches with their respective roles.

**Last-free-slot case.** Manager itself consumes one global slot and cannot launch another execution while holding the final available token. The optional **single-use terminal slot handoff** is a strict two-ledger protocol, not a distributed atomic transaction:

1. **Project prepare and fence FIRST.** Under one project Git CAS, `PrepareManagerHandoff(managerLaunchId, managerGeneration, childLaunchId, assignedRole, demandCredit, operationId)` verifies Manager launch eligibility, reconciles child demand credit and the dispatch journal, writes a pending child launch as `DispatchBlockedPendingHandoff`, and moves Manager to irreversible `TerminalPreparedHandoff`. The immutable project preparation receipt binds both launch IDs, versions, role, demand and a stable **handoff ID**. Stale Manager dispatch/claim writes now fail the project launch generation fence. No browser side effect or account-global token transfer is allowed before this receipt.
2. **Serialize one global disposition: Swapped OR Aborted.** After verifying the exact project prepare receipt, `ResolveManagerHandoff(handoffId, managerLaunchId, childLaunchId, projectPrepareReceipt, choice=Swapped|Aborted, operationId)` commits a single immutable **account-ledger** disposition with one CAS on the same versioned Manager capacity token. Only `Swapped` replaces Manager's occupied global token with the child token; `Aborted` preserves Manager's token, permanently prohibits a later swap for this handoff ID, and authorizes project abort finalization. All clients/reconcilers, including old delayed swap requests, must consult that global disposition; an immutable **historical prepare receipt alone never authorizes a swap after Aborted**. If the reply is lost, recover the original account operation receipt and disposition before any other side effect.
3. **Finalize the winning outcome in the project ledger.** `FinalizePreparedManagerHandoff(handoffId, verifiedAccountDispositionReceipt, expectedProjectVersion, operationId)` is a project CAS that moves `TerminalPreparedHandoff` to a terminal outcome and settles the child's pending demand. For `Aborted`, cancel the never-dispatchable child, create a terminal `HandoffAborted` project receipt for Manager, then release **Manager's** still-owned global token with that receipt. For `Swapped`, Manager is terminal `Handoff` and child owns the sole token; revalidate demand and mark the child dispatch-eligible ONLY if still valid, or terminalize the child with a project receipt and release **child's** global token if cancelled/invalidated. A domain cancellation while the global choice remains unresolved records a pending intent and **cannot prematurely remove the prepared child demand**; after the global decision, finalization processes it deterministically. Every project terminal transition is versioned and idempotent.
4. **Dispatch once, after matching receipts.** Only a `Swapped` account decision plus corresponding verified project finalization/child-eligibility receipt may issue the child's one-shot browser intent. Submit its original launch ID/agent UUID at most once; uncertain submission retains the child token and never retries with new IDs. If `Aborted` won, no dispatch path exists. The Manager launch remains fenced from additional work and the logical handoff does not prove physical provider tab exit.

**Recoverable partial states:** (a) Before project prepare, Manager still holds the token and remains the only eligible project actor. (b) Prepared project but no known account disposition: Manager is fenced and holds its token. The reconciler must commit/retrieve one **account CAS choice** `Swapped` or `Aborted` under the ORIGINAL handoff ID; merely observing unswapped at one head is not permission to cancel child demand. (c) Account `Aborted`, project still prepared: recover the same `Aborted` receipt, finalize project child cancellation and Manager terminal `HandoffAborted`, then idempotently release Manager's token; every delayed `Swapped` attempt fails against the account disposition. (d) Account `Swapped`, project still prepared: child owns token; finalize child dispatch if valid, otherwise terminalize/cancel it and release **child's** token, never Manager's; never leave a cancelled child owning a token without RecoveryNeeded. (e) Child submit uncertain: retain child token and original journal until verified, with no duplicate submit. Every failure between account choice, project finalization and token release is replayable by stable IDs/receipts; no component guesses from missing pushes or snapshots. A global swap without a matching verified project prepare is an invalid fail-closed state requiring reconciliation, not dispatch authorization.

The account CAS cannot fence project work on its own; the **project-fence-before-transfer** ordering is mandatory. Two clients racing project dispatch and prepare serialize under that project CAS. An unsuccessful or ambiguous handoff keeps capacity reserved until positive recovery. Cancellation and late swap are serialized by a globally recorded Swapped-or-Aborted choice, with later project finalization/release acting only on the actual token owner; a competing Manager cannot create another child from the fenced launch. The protocol enables `maxConcurrentAgents=1` to dispatch useful work; until implemented, skip last-slot dispatch instead of exceeding the limit.

Do not spawn Manager merely because the schedule fired if there is no verified actionable/pending control work. The scheduler does not prioritize tasks or choose child roles; those remain Manager decisions. Manager and scheduler must not each spawn an extra Manager recursively. Manager's own role execution is counted from reservation through terminal yield/handoff. Reconciliation reads both global tokens and project-specific launch/demand receipts to avoid stranded capacity after crashes.

The Manager heartbeat can retain the existing AfterAgentIdle scheduling concept initially, adapted to global admission and capacity-release triggers; a global release must coalesce into a bounded scheduler pass, not unbounded recursion. Cross-project demand selection must follow explicit configured fairness/priority rules, not whichever device won a local timer. Do not add recursive Manager launch paths or unattended deployment as part of this specification.

## 9. Session interruption, recovery and background jobs

Normal turn end for a **claimed work activation** must be an atomic YieldWork, CompleteWork or BlockWork. A taskless Manager, predispatch cancellation or zero-claim NoWork execution instead uses the launch-level TerminalizeLaunch receipt, followed by account token release or section 8 handoff. The next session reconstructs its work solely from the authoritative subject, checkpoint(s), exact reachable source snapshot refs and durable events. An agent-facing success message, a closed browser tab, and a local worktree path are not source-continuation evidence.

### First-class stalled executions and automatic lease recovery

**Detection.** Every new launched execution registers a generated **agent UUID** before its first tool response. The launch binds this exact agent ID, project, role, immutable launch ID, server-witnessed `lastSeenAtUtc`, `leaseGeneration` and account-capacity reservation. A fresh session gets a fresh UUID even when resuming the same task or displaying the same numbered role. Tool calls and explicit lightweight client heartbeats (including verified active long-running job ownership) renew a **Working** lease at a bounded cadence. The time source is server-authoritative; an unrelated agent ID, client-local tab timestamp or mere display observation does not extend another execution's lease. Coalesced durable heartbeat receipts survive restart without writing the Git ledger on every UI render. Configuration exposes `stalledAfter` and `reclaimAfter` (`reclaimAfter >= stalledAfter`) at the applicable account/project scope, applied consistently across roles. A Manager/scheduler pass can inspect leases without spawning another agent.

**Execution state:** `Working -> Stalled/StopRequested -> Stopped` (cooperative) or `Stalled/StopRequested -> Reclaimed` (lease recovery) is first-class. A project CAS comparing the current server-witnessed lease generation and last-seen value commits the **Stalled** transition at `lastSeenAtUtc + stalledAfter`, retains the claim/global capacity token, and records a stable `stopAlertId` request addressed to that execution's **agent UUID**. This is a one-way stop instruction, not a transient yellow heartbeat warning: once Stalled/STOP-requested, a later heartbeat cannot silently restore Working. A heartbeat racing the **initial** Stalled CAS may win first and prevent the transition; after Stalled commits, late activity is recorded for diagnosis/cleanup only. The agent must acknowledge by stopping cooperatively (with safe checkpoint/yield or taskless terminal receipt), or be reclaimed after the configured grace period. The TUI must not call it Idle. A submitted-but-unobserved launch has an explicit pending-observation lease and remains counted; absence of a tab or message alone does not authorize release.

**Reuse the existing agent-addressed response alerts.** The same canonical stalled transition invokes or deterministically schedules a single `queue_response_alert` for its exact registered agent UUID with a message beginning `STOP` (for example: `STOP: Your Jarvis execution is Stalled. Stop work, checkpoint only safely recoverable state and yield/terminate. Do not continue the task.`). Use a stable operation ID derived from launch UUID + stalled lease generation + STOP event to deduplicate a Manager/reconciler retry. The existing `get_response_alerts` and `clear_response_alert` remain the inspection/clear APIs; use **no new notification or session-control bus**. The already-implemented response-alert path stores pending alerts in the project orphan ledger and prepends STOP before other instructions on the target agent's next eligible tool response, including a job-result poll; ordinary notification mute/block preferences do not suppress operator response alerts. Respect its existing pending-alert limits, at-most-once consume semantics and possible lost-delivery window. An alert-enqueue failure remains visible/retryable with its original operation ID, but neither enqueue nor successful delivery is proof the agent stopped. A STOP delivered *with a response* cannot undo a side effect from the just-finished tool call, so new work and unsafe mutation must additionally be fenced at the project claim/launch boundary.

**Strict channel separation.** Session-targeted STOP/operational response alerts address **agent UUIDs**. Operator questions, replies, progress notes and decisions address **tasks/work subjects**, persisting across UUID changes. Alert receipt does not mutate task specs, resolve dependencies, release claims or satisfy a terminal transition. No per-role ACL or UUID-based security boundary is introduced.

**Manager recovery.** At `reclaimAfter`, Manager (or a non-agent reconciler when no global capacity exists) may automatically run `RecoverStalledExecution(launchId, agentUUID, expectedLeaseGeneration, stopAlertId, operationId)`. This is a formal **lease-expiry termination policy**: one project-ledger CAS verifies the same agent UUID, Stalled/StopRequested receipt, lease generation, unchanged exclusive claim and safe external-work conditions; records immutable `StalledReclaimed` terminal evidence; increments/fences the prior activation's claim generation; and either releases its item to the priority queue or moves it to `RecoveryBlocked`. A cooperative yield/terminal call racing recovery has one winner. A heartbeat **after** STOP cannot cancel reclamation or revive the old execution. Already-Stalled executions can perform only specifically permitted safe shutdown/checkpoint/terminal operations, not claim another item or advance an unrelated stage. After reclaim, all old work-scoped mutations from that UUID/launch fail stale-generation or terminal checks even if the ChatGPT session resumes; agent-scoped response alerts can still inform the old UUID of the stop but cannot restore its claim. The successor execution gets a new agent UUID and claims the **same durable task work stage** normally rather than being "reassigned" a Worker N slot. Replays return the original recovery receipt; duplicate Manager passes cannot reclaim twice. Independently verify the project terminal receipt before releasing one global logical token via account CAS. This revokes logical Jarvis coordination only, **not** physical provider execution or the owner's underlying file/Git permissions.

**Resumption contract.** Default automated recovery uses the latest independently reachable immutable source/checkpoint snapshot and task conversation, never the previous execution's local worktree. If only an earlier snapshot/base commit is durable, resume from it and record the potentially discarded uncommitted interval visibly in history; do not claim those changes were preserved. Isolated per-activation worktrees and generation-scoped WIP refs ensure a late old process cannot overwrite the new activation's pinned continuation SHA. Pending mutating subprocesses, uncertain Git push/merge, external side effects or missing source provenance that cannot be safely isolated or reconciled cause `RecoveryBlocked` with the exact dependency and operator-visible evidence; do not start a conflicting writer or treat an ambiguous external effect as failed. Pure read-only/planning/review stages may generally be reclaimed automatically after fencing their canonical claim; a review with a recorded verdict can be terminally recovered but **never** reopened by generic requeue. For an undecided claimed review, the recovery CAS must atomically release the existing canonical review claim and the review work item's claim, or block if the review provenance is uncertain. A recovered integration with uncertain push must reconcile exact Git/receipt evidence before retry.

For a Manager stalled in `TerminalPreparedHandoff`, STOP delivery and an expired lease do not authorize direct token release or child cancellation. The reconciler must first commit/recover the global `Swapped|Aborted` decision for that handoff ID, then finalize the project launch/child receipts, and only then release the token currently owned by Manager (Aborted) or child (Swapped). Do not use generic `RecoverStalledExecution` to bypass this rule.

The global capacity limit counts logical leases/launches, not physically alive provider tabs. Stalled/StopRequested but unreclaimed sessions remain in that count; sending or delivering a STOP alert never releases their tokens. An expired lease is sufficient for automatic *project-side logical revocation only when that protocol is implemented and the durable recovery CAS succeeds*; a timestamp alone is not a free-token instruction. Until implemented, retain the old fail-closed RecoveryNeeded behavior for ambiguous sessions. The existing advisory 25/30-minute turn guidance is separate from the configurable stall/reclaim leases, not a substitute for their proof.

After recovery, old activation work-scoped mutations fail stale-version/claim-generation validation; no agent-ID security enforcement is introduced. Ordinary account-authorized source Git/file actions remain possible, so isolated worktrees, exact source commits and known mutating job dependencies remain mandatory.

Long-running mutating subprocesses are part of the active work context. A worker cannot safely yield and requeue a source-writing item while an untracked mutating job may still change that source. It must finish/cancel the job or park the item on a durable job dependency until termination is verified. Read-only jobs and independent artifacts may be treated separately with explicit evidence. A completed background job does not on its own end the agent activation.

**Source-writing continuation contract.** Every source-writing activation uses an isolated workspace derived from a pinned base/source commit and records the expected source repository identity. Required WIP refs must remain independently reachable and protected from garbage collection/deletion until no unfinished source-writing stage or canonical checkpoint depends on their pinned commit; retention cleanup requires verified reachability/closed-work evidence. Before normal yield, it commits all needed tracked and untracked changes (or records deliberately excluded/reproducible artifacts), publishes the WIP state to a generation-scoped, non-review remote ref such as `refs/heads/jarvis-wip/<work-id>/<activation-id>`, then independently verifies the exact Git commit SHA is reachable at that ref on the configured remote. WIP snapshots are marked unfinished, not reviewed or integration-eligible. The final checkpoint records the repository identity, base, exact commit, generation-scoped ref, and unresolved tests/issues. An item with dirty uncommitted state, missing remote proof, or a still-mutating job cannot be made Available on normal yield; it stays claimed pending resolution or is blocked with a durable dependency and a safe handoff fence. Read-only/document-only work can instead checkpoint without a source snapshot.

Subsequent activations create/fetch their own isolated workspace from the checkpoint's immutable source commit, not the predecessor's path or a mutable branch tip. Past WIP refs and immutable commits remain available for recovery until retention policy permits cleanup. A late previous activation may still edit local files or call account-authorized Git tools; the claim generation only fences Jarvis work-state mutations, not filesystem permissions. Per-activation refs prevent a late push from changing the *pinned continuation commit*, and operational instructions/worktree isolation prevent routine concurrent edits. Source pushes precede ledger yield: if the push succeeds and ledger CAS fails, the old claim remains current and the extra WIP ref is recoverable; if the ledger yield succeeds, the exact recorded SHA is already verifiably reachable.

## 10. Task → review → integration workflow

1. A task is created. Lead claims a planning item, records priority and implementation readiness, and publishes implementation work without selecting a worker ID.
2. Manager sees eligible implementation work and starts role sessions up to capacity. Each worker atomically claims one task-stage item and reads its last checkpoint; different turns may be served by different workers.
3. Yield releases unfinished implementation work. A frozen review request completes that implementation stage and publishes a review item, while the task itself remains open or in progress.
4. A reviewer claims the review item, inspects the exact immutable frozen ref/SHA and documents findings. Review claims are still exclusive and review decisions remain canonical. The review stage's checkpoint survives reviewer session changes. Writing a verdict does **not** release the review item claim or complete the reviewer's activation/launch. After the verdict the reviewer must terminally CompleteWork; verdict and terminal lifecycle are independently idempotent, and the integration producer must not be run twice.
5. ChangesRequested joins or creates the one current source-lineage correction stage linked to the exact review findings and previous source context. Multiple independent reviews of the same current revision add findings to that one stage, not multiple concurrently claimable source writers. Feedback for an older superseded source remains auditable and requires Lead triage before modifying current source. Accepted produces an integration item only when task policy and reviewed frozen SHA/target provenance require it. Neither event silently alters task ownership or closes the task.
6. Integrator claims the integration item, submits the existing canonical integration record, checks review acceptance and source/target identities, merges the **exact** accepted commit when conflict-free, runs required validation, pushes and verifies remote ancestry, and records CompleteIntegration idempotently.
7. A merge conflict or required source edit cannot be silently incorporated as unreviewed code. Publish an explicit correction item and require a fresh frozen review for modified source. An uncertain push/integration outcome must first be reconciled against Git and the canonical integration receipt before any retry.
8. Task closure is explicit after the required final workflow evidence; it is not inferred from a work-item completion or review decision.

Non-source tasks can define a shorter workflow; an accepted review need not imply an integration item if the task explicitly has no integration target.

### Canonical review claims and queue projections

The existing independent review record is the sole authority for frozen source SHA/ref, review claim, decision, and version. A review work item is a projection for dispatch/checkpoint; it must never keep a second independently writable reviewer owner. The queue claim and canonical review claim are one Git-ledger CAS. Legacy direct claim/release/withdraw/decide APIs must either participate in that same atomic transition or be disabled by protocol handshake at cutover.

| Canonical event | Work-stage effect |
| --- | --- |
| ClaimNextWork(review) | Atomically set canonical review Unclaimed to Claimed and work item Available to Claimed; bind one activation and immutable frozen SHA/ref |
| Review checkpoint | Keep both claims, do not infer verdict or source integration |
| Release before verdict | Atomically release canonical review and terminalize activation/launch, requeue the same work item once |
| Withdraw before verdict | Canonical review Withdrawn, work item Cancelled and activation fenced with explicit terminal/recovery evidence |
| Decide Accepted or ChangesRequested | Persist canonical verdict and idempotent downstream policy producer, mark still-claimed work verdict-recorded/terminal-pending; do not free reviewer capacity |
| CompleteWork after verdict | Write final checkpoint and terminate stage/launch; cannot decide again |
| YieldWork or BlockWork after verdict | Reject and never reopen/requeue decided review; require CompleteWork or audited recovery |
| Crash after verdict | Preserve verdict and unresolved claim until verified terminal evidence or audited recovery; no second decision or duplicate integration item |

Direct-claim/queue-claim and release/decide races use the canonical review version and one CAS ordering; losers reread. Ad-hoc or non-source reviews do not create integration work without explicit policy and provenance. Integration always pins the exact accepted review ID, reviewed source SHA and target, never mutable branch HEAD.

### Source-writing lineage serialization

Frozen reviews may proceed concurrently, but one mutable implementation lineage has only one actionable source-writing stage and one current writer. Publication and ClaimNextWork revalidate task stage generation, pinned base, lineage writer key and current source continuation. Concurrent Lead readiness and two ChangesRequested verdicts converge on one correction work item with references to both reviews; they do not create two simultaneous correction writers. Older feedback remains as evidence but cannot overwrite a newer stage tip. Lead chooses whether to incorporate stale findings or explicitly establish a new stage.

Parallel implementation branches require distinct explicit lineage IDs, pinned source baselines and a reconciliation/integration plan. Cancellation and supersession preserve all historic review findings. Any stale claim/checkpoint/completion for an obsolete stage generation fails CAS rather than replacing the current source.

## 11. Challenges, blocks and resumability

Existing durable challenge conditions become dependencies of work items rather than dependencies requiring one named worker to keep an attempt in its attention slot. **Work conversations** are addressed to the task, not a Worker N inbox. The pre-existing **one-shot response alerts remain addressed to agents**, now by the exact registered UUID of the ephemeral execution; a STOP alert for a Stalled session is not a task question or challenge. This preserves the already-implemented response-alert mechanism without inventing a new messaging channel. The challenge's issuer, conditions, evidence and satisfied/blocked/cancelled states remain canonical.

A blocked work item keeps its latest checkpoint and source context. Challenge completion reconciles dependency indexes and requeues the same item once when all required conditions are satisfied. If an item has several dependencies, satisfying one does not wake it prematurely. No notification, browser session or synthetic worker assignment is required for wakeup.

**Block/satisfaction race:** BlockWork checks authoritative condition versions and results in the same Git CAS that writes its dependency indexes and transitions the work stage. Already fully satisfied dependencies cannot produce a permanent blocked wait; use an explicit manual block, stay claimed, or complete/yield when safe. If BlockWork commits first, the later challenge-satisfaction transaction wakes the item; if satisfaction commits first, BlockWork's expected versions fail and it retries against current satisfied state. Per-domain source/index high-water marks allow a reconciler to repair missed derived wakeups after crash/restart, without requeuing twice. Multiple dependencies still require all-satisfied.

### Task-addressed two-way operator communication

A task (or canonical non-task work subject such as a standalone frozen review) owns its complete durable conversation. A worker asking a question writes an append-only operator-visible **Question** event referencing the task and, when relevant, its current work item, activation and source/checkpoint revision. The message is not sent to a persistent worker ID. The operator replies **to that task/question**, even if the original session is gone and a different worker later claims it. The next activation receives a bounded conversation history plus an exact cursor over newer messages; no previous ChatGPT conversation or private agent inbox is required.

Messages distinguish **Note**, **Question**, **Response**, and **Decision**; each has an immutable event ID, source subject, originating operator/account or execution label, timestamp, optional reply-to ID, and body. Routine checkpoints and tool telemetry remain in their structured audit streams, not in the human conversation; only meaningful human-directed exchanges appear as messages. An operator may post a message while no worker is active. Informational messages do not alter task specs or claim state. A Decision that changes scope/priority/readiness requires the normal explicit task/Lead mutation, not an implicit chat-to-spec rewrite. Store message bodies once on the Git-backed work-subject event stream; operator-attention lists and inbox unread counts are derived indexed projections with coverage proofs. Optional push/UI notifications are only hints and cannot become workflow authority.

A Question is **blocking only when the worker explicitly links it to a durable operator-response challenge condition** and BlockWork commits the checkpoint/dependency. Nonblocking questions can coexist with ongoing work. A response addressed to the question is committed with the matching challenge condition satisfaction, checked against its version/issuer/subject, so all required dependencies can wake the same blocked item exactly once. A response is not an authorization for unrelated actions, a review acceptance, or a silent task closure. If no execution is active, the response remains visible and the next eligible worker retrieves it. Replies are not routed to a historical agent label.

Project-wide questions without a natural task can use a durable planning/decision work subject and appear in the same operator worklist; do not create a permanent 'Lead inbox' as an alternate channel. The existing durable challenge API remains the source of truth for condition state and operator consent; the subject conversation provides the readable question/answer context without duplicating decision semantics.

The operator's primary view is **Needs my response**, grouping outstanding questions by project/task title, context, urgency and dependency effect. After replying, the task either remains actionable or is requeued by its canonical dependency transition. There is no need to find the numbered worker that asked.

Subject-specific review, integration, task and challenge APIs remain canonical. Queue operations either call those existing domain mutations or coordinate with them transactionally; they do not invent alternative verdicts, approvals or merge authority.

**Existing alert APIs, not new proposed APIs:** `queue_response_alert(project, agentUUID, STOP..., stableOperationId)`, `get_response_alerts(project, agentUUID)` and `clear_response_alert(project, agentUUID, alertId)` continue addressing the exact registered agent; the dispatcher preserves current at-most-once delivery behavior, STOP-first instruction ordering and notification-block independence. `MarkExecutionStalled` durably records a stop-request event and schedules the existing alert enqueue by deterministic operation ID. A successful alert response is not a termination acknowledgment or release receipt. Routine task updates never go through these agent alerts.

Bootstrap must receive its **generated immutable agent UUID**, assigned role, pinned role instructions/subscriptions version, project and launch ID, never an assumed task owner ID. The launch is registered before any response-alert delivery; every future agent-facing tool call uses that same UUID for exact alert routing and history. The claim response supplies complete durable continuation context, including conversation cursor and outstanding operator answers/questions. A fresh bootstrap/resumed task creates a fresh UUID. The client may automatically render concurrent executions as `Worker 1`, `Worker 2` etc., but numbers are not canonical identifiers, alert targets or capacity slots.

## 13. UI, audit and diagnostics

The primary TUI **Agents / Work** view is **task-title first, not Worker N first**, and retains the previously agreed prioritized queue. Its default layout is two adjacent sections (or filterable panes in a narrow terminal):

1. **Active & Stalled** — Every currently Claimed work stage, grouped by canonical task/subject title. Row shows the task title as primary text, current stage (Implementation/Review/Integration/Planning), role and optional client-generated execution label, `Working` or `Stalled / STOP requested`, last-seen age, checkpoint age and priority. The exact agent UUID and STOP-alert enqueue/at-most-once delivery evidence appear in execution details, not as the primary row title. Put Stalled rows above other Active rows when they require Manager/automatic recovery attention; a task with multiple concurrently valid stages is grouped once with stage subrows, not incorrectly collapsed into one exclusive task owner. Submitted/unclaimed launches are shown separately as `Starting`/Uncertain capacity, never as a fabricated task claim.
2. **Next in queue** — Top configurable number of verified Available work stages in deterministic priority order, with title, stage, priority and age. These are **Queued**, not Active. Do not hide the prioritized queue merely because no agent currently claims its items.

A separate **Blocked / Needs operator** filter shows task-based outstanding questions, durable dependencies and RecoveryBlocked entries, without mixing them into runnable queue depth. Completed/cancelled history is accessible by search or an All filter but does not dominate the live view. The header shows global logical capacity `reserved+active+uncertain / maxConcurrentAgents`, the number of Stalled and RecoveryBlocked executions, and queue/index coverage health.

**Derived task presentation, not an extra canonical lifecycle.** Work-item state `Claimed` with a valid running lease projects as `Active` at the task level; a Claimed item with an expired lease projects as `Stalled` until a project recovery CAS. An item made Available by successful recovery projects as `Queued`, with a durable `Recovered from Stall` audit event and a new claim only when another execution wins it. `Blocked` remains a work/dependency state. Task lifecycle Open/InProgress/Closed and work-stage Claim/Available/Completed remain canonical, never dual-written with an independent `Task.Active` flag. Selecting the task opens its complete durable conversation, work-stage history, launch attribution and exact source/checkpoints. Replying to the task requires no historical Worker ID; numbered role display labels remain presentation only.

Each work history includes item creation, exact subject/event provenance, claim and generation, generated agent UUID/role binding, activation start, server-witnessed last-seen/heartbeat receipts, transition to Stalled, the UUID-addressed STOP alert request and any known delivery state, cooperative shutdown or lease-recovery receipt, requeue generation, checkpoints, yield, block/wake, stage completion and exact source snapshot/integration evidence. Durations are wall-clock observations, not productive CPU time. Once the Stalled/STOP-requested transition commits, a new heartbeat alone cannot resume that execution; the task only returns to Queued after explicit cooperative terminalization or safe recovery CAS, and a later Active execution has a **different UUID**.

Do not migrate old Waiting/Parked state totals into new agent counts. Report pending work and active executions separately. No claim that an agent is Waiting is meaningful merely because it subscribes to a queue. Preserve old agent-name-addressed notification and response-alert history, but **future response alerts still target agents**, now by per-execution UUID. Legacy agent-label queues must not be silently redirected to a different session that reuses a `Worker N` display label. During migration, link resolvable task-specific outstanding *conversation questions* to their canonical subject without rewriting their original event; ambiguous/project-wide messages become explicit planning/triage attention, never silently dropped or guessed at.

## 14. One-time migration and compatibility

This replaces the current orthogonal assignment model and must have a separately reviewed, explicitly operator-authorized cutover. Do not dual-write old assignments and new work claims indefinitely.

**Account-scoped migration epoch and visibility gate.** Migration over multiple project ledgers and the account-global capacity ledger is **staged, never claimed as an atomic multi-repository commit**. The account admission ledger records one immutable epoch ID, a frozen membership set of participating projects, expected source/protocol versions and verified ledger heads, and a CAS-controlled state sequence `LegacyActive -> Frozen -> Preparing -> Validated -> Activated` (or `Aborted` before activation). The epoch also pins a per-project `Prepared(epoch, baseHead, newIndexCoverage, conversionReceipt)` record and an account-capacity schema preparation receipt. The old schema remains the authoritative **read-only** view in Frozen/Preparing/Validated; new queue availability, new role dispatch and new-format mutations must not become externally visible merely because one project's prepared commit exists. Any client that sees incompatible/unverified or partially replicated epoch records reports `MigrationInProgress/RecoveryNeeded`, not a healthy empty queue.

**Writer and reader gates.** Before the first prepared mutation, centrally enforce a minimum protocol/schema handshake that rejects all old clients' incompatible writes and new queue launch submissions, freeze project registration/membership for the epoch, and reconcile pending old intents with exact receipts. Project conversion writes only inert staged records and proof markers; noncanonical local files are not substitutes. Validate *every* project's injective conversion/coverage, preserved source/ref/challenge history and the account-capacity schema under verified heads before moving the account epoch to Validated. After explicit operator authorization, one account-ledger CAS moves the epoch to Activated; new readers/writers are permitted only when both **verified account Activated(epoch)** and the matching **project Prepared(epoch)** and compatible protocol handshake are present. Old clients remain fenced. A delayed project reader or incomplete proof must fail closed even if the account epoch is Activated.

**Abort and crash recovery.** A crash after preparing Project A but before Project B leaves the global epoch nonactive: new dispatch is suppressed everywhere, and readers see only old-schema authoritative history (or migration diagnostics). Recover by exact operation-ID and Git-head reconciliation to finish the same epoch or explicitly Aborted it before activation. Aborting leaves inert prepared Git evidence in history; it never force-rewrites a ref, discards a pending operation or fabricates an old-world success. Only after every participant is verified safely restored to a legacy-compatible mode can its writer gate reopen. Once Activated, no implicit rollback rewrites committed new-format work: corrections must use a new audited forward epoch/migration.

1. Inventory verified heads of **every project work ledger and the shared account-global capacity ledger**, all active tasks/attempts, review requests and verdicts, integration submissions, challenge waits, agent checkpoints, working sessions, **existing legacy agent-keyed response alert queues and pending STOP instructions**, **all connected devices' pending-operation journals**, outstanding browser schedules/launches and Manager launch journal. Snapshot and verify rollback sources. Preserve existing attempt source bindings (repository, baseOid, targetRef, sourceRef) and verify every old logical stage maps injectively to one new work item.
2. Drain or explicitly resolve live Working assignments, **claimed independent reviews**, in-flight integrations, source-mutating background jobs, outstanding launch demand reservations, pending write intents/unknown outcomes across devices, and uncertain Manager/browser launches before cutover. Claims, jobs and reviews need verified terminal/release evidence; a reviewer verdict alone is not execution termination. If any execution, local worktree mutation, or dispatch remains active/ambiguous, refuse activation rather than inventing completion. Park the Manager schedule and fence old-protocol writes during conversion.
3. Convert each actionable queued/started task stage into one deterministic implementation item. Preserve original spec, attempt generation, frozen source and checkpoint history. Verify that every unfinished source-writing stage has a reachable, immutable continuation SHA or an explicit blocked manual recovery condition; a dirty local worktree is not a recoverable checkpoint. Old ownerAgentId/agent assignment records remain readable as historical attribution only.
4. Convert **unclaimed** reviews into review work items without rewriting frozen review refs or recorded verdicts. A claimed review must first have a verified verdict/release/explicit audited recovery before conversion; never manufacture an unowned review claim while an old reviewer may still be running. Convert accepted-but-not-integrated reviews into integration items only after verifying canonical acceptance, exact frozen source SHA and absence of a completed integration record.
5. Preserve deferred/blocked work as blocked items with equivalent durable dependencies and reverse indexes. Do not drop pending operator/challenge evidence. A formerly Parked or NeedsWork agent with no underlying work must not manufacture a queue item.
6. Materialize complete queue/attention indexes with per-producer and per-shard high-water coverage marks in each participant's inert Prepared(epoch) record at its verified source head. Account epoch validation checks the full fixed project membership set and account-capacity preparation; missing/partial/lagging coverage must never present as zero work and prevents Activated.
7. Perform disposable two-client and **two-project plus account-ledger** conversion tests, restart tests, and one controlled local shadow planning run. Include claimed reviewers, pending integration/ledger-write intents, dirty worktrees, mutating jobs, partial conversion crashes, incompatible old writers and uncertain launches as explicit refuse-to-cutover fixtures. Deploy matching client/server schema versions with a verified handshake that fences old writers **before** the first epoch preparation. A failure in Preparing/Validated keeps the old schema authoritative and all new queues invisible; idempotent replay or pre-activation abort, never overwrite immutable history.
8. Verify the global cap and all project Prepared(epoch) proofs, exact frozen SHA/integration/challenge/checkpoint histories, complete queue/attention coverage, scheduler skip-at-cap, Manager terminal/handoff and crash reconciliation before *operator-authorized* account Activated(epoch) CAS. Every queue reader/Manager bootstrap rechecks the matching account/project epoch; partial activation or stale client fails closed. After activation, rollback must never erase work committed under the new schema.

Existing live rollout of the current Manager/scheduler is a separate undertaking. Do not combine this migration with an unreviewed production upgrade or enable unattended scheduling as a side effect of creating this spec.

## 15. Incremental implementation plan

**Phase A — Frozen contracts and simulations.** Review this specification; define exact records/transitions, source-to-queue adapters, operation names and the cutover ledger schema. Build a pure deterministic queue/claim/activation planner against disposable Git fixtures. No production mutation.

**Phase B — Canonical work ledger.** Implement queue items, idempotent publication, claim CAS, checkpoint, yield, completion, block/wake, per-session agent UUID association, server-witnessed lease/heartbeat receipts, first-class Stalled/StopRequested/Reclaimed execution states and recovery history. Add bounded indexes and coverage markers with multi-client consistency tests. Lease expiry must never release a claim without its exact project CAS terminal/recovery event.

**Phase C — Producers and role subscriptions.** Adapt task intake/Lead prioritization, review submissions/verdicts, challenge dependencies and integration readiness to publish deterministic work items. Store subscriptions by role without new agent-level permissions.

**Phase D — Manager and ephemeral bootstrap.** Replace persistent Ready-worker/NeedsWork-reviewer selection with queue availability, per-launch generated UUIDs and explicit role-assigned launches, existing agent-addressed STOP response alerts, and **one global account-capacity semaphore** shared across projects. Add scheduler admission preflight that skips Manager when globally full, role-instance auto numbering in the client, idempotent two-ledger admission/reconciliation and terminal Manager-slot handoff. Provide Manager/non-agent reconciler with configurable stalledAfter/reclaimAfter and an idempotent lease-expiry recovery path, including capability to recover capacity when no model slot is available. Reuse one-shot browser launch journal, uncertain-outcome handling, confirmed tab close, and exact activation terminal evidence. Implement no-work exits.

**Phase E — Domain cutover.** Decouple implementation attempt ownership from worker labels; preserve historical alert recipients while routing new per-session STOP alerts to registered agent UUIDs; keep immutable review/ref/integration behavior and migrate historical checkpoints and work records. Adapt TUI to task-title-first Active & Stalled plus prioritized Next queue, blocked/operator filter, and derived task Active status without adding a second lifecycle state. Run two-client/restart/performance validation.

**Phase F — Release and controlled activation.** Independent frozen reviews and exact integrations at each boundary. Stage client/server binaries and data conversion with rollback. Obtain operator release authorization; run an isolated end-to-end workflow with mixed roles (Manager, Lead, Worker, Reviewer and Integrator) sharing one configured global maximum, including cross-project saturation and last-slot handoff. Only then retire legacy state-writing APIs.

Do not start Phase F until independent reviews of the current Manager duplicate-launch correction and pending rollout constraints have been resolved.

## 17. Explicit non-goals

- No agent-ID-based permissions, role ACL, identity binding or contribution account security system. Contributor permissions are a separate future **account-level** feature.
- No generic workflow scripting engine, arbitrary event bus, automated source merges, automatic review acceptance, or forced identical pipeline for every task.
- No assumption that ChatGPT tab closure, elapsed time, or a new opaque session ID proves prior execution termination.
- No replacement for protected Git refs, immutable frozen reviews, ordinary test evidence, or operator-controlled deployment.
- No immediate migration or automatic Manager activation as part of writing this document.

## 18. Design choices intentionally settled

- Work claims are **per activation**, not per persistent worker ID; a task's displayed Active/Stalled status is derived from its currently claimed work stages, not an additional independently persisted Task lifecycle.
- Work checkpoints survive arbitrary session/agent changes, including verified remotely retrievable source snapshots for source-writing work.
- Manager dispatches role-assigned sessions from **unreserved queue demand**, not an idle-agent roster; failed global-first admission uses a project abort-only terminal tombstone for safe token release, and canonical CAS credits maintain an injective compatible matching across outstanding launches. Worker claims the highest-priority feasible item only when the same project CAS can atomically rematch every other affected live credit, or fails closed. Concurrent Managers cannot reserve duplicate demand.
- A single `maxConcurrentAgents` account-global semaphore covers every role and project, **including Manager and Lead**; there are no per-role quotas or numbered-agent capacity slots. Scheduler skips spawning Manager when full. Normal taskless Manager/no-work launches terminalize via verified project receipt then release their account token. Last-slot handoff uses project-fence-before-account-swap, never fictitious cross-ledger atomicity. Limit reductions below occupied tokens are rejected by account CAS.
- Every new execution/session is assigned one immutable generated agent UUID, registered with its launch and role. The existing agent-addressed response alerts use that UUID as their exact destination; role numbers are presentation-only and may be reused, while UUIDs are never reused or treated as permissions.
- Review and integration are regular queue subjects with existing canonical evidence, not special lifetime tasks.
