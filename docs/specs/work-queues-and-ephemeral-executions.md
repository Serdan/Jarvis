# Work queues and ephemeral agent executions

**Status:** Proposed architecture specification; design reference, not implemented or deployed. This branch is a Lead correction draft, not the frozen original under independent review.
**Revision basis:** `e737c2da901ae4073f7ecc066781f428020ffdd1` (frozen review `d4fbb56e2d4c451eab1ef23c281dc647`).
**Date:** 2026-11-15
**Scope:** Jarvis per-project coordination, Git-backed work ledger, deterministic Scheduler/reconciler, role launches, blocking-first FIFO, dependency cycle diagnostics, resumable execution, reviews, integration, Task/Role conversations and migration.
**Authority:** This document proposes a future replacement for the persistent agent-assignment portions of docs/specs/orthogonal-agent-state.md and the current Manager/reviewer launch convention. Existing APIs and live ledger semantics remain authoritative until a separately reviewed, operator-approved cutover.

## 1. Decision

Jarvis runs **durable work queues, deterministic non-agent scheduling and ephemeral role executions**, with operator conversations addressed to durable Task or Role subjects. There is **no Manager model agent** in the target architecture. The old Manager role, Manager heartbeat and Manager-to-child last-slot handoff are retired after the audited migration; their historical ledger evidence remains readable. This document supersedes the Manager-centric contract accepted at source `35e7465a122fd9d767a9f75494b241ff2eb7fe72` without changing that frozen source or its review.

**Autonomous loop:** Lead creates/specifies work and records hard dependencies; canonical producers mark stages Available; the server-side Scheduler chooses ready demand by two priority tiers (**blocks another unfinished stage first**, then **FIFO** within each tier), checks compatible role subscriptions and one account-global concurrency limit, reserves/dispatches one role-assigned launch per eligible uncovered demand, and the connected execution atomically claims the highest-ranked feasible work. The non-agent reconciler repairs uncertain launches and stale leases. Lead never needs to assign Worker N or manually score routine work.

- A work item is an actionable task, review, integration, operator message or planning/challenge stage. **Blocked work is not runnable** even when it is itself a prerequisite of other stages.
- Only **hard unsatisfied prerequisites** determine whether a runnable item is in the blocking tier. Normal work is FIFO; no weights, numerical priority ranks, role quotas, aging, arbitrary scoring, or permanently preferred workers.
- Dependency cycles are diagnosed at the **work-stage generation** level by strongly connected components, displayed to Lead/operator without rejecting the edit; warnings never make a blocked item runnable.
- New role launches have a stable `launchId` **before browser dispatch**, but **no agent UUID yet**. On first actual Jarvis connection `InitializeAgent(launchId, sessionKey, operationId)` atomically registers exactly one fresh UUID and returns the pinned project, role, instructions, subscriptions and claim context. The minimal session bootstrap carries a launch token/reference, not a task ID or prefabricated agent UUID; a browser bridge may inject that context without prompt text.
- Each execution has at most one primary work claim. Task ID and full specification are returned by successful claim; yielding/terminating releases/requeues according to durable evidence, without persistent assignment.
- Operator conversations are addressed to `Task(project, taskId)` or `Role(project, roleId)`. The first eligible task/role execution to win the canonical handler CAS takes responsibility; the thread persists across sessions. Existing STOP response alerts continue addressing the registered agent UUID, not the role.
- The account-global `maxConcurrentAgents` counts reserved, registered, active and uncertain **logical launches**, across projects and devices. Scheduler/reconciler consume no model slot. All sessions share the owner's existing tool/account permissions; role and UUID are coordination handles, not security principals.

| Role | Responsibility |
| --- | --- |
| Lead | Planning, requirements, hard dependencies, operator decisions and project-level coordination; can be launched from planning demand or messages to Role(Lead) |
| Worker | Claim the earliest feasible runnable implementation stage under blocking-first FIFO; implement, checkpoint, yield, block or complete |
| Reviewer | Claim frozen independent review stages and publish exact-source findings/verdicts |
| Integrator | Claim integration stages pinned to independently accepted source, validate and record exact integration evidence |
| Other configured roles | Claim compatible queue demand according to the same scheduling and lifecycle contract |

The **Scheduler and reconciler are deterministic Jarvis services**, not roles in this list. Reviews, integrations and role-message handling need no synthetic long-lived assignment. No runtime cutover, unattended launches, deployment or restart is authorized merely by updating this specification.

## 2. Explicitly retained boundaries

1. Each project's canonical Git orphan ledger remains the sole authority for its tasks, stages, reviews, dependencies, role/task conversations, demand credits, claim and immutable terminal proofs. An account-scoped Git admission ledger exclusively owns the **global** token pool, configuration/version and migration epoch. No extra mutable task database or general-purpose message bus.
2. Git source refs, protected main, immutable frozen review refs, integration evidence and remotely reachable WIP continuations remain distinct from orchestration state. An individual ChatGPT conversation is never the work record.
3. Existing authenticated **account** permissions remain unchanged. Agent UUIDs, role subscriptions, launch IDs and claim generations are protocol coordination/audit handles, not role ACLs or security identities. Future contributor permissions belong to authenticated accounts.
4. Completion is not review acceptance; acceptance is not integration; integration is not task closure. Each remains an explicit versioned domain transition.
5. There are **no persistent Worker, Reviewer, Integrator, Lead or Manager assignments** in the new flow. Old assignments and Manager launch evidence are retained for audit, not translated into new-live Manager demand. Display-only `Worker 1`/etc. labels may be reused; never target alerts or tasks by those labels.
6. Browser submit is one-shot with immutable launch ID and side-effect journal. A confirmed bootstrap tab may be closed; tab closure is not proof that a provider execution terminated. Unknown submit outcome is reconciled, not blindly retried.
7. A new execution registers an agent UUID only when connecting to Jarvis, not when capacity is reserved or browser submit starts. Unregistered launches have separate pending-registration and recovery paths; they are not fabricated Working agents.
8. Document revision, frozen review and staging do **not** authorize production migration, schedule activation, release, deployment, restart, or bypass of existing in-flight Manager/rollout work. Operator authorization remains a separate gate.

## 3. Vocabulary and durable objects

**Task** — Durable canonical specification, lifecycle and dependency owner; it may produce several stages/reviews and outlive arbitrary model sessions. Messages addressed to a Blocked/Closed/Cancelled/no-actor Task persist as passive attention, not a cause to reopen or launch a session.

**Work item** — One actionable stage/event with immutable subject, queue, stage generation, eligibility and current exclusive claim. `Available`, `Claimed`, `Blocked`, `Completed`, `Cancelled` remain canonical; an already Claimed item may carry a fenced `DependencyGatePending` substate when a new hard prerequisite is introduced. Active/Stalled are derived display projections. A Task-addressed operator message instead creates **passive attention only** until an eligible actor is already working on that Task, not standalone Scheduler demand or a new runnable work item.

**Queue** — Project ledger index of eligible work items: planning, implementation, review, integration, challenge triage, Task/Role operator-message attention and configured variants. Not an authorization boundary.

**Role** — Persistent versioned instructions and queue subscriptions. There may be zero, one or many concurrent instances. Role-addressed conversation is stable across all of them. Unlike Role-message work, Task-addressed message attention without a current eligible task actor remains passive, not a new Scheduler demand source.

**Launch ID** — Stable, unique pre-dispatch ID for one reserved role execution, project, role configuration version, demand credit, account-global token and journaled one-shot browser intent. A launch begins **without** an agent UUID. Its registration state is `Unregistered | Registered(agentUUID, sessionKey) | Terminal` and is CAS fenced. One launch may successfully bind one provider-session registration only.

**Session key** — An opaque high-entropy registration key generated **exactly once per actual provider execution** by its browser bridge/session bootstrap (or the connecting client at that session's first tool connection), persisted/recovered in that same execution context for retries, and **never generated per launch, copied into the common launch prompt, or reused for a distinct provider execution**. It is a cooperative replay/duplicate-registration handle, not authentication or permission. If the bridge cannot verify that a resumed tab/route is the *same* provider execution, it must not reuse an earlier session's key; a new key may fail `AlreadyRegistered` and be diagnosed as uncertain instead of sharing one UUID/lease. A retry from the same verified execution recovers the original key and initialization operation ID and returns the same UUID. A distinct execution must generate a different key; the server rejects different-key registration against a claimed launch. Without provider-backed attestation the server cannot distinguish **deliberately copied** keys: enforce no copying through the bridge/bootstrap contract and report this cooperative limitation, without inventing an agent-level security boundary. Never manufacture a new launch after an uncertain browser submit.

**Agent UUID** — Server-generated UUID assigned **on successful first `InitializeAgent` connection**, bound one-to-one to the launch ID plus session key. It is immutable per model execution, is the recipient for existing agent-specific response alerts and server-witnessed lease history, and is never reused for a successor session. An unregistered launch has no UUID and cannot receive an agent-UUID STOP alert; it can be cancelled/fenced by launch ID.

**Activation** — A successful single primary work claim by a registered launch; has activation ID, claim generation and immutable checkpoints. At most one primary activation per launch. A dedicated Role-message primary activation owns **one deterministic message work item for one message ID** and terminates through the same atomic work/launch-completion contract as implementation/review work, with a message acknowledgement in that CAS. A role-message handler lease may additionally attach to an already active session without taking a second primary work item, subject to compatible credit matching.

**Claim** — Exclusive work-item reservation/handling responsibility protected by project Git CAS and version/generation. Message responsibility is either the **primary message work claim** or an **ancillary handler lease**, never a second primary claim. Not an agent permission.

**Checkpoint** — Immutable durable summary, next action, dependencies, evidence and when source-mutating an independently reachable exact source SHA/ref.

**Hard dependency** — An unsatisfied explicit stage-generation prerequisite that prevents a dependent work item from being runnable. Derived blocker priority and circular-dependency diagnostics use these hard edges only. Informational and alternative/non-blocking relations do not create edges.

**Available sequence** — Server-witnessed `availableAtUtc`, per-project monotonic `availableSequence` and stable work ID captured on each transition to Available, including yield/requeue. This defines FIFO; stages freshly requeued go to the back of their tier. Source/event identity is distinct and remains idempotent.

**Global capacity token** — Account-scoped logical launch reservation, not an agent UUID. Scheduler and reconciler consume no slots. Reserving, resizing, releasing and handling uncertain states serialize on one account Git CAS authority.

**Work conversation** — Append-only Task/Role or other canonical subject thread, with operator/agent messages and message-handler leases independent of any execution identity. Reading never consumes; one handler CAS owns action and reply acknowledgment.

**Execution states** — `ReservedUnregistered`, `SubmittedUnregistered`, `Registered/Working`, `Stalled/StopRequested`, `TerminalPendingRelease`, `RecoveryNeeded/RecoveryBlocked`, `Terminated`; a live claim with new hard prerequisites has fenced `DependencyGatePending` until safe terminalization. No permanent Waiting/Parked/NeedsWork roster. Unregistered Pending starts are shown as Starting/Uncertain, never as live agents. Blocked belongs to work/dependency state.

**Scheduler** — Non-model service for verified readiness, two-tier FIFO selection, matching compatible role demand against in-flight credits, global capacity admission and one-shot launch dispatch. **Reconciler** — Non-model service for original operation/side-effect receipts, stale/unregistered launches, lease recovery, index repair and token release. Neither makes planning/review judgments.

A launch may bind one agent UUID, create at most one primary activation and hold ancillary role-message handler leases. The agent UUID is the exact recipient for existing registered-session STOP response alerts. A terminated/failed pre-registration launch has no recipient UUID; do not forge historical agent IDs for unstarted sessions.

**Two-ledger authority.** The project Git orphan ledger owns tasks, reviews, task/role messages, hard dependency graph, derived circular warnings, demand matching, launch registration and terminal receipts. The account Git ledger owns global tokens, global capacity configuration and migration epoch; it never owns duplicate task, review, dependency or message authority. Global reservation precedes project demand CAS; an unbound failure requires the C01 abort-only project tombstone before global release. Ambiguous Git pushes/reads retain the token until the same operation receipt or a fenced terminal proof is verified. The bridge's one-shot dispatch journal is external-effect evidence, not queue admission authority. No distributed atomic commit is claimed.

**Work identity:** deterministic project + queue + authoritative subject + event/stage generation; replay produces no duplicate item. `CompleteWork` may publish a newly generated follow-up stage but cannot mutate an already accepted frozen source.

**Source-writer lineage:** canonical key project + repository + task + target ref + explicitly selected lineage ID. Each mutable stage carries pinned base, current reachable continuation SHA/ref and generation. One source-writing stage per lineage may be actionable/claimed at once; parallel independent frozen review stages are permitted. `ClaimNextWork` validates work item and source-lineage generation under a single project CAS. Distinct lineages need explicit branching/merge policy.

**Historical records:** Old numbered-agent assignments, Manager launches, role alerts and provider sessions stay readable as audit. Only newly admitted role launches use the target `Unregistered -> Registered` semantics; migration does not relabel an old already-running execution as one with a generated-on-connect UUID.

## 5. Source-of-truth, work publication and dependency graph

- A runnable work item references canonical subject data and does not duplicate task specifications, role/task conversation contents, frozen source/ref, review verdict or integration evidence as another authority. Every actionable event that is eligible for model launch has one deterministic work identity; passive Task message attention is indexed separately and is not scheduler demand.
- Domain producers (task intake, Lead planning decision, review submission/verdict, integration readiness, role/task operator message, hard dependency satisfaction, challenge) publish or change work items in the **same project Git CAS** as their authoritative event; if not possible, a deterministic reconciler repairs missing projections after exact source/head verification, before exposing new demand.
- Queue/attention indexes track source producer high-water marks and shard coverage against the verified project head. A stale, absent, partial or unverified projection is `Incomplete`, not a healthy empty queue. Scheduler must not dispatch and ClaimNextWork must not return ordinary NoWork from such an index.
- Hard stage-generation prerequisites are canonical dependency edges, with explicit dependency kind and satisfaction state. For a **currently Claimed** target, adding a new unsatisfied hard prerequisite atomically sets `DependencyGatePending` on that claim and fences its completion until the claimant safely checkpoints and terminates as Blocked/Available; editing a Completed generation fails and requires explicit successor work (§7). **Task workflow producers must create hard dependency edges for genuinely gating task/review/integration stages** (for example, a required frozen review before implementation correction or integration, or an accepted integration before downstream dependent task work), not merely assume the Scheduler knows that reviews are important. `Available` requires all hard prerequisites satisfied. A dependency edit, review decision, cancellation or wake recomputes runnable/blocked projections atomically or fences them until verified reconciliation. Derived `blocksOtherUnfinishedStage` flags and SCC cycle warnings use the same verified graph revision; warnings do not add a new canonical Blocked state.
- A hard-edge cycle is diagnosed by SCC after graph edits and by bounded deterministic reconciliation against the latest verified graph; report exact nodes/edges to Lead/operator. It is an advisory **warning**, not a rejection or automatic edge deletion. Incomplete index/remote graph means unknown diagnosis, never silently clean. Work stages on unsatisfied cycles remain Blocked.
- In-memory counts/sort keys accelerate reads but never authorize claims. All role/priority/dependency/source/credit checks repeat against canonical latest project CAS. No broad event bus or generic scripting rule engine.

| Authoritative event | Resulting actionable queue item / projection |
| --- | --- |
| New requested task or undecided project issue | planning item for Lead |
| Lead records implementation readiness and hard prerequisites | one implementation stage when ready, otherwise Blocked |
| Frozen independent review requested | review item pinned to exact frozen SHA/ref, plus hard prerequisite edges to stages that truly await its verdict when task policy requires review |
| Review ChangesRequested | one current lineage-correction stage, retaining all applicable findings; stale verdicts go to Lead |
| Review Accepted and explicit integration policy applies | integration item pinned to accepted review ID/SHA/target; any downstream stage blocked on exact integration gains a hard edge to it |
| Challenge unsatisfied and requires action | challenge-triage or blocked dependency, according to domain rule |
| Challenge/dependency satisfied | original Blocked item wakes once and receives new FIFO availability |
| Operator posts message to Task(project, taskId) | durable Task conversation plus **passive pending attention** for the next eligible actor on that task; **no independently runnable launch demand**, task reopening, unblock, or reassignment |
| Operator posts actionable message to Role(project, roleId) | durable Role thread plus **one deterministic eligible role-message work generation per message ID**; Scheduler can launch a compatible role even with no active session |
| Hard dependency graph edited | update availability/blocker tier; recompute SCC warnings without rejecting edit |

Task completion without review, accepted review without integration, and non-code tasks are valid explicit policy variants. Lead controls workflow requirements/dependencies; routine relative scheduling order remains **blocking-first FIFO**, not manual priority rank.

## 6. Role subscriptions, blocking-first FIFO and cycle diagnostics

Each project defines role subscriptions, immutable versioned instructions and compatible queue IDs. Default: Lead=planning plus Role(Lead) messages, Worker=implementation, Reviewer=review, Integrator=integration; additional roles must be configured explicitly. Scheduler directly creates role-specific launches. No Manager role, special scheduler model turn or Worker-N assignment exists. Configuration changes affect future launches; current pinned role sessions retain their version.

**Exactly two runnable tiers:**
1. **Blocking others** — Available work whose completion is a hard unsatisfied prerequisite of at least one other unfinished canonical work stage, including frozen reviews or integrations holding dependent work. This relationship is derived from the verified dependency graph, not manually tagged priority.
2. **Ordinary** — Every other Available work item.

Within each tier, **FIFO** by immutable server-witnessed `availableAtUtc`, project ID, per-project `availableSequence`, then stable work ID. A newly Available item enters its tier at the back; requeued/yielded work receives a new availability record and position. A change in current hard-dependency edges may move an item between tiers **without changing its FIFO timestamp**. No priorityRank, weighting, role quotas, random shuffling, aging, manual bump, or cross-queue numeric priorities. If two projects have concurrent timestamps, project ID/sequence break ties deterministically; project-local FIFO is strict, cross-project order is best-effort according to the verified server timestamps, without a second cross-ledger global enqueue counter.

**Runnable means** item Available, dependencies satisfied, reviewed/source-lineage invariants satisfied, queue/source index coverage verified, and a compatible role present. A Claimed stage marked `DependencyGatePending` is neither runnable nor independently free capacity; it must be safely terminalized and its matching token reconciled before successor demand can be admitted. Being a prerequisite gives **selection preference**, not exemption from one's own unsatisfied dependencies. For a claim, select the oldest **feasible** item in the highest available tier for that role; feasibility additionally requires a complete compatible injective rematch for other already-admitted unclaimed launch credits. An older item must be skipped only for explicit incompatibility/dependency/matching reasons; record those reasons in diagnostics. One primary claim per launch, no automatic second item.

**Cycle diagnostics:** On hard dependency edits and reconciliation, examine the **stage-generation** dependency graph from a verified project-ledger snapshot. Compute strongly connected components (Tarjan or equivalent O(V+E)); any component of size >1 or a self-loop is a circular hard prerequisite. Publish a derived warning with exact work/stage IDs and witness dependency edges, source snapshot/high-water and Lead/operator attention, without rejecting the underlying edit or inventing a new Blocking state. Affected stages stay blocked by their actual unsatisfied prerequisites; cycles never make them runnable or higher-priority. Recompute/clear warnings when edges or generations change. Failed/incomplete graph coverage is `DependencyGraphIncomplete`, **not** proof of no cycle; cross-project edges require verifiable remote evidence or explicit unresolved diagnostics, not inferred acyclicity.

**Lead** plans tasks/dependencies and resolves circular warnings. The system handles routine ordering; Lead does not hand-rank ordinary items. The operator may change the actual dependency graph, not a hidden scheduling score. Subscription compatibility is protocol behavior, not access control.

## 7. Claim, registration, checkpoint and terminal state machines

**Work-item state** (one exclusive primary claim per item):

~~~text
Available --ClaimNextWork CAS--> Claimed
Claimed   --CheckpointWork-->  Claimed
Claimed   --new unsatisfied hard edge CAS--> Claimed(DependencyGatePending)
Claimed(DependencyGatePending) --safe dependency-gate resolution CAS--> Blocked | Available (new FIFO availability), launch terminal
Claimed   --YieldWork CAS-->   Available (new FIFO availability)
Claimed   --BlockWork CAS-->   Blocked
Blocked   --dependency satisfied--> Available (new FIFO availability)
Claimed   --CompleteWork CAS--> Completed (optional next stage)
Available/Blocked --CancelWork CAS--> Cancelled
~~~

A work-stage terminal outcome is not necessarily a terminal **task**, review verdict, integration or agent process.

**Launch state** (one account token, one launch ID, **no UUID before registration**):

~~~text
GlobalReservedNoProject --project admission CAS--> ReservedUnregistered
GlobalReservedNoProject --abort-only project tombstone CAS--> TerminalPendingRelease
ReservedUnregistered --one-shot browser intent/submit--> SubmittedUnregistered
ReservedUnregistered --verified pre-submit cancellation--> TerminalPendingRelease
SubmittedUnregistered --InitializeAgent CAS--> Registered(agentUUID, sessionKey)
Registered --ClaimNextWork CAS--> Running / Claimed
Registered(no claim) --TerminalizeLaunch(NoWork|Finished|Error)--> TerminalPendingRelease
Registered(claimed) --Yield|Complete|Block CAS--> TerminalPendingRelease
Registered/Stalled --RecoverStalledExecution CAS--> TerminalPendingRelease | RecoveryBlocked
SubmittedUnregistered --RecoverUnregisteredLaunch CAS--> TerminalPendingRelease | RecoveryNeeded
TerminalPendingRelease --verified account token release CAS--> Terminal
Any unresolved side effect or Git reply --> RecoveryNeeded (global token held)
~~~

**Global-first admission failure / abort tombstone (retained C01).** `ReserveGlobalAgentSlot` obtains an account token for a stable launch ID and role first; `ReserveProjectLaunchDemand` subsequently creates the project-local launch and compatible demand credit under project Git CAS. If the project demand CAS conclusively fails **before any project launch exists**, `AbortUnboundProjectAdmission(project, launchId, originalAdmissionOperationId, expectedProjectHead, operationId)` commits a minimal project abort-only launch tombstone bound to that same launch ID and operation ID. The original admission replay and abort race on the same project launch-ID absence/version condition. A lost/ambiguous reply is not proof of rejection: reconcile the exact original admission operation/head or retain the token until a serialized tombstone or normal launch terminal receipt can be verified. Only independently verified terminal proof permits account CAS release of that launch token. An unbound aborted launch never gains a UUID, role message handler or browser dispatch.

**Connect-time registration.** `InitializeAgent(launchId, sessionKey, operationId)` is the first successful model-session Jarvis operation. The bridge/client creates and retains a fresh high-entropy **per-actual-execution** session key, not a launch-global constant; retries must recover the same key and operation ID from that session context. Duplicate dispatches creating two provider executions get different keys and cannot share one registered UUID by normal protocol. An unverifiable resumed session must not claim the prior execution's key. A single **project Git CAS** validates an admitted, nonterminal, non-stalled launch, a legitimate original one-shot dispatch intent/receipt for that launch, pinned project/role configuration and no existing different session registration; then generates the first **server-side** agent UUID and records immutable `(launchId, agentUUID, sessionKey)` with generation and first server-witnessed lease. A retry with identical launch ID/session key and operation payload returns exactly the same UUID and bootstrap; a different session key encounters `AlreadyRegistered`, **not a second UUID or claim**. This is duplicate-execution coordination, not authentication or permission hardening. If the original initialization reply was lost, recover its exact operation receipt/binding; never retry with a new session key. If a launch was fenced/cancelled/reclaimed before registration, InitializeAgent returns the terminal reason and creates no UUID. The connection returns full project, role, versioned instructions, compatible queues, pending Task/Role-message metadata and any launch continuation. Task ID is **not** a bootstrap prerequisite: it arrives with successful claim.

**ClaimNextWork.** A Registered launch invokes one idempotent operation with its launch ID/agent UUID, subscribed queue set and stable operation ID. When the selected item is a dedicated Role-message generation, the same CAS binds **exactly its one message ID** to the primary activation's handler generation; no second message lease or additional primary claim is created. A project Git CAS chooses the **blocking-first, FIFO-oldest feasible** eligible item according to §6; feasibility preserves compatible matching for all other still-live unclaimed launch credits (§8). It atomically records activation ID, work item claimed/generation, source-lineage fence, launch's one-lifetime-claim marker, consumed demand credit and remapped other credits. The response supplies the task/work subject, exact source/frozen review, conversation cursor, prior checkpoint, current dependency/priority evidence and next action context. An unknown/lost claim reply is *not* NoWork: query the original operation receipt/launch claim before attempting any different claim. Competing claims have one winner. A launch that already claimed once can never claim a second primary item after its terminal outcome.

**TerminalizeLaunch / token release.** An admitted launch **with no current or historical active primary work claim** can write one immutable project terminal receipt for NoWork, Finished, verified predispatch cancellation or documented error, using expected launch version/generation and stable operation ID. **Dedicated Role-message launches that claimed message work cannot use this route**: they must atomically acknowledge their one message, complete its primary work item and terminalize their launch through `CompleteMessageWork` (the ordinary `CompleteWork` state machine with a message receipt). An ancillary message handler attached to some other primary task never terminalizes that task on message acknowledgement. For a claimed work activation, `YieldWork`, `CompleteWork` and `BlockWork` atomically update the item/claim and write the originating **launch** terminal receipt in the same project Git CAS; there is no independently releasable claim. A pending account token remains occupied until `ReleaseGlobalAgentSlot` verifies the exact matching project terminal receipt (or unbound abort tombstone) and the current token owner in the account ledger, then releases exactly once under account CAS. A stale/historical receipt or lost reply cannot release twice. Logical launch termination fences all future claim/handler/dispatch mutations even if a provider tab remains alive. Strict physical-provider-process capacity would require separate host-exit proof and is **not** inferred here.

**Claimed-stage hard dependency edit and active-claim fence (F04).** `SetHardPrerequisites(stageGeneration, expectedGraphVersion, expectedStageVersion, edges, operationId)` is one project-ledger CAS checking the **current target stage and claim**. If a new **unsatisfied hard prerequisite** is introduced while a stage is Claimed, the CAS commits the new graph/derived coverage and atomically flags the existing activation `DependencyGatePending` with the originating claim generation, new dependency edge/graph version and one immutable stop-work intent. **The work remains claimed and its launch/capacity token retained** while the currently active source writer safely checkpoints; it does **not** silently become Available, duplicate its work or transfer its token. Ordinary `CompleteWork`, further stage-advancing mutation, and normal `YieldWork` are refused by that claim's gate; a lost response can be recovered from the project CAS receipt. Allowed operations for the old activation are read-only status, safe `CheckpointWork`/source WIP handoff, and `ResolveDependencyGate` / safe `BlockWork` / explicit recovery. On the next agent-visible Jarvis response, the durable gate and stop-work instruction are returned to that registered UUID (existing response-alert path may be used as a hint); no new session-control bus and no assumption that a STOP can undo already-completed source effects.

`ResolveDependencyGate(stageGeneration, claimGeneration, expectedGateVersion, durableSourceProof, operationId)` atomically verifies a safe checkpoint, any mutating job/source side effects, current graph edges and launch/version, then **terminalizes the old activation and launch** and (a) marks the work `Blocked` when an unsatisfied hard dependency remains, or (b) makes it `Available` with a **fresh FIFO availability** when every current dependency has already been satisfied/removed. A late dependency-satisfaction event does **not** silently revive the gated activation; it still requires safe project CAS terminalization. If no safe WIP/side-effect proof exists, retain `RecoveryBlocked/DependencyGatePending` with source fences and the token until explicitly reconciled; lease recovery must honor the same gate and cannot requeue an unsafe writer. The original claimant's stale `CompleteWork`/checkpoint/recovery operations cannot bypass the new graph generation. If `CompleteWork` wins the project CAS **before** the Lead's edit, insertion of a new hard prerequisite into that **already Completed immutable stage generation** fails `StageAlreadyTerminal`; Lead must create an explicit successor/correction stage for new work rather than retroactively invalidate an accepted stage. If the edit wins first, a racing `CompleteWork` fails its version/DependencyGate check and cannot bypass the newly required prerequisite. The same rule protects claimed frozen-review/integration stage provenance: committed canonical verdicts/integrations are not retroactively reopened by dependency edits.

**Checkpoints and source continuity.** `CheckpointWork` appends immutable summary, next action and exact evidence with operation-ID idempotence; reused operation ID with changed payload fails. `YieldWork` returns unfinished safe work to Available with a **new FIFO position**. A source writer must first publish and independently verify a remotely reachable immutable continuation commit/ref with repository, lineage, pinned base and SHA; dirty/unpublished changes do not constitute a resumable checkpoint. `BlockWork` terminalizes the launch and keeps the item Blocked on canonical dependencies; mutating jobs/unverified pushes are explicit RecoveryBlocked dependencies and may retain necessary source/worktree fences. `CompleteWork` marks that stage done, and only authorized domain producers create next-stage items; it does not silently accept review, merge or close a task. All post-terminal old activation writes fail project version/generation CAS.

**Message handling within a role execution.** A Registered role session may CAS-claim pending Task/Role operator messages as ancillary handling **only while its separate primary claim is already active**, provided §8's compatible reservation matching is preserved; claimed message responsibility does not authorize extra source writes or another work item. Message ack/reply and unhandled-lease recovery remain project-CAS operations described in §11. A role session launched **solely** for Role-message demand consumes exactly one deterministic message work item as its **primary** activation. **It must complete that primary item and the launch atomically when the message is handled**; `TerminalizeLaunch(Finished|NoWork)` is forbidden while its primary activation remains Claimed. Passive conversation reads do not consume or acknowledge messages.

**Verified lease recovery.** For a registered session with a claimed item, `RecoverStalledExecution` fences old claim/launch generations and safely requeues the same stage or marks RecoveryBlocked with exact external/source evidence (§9). For a registered **zero-claim** session, `RecoverStalledLaunchWithoutClaim` validates original UUID/lease/STOP, absence of a claimed item, launch/job/submit journals and one CAS terminal receipt `StalledReclaimedNoClaim`. There are **no Manager child launches to reconcile** in this target architecture. A concurrent NoWork/claim/complete or late heartbeat races on the same versioned state. Release the matching token only on verified project terminal receipt. Pending **unregistered** submitted launches use a distinct `RecoverUnregisteredLaunch` path: after configured observation/registration grace and reconciliation of the original one-shot dispatch journal, project CAS irrevocably fences late `InitializeAgent` and records terminal `UnregisteredReclaimed`; only then account release. If the dispatch journal or externally mutating effect is unresolved, remain RecoveryNeeded and hold the token; do not assume a missing tab or absent UUID means no model was submitted. A late provider session seeing terminal launch cannot register/claim, though the physical session may exist. No STOP-to-UUID is possible before registration.

Every terminal/recovery transition is idempotent by original launch ID/operation ID, preserves immutable audit evidence, and never requires a Manager model agent.

## 8. Deterministic Scheduler, matching and account-global capacity

**No model Manager.** The Scheduler is ordinary non-agent Jarvis server control-plane logic. It does not reserve its own agent slot, consume model tokens, hold a persistent conversation or spawn a recursive Manager. The non-agent reconciler runs even when global capacity is full. At `maxConcurrentAgents=1`, Scheduler can launch the oldest eligible role session directly; **there is no Manager last-slot handoff, project prepare, Swapped/Aborted disposition or child token** in the new protocol. Historic Manager receipts are migrated/audited, not used by new-launch code.

**Simple selection:** at a verified compatible project/account snapshot, find all runnable work, including uncovered **Role**-message demand (Task-message attention is passive and never launch demand), sort by `(blocksOtherUnfinishedStage ? 0 : 1, availableAtUtc, projectId, availableSequence, workId)`; choose the first candidate compatible with at least one configured role and the currently reservable unclaimed launch-credit matching. Reserve up to `maxConcurrentAgents - occupiedGlobalTokens`, one item of demand per launch, and dispatch until no verified uncovered demand, compatible role or capacity remains. If a work item has multiple compatible roles, use a stable configured role ID tie-breaker; **not** an ML decision, FIFO weight or permanent Worker slot. Keep role subscription rules in project config. Blocked stages, circular-dependency warnings, superseded reviews, unresolved source lineage and stale indexes never count as ready demand. An urgent review blocks a dependent implementation when its canonical dependency edge exists, so it is tier 1, not because of a special reviewer quota.

**Demand credits, never task preassignment.** Every admitted **unclaimed** launch has exactly one project-local demand credit covering one distinct currently Available compatible work generation. A Role-message work generation is keyed by exactly **one pending message ID**; multiple messages remain distinct work/credit generations rather than silently expanding a dedicated primary activation. Passive Task-message attention is **not** a work generation and cannot admit a launch on its own. For project snapshot S, a canonical injective matching maps the set of live unclaimed launches L to distinct eligible work generations U compatible with their role subscriptions. A bounded deterministic augmenting/rematching operation under one project Git CAS must establish complete matching before adding a launch. The mapping is scheduling coverage, **not a task assignment**. A role execution claims the oldest **feasible** item in §6 order while atomically consuming its own credit and rematching all other live credits against remaining items. If a role is eligible for A+B and another admitted role only A, it must claim B when taking A would strand the A-only reservation. If the earlier globally ranked item is infeasible, record the precise matching reason and choose the next feasible item. Two devices must not each reserve/claim the same item or report covered work as free. If eligibility disappears due to block/cancel/review supersession/role change, project CAS rematches affected credits or marks `DemandInvalidatedPendingTerminal` and fences claim; an invalidated launch retains its global token until an explicit terminal receipt. Uncertain index/operation status fails closed, never becomes NoWork or free capacity.

**One account-global limit.** `maxConcurrentAgents` counts every **logical** reserved, submitted, registered, Working, Stalled and uncertain role launch across all projects/devices and role types. There are no per-role caps or numbered reserved workers. `SetGlobalAgentCapacity(expectedConfigVersion, newLimit)` and Reserve/Release operations share a **single versioned account Git CAS domain**, so a shrinking limit below occupied/uncertain tokens is rejected with the occupied count; a racing reserve cannot violate a limit reduction. No eviction or inferred provider-session exit. The control-plane scheduler, reconciler, index repair, cycle detector and operator message submission consume no agent slots.

**Admission and one-shot launch:**
1. Read complete project queue/dependency/index coverage and account capacity/migration gate. If any producer/head/graph is incomplete, or global occupancy is full, skip dispatch and record a bounded reason; recheck after a verified availability/capacity event or periodic fallback. Do not spawn an LLM to inspect an empty queue.
2. Generate one stable **launch ID** and pin project, **role**, role-config version, compatible queues, optional demand intent and scheduling epoch. Reserve exactly one global account token by CAS under that launch ID. A launcher may not invent a UUID yet.
3. Reserve a compatible distinct demand credit and project-local `ReservedUnregistered` launch by project Git CAS. Global and project are separate ledger scopes: if project admission conclusively fails before launch registration, write/verify an **abort-only project tombstone under the original launch ID** before releasing global token; on ambiguous project commit, retain token and reconcile original operation receipts/heads (§7 C01). No fictitious cross-ledger atomic transaction.
4. Record one browser-intent operation with original launch ID, project, pinned role version and minimal bootstrap. The prompt needs only the **launch reference** plus "Connect to Jarvis, initialize, follow your role and yield when finished"; an extension may inject the launch reference without prompt text. The browser bridge/session layer must create a **new high-entropy sessionKey once per actual provider execution**, independently of launchRef, and recover that key only for retries of **that same** provider execution. A launch-global bootstrap template is **never** the source of sessionKey, and duplicate provider submissions get different keys by construction. If provider session continuity cannot be established, treat the identity/registration as uncertain and fail closed rather than lending a previous UUID to a distinct session. **Never include a task ID, pre-generated agent UUID, full spec, detailed role or review instructions in the prompt.** Every new session loads those from Jarvis on `InitializeAgent` and `ClaimNextWork`. Browser submit is one-shot; a timeout after dispatch is `OutcomeUnknown`, not permission to submit again with a different launch.
5. Once the model session actually connects, `InitializeAgent` atomically binds the first UUID and returns role context (§7). It claims the best feasible work under project CAS; Task/Role message handling uses the same project-matching discipline. If no eligible item remains, terminalize NoWork, verify project terminal receipt and idempotently release its account token.
6. Yield, CompleteWork, BlockWork, safe registered/no-claim recovery or late-cancelled unregistered reclamation writes a **project terminal receipt first**, then the matching account release CAS. A release wakeup coalesces a fresh non-agent scheduling pass. An unknown terminal response holds capacity while original receipts are recovered. No Manager/child slot transfer exists.

**Unregistered launch timeout/recovery:** A launch may be reserved, browser-submitted but never connected, and therefore has **no UUID, response-alert inbox or Working heartbeat**. The Scheduler/reconciler tracks a server-witnessed pending-registration grace and the one-shot browser journal under launch ID. A definitive pre-submit cancellation can terminalize immediately. Following a submitted/uncertain one-shot intent, it may commit `RecoverUnregisteredLaunch` **only after the registration deadline and complete project CAS/journal reconciliation**, fencing `InitializeAgent` at that same project head. The late session cannot initialize after revocation; logical release follows independently verified project terminal proof, while physical provider process exit is not asserted. If unknown side effects or conflicting registered identity cannot be fenced/reconciled, retain token RecoveryNeeded. Lost registration replies are replayed using stable session key and operation ID, not treated as no registration. This path is separate from Registered Stalled/STOP recovery.

**No handoff or planning scheduler.** If no demand is ready, no model starts. Existing active role executions may opportunistically claim Role messages without a new slot while preserving compatible outstanding credit matching. Lead creates planning work as a normal queue item; if a planning decision requires human judgment it remains a Lead-role task/message, **not** an unbounded Manager loop. Reconciliation of failed project admissions, lost receipts, stale registration or claims, migration epochs and safe token release is deterministic and can run at zero free capacity. Optional fairness or global numeric priorities are deferred; current contract is two-tier FIFO only.

## 9. Session interruption, stall recovery and source handoff

A connected session with a claimed work stage must end with atomic `YieldWork`, `CompleteWork` or `BlockWork`; a registered zero-claim session uses `TerminalizeLaunch`. All terminal paths write project proof **before** releasing exactly one matching global token. The next execution reconstructs from the durable subject, source, checkpoints and conversation, not from the predecessor's tab, local worktree or prose.

### Registered execution leases and STOP alerts

**First connection and heartbeat.** A pre-dispatch/reserved/unregistered launch has no agent UUID and cannot receive an agent-specific STOP. Its deadline and browser intent are handled by `RecoverUnregisteredLaunch` (§7–8), not by forging a heartbeat. Only `InitializeAgent(launchId, sessionKey, operationId)` creates the registered agent UUID, `lastSeenAtUtc` and server-witnessed lease generation. Registered tool calls and explicit lightweight client heartbeats, including verified long-running job ownership, extend Working leases at a bounded cadence. The server clock is authoritative; another session's UUID, UI tab observation or local timestamp cannot renew it. Durable coalesced lease receipts survive server restart. Configuration exposes `stalledAfter` and `reclaimAfter >= stalledAfter`.

**Stop-requested transition.** `Working -> Stalled/StopRequested -> Stopped` (cooperative) or `-> Reclaimed` (reconciled) is one-way. Project CAS compares registered launch/UUID and verified lease generation/last-seen; at threshold it writes one durable Stalled receipt retaining the work claim and global token, and schedules one deterministic STOP response alert **to that registered UUID**. A heartbeat that wins before the Stalled CAS prevents it; a heartbeat after Stalled may be logged but **cannot restore Working**. The original session may only perform safe shutdown/checkpoint/terminal operations, not claim new work or advance unrelated stages.

**Use existing response alerts.** `queue_response_alert`, `get_response_alerts` and `clear_response_alert` continue unchanged, addressed to the exact registered agent UUID. Stable operation ID = launch ID + UUID + stalled generation + STOP intent. On eligible tool response (including job-result poll), STOP is ordered ahead of other instructions despite ordinary notification-block settings. The existing queue has bounded pending alerts and **at-most-once** consumption; a lost response may lose an alert. Neither queued nor consumed STOP proves the session actually stopped, and it cannot undo a side effect from the previous tool call. Log/retry an enqueue failure with the same operation ID. **Unregistered launches use only launch-ID cancellation/fencing**, never an invented UUID STOP.

**Claimed-work recovery.** At `reclaimAfter` the non-agent reconciler calls `RecoverStalledExecution` with original launch ID, UUID, lease generation, STOP event and stable operation ID. One project Git CAS verifies the exact claim generation, source/job/review status and safe termination, writes `StalledReclaimed`, fences old activation/launch mutations and either requeues recoverable work (new FIFO position) or records `RecoveryBlocked`. A concurrent cooperative yield/finish/late heartbeat has one winner. A stale session can no longer make work-state claims/checkpoints; successor starts a separate launch and gets **its own new UUID upon connection**. Account token release only after independently verified project terminal proof; STOP receipt alone never releases capacity.

**No-claim registered recovery.** A submitted Registered Reviewer, Worker, Lead, Integrator or other role may stall before ClaimNextWork. `RecoverStalledLaunchWithoutClaim` verifies registered UUID/lease, no active primary claim, original one-shot/journal/handler receipts, and project CAS fences future claims/handling. It writes `StalledReclaimedNoClaim` or RecoveryBlocked, then conditionally releases the original global token after independent terminal verification. No child-launch/handoff special-case exists. A NoWork terminalization and an in-flight ClaimNextWork compete on the same launch version, never both succeed.

**Unregistered recovery.** `RecoverUnregisteredLaunch` uses the pending registration deadline, original one-shot browser journal and project launch generation. A definitive pre-submit cancellation is immediately terminal; after a submitted/ambiguous intent, a safe later project CAS may irrevocably refuse all future InitializeAgent calls before account release, but only with reconciled side-effect receipts or explicit RecoveryNeeded. A late ChatGPT session cannot claim work on a terminal launch. This is a **logical capacity fence**, not proof that the provider terminated or that agent IDs supply permissions. An ambiguous physical browser submit never justifies duplicate submission.

**Resumption and source safety.** A successor uses the latest independently reachable immutable checkpoint/source snapshot and Task/Role conversation, never the previous execution's mutable local workspace. If only an earlier snapshot is safe, record the potentially lost uncommitted interval. Every source-writing activation gets an isolated worktree at a pinned repository/base/source SHA with generation-scoped remote WIP refs. Before normal yield publish tracked/untracked required changes and independently verify the exact WIP commit SHA reachable at a protected remote ref such as `refs/heads/jarvis-wip/<work-id>/<activation-id>`; record repo, base, ref, SHA, tests and unfinished issues in the final checkpoint. Retain reachable WIP refs until no unfinished stage/checkpoint depends on them. A dirty/unpublished source writer, unresolved mutating subprocess, unknown push/merge or external side effect **cannot** requeue as safely resumable. Use RecoveryBlocked with specific durable dependencies and isolate late writes.

Pure read-only/planning/review stages may be reclaimed after proven project fencing; a **decided frozen review must never reopen**. A pending undecided review recovery CAS atomically releases both canonical review claim and projected work claim, or fails closed on uncertain review evidence. Integration with unknown push must reconcile actual Git remote ancestry and canonical integration receipt before retry. Source ref immutability plus per-activation worktrees restrict ordinary collision risk, but **do not** revoke account-authorized file/Git access from a late old process; account permissions remain shared.

Long-running mutating jobs are part of work context. An agent must finish/cancel/reconcile a mutating job before yielding source work as Available; completed job alone does not end execution. Concurrent external effects with uncertain outcome retain exact original journal and necessary worktree/source fence. A scheduler or reconciler operating at zero free capacity may repair safe leases/tokens without launching another model session.

## 10. Task → review → integration workflow

1. A task is created. Lead claims a planning item, records hard dependencies and implementation readiness, and publishes a stage without selecting a worker ID or numeric priority.
2. The deterministic Scheduler sees verified eligible implementation/review/integration/role-message demand, selects blocking-first FIFO work and launches compatible role sessions up to the global capacity limit. A Worker claims its feasible stage atomically and reads its last checkpoint; successive turns can use different UUIDs.
3. Yield releases unfinished implementation work. A frozen review request completes that implementation stage and publishes a review item, while the task itself remains open or in progress.
4. A reviewer claims the review item, inspects the exact immutable frozen ref/SHA and documents findings. Review claims are still exclusive and review decisions remain canonical. The review stage's checkpoint survives reviewer session changes. Writing a verdict does **not** release the review item claim or complete the reviewer's activation/launch. After the verdict the reviewer must terminally CompleteWork; verdict and terminal lifecycle are independently idempotent, and the integration producer must not be run twice.
5. ChangesRequested joins or creates the one current source-lineage correction stage linked to the exact review findings and previous source context. Multiple independent reviews of the same current revision add findings to that one stage, not multiple concurrently claimable source writers. Feedback for an older superseded source remains auditable and requires Lead triage before modifying current source. Accepted produces an integration item only when task policy and reviewed frozen SHA/target provenance require it. Neither event silently alters task ownership or closes the task.
6. Integrator claims the integration item, submits the existing canonical integration record, checks review acceptance and source/target identities, merges the **exact** accepted commit when conflict-free, runs required validation, pushes and verifies remote ancestry, and records CompleteIntegration idempotently.
7. A merge conflict or required source edit cannot be silently incorporated as unreviewed code. Publish an explicit correction item and require a fresh frozen review for modified source. An uncertain push/integration outcome must first be reconciled against Git and the canonical integration receipt before any retry.
8. Task closure is explicit after the required final workflow evidence; it is not inferred from a work-item completion or review decision.

Non-source tasks can define a shorter workflow; an accepted review need not imply an integration item if the task explicitly has no integration target.

### Canonical review claims and queue projections

The existing independent review record is the sole authority for frozen source SHA/ref, review claim, decision, and version. A review work item is a projection for dispatch/checkpoint; it must never keep a second independently writable reviewer owner. The queue claim and canonical review claim are one Git-ledger CAS. Legacy direct claim/release/withdraw/decide APIs must either participate in that same atomic transition or be disabled by protocol handshake at cutover.

| Canonical event | Work-stage effect |
| --- | --- |
| ClaimNextWork(review) | Atomically set canonical review Unclaimed to Claimed and work item Available to Claimed; bind one activation and immutable frozen SHA/ref |
| Review checkpoint | Keep both claims, do not infer verdict or source integration |
| Release before verdict | Atomically release canonical review and terminalize activation/launch, requeue the same work item once |
| Withdraw before verdict | Canonical review Withdrawn, work item Cancelled and activation fenced with explicit terminal/recovery evidence |
| Decide Accepted or ChangesRequested | Persist canonical verdict and idempotent downstream policy producer, mark still-claimed work verdict-recorded/terminal-pending; do not free reviewer capacity |
| CompleteWork after verdict | Write final checkpoint and terminate stage/launch; cannot decide again |
| YieldWork or BlockWork after verdict | Reject and never reopen/requeue decided review; require CompleteWork or audited recovery |
| Crash after verdict | Preserve verdict and unresolved claim until verified terminal evidence or audited recovery; no second decision or duplicate integration item |

Direct-claim/queue-claim and release/decide races use the canonical review version and one CAS ordering; losers reread. Ad-hoc or non-source reviews do not create integration work without explicit policy and provenance. Integration always pins the exact accepted review ID, reviewed source SHA and target, never mutable branch HEAD.

### Source-writing lineage serialization

Frozen reviews may proceed concurrently, but one mutable implementation lineage has only one actionable source-writing stage and one current writer. Publication and ClaimNextWork revalidate task stage generation, pinned base, lineage writer key and current source continuation. Concurrent Lead readiness and two ChangesRequested verdicts converge on one correction work item with references to both reviews; they do not create two simultaneous correction writers. Older feedback remains as evidence but cannot overwrite a newer stage tip. Lead chooses whether to incorporate stale findings or explicitly establish a new stage.

Parallel implementation branches require distinct explicit lineage IDs, pinned source baselines and a reconciliation/integration plan. Cancellation and supersession preserve all historic review findings. Any stale claim/checkpoint/completion for an obsolete stage generation fails CAS rather than replacing the current source.

## 11. Challenges, blocks and resumability

Existing durable challenge conditions become dependencies of work items rather than dependencies requiring one named worker to keep an attempt in its attention slot. **Work conversations** are addressed to the task, not a Worker N inbox. The pre-existing **one-shot response alerts remain addressed to agents**, now by the exact registered UUID of the ephemeral execution; a STOP alert for a Stalled session is not a task question or challenge. This preserves the already-implemented response-alert mechanism without inventing a new messaging channel. The challenge's issuer, conditions, evidence and satisfied/blocked/cancelled states remain canonical.

A blocked work item keeps its latest checkpoint and source context. Challenge completion reconciles dependency indexes and requeues the same item once when all required conditions are satisfied. If an item has several dependencies, satisfying one does not wake it prematurely. No notification, browser session or synthetic worker assignment is required for wakeup.

**Block/satisfaction race:** BlockWork checks authoritative condition versions and results in the same Git CAS that writes its dependency indexes and transitions the work stage. Already fully satisfied dependencies cannot produce a permanent blocked wait; use an explicit manual block, stay claimed, or complete/yield when safe. If BlockWork commits first, the later challenge-satisfaction transaction wakes the item; if satisfaction commits first, BlockWork's expected versions fail and it retries against current satisfied state. Per-domain source/index high-water marks allow a reconciler to repair missed derived wakeups after crash/restart, without requeuing twice. Multiple dependencies still require all-satisfied.

### Task- and role-addressed operator communication queues

**Address type.** Operator messages have one immutable recipient subject: `Task(projectId, taskId)` or `Role(projectId, roleId)`; existing canonical non-task work subjects remain available for review/integration/planning. The operator can send to a role such as `Jarvis / Lead` even if no Lead execution currently exists. The Role conversation and pending-message queue are owned by the project/role, not any execution UUID, display number or role-config version. A role may have zero, one or many concurrent instances. Replies return to the **same subject thread**, so successive Lead sessions see the full conversation and operator does not need to track a particular instance. An agent may post messages to its task thread and, when appropriate, its role thread; neither thread is a new permission principal.

**Message versus handler responsibility.** `PostOperatorMessage(subject, messageId, body, replyTo?, operationId)` atomically appends one immutable conversation message and a deterministic subject attention projection. A **Role** message additionally publishes exactly one runnable primary work generation keyed by its message ID; a **Task** message publishes **passive attention only**, not a standalone runnable stage or demand credit. Pending message text and conversation history remain readable by eligible sessions; **reading or viewing does not consume a message**. The first execution to take the next eligible action on that task or role calls `ClaimPendingSubjectMessages(subject, agentUUID, launchId, expectedSubjectQueueVersion, operationId)`, or performs an equivalent atomic intake in its task/role activation. One project Git CAS assigns exclusive **handling responsibility** for the pending message IDs to the winning current launch/activation generation, returning their ordered contents and a conversation cursor. For a **dedicated Role-message primary** work item, `ClaimNextWork` atomically binds that one message ID's handler responsibility in its **existing primary claim CAS**; it does **not** also call `ClaimPendingSubjectMessages` as a second handler claim. `ClaimPendingSubjectMessages` is for **ancillary** Task/Role handling by an existing eligible execution only. A competing Lead/Worker/Reviewer learns that handling is already claimed; it must not independently respond as the designated handler. `first` means the first successful canonical CAS, not the first tab that viewed the thread or the oldest numbered worker.

**Who is eligible.** For a Task subject, only the current eligible actor **already acting on that task's canonical actionable stage** can take pending Task messages. If multiple stages are independently active, the first compatible claimant wins under project CAS. Task message intake is **passive until then**, never a separate Scheduler launch or source-stage claim: if the task is Blocked, Closed, Cancelled, has no eligible actor, or is awaiting an unrelated prerequisite, messages remain Pending in verified operator attention with an explicit `AwaitingTaskActor` reason. It does **not** automatically reopen, wake, approve, reassign or bypass a dependency. If the operator wants an immediate Lead decision rather than waiting, they address `Role(Lead)` or explicitly create a **separate** Lead triage stage through its normal task/Lead producer, with no implicit Task lifecycle change. Message intake never grants scope or accepted-source mutation authority. For a Role subject, any active execution with that pinned role may claim pending messages at its next role interaction, whether or not it already has one primary work claim; **a message-handling lease is ancillary conversation responsibility, not a second primary work claim or task ownership transfer**. If no role execution takes responsibility, the pending role messages count as verified role-specific queue demand, allowing the non-agent Scheduler to launch an ephemeral session for the role under the same global capacity and demand-credit rules. A launch created solely for **Role-message** work claims **one message ID = one primary work generation**. It handles that one message and terminally completes work+launch atomically, not with no-claim `TerminalizeLaunch`; additional messages stay distinct Pending generations. An already-active execution can CAS-claim a compatible **batch of unhandled/uncredited** Role messages as ancillary work, but a dedicated message-primary launch cannot steal a second live launch's message credit or silently widen its primary claim. When an **already active** execution wants to accept a message as ancillary responsibility, the same project CAS must mark that message's pending work generation covered/claimed and **preserve a compatible injective matching for all other admitted, unclaimed role-message launch credits**. It may atomically rematch other credits to other messages; if no compatible matching remains, the active execution does **not** steal the reserved message from a pending launch. Otherwise the active role session can answer promptly without waiting to end its one primary task activation. This is the same demand-credit safety rule as section 8, not an extra account-global slot or permission. Do not launch a duplicate session for messages already covered by a live eligible handler or demand reservation. This means operator-to-Lead conversation works without inventing a permanent Lead task or agent inbox.

**Handling, acknowledgement and recovery — two disjoint claim kinds.** A **dedicated Role-message primary launch** owns one message work generation `W(messageId)` and its single activation. It finishes with `CompleteMessageWork(workId, launchId, agentUUID, claimGeneration, messageId, replyOrActionReceipt, operationId)` (typed `CompleteWork`): under **one project Git CAS**, verify that message `Pending/Claimed` and work `Claimed` belong to the same launch/handler generation; append or reference an immutable idempotent reply/action receipt, mark only that message `Handled`, complete `W`, clear its primary claim, fence the activation, and commit the launch terminal receipt. Account token release follows **only after independent verification of that terminal receipt**. There is **no intermediate state** in which a primary message handler's `Handled` event leaves W Claimed or permits token release without W completion. Replaying the same operation returns identical message/work/launch receipts. A message reply may be durably prepared in a separate canonical event, but the final complete CAS verifies the original reply ID/content and performs all remaining transitions atomically; a lost response/restart reconciles the original operation before trying another reply, completion or launch.

For an **ancillary Task/Role handler** attached to an execution **already holding another primary work activation**, `ClaimPendingSubjectMessages` atomically binds the message IDs to that existing launch's ancillary handler generation. For Role messages, the same project CAS marks each selected Available message work generation **`Claimed(handlerKind=Ancillary)`** and rematches other live launch credits; for Task messages it claims only passive attention and **no** independent work item. `CompleteSubjectMessageHandling(subject, messageIds, handlerGeneration, replyOrActionReceipt, operationId)` atomically records the reply/explicit handled outcome (or verifies the precommitted receipt), marks the selected message IDs Handled, and **Completes each corresponding ancillary-claimed Role-message W** (or clears each passive Task attention entry) while releasing the ancillary handler leases. It **never** completes, checkpoints, reassigns, releases or terminalizes the execution's unrelated primary activation. A Registered execution with **no primary activation** cannot use this ancillary path; it must `ClaimNextWork` for a Role message W or wait for eligible Task work. Every changed Role-message projection and all already-admitted unclaimed launch credits must be rematched or fenced by the same project CAS; a message with a live incompatible reservation cannot be stolen. A single dedicated primary claim covers **exactly one** message ID; no opportunistic batch widening. An ancillary execution may accept a bounded batch only when every affected unclaimed role-message credit remains injectively matchable (or else accepts fewer/none).

Merely showing a message in a tool response, incrementing an unread cursor, or receiving an agent response alert never marks it handled. Merely showing a message in a tool response, incrementing an unread cursor, or receiving an agent response alert never marks it handled. Responses and attachments persist in the original subject conversation. If the **ancillary** handler yields, terminates, stalls, is reclaimed or loses an acknowledgement reply, its unfinished handler leases are released/recovered by the same project-ledger terminal/generation CAS; the affected unhandled Role work generations become Available again (new FIFO timestamp) and Task attention remains Pending, with prior conversation and partial work preserved. For an unfinished **primary Role-message activation**, ordinary `YieldWork` safely releases W to Available with a new FIFO position and clears its primary message handler generation in the same CAS; `BlockWork` links actual dependencies, and stalled claim recovery fences W/launch before requeue; never treat an uncommitted reply as Handled or free the global token without project terminal proof. Unfinished **ancillary** Role-message W claims likewise return to Available with a fresh FIFO position when the handler's main launch yields/terminates/stalls; passive Task attention stays Pending with no work-item generation. If the reply and terminal commit did occur, recovery treats W and message as Completed/Handled and must **not** reopen either. A replay verifies original message/response operation IDs before posting another reply, so crash/retry cannot lose the message or produce duplicated canonical answers. When a message is a request for a spec/priority/approval change, the required explicit task/Lead/challenge mutation remains authoritative; `Handled` alone never performs an approval or changes task scope. Message queues use the same verified source-high-water/index-coverage discipline as all other work queues.

**Channel separation.** These are operator **conversations and actionable message queue items**, not the existing agent-addressed STOP response alerts. STOP and exceptional execution-specific alerts still use `queue_response_alert` to the exact agent UUID; operator messages to `Role(Lead)` and `Task(T)` use durable subject message queues. Do not fan role messages out as alerts to every current Lead or implement a separate general-purpose chat bus.

### Subject-addressed two-way operator communication

A task or role (or canonical non-task work subject such as a standalone frozen review) owns its complete durable conversation. An agent asking a question writes an append-only operator-visible **Question** event referencing its Task or Role subject and, when relevant, its current work item, activation and source/checkpoint revision. The message is not sent to a persistent worker ID. The operator replies **to that task/question**, or **to that role thread** when the message targets a role, even if the original session is gone and a different agent UUID later acts. The next eligible activation receives a bounded **task or role** conversation history, pending message claim receipts and an exact cursor over newer messages; no previous ChatGPT conversation or private agent inbox is required.

Messages distinguish **Note**, **Question**, **Response**, and **Decision**; each has an immutable event ID, source subject, originating operator/account or execution label, timestamp, optional reply-to ID, and body. Routine checkpoints and tool telemetry remain in their structured audit streams, not in the human conversation; only meaningful human-directed exchanges appear as messages. An operator may post a message while no worker is active. Informational messages do not alter task specs or claim state. A Decision that changes scope/priority/readiness requires the normal explicit task/Lead mutation, not an implicit chat-to-spec rewrite. Store message bodies once on the Git-backed work-subject event stream; operator-attention lists and inbox unread counts are derived indexed projections with coverage proofs. Optional push/UI notifications are only hints and cannot become workflow authority.

A Question is **blocking only when the agent explicitly links it to a durable operator-response challenge condition** and the appropriate BlockWork/role-message handling dependency transition commits that condition. Nonblocking questions can coexist with ongoing work. A response addressed to the question is committed with the matching challenge condition satisfaction, checked against its version/issuer/subject, so all required dependencies can wake the same blocked item exactly once. A response is not an authorization for unrelated actions, a review acceptance, or a silent task closure. If no execution is active, the response remains visible and the next eligible actor on the matching Task/Role subject retrieves it. Replies are not routed to a historical agent label.

Project-wide questions directed to a responsibility such as Lead use the stable `Role(project, Lead)` conversation and corresponding role message queue, not an individual Lead agent's inbox. Questions with no appropriate Task or Role may still use a durable planning/decision work subject. Do not create a **permanent agent-ID Lead inbox** as an alternate channel. Existing durable challenge APIs remain the source of truth for condition state and operator consent; subject conversations provide readable message context without duplicating decision semantics.

The operator's primary view is **Needs my response**, grouping outstanding agent questions by project/task or project/role subject, context, urgency and dependency effect. Task-addressed pending operator messages show `AwaitingTaskActor` for Blocked/Closed/Cancelled/no-active-stage tasks and never appear as unexplained runnable queue demand. The operator also has a **Compose message** target selector (Task or Role) and can open a durable **Role / Lead** thread with pending/claimed/handled status, current handler UUID in details and the same conversation history across successor sessions. After replying, the task either remains actionable or is requeued by its canonical dependency transition. There is no need to find the numbered worker that asked.

## 12. Proposed API surface (names provisional)

Phase A must freeze exact typed statuses, CAS preconditions and stable operation receipts. All writes use project/account Git-ledger CAS, caller-stable operation IDs and fail-closed incomplete-coverage behavior. The owner's authenticated account supplies permissions.

**Reads:**
- `ListQueues`, `ListAvailableWork`, `GetWorkItem`, `GetWorkHistory`, `ListQueueHealth`: verified blocking-tier/FIFO keys, demand-credit coverage and source/index high-water marks.
- `GetHardDependencyGraph(project, verifiedSnapshot)` and `ListCircularDependencyWarnings(project, cursor)`: stage-generation hard edges, SCC/self-loop members, witness paths, graph high-water and incomplete-remote status.
- `GetRoleConfig(roleId, version)`, `ListRoleSubscriptions`, `GetRoleInstructions`, `GetLaunchById`, `GetRegisteredExecutionByUUID`, `ListUnregisteredLaunches`, `ListStalledExecutions`, `GetGlobalAgentCapacity`, `GetAccountMigrationEpoch`.
- `GetSubjectConversation(Task|Role, cursor, limit)`, `ListPendingSubjectMessages`, `ListRoleMessageQueue`, `ListOperatorAttention` with immutable reply/claim proof.

**Project work and dependency writes:**
- `PublishWork`, `StageWork`, `SetHardPrerequisites(workGeneration, edges, expectedGraphVersion, expectedStageVersion, operationId)`, `WakeWork`, `CancelWork`: domain producer CAS plus current derived blocking/FIFO/SCC diagnostics. Newly unsatisfied hard dependencies on a Claimed generation atomically record `DependencyGatePending`; terminal work rejects retroactive hard edges rather than reopening accepted stages.
- `ClaimNextWork(launchId, agentUUID, queues, expectedProjectHead, operationId)`: oldest **feasible** blocking-first FIFO candidate; one primary claim/launch; complete compatible credit rematch; task ID/spec/context returned after claim.
- `CheckpointWork`, `YieldWork`, `CompleteWork`, `BlockWork`, `RecoverWorkActivation` require exact work, activation and claim generations plus source/checkpoint proof. `ResolveDependencyGate(stageGeneration, claimGeneration, expectedGateVersion, durableSourceProof, operationId)` safely terminalizes gated activations into Blocked or newly Available based on the **current** dependency graph; pending WIP/mutating jobs keep gate/source fence and logical token.

**Scheduler, launch and account writes (non-agent control-plane):**
- `CheckScheduleAdmission(account, projects, verifiedGlobalHead)`: role-demand/FIFO/global preflight, no model session if cap full, empty or coverage incomplete.
- `ReserveGlobalAgentSlot(account, launchId, projectId, roleId, operationId)` then `ReserveProjectLaunchDemand(project, launchId, roleConfigVersion, eligibleDemand, operationId)`; on definite project CAS failure, `AbortUnboundProjectAdmission(project, launchId, originalAdmissionOperationId, expectedHead, operationId)` records a verified abort-only project tombstone before global release. Ambiguous outcomes retain token.
- `RegisterLaunchDispatchIntent(project, launchId, oneShotBrowserOperationId, operationId)` and original browser-journal reconciliation. Browser effects are one-shot; an unknown submit is never retried under a different launch ID.
- **`InitializeAgent(launchId, sessionKey, operationId)`**: FIRST model-session connect generates the new server UUID and binds the original session key by project CAS. A same-session replay returns that UUID/context; a different session key fails AlreadyRegistered, terminated launch fails Terminal. No pre-generated UUID or task ID in the prompt.
- `TerminalizeLaunch(launchId, expectedGeneration, reason, journalProof, operationId)`, `RecoverUnregisteredLaunch(launchId, expectedGeneration, originalDispatchJournal, operationId)`, `ReleaseGlobalAgentSlot(launchId, verifiedProjectTerminalReceiptOrAbortTombstone, operationId)`.
- `RenewExecutionLease(launchId, agentUUID, leaseGeneration, serverWitness, operationId)`, `MarkExecutionStalled`, `RecoverStalledExecution`, `RecoverStalledLaunchWithoutClaim` use registered UUID/lease/STOP receipt; unregistered recovery uses launch ID only.
- `SetGlobalAgentCapacity(expectedConfigVersion, newLimit, operationId)`: same account CAS domain as tokens; reject resize below live/uncertain occupancy.

**Operator Task/Role messages:**
- `PostOperatorMessage(subject=Task|Role, messageId, body, replyTo?, operationId)` creates **passive Task attention** or **one runnable Role-message work generation per message ID**. `ClaimPendingSubjectMessages` applies to ancillary handlers. **`CompleteMessageWork(workId, launchId, agentUUID, claimGeneration, messageId, replyOrActionReceipt, operationId)`** is the dedicated primary Role-message path: one project CAS atomically marks message Handled, work Completed, launch/activation Terminal; verify that receipt before account token release. `CompleteSubjectMessageHandling(subject, messageIds, handlerGeneration, replyOrActionReceipt, operationId)` and `ReleaseSubjectMessageHandling` handle ancillary leases only and never terminalize another primary activation. Existing unclaimed demand credits must stay injectively matched.
- `PostWorkMessage`, `RequestOperatorAnswer`, `RespondToWorkQuestion`: retain canonical Challenge dependency satisfaction and explicit spec/approval authority.

**Migration:** `FreezeMigrationEpoch`, `PrepareProjectEpoch`, `ValidateAccountEpoch`, `ActivateAccountEpoch` (explicit operator authorization), `AbortUnactivatedEpoch`, with account/project protocol reader/writer gates.

Existing `queue_response_alert`, `get_response_alerts` and `clear_response_alert` are UUID-targeted only **after** InitializeAgent; they are not Task/Role communication or a terminal receipt. There are no `PrepareManagerHandoff`, `ResolveManagerHandoff` or `CheckManagerScheduleAdmission` calls in the new API.

**Minimal bootstrap:** one stable launch reference and the instruction to connect/initialize/follow the resolved role; bridge injection may omit even the explicit reference from prompt text. The sessionKey is **not** a launch-global bootstrap value: the bridge/client creates and persists it independently for each actual provider execution, reusing it only for that execution's own retries. **Never supply a task ID, pre-generated agent UUID, full spec or detailed role instructions.** InitializeAgent returns UUID/project/role; ClaimNextWork returns task ID, frozen source, checkpoints and conversation.

## 13. Client/TUI, operator attention and audit

The default **Agents / Work** view is **task/subject-title first**, not an agent roster:

1. **Active & Stalled** — Claimed work stages grouped by task/subject, with stage, role, blocking tier, checkpoint, last seen, Working/Stalled/STOP and optional display-only role label. UUID exists in details only after first registration. Unregistered launches show **Starting / Pending registration / Unknown submit** and launch ID; do not invent an agent UUID.
2. **Next in queue** — Verified Available stages sorted **blocks other work first, FIFO within each tier**, with availability age, role, and reason an older item is infeasible. No manual numeric priority rank or Manager roster.
3. **Blocked / Needs operator** — Hard prerequisites, questions by Task/Role, RecoveryBlocked, incomplete graph/index and **Circular dependency** diagnostics listing exact stage generations and witness path. Cycles remain blocked, never runnable because they block others.
4. **Conversations** — Compose to Task or Role (including Project / Lead); immutable thread with Pending/Claimed/Handled status and handler UUID in details; conversation exists without a currently active role agent.
5. **Launches / Diagnostics** — One account-wide reserved/registered/active/uncertain/max summary, pending registration deadlines, one-shot browser journal, project terminal and account release receipts, launch/UUID bind history and index health. The Scheduler/reconciler are non-agent services, not model role rows.

**Derived presentation.** Stage Claim/Available/Blocked/Completed and Task lifecycle remain canonical. Active/Stalled, blocking tier, and SCC cycle flags are verified projections, never separately writable `Task.Active`, `Task.PriorityRank` or `Task.Circular`. Requeue gives a new FIFO availability sequence. Completed/Cancelled history remains searchable.

Audit includes launch reservation and original browser submit, **first connection generating UUID** and session-key replay, role version, source claim/checkpoints, Task/Role message claims/replies, server lease and STOP alerts for registered UUIDs, registered/unregistered recovery, project terminal/account release receipts and exact frozen source/integration evidence. Historical Manager and numbered-worker evidence is retained read-only. UI time never proves provider termination.

## 14. Audited migration and protocol compatibility

This target supersedes the current persistent assignments and the **previously reviewed model-Manager scheduler**, and requires a separately reviewed, **operator-authorized** cutover. Historical Manager launches, capacity/slot handoffs and existing agent-keyed alerts remain immutable audit records. No old live Manager is silently mapped to a new role launch, and no two independent schedulers may dispatch simultaneously.

**Account-scoped epoch:** Account admission ledger records a fixed participant project set, schema/protocol versions and verified heads with CAS state `LegacyActive -> Frozen -> Preparing -> Validated -> Activated` (or `Aborted` only before activation). Every project records inert `Prepared(epoch, baseHead, indexCoverage, conversionReceipt)`; the account ledger records global capacity schema/occupancy proof. New work, queue availability, role registration and ScheduleAdmission remain invisible/disabled until **verified account Activated(epoch)** AND matching **project Prepared(epoch)** AND compatible client protocol handshake. In Frozen/Preparing/Validated, old read-only authority remains available with writes fenced. A partial cross-project migration is never advertised as an atomic transaction or healthy queue.

**Writer gate:** Before project preparation, enforce a server-side minimum compatible client protocol across connected devices; fence incompatible legacy assignment, Manager launch, reviewer and integration writes and old scheduler dispatch, and settle pending operation/browser/claim journals. A project with an old writer allowed to mutate authoritative state cannot commit a supposedly safe new Prepared receipt. Conversion writes only staged proofs, never an independently authoritative parallel task copy. On activation, the non-agent Scheduler is the **only automatic launch authority**, replacing the Manager heartbeat; old Manager role cannot enqueue demand.

**Inventory/drain:**
1. Snapshot exact account/project Git heads, open tasks/attempts/stages, frozen reviews/verdicts, integration submissions, challenges, messages, hard dependencies, old priorities, source/checkpoints, WIP refs, active workers/reviewers, registered legacy agent keys/alerts, **historical Manager project prepare/swap/abort token dispositions**, global tokens and all devices' in-flight browser/operation journals.
2. Quiesce and prove termination or explicit safe recovery of existing Manager schedules/launches, assigned workers, claimed reviews, integration mutations, mutating subprocesses, orphaned job/result receipts and uncertain browser submissions. An unverified Manager handoff/child token remains occupied until old-protocol exact receipts settle; do not erase it or assume the new design's lack of handoff releases it. Operator approval is required before replacing a currently running scheduler.
3. Convert each authoritative unfinished stage to exactly one deterministic item. Preserve task spec, attempt/source lineage, accepted review SHA, challenge/block conditions, immutable checkpoints and remote WIP reachability. Preserve old assignment/Worker-N/Manager identities as history, not as current owner. Unrecoverable local-only state is an explicit RecoveryBlocked dependency.
4. Convert unclaimed frozen reviews only if canonical exact SHA and review state are verified. Claimed reviews, integrations and unknown pushes require exact terminal evidence first. Accepted review may publish integration demand only when project policy actually requires it.
5. Convert hard stage prerequisites and operator message/role threads as canonical edges/events, with verified graph/index source-high-water. Compute derived blocking-first FIFO tiers, record server-witnessed availability time/sequence for every genuinely Available stage at cutover, and run deterministic **Tarjan SCC** diagnostics. Existing manually configured priorityRank/Manager ordering is **historical only** and does not silently drive new scheduling. Legacy cyclic data is visible with warnings, never rejected or made runnable.
6. Register new launch schema with `Unregistered(agentUUID=null)` until a live session calls InitializeAgent, stable launch/session-key CAS, timeout/reclaim behavior, and one account-global capacity authority. Preserve existing historical UUID alerts under their actual original recipients; no stale Worker-N alert is delivered to a new reused display number.
7. Validate across **every** project and account proof: project queue/dependency/message coverage, credit matching, FIFO and cycle diagnostics, global occupancy/resize, one-shot browser dispatch, fresh connect-time UUID, registered/unregistered safe recovery, frozen review/integration lineage, and migration writer fences. Incomplete proof means no activation.
8. Only an explicitly operator-authorized account CAS moves epoch to Activated. New reads/writes require matching project proof; old clients remain fenced. A crash midway through preparation leaves new scheduling suppressed; recover original stable operation receipts or abort with inert staged Git history. **No implicit destructive rollback after activation.**

Staged deployment of client/server binaries, controlled canary and historical Manager removal are separate release tasks. Updating this document or acceptance of its design review alone does not authorize any production action.

## 16. Acceptance and negative-space tests

This is the **current target acceptance suite**, replacing the old Manager-centric cases 1–66 in the independently accepted prior revision. Retain the exact frozen review history and regression provenance (F01–F06, B01–B05, C01, C02, S01) in Git/review documents; **C02 Manager Swapped-or-Aborted handoff is only a legacy migration/retirement test**, not a new dispatch API. The cases below (1–65) require executable deterministic two-client Git-ledger tests, lost acknowledgements, reordered project/account commits, relevant Release fixtures and UI coverage. Cases 50–65 specifically address frozen review `f8c5216d9488464c9cb2e175fed3b16c` F01–F04. A specified case is not evidence it has passed.

1. **No model Manager.** With one global slot and one eligible Worker stage, Scheduler reserves and dispatches Worker directly. There is no Manager capacity token, Manager bootstrap, child token or last-slot swap; scheduler and reconciler run with zero model slots.
2. **Empty/blocked work.** When every stage is completed, blocked or index-incomplete, Scheduler starts no model. A role may have configuration but no permanent idle execution. Non-agent diagnostics remain available at cap zero/full.
3. **Blocking-first.** Available A blocks task B; Available C has no dependents and an earlier timestamp. A is selected before C; the same is true if A is a frozen review blocking another stage.
4. **FIFO ordinary.** With no hard blocker edges, ready A, B, C of compatible roles run in original availability order, not task creation date or manually stored old priorityRank.
5. **FIFO within blocking tier.** Three blocking stages with distinct availability records are selected oldest-first, including review and implementation items; no role quota or special review multiplier.
6. **Blocked is not runnable.** Stage X blocks Y but X itself awaits unsatisfied Z: X is not runnable and cannot be admitted solely for blocking Y; if Z becomes Available and blocks X, Z has precedence.
7. **Yield/wake position.** Yield or dependency wake writes a new availability timestamp/sequence, moving the stage to the end of its current tier; changing blocker flags without a new availability transition preserves the original timestamp.
8. **Role feasibility.** An oldest global stage is incompatible with the current role; Scheduler selects next compatible feasible stage and records the skip reason. A configured role ID tie-breaker is stable, never an LLM choice.
9. **Cross-project deterministic order.** Two projects produce equal server-witnessed timestamps; order resolves by project ID, per-project availability sequence and item ID. No fictitious cross-repository global enqueue transaction is assumed.
10. **Graph cycle warnings.** Hard stage-generation dependencies A->B, B->C, C->A create one SCC warning with exact edges. A self-loop creates its own warning. Neither edit is rejected, and none of its blocked members becomes runnable.
11. **Cycle deletion/revision.** Removing an SCC edge or advancing to a new stage generation recomputes/clears the diagnostic from verified graph. Informational dependencies and alternative satisfied relations create no false cycle.
12. **Graph/index incomplete.** Missing or stale graph shard, remote hard-edge proof, producer high-water mark or queue index yields Incomplete/Unknown diagnosis and suppresses unsafe dispatch/claim; never reports an empty healthy queue or no-cycle certainty.
13. **Global capacity.** At cap six, six roles across three projects hold six total reserved/uncertain logical tokens; a seventh reserve fails. Scheduler/reconciler do not occupy a token.
14. **Resize CAS.** Lowering cap from eight to three with eight occupied fails, and a racing ninth reservation cannot bypass same account CAS. Once occupancy falls to three, a version-checked reduction succeeds.
15. **Launch pre-registration.** Scheduler reserves account and project demand for L, one-shot submits role=Worker. Before first connection L has launch ID and token but agentUUID=null; there is no fabricated Working agent or STOP recipient.
16. **First-connect UUID.** The actual model session calls InitializeAgent(L, sessionKey=K, operationId=I): project CAS generates exactly UUID A and returns project, role, pinned instructions, eligible queue; repeating same I/K returns A.
17. **Competing connect.** Two different session keys K1/K2 race to initialize L across two Git clones: exactly one binding/UUID succeeds; loser gets AlreadyRegistered, no extra UUID/claim. A late connect after terminal/reclaim fails Terminal.
18. **Lost initialization response.** A successful first-connect Git push loses reply; replay of original I/K reconciles same A, never chooses new UUID or project role. A different operation payload with same I is rejected.
19. **Minimal bootstrap.** Browser launch prompt contains only stable launch reference (or bridge supplies it) plus connect/initialize instruction. No task ID/UUID/task text/role policy duplicated; successful ClaimNextWork supplies full canonical task/source/checkpoint context.
20. **One-shot submit.** Browser submit times out after possible side effect. Original launch/intent retained as uncertain; no second browser submit under another launch. Confirmed tab close provides no terminal/process-exit evidence.
21. **Unregistered recovery.** L submitted but never connected: after registration deadline, reconciler verifies original side-effect/journal and project CAS fences late InitializeAgent before writing UnregisteredReclaimed terminal proof; account token release follows. Unknown dangerous side effect remains RecoveryNeeded.
22. **Unbound admission C01.** Global token reservation succeeds but project-demand CAS conclusively loses before any project launch. Abort-only project tombstone under original launch ID/operation precedes exact account release; delayed project admission push cannot resurrect launch.
23. **Ambiguous admission C01.** Original project reservation might have committed but reply lost; a negative snapshot read cannot release token. Exact original operation and project CAS resolve to either admitted live launch or abort-only tombstone; duplicate releases fail idempotently.
24. **Demand-credit injection.** Two roles' unclaimed launch credits match A and B injectively. Concurrent scheduler passes cannot cover either with a third launch; claim A by B-credited launch rematches remaining credit to B in same project CAS.
25. **Feasible FIFO rematching.** A-only role and A+B role coexist; flexible role cannot take oldest A if that strands A-only live launch, and takes next feasible B instead. The skip is attributable to matching, not manual priority.
26. **Demand invalidation.** Cancel, block, priority-tier change, supersede review or edit role compatibility concurrent with reservation: one project CAS rematches valid credits or fences invalidated launch as DemandInvalidatedPendingTerminal. No duplicate work or silent free token.
27. **NoWork vs claim.** Two clients race one registered launch's ClaimNextWork and TerminalizeLaunch(NoWork); exactly one terminal/claim-generation path wins; an unknown claim result is recovered before a new claim or NoWork.
28. **One primary claim.** A launch claims exactly one work stage, checkpoints, yields/blocks/completes then terminalizes with a project receipt. It cannot take a second primary item even if its role subscribed to multiple queues.
29. **Yield source continuation.** Source writer snapshots tracked/untracked required changes at generation-scoped remote WIP commit, independently verifies SHA reachable, checkpoints/yields CAS and requeues with fresh FIFO key. Missing commit/dirty worktree or mutating job blocks safe yield.
30. **Late writer.** Old source activation resumes after new claim: stale project claim generation cannot checkpoint/complete; remote per-activation ref and isolated worktree preserve successor pinned commit. Underlying account Git/file rights are unchanged.
31. **Review canonicality.** ClaimNextWork for frozen review atomically claims both canonical review and work item. Review verdict does not itself terminate execution; post-verdict Yield/Block cannot reopen decided review or cause duplicate integration producer.
32. **Source lineage.** Multiple ChangesRequested reviews of same current source generation join one correction stage; stale accepted review/findings cannot reset current writer. One actionable source writer per repository/task/target/lineage.
33. **Exact integration.** Integrator may merge only the exact frozen Accepted SHA under task policy and verify target ancestry. Conflict-modified source requires a new frozen review; unknown push must reconcile original Git and ledger receipts.
34. **Task/Role messages no agent.** Operator posts Role(Jarvis,Lead) M with zero Lead sessions. Canonical role thread and one message demand persist; Scheduler admits a compatible Lead role session under global cap, no permanent Lead inbox.
35. **First handler claim.** Two same-role sessions see M by read; exactly one project handler CAS wins. Loser can read conversation but not independently answer as designated handler.
36. **Ancillary handler/credit matching.** Active Lead handling another task tries to claim M while a pending unclaimed Lead launch is credited M: it must rematch that launch to another compatible generation or refuse; cannot strand reserved role demand.
37. **Message reply replay.** Handler replies durably but loses acknowledgement; recover exact response/message operation receipts without duplicate canonical answer. Incomplete handler on yield/stall is requeued preserving original thread and message IDs.
38. **Task message versus review.** Task T has Worker and an independent Reviewer; first compatible actor to CAS-claim M handles it once. Posting M alone cannot reopen/unblock T or bypass authoritative Challenge/review/spec mutation. Task-addressed M with no eligible task actor remains passive AwaitingTaskActor, never direct Scheduler launch demand.
39. **STOP separation.** Registered UUID receives existing STOP response alert at next eligible Jarvis tool response; role message does not fan out as alerts. At-most-once/lost STOP is never terminal proof, and unregistered L receives no UUID-targeted STOP.
40. **Registered stall.** Heartbeat races Stalled CAS: before may prevent STOP, after cannot restore Working. Reconciler fences claim generation after verified reclaimAfter, creates immutable terminal proof and only then releases matching token.
41. **Registered no-claim stall.** Lead/Reviewer/Worker registered but not yet claimed work stalls. RecoverStalledLaunchWithoutClaim safely verifies no claim/handler effects, writes one project receipt and releases token; concurrent NoWork/ClaimNextWork/late old writes lose CAS.
42. **Unsafe recovery.** Pending mutating source job, unknown merge/push or unverified review state leaves RecoveryBlocked, without duplicate conflicting writer or free token based solely on time/alert.
43. **Token release.** Verified project terminal receipt or C01 abort tombstone frees exactly one account token; duplicate reconciler requests/cross-project release retries are idempotent and cannot release another launch's token.
44. **Role-message primary terminal.** Dedicated Role(Lead) launch claims one message work item W(M) as its one primary claim; `CompleteMessageWork` in one project CAS commits reply/Handled(M), Completed(W), terminal activation+launch receipt, then independently verified account token release. `TerminalizeLaunch(Finished|NoWork)` is rejected while W is Claimed. Another session can read the durable role thread with a fresh first-connect UUID.
45. **Migration stage gate.** Account epoch Frozen/Preparing/Validated with project A prepared and B missing cannot expose new queues/UUID registration or dispatch. Old incompatible writers are fenced; partial Git proof is not mistaken for an atomic multi-project commit.
46. **Manager migration boundary.** Old in-flight Manager handoff and token receipts are reconciled/deliberately drained under old code before operator-authorized activation; new Scheduler never creates Manager and no old Manager timer may dispatch alongside it.
47. **Migration historical data.** Old assignments, Manager launch/alerts, priorityRank and review/integration evidence retain historical provenance; new hard edges/FIFO availability and Task/Role conversations convert injectively without rewriting frozen SHA or inventing UUID for legacy sessions.
48. **Migration crash recovery.** Crash after preparing one project or lost account activation reply replays original epoch receipts; abort before activation leaves inert staged history; after Activated, no force-ref rollback erases new-format work.
49. **Operator activation gate.** Only explicit operator-authorized account Activated CAS after every project Prepared/index/SCC/credit/source and connected-client protocol fence proof permits new Scheduler. Document review, implementation completion or tab closure is not authorization.
50. **F01 dedicated message CAS.** Scheduler launches L credited to one Role-message generation W(M1). ClaimNextWork atomically binds message handler M1 and primary W; CompleteMessageWork atomically commits one reply/Handled(M1), Completed(W) and L terminal receipt; independent account CAS releases one token. Separate no-claim TerminalizeLaunch is forbidden once W claimed.
51. **F01 lost reply/commit replay.** Reply event for M1 is durably prepared, then final CompleteMessageWork project push or response becomes ambiguous. Reconcile original operation/receipt; no duplicate canonical answer, no reopening Handled M1 or completed W, and no global token release before verified project terminal evidence. Retrying same operation/payload is idempotent.
52. **F01 two messages/two launch credits.** Role(Lead) receives M1 and M2 with separate W1/W2 and two pending launch credits. Dedicated primary L1 may only own/complete M1; M2 remains claimable by L2. A second message arriving during L1's response never silently widens W1 or steals L2's reserved work.
53. **F01 NoWork/claim race.** TerminalizeLaunch(NoWork|Finished) and ClaimNextWork(W1) race on one Registered launch version: at most one wins. If W1 is Claimed, NoWork/Finished is rejected; only safe CompleteMessageWork, YieldWork/BlockWork or verified stalled recovery can terminalize the primary activation.
54. **F01 ancillary isolation.** Active Lead holding primary Task A claim accepts an eligible ancillary Role-message batch. The handler-claim CAS marks selected Role-message W as Claimed(handlerKind=Ancillary); ack atomically handles messages and Completes those W, without Task A completion, claim release, launch terminal receipt, second **primary** claim or global token release. Registered zero-claim Lead cannot use ancillary handler path.
55. **F02 passive blocked Task attention.** Task T is Blocked by prerequisite B and has no actor. Operator posts Task(T) M: Pending/AwaitingTaskActor attention is durable; Scheduler creates no message-only launch and T remains Blocked. Only when the normal canonical task stage becomes active can a compatible actor claim M.
56. **F02 terminal Task attention.** Task T is Closed/Cancelled or has no actor, operator sends M. The thread remains readable and M Pending with explicit AwaitingTaskActor; no implicit reopen, unblock, approval or runnable demand. A separately addressed Role(Lead) message or explicit Lead triage stage can handle the operator's intent without mutating T by chat alone.
57. **F03 bridge session-key lifetime.** Two distinct provider executions created from one launch reference receive independently generated high-entropy session keys from the bridge, never a launch-level cached key. First InitializeAgent CAS binds one; other receives AlreadyRegistered even under duplicate browser submit. The loser cannot claim/renew the winner's lease.
58. **F03 same-session retry.** One provider execution loses InitializeAgent response, reconnects after browser route/tool retry and recovers the same stored session key and original operation ID, returning identical UUID and project/role configuration. Refresh with unprovable provider-session continuity must not reuse prior session key and is diagnosed rather than silently merging two physical sessions.
59. **F03 copied bootstrap ambiguity.** Deliberately supply two different provider sessions the same copied launch-global sessionKey in a bridge fixture: bridge preflight refuses the shared bootstrap key or regenerates distinct per-session values. Document that a server-only equal-key replay cannot distinguish intentional key copying without provider attestation, and do not claim an agent security principal.
60. **F04 hard-edge beats CompleteWork.** Worker claims source stage A; Lead CAS inserts unsatisfied hard A-requires-B first. Same project CAS sets DependencyGatePending and fences stage advance. Concurrent CompleteWork with old graph version fails; agent may safely publish WIP/Checkpoint and ResolveDependencyGate, not finish A before B.
61. **F04 CompleteWork beats hard-edge.** A's canonical CompleteWork/terminal project CAS wins before Lead's edit; attempting a new unsatisfied hard prerequisite on this immutable Completed A generation rejects StageAlreadyTerminal. Lead must create explicit successor/correction stage, preserving accepted review/integration history.
62. **F04 safe gate terminal and wake.** New hard prerequisite gates A while claimed; claimant publishes verified WIP snapshot, reconciles mutating jobs, then ResolveDependencyGate project CAS ends old launch and makes A Blocked while B unfinished. If B completes or edge is removed before finalization, the same gate resolution makes A Available with new FIFO position; it never silently resumes the old activation.
63. **F04 unsafe gate recovery.** Worker A has a mutating subprocess or unknown push when new hard edge is committed; YieldWork/CompleteWork or lease recovery cannot requeue A as safe, retain DependencyGatePending/RecoveryBlocked and the relevant source/lease fences until exact side effect reconciliation. A stale worker or second device cannot bypass gate by replaying old checkpoint or terminal receipt.
64. **Cross-case credit/handler race.** A Role message W is Claimed as dedicated primary while an already-active role tries ancillary handling and a pending launch is credited another message: project CAS permits exactly one W handler and preserves injective reservations, no double reply or token release. If an ancillary claim wins first, its CAS marks W Claimed(handlerKind=Ancillary) and ack Completes W without terminalizing the unrelated primary activation.
65. **Cross-case index coverage.** Missing/partial Task-attention, Role-message primary work, hard-dependency graph or handler-lease coverage returns explicit Incomplete; a passive Task message is not miscounted as runnable launch demand, and no negative index read authorizes token release.

A full Release gate additionally verifies no unauthorized provider/process assumptions, no role/UUID ACL invention, historical immutable source/ledger retention, and operator-only production activation. Coverage over cross-project two-ledger CAS, account cap and Stage/Review/Role-message invariants is mandatory before Phase F.

## 17. Explicit non-goals

- No model Manager, recursive Manager heartbeat, Manager-to-child last-slot swap, manually numbered agent assignments or role-specific reserved capacity in the **target** architecture. Historical behavior remains audited until migration.
- No agent UUID pre-generation before the first session connection. No task ID, full role instructions or lengthy task/review instructions in browser bootstrap prompts.
- No agent-ID permissions, role ACLs, false secure-identity binding or contributor account authorization design. Future contributors use authenticated account-level permissions.
- No manually scored priority ranks, role queues with special quota, starvation/aging heuristic, machine-learning scheduler or elaborate cross-project fairness policy. **Blocking work first; otherwise FIFO.**
- No hard rejection of dependency cycles or automatic alteration of hard dependency edges. SCC warnings are diagnostics only, and blocked cycle members remain blocked.
- No generic scripting/workflow event bus, automatic approvals, unreviewed source merges, invalidation of frozen review identities or forced identical pipeline for all tasks.
- No assumption that closed tabs, passed time, STOP-alert delivery, or new provider session proves physical termination. Logical lease revocation requires project CAS and exact terminal/release receipts.
- No immediate production cutover, scheduler activation, deployment, restart or live Manager retirement authorized by writing or reviewing this spec.

## 18. Settled target decisions and superseded history

- **Scheduling is non-agent Jarvis logic.** No Manager LLM or Manager handoff; the non-agent Scheduler selects verified uncovered queue demand and dispatches directly into available global slots. Lead performs planning and edits hard dependencies, not routine manual ranking.
- **Two tiers only:** an Available stage that is a hard prerequisite of any other unfinished stage is first; every other Available stage follows. **FIFO within tier**, with new availability time/sequence after yield/wake and explicit deterministic tie breakers. A blocked stage is never runnable merely because it blocks something else. Compatible credit matching may skip an older infeasible item, recording why.
- **Cycle warning:** Derived SCC/self-loop diagnostics over verified hard stage-generation edges, recomputed after dependency edits. Do not reject the edit, invent new task lifecycle states or infer acyclicity from incomplete coverage; surface exact witnesses to Lead/operator.
- **Identity split:** Scheduler creates a stable launch ID and reserves capacity/role/demand **without** agent UUID. First successful model-session `InitializeAgent(launchId, sessionKey, operationId)` atomically generates and binds exactly one UUID; replay from same session gets same, different session gets AlreadyRegistered. UUID is an alert-routing/audit handle, not permission. Task ID is returned after queue claim, never preassigned.
- **Minimal prompts:** launch reference only (or bridge-injected) plus "connect and initialize"; all project, role, instructions, queue subscriptions, task spec, review and checkpoint context live in Jarvis.
- **No durable assignments:** an execution claims one primary work item at a time and terminalizes/yields; successor gets fresh launch/UUID. Durable Task/Role conversations remain stable. Existing response STOP alerts target registered agent UUID, never Role.
- **Role messages:** first compatible agent to claim handling via project CAS owns the pending batch; passive read does not consume. Already-active role sessions may accept ancillary message work only if other live launch-demand credits remain matchable. Replies, acknowledgement, release and crash replay are durable.
- **Global capacity and admission:** one account CAS for all roles/projects and resize, no Manager token. Global-first project demand admission requires C01 abort-only project tombstone on definitive failure; uncertain receipts hold token. Unregistered launch cancellation/recovery fences late InitializeAgent before global release; registered claim/no-claim recovery uses original UUID/lease and project terminal receipt.
- **Review/integration exactness:** canonical frozen review refs and verdicts; one source writer per lineage; immutable remotely reachable WIP snapshots on safe yield; explicit integration of accepted SHA and task closure, with unresolved external effects RecoveryBlocked.
- **Migration:** Existing accepted Manager-centric design at `35e7465a122fd9d767a9f75494b241ff2eb7fe72` and previous C02 handoff/S01 taskless-Manager provisions are retained **only as historical review/cutover provenance**. The new target removes those codepaths and requires a new independent frozen review, exact integration and operator-authorized multi-project/account epoch activation. Old live Manager must not silently continue alongside the new Scheduler.
- **No new permissions:** Account-authenticated source/tool access remains unchanged; role/UUID/claim are coordination and CAS-fence data, never substitutes for account authority.
