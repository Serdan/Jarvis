# WQ-01 Phase A: work queues, launch contracts and deterministic fixtures

Status: **isolated contract/fixture implementation, not production activation**. The accepted architecture is [work-queues-and-ephemeral-executions.md](work-queues-and-ephemeral-executions.md), at base commit `90ed868d04524d0483ccd979cffb5029d8cf7027`. The target architecture's §16 enumerates 80 acceptance/negative-space cases; this branch is **not evidence that all 80 have passed**.

## Boundary

- `Server/WorkQueueContracts.fs` defines pure F# contracts and state transitions, included in the server assembly but **not invoked by server handlers, scheduling, browser submission, project account persistence, production migration or deployment**. No production or schema behavior changes as a result of these functions being compiled.
- `Server.Tests/WorkQueueContractTests.fs` exercises immutable snapshots, explicit expected versions and operation IDs; `Project` and `Account` represent **separate** versioned CAS domains. Publish-stage, post-message and project-admission receipts compare complete immutable typed request values (including nested dependencies, lineage, subject/work and token/role-version fields), with distinct mutation discriminants. Negative-space tests race stale and winning logical snapshots; the production ledger still needs a stable schema-versioned canonical encoding/hash for persisted receipts.
- The two-client disposable Git fixture creates a bare Git project and two clones, demonstrates one non-force push winning and the second stale snapshot being rejected, then fetches the original winning receipt. It does **not** yet serialize every contract transition to the real Git task ledger. Further two-repository/account project interleavings belong in the canonical persistence implementation.
- The pure contract caller explicitly supplies canonical server/virtual `now` for dependency projections (ordinary/Role-message/ancillary completion, hard-edge edit, cancellation, verified waiver, dependency-gate resolution and integration-exception resolution) and any terminal ancillary requeue, as well as registration, heartbeat, STOP and reclaim. The timestamp witness is independently bound into each mutating operation receipt; `AvailableAt` is never synthesized from the FIFO sequence. A later runtime must provide an authenticated, monotonic server-clock witness, canonical persistence and provider/STOP continuity evidence.

## Invariants modeled and tested

| Boundary | Model / negative-space coverage |
| --- | --- |
| FIFO and dependencies | Two tiers: blocking-first then independently witnessed availability timestamp, project, monotonic sequence, work ID; no permanent Worker quotas or Manager model. Phase A `Blocked` is valid only for an unmet hard prerequisite (explicit unrelated/operator/recovery holds require separate typed authority in later phases). Publication rejects clear-gate `Blocked` with no unmet hard edge, including Role-message work. A completion/cancellation/waiver projection wakes resolved dependencies once with `AvailableAt=now` and a fresh unique sequence, including same-time multi-wakes and lost-ack replay. Cancellation alone never satisfies a hard edge. No-wake on unrelated edits/completions, unresolved cycles or missing indexes; Tarjan SCC includes self-loops and exact cycle edges. |
| Source lineage | Explicit repository/task/target/lineage identity fences concurrent actionable implementation stages; a completed generation permits an intentional successor. Read-only proof is not sufficient for mutable implementation source. Exact task/repository/lineage, active stage/claim generation, pinned expected source ref/SHA, verified remote continuation ref/SHA and job reconciliation are checked at the pure boundary. The accepted continuation ref/SHA is persisted in the successor WorkStage.SourceLineage before requeue. This does not prove a real Git remote is reachable. |
| Account capacity | Reserve/resize/release share one versioned account CAS; a token cannot be released by absent/mismatching project terminal proof; global-before-project admission abort writes an abort-only project tombstone under the original launch before account release. |
| Launch identity and lease | One-shot submit; UUID appears only on first successful registration with a per-provider-execution session key. Same operation replay returns identical UUID; competing registration rejects; heartbeat versus STOP uses project CAS lease generation; no-claim reclaim and unregistered reclaim fence late work. |
| Demand credits | Deterministic maximum-cardinality injective role-compatible matching protects role-specific work. Every modeled eligibility change rematches all unclaimed credits inside the same project CAS or fences unmatched ReservedUnregistered, SubmittedUnregistered and Registered launches as DemandInvalidatedPendingTerminal. These cannot dispatch, first-connect or claim; the phase-specific original-dispatch/session terminal proof must precede the separate account token release. |
| Operator messages | Role messages generate one primary work item per pending message. Dedicated primary reply completion commits message Handled, W Completed and terminal launch in one project CAS. Ancillary handler acknowledgement does not terminate unrelated primary work; unfinished ancillary claims return to Pending/Available on that primary launch's terminal transition using a fresh witnessed time and sequence. Role-message stages obey the same Blocked publication and dependency wake rules as ordinary work. Task messages are passive, not standalone launch demand. |
| Frozen review finality | Decided review becomes DomainFinalizedTerminalPending while work is still Claimed, rejects retroactive hard dependencies and cannot complete work before its canonical verdict. Gate-before-verdict rejects the stale decision. |
| Integration external effects | Original one-shot push journal pins accepted source SHA, target and operation ID. Positive observation requires those identities plus verified ancestry/job reconciliation, not merely a timestamp or negative remote read. A hard dependency creates a hold; observed effect remains a GateException, not Integrated/IntegrationAuthorized, until satisfied prerequisites or a *typed, scoped, canonically asserted* Lead/operator waiver; waived historical edges remain recorded. The asserted verification boolean/approval version is a pure test input, **not** real account authorization. |
| Migration | Only all-Activated account/project snapshots permit the modeled new dispatch epoch; no Manager handoff path is added. |

The new NUnit fixtures include both success and denial cases. Their names cite the §16 case numbers they exercise; **a shared number is a targeted regression scenario, not a claim of exhaustive end-to-end case coverage**. Full canonical Release gates must still execute all 80 target acceptance cases with actual two-client ledger storage, lost acknowledgement/recovery, browser bridge, mutating job journal, account capacity and migration epoch instrumentation.

**Review #1 correction coverage:** six new focused NUnit tests cover Blocked wake/replay, cancellation and scoped waiver, three preclaim invalidation phases/terminal receipts, partial injective rematch and competing admission, complete typed payload replay, and exact continuation lineage. **Review #2 corrections:** independent server/virtual wake timestamps are passed through all eligibility-changing CAS paths; same-time wakes get unique sequences and same-operation replay retains the original witness. New negative fixtures use deliberately different timestamp and sequence domains (old ready work at 1000/2000, later wake at 3000), reject fabricated empty-edge `Blocked` publication for ordinary and Role work, and verify unresolved cyclic/Role blocks cannot wake through unrelated edits or completion. Counts describe pure contract fixtures only; there are still no production assertions for all 80 cases. Runtime clock authentication and monotonicity remain for the production ledger integration.


**Review #3/#4 ancillary hard-edge coverage:** A Role-message handler cannot reply/complete across an unsatisfied hard dependency or a pending gate. On primary terminal, a pure ancillary handler is atomically released to coherent Blocked/Available state. Crucially, `resolveAncillaryDependencyGate` also permits its **independent** release while an unrelated registered primary Plan remains Claimed: a single project CAS compares launch version, handler/claim generation, pending gate graph version and current prerequisites; it marks the message Pending, removes only the ancillary lease, clears the gate and either remains Blocked or obtains a newly witnessed FIFO time/sequence. It preserves the primary work claim, launch lease, and account token; existing unclaimed demand credits are reconciled in that same CAS. New fixtures check B completion and versioned waiver before Plan terminal, stale two-client snapshots, claim/graph generation mismatch, original operation replay and payload mismatch, primary terminal races, unsafe source effects, reclaims, downstream D blocked until real W completion, and credit/token non-duplication. This is contract semantics only; actual versioned ledger, session, waiver verification and global token orchestration remain subsequent phases.

## Review notes

The intent is to give later implementations a reusable *executable semantic reference* with explicit rejection outcomes, rather than put mock dispatch logic on the production code path. Since account and project CAS cannot be combined atomically, the C01 abort-only project proof and exact account release remain separate and must be confirmed across real Git clients. Since Git external push is not atomic with project CAS, `ExternalEffectObservedPendingGate` is an observed fact and a durable workflow **hold**, never a permission to publish downstream integration success.
