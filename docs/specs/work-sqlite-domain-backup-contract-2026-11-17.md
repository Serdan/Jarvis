# Trusted SQLite Work-state backup and recovery projection contract

**Date:** 2026-11-17  
**Status:** DESIGN ONLY; hard NO-GO for full-domain export/restore or live activation until the gaps and gates below are implemented and independently reviewed.  
**Source pin:** clean `origin/main` / `a5cb1906ab5402d047d525e495cbc38fe750cd5c`. This is a proposed boundary for F1 (`work-json-backup-restore`) and G1b (`work-recovery-role-fences`), not a claim that either lane has passed a full-domain gate. No code, migration, test, build, host, Scheduler, or cutover was executed for this contract.

## 1. Decision and hard constraints

**Choose a versioned, typed projection/inverse over the existing B SQLite transaction snapshot and F1 physical backup/restore plumbing, with G1 persistent Recovery fencing.** Keep one authoritative SQLite database and the existing asynchronous F1 outbox/Git publisher; do not add a second coordinating ledger or generic reflection serializer. A narrowly extended F1 canonical JSON envelope (provisionally **format v3**) may preserve its `records`/`capacities`/`receipts`/`audit` structure, but `bodyJson` must originate from a *closed authenticated Work-domain representation* and be round-trippable through its trusted inverse. A schema change for missing durable fields must be a separately versioned SQLite migration (not hidden behind a format bump).

**Current implementation is NO-GO for complete authenticated B/E/G backup, regardless of F1 physical durability:** `WorkSqliteAuthority` accepts any JSON-object `BodyJson` and unrestricted record kinds within its enum; `WorkSqliteBackup.safeBody` only admits nonempty flat `state`, `status`, `credentialVerifierSha256` fields, whereas real E0/G1 bodies carry arrays, IDs, generations, provenance, nested recovery evidence and more. Neither boundary proves non-disclosure of a scheduled bearer when an otherwise allowed arbitrary string is supplied. `WorkSnapshotCodec` F0 v1 cannot represent the whole B row/receipt/audit model. The current F1 manifest SHA-256 detects corruption, **not** an attacker able to replace both files; the trust of the backing Git commit/repository must be established separately. G1a's caller-supplied complete snapshot is not an authenticated F1 restore witness, and F1's `RequiresRecovery=true` receipt does not itself persist a Scheduler/authorization lock.

The intended architecture remains the accepted `work-stateful-orchestration-2026-11-17.md` sections 8–10 and `work-stateful-implementation-alignment-2026-11-17.md` G2/G4/G6: locally durable SQLite; separate Git source artifacts and backup history; stale restore => explicit Recovery, never inferred absence of an external effect; no two live writers; no operator-independent cutover.

### Non-obvious admissibility gap

B's `boundedId` accepts strings not representable in F1 `safeId`. More seriously, B accepts a valid JSON object with any property name/value. Thus a malicious or buggy caller can commit `{"state":"Open","bearer":"..."}` (or a secret-shaped otherwise-valid identifier) through the internal B boundary; F1 fails export, while a naive "allow all bodies" fix leaks it. **A format validator alone cannot make an unrestricted source into a credential-safe, total projection.** Narrow B writes to authenticated typed commands, or track a formally closed subset and refuse new live B/E/G data until all supported row kinds have exact lossless projections; a partial exported database must not be published as complete. A string allowlist without trusted provenance cannot prove the string was not populated from bearer input. Even UUID-looking or SHA-looking values may be attacker-supplied; source/ID/role constructors must control their origin.

## 3. Proposed minimal format and typed boundary

1. **B command boundary:** authenticated importer/producer/claim/recovery handlers construct domain variants (`ProjectVn`, `WorkVn`, `StageVn`, `LaunchVn`, `RoleVn`, `ReviewVn`, `IntegrationVn`, `ExternalEffectVn`), never arbitrary caller JSON. Each variant has a strict parser, canonical serializer, exact allowed fields, semantic invariants and source provenance witness from the verified original producer. Keep raw `BodyJson` private to the B adapter; prohibit unverified alternate `Commit` callers at host activation. Completeness is proved for the full writer set and all historical admitted rows, not inferred from one fixture.
2. **Secrets are non-exportable types:** scheduled `BearerSecret` exists only in dispatch/tool-auth channel. Durable `ScheduledVerifier` is a separate type containing one-way verifier SHA256 plus typed reservation binding; its serializer cannot see `BearerSecret`. Original repo/ref and IDs come from verified canonical source/ID constructors, not user-supplied arbitrary strings. ManualGrant is a memory-only ADT with **no SQLite variant/backup serializer**, no generic extension map and no outbox/log fallback. Do not serialize `originalStages.bodyJson` from G1 as arbitrary nested text. Perform red-team serialization tests on all string-capable fields, including IDs, refs, user text and JSON escape sequences. A validator cannot guarantee secrecy against a user who independently pastes identical bytes into arbitrary public text; the enforceable property is no path from *Jarvis-held credentials/grants* into serialized output, even via untrusted command smuggling.
3. **Projection:** acquire all B tables (`work_meta`, `work_records`, `work_capacity`, `work_receipts`, `work_audit`) in one read transaction as F1 already does (`WorkSqliteBackup.fs:278–316`). Parse each `BodyJson` to the exact typed kind/schema (reject duplicate keys, unknown extensions or invalid tags); associate row metadata with typed provenance, complete account membership, source/ref/commit and credential verifier scope. Cross-check all graph/stage/role/launch/effect relations. Emit canonical deterministic UTF-8 JSON with stable ordering, an explicit format version, database schema version, committed sequence, project/account identities, source provenance, an optional informational snapshot timestamp if canonical rules fix it, plus content checksums. No mutation of DB during export. Include receipts/audit, not only current rows. Preserve existing F1 `authority.json` + `manifest.json` to minimize changes; per-project partitioning is a separately reviewable scaling enhancement, not a prerequisite.
4. **Inverse:** verify a *trusted* backup Git repository/commit identity and protected ref or other pinned authenticated restore root **before** parsing its files; hash/checksum alone is not authenticity. Strictly parse exact version, fields, byte canonicalization, file list, bounds, source/ref/commit, unique cross-project IDs, one-to-one history and sequence. Reject missing or unsupported records, unsupported source lineage, mismatch of cached projections, unknown effect state or incomplete role/claim/permission binding. Rehydrate typed domain, then write only to an empty quarantined DB in one transaction, preserving original version/sequence/receipt/audit values; re-export and byte-compare **pre-fence**. No per-record synthetic sequence or fabricated authority. Enforce size/count/depth limits before allocating or iterating 1..N.
5. **Version policy:** format-only rendering change => increment snapshot format version with an exact reader; missing authoritative original repository/ref/credential-binding data or tombstones => reviewed DB schema migration/importer contract, bump SQLite `user_version` and format version as appropriate. Current `formatVersion=1` is *not* a lossless B importer. Current F1 `formatVersion=2` may remain usable for its narrow already accepted fixture subset, but not as a whole-domain restore witness. Do not auto-migrate unknown formats or silently coerce unknown fields. For a legacy row lacking a required witness: hard NO-GO, re-import from independently verified original Git evidence or retain blocked Recovery state with explicit missing evidence; no fabricated positive receipts.
6. **Zero-loss vs lag:** an export at sequence N is immutable evidence of N, **not** of actions N+1..M. Versioned snapshot manifests include exact source refs *as evidence*, not live authority. Outbox captures/flushes/retries and publishes as in `WorkBackupReplication.fs:42–125,179–252`; network failure never blocks SQLite hot-path commits. Disallow publishing bundles that fail total typed projection. Preserve separate Git backup history; no force push or hidden new source writer.

### Tombstone policy

Until there is a reviewed deletion command, B record deletion is unsupported; therefore future import/export must reject a disappearing key within a supposedly lineage-contiguous series without explicit authorized evidence. If deletion becomes necessary, add a typed tombstone (original key, last version, operation/sequence, source/reason and relevant claim/effect fence), retained through backup and recovery, or an equivalent authenticated event stream. Its introduction changes the authoritative schema and format; do not mistake an omitted row for safe tombstoning. An external branch deletion cannot authorize removing a local Work/receipt.

## 4. Mandatory stale-restore gate

After verified JSON -> empty SQLite round-trip **but before the sealed DB is visible to a host**, persist a database-enforced `RecoveryRequired` boot mode in the restoration transaction or an equally strong reviewed schema-level barrier. A returned process-local `RequiresRecovery=true` boolean is insufficient. Every Scheduler admission/claim, tool permission, reserved scheduled verifier, external-effect dispatch and other mutating command must fail closed while it is set. Restore with a lock is different from ordinary restart of intact SQLite (no unnecessary fencing). In the isolated recovery transition, atomically commit the B/G1 coverage downgrade, stage `Blocked/SourceRecoveryBlocked` gates, original captured identities and unknown effects, plus account-version CAS and a recovery receipt. G1a's `CompleteProjectSet` supplied by a caller cannot substitute for the F1 verified, authenticated *complete account* snapshot. Recoverer may later release individually resolved scope only with exact source/ref/commit/review/integration/effect provenance and versions; all still-unknown in-flight operations remain fenced. Never re-use a historical receipt as permission for a launch (`WorkSchedulerSqlite.fs:494–498,590–664`). If fencing or validation fails, leave DB quarantined; no partial serve.

This reconciles `WorkSqliteBackup.restoreEmpty`'s verified staging/sealing (`:397–493`) with `WorkRecoverySqlite.seed`'s CAS fence (`:193–270`), without letting the scheduler start in between. A backed-up `Verified` project must not remain runnable merely because its stale rows were restored with identical bytes. The pre-fence byte comparison proves backup fidelity; subsequent fence changes must be new audited state, not claimed equal to the old snapshot.

## 5. Executable future acceptance plan (NOT executed)

Implement in F1/WorkSnapshot/WorkBackup and G1b/Recovery-owned lanes against one agreed B schema/typed DTO package, without cross-editing or live host registration. Every gate is binary and reports exact fixture, source commit, schema/format version and DB sequence.

**Positive two-project fixture (account A, projects P and Q):** create an empty disposable B DB through authenticated typed writers, with all eight supported record kinds across P/Q; a Project/System/Feature graph with hard cross-system dependency, required/optional descendants and Draft/Proposed/Open transitions; priority/FIFO and role digest/version/subscriptions; two live launches with reservation-operation/account/work/generation, an actual claim and STOP generation; exact original repository ID, refs, commit SHAs, review verdict and integration receipt/target; `Prepared` and `Unknown` effects with original one-shot identity; durable scheduled verifier (hash only) bound to reservation and permissions; account maximum/reserved/version and complete project set. Include multiple updates of one row so row version, per-transaction audit sequence and global sequence differ; a receipt replay; and an empty-row or tombstone phase if deletion becomes supported. Capture via one SQLite read transaction, export twice => byte-identical canonical files (except deliberately defined deterministic snapshot metadata); restore to fresh empty DB, compare typed full domain + every physical B table row/receipt/audit/sequence against pre-fence source, re-export => identical bytes. Confirm normal process restart is stable. Then add persisted recovery gate, restart host adapter against disposable DB; no admission, credential, claim or external effect succeeds before reviewed release. **No execution of real dispatch.**

**Reject matrix (each independent test must fail before publishing/serving):** tampered content, recomputed hash without trusted backup root, missing/extra file, duplicate property/row/key or spoofed project/account identity; invalid/changed application ID or schema, unsupported format/kind/body-tag, too-long legitimate B ID rejected by mismatched serializer (positive parity or explicit producer-side migration required); malformed SHA/ref or source repo/commit substitution, missing role digest/role row, stale graph/claim/STOP/source, missing review or integration decision link, reservation verifier without reservation, project P omitted from account A, reserved-capacity mismatch; skipped/reused/non-monotonic sequence, receipt/audit/hash mismatch, missing last transaction, duplicate operation ID, forged historical replay as fresh authorization; unknown/Prepared/Observed effect erased, unknown launch receipt after backup N, newer Git source/review/Integration evidence after N, stale restored grant or role reused, attempted full export with a B-admissible arbitrary `BodyJson`; corrupted WAL/sealed restore, interrupted rename, Git outage and outbox replay; unsupported future tombstone, legacy v1/v2 falsely imported as complete v3, oversized/deep JSON and partial host loss.

**Credential adversarial table:** inject a distinctive scheduled bearer in (a) raw body `credential`/`bearer` or nested `originalStages.bodyJson`, (b) `state`/`status` or other otherwise-allowed fields, (c) IDs, queues, role digest, source ref, review ID, free text, JSON unicode escape and a credential-shaped UUID; attempt to persist an ephemeral ManualGrant as a project/role/effect body or as an outbox item. The tests must demonstrate rejection *at the trusted ingress/projection boundary* for unauthorized bearer-origin values and **zero occurrences of plaintext token/manual grant bytes across authority JSON, manifest, spool, Git publisher staging, failure logs and recovery evidence**. A structurally legal identifier supplied by a malicious caller is not automatically trusted. Hash-only verifier output must match expected binding, never reveal the bearer. A malformed/untrusted row blocks full export; don't "sanitize by dropping" it.

**Host-loss rehearsal:** snapshot at N, then commit N+1 launch/claim and newer frozen review/integration/source Git artifacts; destroy only disposable host DB, choose authenticated backup N, restore with durable boot fence and restart fake two-client host; verify no duplicate launch, claim, one-shot remote action, grant or false approval; inspect source and Git backup history, create Recovery queue, reconcile proved artifacts, leave unsupported outcomes Unknown/review-required and explicitly release only resolved work with new receipt. Also simulate absent Git access and incomplete original source leases: scheduler stays fenced and reports backup lag, not a fabricated negative. Verify manual grants vanish on restart and no stale scheduled credential reauthorizes.

**Review and handoff:** F1 owner implements the typed export/inverse/format, strict manifest and tested empty restore; G1b owner implements persisted boot/recovery fence and verified source reconciliation. The B/source-importer owner must first define missing authentic source repository/ref and closed writer/credential binding; without it neither F1 nor G1b can assert full GO. Review exact frozen commits independently, run disposable .NET 11 Release tests and complete two-project negative matrix. **No implementation or cutover authorization from this design.**

## 6. Alternatives rejected

- **Use F0 v1 directly:** readable and well-validated for its own closed logical records, but cannot reconstruct complete B rows, all generations, exact receipt/audit history, provenance mapping or recovery bodies. F0 `Sequence` cannot be safely inferred from B last sequence. Keep its canonicalization/strict-parser ideas, not a fictional v1 back-compat promise.
- **Widen F1 `safeBody` to any JSON:** yields convenient round-trip but indiscriminately exports arbitrary B `BodyJson`, including scheduled bearer or nested recovery copies. Unsafe without trusted typed ingress and exhaustive domain coverage.
- **Keep only physical DB image or a second Git authority:** physical-only is not the promised readable and versioned JSON restore; synchronously writing Git or creating a second Work authority defeats local transaction and recovery invariants. Reuse F1 physical row snapshot as the lossless *internal* substrate, but make its readable exported form typed/authenticated.

**Final gate:** typed, complete and credential-safe round-trip plus proven stale-restore lock is the predicate for full-domain backup/recovery GO. Until that predicate is demonstrated, F1 durability and G1a recovery tests have their existing narrower meaning, and the migration remains default-off.
