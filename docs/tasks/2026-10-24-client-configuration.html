Persistent user-level client configuration

Status: Open. Date: 2026-10-24.

Goal

JarvisClient loads and manages persistent, machine-local settings from the current OS user's standard configuration directory. Every copy of the executable launched by that user shares the same configuration, regardless of executable location, working directory, downloaded version, or self-update. A friendly machine name becomes configurable without changing the stable device identity used for multiclient routing.

Location and file format

Use a human-editable, versioned config.json in the per-user OS configuration location. Resolve Linux via $XDG_CONFIG_HOME/Jarvis/config.json, defaulting to ~/.config/Jarvis/config.json; Windows via %APPDATA%\Jarvis\config.json; macOS via ~/Library/Application Support/Jarvis/config.json. Use platform APIs where appropriate and test the exact path resolution. The location is shared by installations for one OS account, not a server-hosted or repository-scoped store.

Continue using the existing persistent device ID; preserve its value and established location across client upgrades. Reuse a common platform-directory resolver where it helps, without regenerating identities on migration. Store configuration outside the binary installation, project directories, Git repositories, and updater replacement paths.

Initial settings

{
  "schemaVersion": 1,
  "machineName": "Home Desktop",
  "workspacePath": "/home/user/Projects",
  "trustLevel": "partial",
  "allowedEnvironmentVariables": [],
  "maxImportBytes": 33554432
}

The example is illustrative; missing keys use existing defaults. machineName defaults to the OS hostname and is only a display label; the UUID in device-id remains the routing identity. The remaining fields correspond to existing startup options (--path, --trust, --allow-env, and --max-import-bytes). Preserve existing environment-variable overrides for OAuth and permitted environment names, and define and document their effective resolution.

Behavior

  • Startup resolves defaults, persisted configuration, environment variables, and CLI overrides deterministically. Explicit CLI values override stored scalar settings. Keep the existing additive semantics for allowed sensitive environment variables, with duplicate removal; document how a stored allowlist, environment list, and repeated --allow-env flags combine.
  • Provide a local CLI interface for inspecting the effective configuration and source file, setting a key, and removing an override, e.g. JarvisClient config show, JarvisClient config path, JarvisClient config set machine-name "Home Desktop", and JarvisClient config unset machine-name. These commands operate without OAuth login or a connected server. Also support a temporary --machine-name startup override.
  • Register the resolved machine name at every client connection or reconnection. Changes to its persisted value appear on the next registration; they must not create a second device or alter conversation device selections. Preserve multiclient routing by UUID even when names are duplicated.
  • Handle absent config by using current defaults. Reject invalid JSON, unsupported schema versions, invalid values, and unsafe or unreadable configuration with an actionable local error. Never silently switch from a requested restrictive trust configuration to a more permissive one. Permit manual JSON editing.
  • Write configuration atomically using a same-directory temporary file and replacement; preserve unrelated well-formed fields when changing one key. Protect user configuration with appropriate OS file permissions and keep secrets and OAuth refresh tokens out of plain configuration. Do not provide an agent-accessible remote MCP settings mutation command.

Implementation slices

1. Location, schema, and persistence

Implement the platform directory resolver and typed, validated, versioned JSON loader/writer. Add tests for Linux XDG overrides/defaults, Windows and macOS directories, absent/malformed/unsupported files, value validation, atomic replacement, and preservation of existing device identity.

Accept: Two client executables launched under the same OS user resolve the same config file independently of their binary paths; corrupt configuration never silently changes security posture.

2. Startup resolution and registration

Integrate stored values with existing startup defaults, CLI arguments, and environment settings. Add --machine-name. Register the resolved name while retaining the same UUID. Test precedence, allowlist combination, reconnects, renamed devices, duplicate labels, and launch from different directories.

Accept: A saved machine name and workspace are applied at startup, CLI values can temporarily override them, and device routing remains stable.

3. Local config commands and safe edits

Implement config path/show/set/unset with documented key names and noninteractive operation, including updates to numeric, list, and enum settings. Test round trips, atomicity, unknown/invalid keys, restricted file access, and read-only inspection without authentication.

Accept: A user can rename the registered machine persistently without editing files manually, and a later client restart uses that choice.

4. TUI settings screen

Add an interactive Settings screen to the existing ConsoleTui, entered with g from the activity view. The current activity view already uses s for status filtering, so keep that shortcut unchanged. Add the new shortcut to the displayed help text and use the existing mode-specific keyboard handling and rendering.

  • Display all supported client settings: friendly machine name, workspace directory, trust level, allowed environment variables, and maximum import size. Show the location of the shared config.json, effective values, configured values, and defaults. Clearly mark settings currently overridden by startup CLI/environment values.
  • Support keyboard-only navigation and editing: Up/Down select a field, Enter opens a field-appropriate editor, Enter confirms the field, Escape cancels an edit, s saves the pending changes atomically, and Escape from the screen discards unsaved changes and returns to activity. Provide a visible way to unset a configured field and restore its default (e.g. u on the selected field). Offer simple validation errors in the screen without losing pending edits.
  • Use the same validated configuration service as config set/unset; no second settings store, TUI-only state file, or direct JSON writes from the rendering layer. Treat edits as staged until Save and report success/failure accurately.
  • Changing trust to full requires an explicit local confirmation. Show warnings for sensitive environment-variable allowlist changes. Never treat configuration changes as remote agent approvals or expose settings editing through MCP.
  • Show which changes are effective immediately and which require the client to restart or reconnect. A saved machineName is used at next registration without changing device ID; runtime options such as workspace, trust, and import limits should either be reapplied safely to the running runtime or clearly marked restart required. Do not silently show stored values as active when startup overrides are in force.
  • Keep the activity log and pending permission requests functional while Settings is open. Show a pending-permissions indicator and allow the user to reach permission review without losing staged edits. The screen must work with disconnected clients and must never require OAuth for local settings edits.
  • Handle narrow terminals, long paths, empty fields, Unicode machine names, resize/redraw, concurrent external config edits, and I/O failures without corrupting configuration or crashing the input loop. Detect stale edits rather than silently overwriting an independently changed file.

Tests: TUI mode transitions and key handling, field editing/cancel/save/reset, data validation, trust-escalation confirmation, startup override badges, permission prompt access, successful/failed persistence, external-edit conflicts, disconnected operation, and terminal resize. Exercise real startup/restart behavior with a TUI-set machine name and workspace.

Accept: A user can open the TUI, edit the machine name and other persisted settings, save them, and see those values on the next client launch/registration; TUI, CLI, and hand-edited JSON remain consistent.

5. Documentation and end-to-end verification

Document paths, schema, examples, precedence, security-sensitive settings, TUI navigation/editing, and migration from startup flags in README/client help. Cover existing client update/restart behavior and verify that replacing or moving the binary does not change configuration or identity. Run focused client tests and the full Jarvis test suite; commit each verified slice independently.

Accept: Linux, Windows, and macOS path/serialization tests pass; manual multiclient registration and self-update checks preserve existing identity and selection.
