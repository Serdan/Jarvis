Runpod GPU benchmark pod lifecycle and cost guard

Status: Open. Date: 2026-10-24.

Goal

The always-on Jarvis server owns the cost-sensitive Runpod GPU pod lifecycle. When an authorized benchmark agent acquires an exclusive cloud slot, Jarvis starts the existing pod, restores its environment, and waits for a healthy client. On explicit release, or after a genuinely idle expired lease, Jarvis automatically stops the pod and verifies that billed GPU compute has ceased. Pod shutdown is not a ChatGPT background promise and does not depend on the agent conversation remaining open.

Operational model

Keep a user-authorized, single exclusive GPU lease per configured pod. Track Stopped, Starting, Restoring, Ready, Busy, Draining, Stopping and Unknown as observable states, with durable journal and monotonically increasing generation. Successful GET of the Runpod resource, not a disconnected Jarvis client alone, determines remote pod state.

Acquisition is explicit and cost-affecting: atomically reserve the slot, call Runpod START if stopped, bound startup and restore time, resolve dynamic SSH endpoint safely, run the /workspace restore entrypoint, and confirm the Jarvis client has registered/reconnected before admitting GPU work. Concurrent acquisitions for the same pod must not double-start or grant overlapping leases.

Release is explicit: mark the lease draining, refuse to stop while any Jarvis job is still running on that cloud device across ALL projects, then send Runpod STOP and poll for a verified stopped state. In ordinary operation allow no more than 60 seconds between all jobs finishing and issuing the stop. Do not interpret a temporarily empty per-project ListJobs query as proof of idleness.

An always-on watchdog independently checks leases and job inventory every minute. A lease must be renewed/heartbeated by its owner; short gaps between benchmark jobs are protected by its unexpired lease, not by keeping the pod alive forever. After an unrenewed lease expires (default 10 minutes) and no jobs remain, stop the pod. After client disconnect with unknown job state, use the configured conservative recovery grace and a separate hard upper bound on billed uptime; log a cost-risk warning, and never silently kill a job merely because its client's transport disconnected. Make thresholds configurable; default to cost minimization. Explicit release plus drained jobs should stop promptly regardless of the full idle expiry.

A failed stop, timed-out start, ambiguous pod state, invalid credentials, or unexpected remote workload produces durable diagnostics/alerts. A failed start still must have an automatic later stop deadline; no start path may create an unbounded paid idle session. Restart only on explicit new acquisition, never automatically in response to the expected Jarvis disconnect caused by a successful stop.

Authorization and secrets

Store a dedicated Runpod API token only in the always-on Jarvis server secret store or protected environment variables; never in Git, task JSON, Jarvis client arguments, logs, webhook URLs, prompts or task descriptions. Restrict pod ID to an administrator-configured allowlist; verify exact identity before every mutation. Enforce authenticated, user-scoped tool permissions for acquire/start/release/stop; expose read-only status separately. Redact sensitive API response fields; use REST v2 Authorization Bearer header. Do not reuse the ephemeral pod-scoped token as a permanent account credential.

Testable implementation slices

1. Provider adapter and status

Implement a Runpod REST v2 client and typed, redacted status model for the allowlisted pod. Test 200/202/204 responses, RUNNING/EXITED/initializing, retryable 429/5xx/network errors, unauthorized responses, timeouts, unknown data, exact pod ID, and that no API path can DELETE or terminate. Accept: provider mocks exercise start/stop/status without network or credentials.

2. Persistent lease and watchdog

Implement a durable single-owner, generation-checked lease, renewal, drain, stop-on-release, idle-expiry and restart-safe watchdog using the always-on server's persistence. Account for active jobs across all cloud projects and for an agent thinking between jobs. Inject clock/job inventory/provider fakes. Test simultaneous agents, active jobs, client disconnects, provider outage, expiry, repeated STOP and server restart. Accept: exactly one owner gets the slot; release or genuine expiry stops unused GPU within bounded delay while an active job is protected.

3. Resume and environment readiness

Start the existing stopped pod on explicit acquisition, bound start time, resolve changed SSH host/port/host key securely, invoke the existing persistent /workspace/Wayfold-toolchain/restore.sh, verify .NET, local BGEE cache, nine-source city and stable client registration, and only then mark Ready. Test partial boot, missing tmux, missing SDK/volume, changed endpoint, permission failure, no duplicate client and an orphaned START rollback/stop.

4. Jarvis commands and agent contract

Expose authorized, discoverable Jarvis commands for GetBenchmarkHostStatus, AcquireBenchmarkHost, RenewBenchmarkHost and ReleaseBenchmarkHost. Return lease identity, expiry, pod state, cost/uptime metadata, next safe action, and stop confirmation; never return secrets. Agents must acquire before executing cloud jobs, renew before expiration, and always release after final checkpoint or failure. Unexpected agent loss is handled by watchdog independently. Render stopped cloud clients as intentionally offline, not a reason to auto-start.

5. Deployment and end-to-end acceptance

Deploy watcher on the always-on Jarvis service (NOT on the billable Runpod pod and not solely on the user's home computer). Provision an account key out-of-band into server protected configuration, update server safely, and test real cycle with user permission: stopped->start->restore->healthy Jarvis->one focused headless probe->release->verified EXITED; verify all original /workspace files and frozen evidence after reboot. Repeat with crashed agent and simultaneous start attempts. Record actual GPU billing end/time while stopped, note continuing storage charges. Do not deploy a start trigger or keep the pod running to test until authentication and controls are ready.

Completion criteria

Jarvis reports STOPPED with verified provider evidence when no GPU lease is active, and the next legitimate benchmark resumes the same preserved dataset without manual GPU cleanup. Stop-on-release and an autonomous deadline are both enforced by server-side code. No competing cloud jobs, accidental Pod deletion, leaked credentials, unnecessary restart, or unbounded paid idle are possible in normal and error paths.
