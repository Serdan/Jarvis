Reliable task-description limits and retrieval

Status: Open. Date: 2026-10-25.

Goal

Allow human-readable, Git-tracked task descriptions up to 1 MiB (1,048,576 UTF-8 bytes) to be created, attached, and read reliably. A response must never present truncated task content as though it were complete. Give agents a way to retrieve the entire supported description even when it cannot fit in one MCP response. Keep canonical task descriptions and task state in source control as defined by the Git-backed worktree/task specification.

Current behavior and integration points

Existing AttachWorkTask and GetWorkTask resolve the committed task description through ClientShell.taskContentAt, which invokes git show <commit>:<taskPath>. The common Git wrapper uses runProcess's default 64 KiB maximum output. Although RunCommandResult.Truncated is available, taskContentAt currently accepts StdOut without checking it. Independently, Client/SignalR/Client.fs enforces AgentProtocol.maxResponseBytes of 900 KiB for ordinary command responses, including instruction documents. The planned Git-backed task APIs are specified in docs/GitWorktreesAndTasks.md and docs/tasks/2026-10-23-worktrees-and-tasks.md; apply the same content-size and completeness contract to their GetTask/CreateTask/UpdateTask operations as they are implemented.

Content limits and response contract

  • Accepted description: maximum 1,048,576 bytes for the complete committed task-description blob. Measure Git blob bytes, not .NET character count or encoded JSON response size. UTF-8 HTML/Markdown must decode fully; chunk boundaries must not split a Unicode scalar value.
  • Oversized description: return a typed, actionable validation error with task ID/path, actual size, and allowed size. Detect size before attempting to materialize or return the full content. Attach/create/update paths must refuse the oversized content before mutating task state or committing task files.
  • Complete vs. deferred content: a successful full-content response means the entire description was returned. If the content would exceed the safe response budget, return task metadata plus an explicit content available separately status and a stable content reference, never a partial string masquerading as the full task. Differentiate missing description, deferred content, invalid/oversized content, and actual read failure.
  • Chunked content: expose an explicit bounded read operation for committed task text, using a stable source revision (commit and blob identity) and byte offset/cursor. Each response includes the source identity, requested/returned offset, UTF-8 byte count, total byte count, next offset or completion marker, and content. Reassembling all chunks must reproduce the exact decoded description. Reject invalid ranges and stale/mismatched source revisions explicitly.
  • Response budget: choose a conservative fixed maximum chunk payload below the 900 KiB ordinary response ceiling, allowing for JSON escaping, metadata, instruction injection, and serialization overhead. Verify the fully serialized envelope, including instructions, respects the existing protocol response limit. Do not raise that global limit as the workaround.
  • Small descriptions: preserve the current convenient single-call content path for descriptions that safely fit, and keep metadata/list/checkpoint operations compact. The client should not read or attach a 1 MiB blob merely to list task summaries.
  • Correct authority: read immutable committed blob content, not uncommitted working-tree edits. Honor the selected, Git-verified project/worktree and repository path confinement. A task's commit/blob identity must remain stable throughout a paged read, even if another branch or worktree is updated.
  • Diagnostics: never ignore process exit codes, Git output truncation flags, malformed UTF-8, a missing blob, or output size discrepancies. Surface a distinct error rather than returning partial task data or silently replacing it with empty content.

Implementation slices

1. Size-aware committed-description retrieval

Introduce a dedicated Git blob-reading service for task descriptions. Determine committed blob size before retrieval (for example, by git cat-file -s on a verified commit/path), enforce the 1 MiB ceiling, read with an explicit sufficient output bound, check process exit/truncation, and validate complete UTF-8. Reuse it from existing taskContentAt and the future canonical task read path.

Tests: small HTML; descriptions at 64 KiB−1, 64 KiB, and 64 KiB+1; exactly 1,048,576 bytes; 1,048,577 bytes; multibyte UTF-8; malformed blob; nonexistent commit/path; injected Git failure; truncation and byte-count mismatch. Use disposable Git repositories.

Accept: committed descriptions above 64 KiB are read fully and byte-perfectly; descriptions above 1 MiB yield an explicit error; no successful read can contain silently truncated data.

2. Stable, bounded content pagination

Add a task-content read contract, reachable through client protocol and MCP, that pages content from a known committed task revision. A content-bearing GetWorkTask/AttachWorkTask result embeds content only when it fits the response allowance; otherwise it returns metadata plus the stable source locator and tells the caller how to fetch the remainder. Integrate equivalent behavior with the planned GetTask API. Keep existing callers of short descriptions working unchanged.

Tests: one-chunk and multi-chunk reads; reconstruct a 1 MiB description exactly; UTF-8 character across a requested byte boundary; empty content and EOF; invalid cursor; repeated/overlapping pages; source revision changes between requests; large JSON-escaped text and instruction documents that approach the 900 KiB response budget.

Accept: the complete supported description is always recoverable through finite, bounded requests without exceeding the MCP response limit.

3. Validation across task lifecycle commands

Apply the same limit and explicit completeness semantics to AttachWorkTask, GetWorkTask, and task creation/updates in the canonical Git-backed task workstream. Validate source size and expected revision before any task-state mutation or task-file commit. Include size/content availability in returned task metadata while leaving list/checkpoint results concise. Preserve existing task ID and path validation, Git-backed authority, and worktree isolation.

Tests: attach an exact-limit task; reject an over-limit attach without a new local checkpoint; retrieve a short legacy task; update an existing task across the size boundary; two agents reading different revisions concurrently; ensure listing and checkpoint updates do not implicitly fetch large content.

Accept: every task operation gives a consistent, testable answer about existence, revision, size, and content completeness, without partial state changes on rejection.

4. End-to-end tests and documentation

Document the 1 MiB description limit, the distinction from the 900 KiB response limit, content pagination, explicit errors, and behavior for existing tasks. Extend client, protocol/serialization, and MCP tests; run the full client and server suites with a real disposable Git repository. Add a regression fixture larger than 64 KiB that would previously have returned incomplete text.

Tests: full agent-facing attach/read/reassemble flow; error formatting for oversized and corrupt descriptions; task worktree/revision stability; no new truncation in small-task responses; full suite and solution build.

Accept: fresh agents can recover the entire description of any valid task up to 1 MiB with unambiguous completion semantics; no route can silently truncate it.
