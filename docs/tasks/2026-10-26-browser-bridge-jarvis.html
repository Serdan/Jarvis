Local browser bridge and MCP command routing

Scope: Jarvis-side foundation in Jarvis::browser-bridge, branch feature/browser-bridge. Implement the .NET client, shared protocol, MCP surface, policy, and test harness. Do not implement a browser extension in this task, merge to main, or deploy.

Goal

Let an authenticated ChatGPT/Jarvis session inspect the tabs that the local user has explicitly shared with Jarvis and execute JavaScript in one selected shared tab. The path is MCP caller → existing authenticated Jarvis server/SignalR routing → selected JarvisClient → local loopback WebSocket → paired browser-extension client. The extension will be implemented separately; complete this task against a realistic simulated extension.

Existing integration points

Follow existing F# conventions: Common/Messages/AgentCommand.fs for command/DTO/capability definitions; Server/McpTools.fs for MCP endpoints, scopes and per-request device routing; Client/SignalR/Client.fs for dispatch/audit and bounded response serialization; Client/Modules/PermissionPolicy.fs for local command approval; Client/Program.fs and runtime for lifecycle; Client/Modules/ClientConfig.fs for OS-user-level settings. Existing server → client routing already handles request correlation. Browser access must be device-local and independent of the project root, while preserving existing device selection and concurrent-agent isolation.

MVP command surface

  • BrowserListTabs(deviceId?): return only currently shared/authorized tabs exposed by the paired extension, with opaque browser-connection/tab handles, title, URL/origin and grant state. Never enumerate or transmit unrelated browser tabs.
  • BrowserExecuteJs(tabHandle, code, deviceId?, timeoutMs?): run bounded caller-provided JavaScript in one explicitly shared tab and return a JSON-compatible result, console-independent execution errors, and useful timing/correlation metadata. Default to an isolated execution world, allowing DOM reads/changes; if a page-main-world option is later supported it must be explicit and independently reviewed. This tool is powerful and can act on the user's authenticated pages.
  • DOM inspection is possible with BrowserExecuteJs (e.g. document.documentElement.outerHTML with output limits). A dedicated DOM/screenshot/wait/navigation API and browser extension UI are separate follow-on work.

A tab handle is scoped to an authenticated client device, a specific paired extension connection, and the tab authorization generation. Do not store a global “selected tab” in server process state. Stale handles must fail, not silently retarget another tab.

Bridge protocol and lifecycle

  • Host a configurable, disabled-by-default loopback-only WebSocket endpoint in JarvisClient (127.0.0.1, never 0.0.0.0; choose a configurable default port with collision diagnostics). Do not expose the bridge from the public Jarvis server.
  • Specify and implement a versioned JSON envelope: hello/pair, tabs/tabGranted/tabRevoked, executeJs, result, error, cancel and ping/pong as appropriate. Include request ID, protocol version, extension connection ID, tab/grant ID, origin, operation, payload, and structured status/error. Document exact schema and provide runnable mock-extension fixtures.
  • The extension initiates the WebSocket connection to JarvisClient. JarvisClient sends a request frame, correlates the result on that same connection, then returns it over the existing SignalR response path. Handle concurrent calls, duplicate/out-of-order replies, disconnect/reconnect, client shutdown, cancellation, and timeouts without cross-request responses or leaked pending tasks.
  • Use bounded frames, code size and returned JSON/text limits; enforce the existing MCP response ceiling. Establish specific defaults in the implementation documentation (suggest 64 KiB input script, 256 KiB result, 15 s default timeout, 30 s hard timeout, and a small in-flight cap), and reject over-limit requests/responses explicitly rather than truncating silently.

Local pairing, tab consent, and authorization

  • Do not trust a localhost WebSocket connection merely because it came from localhost: ordinary websites and local processes may reach loopback. Validate the extension's expected Origin and perform an explicit user-initiated pairing using a high-entropy per-installation secret or one-time challenge. Keep credentials out of URLs, browser page scripts, command responses, persistent activity logs, and source control. Offer a local CLI/TUI pairing/disable/revoke path suitable for the future extension.
  • Pairing only authenticates the extension. A separate explicit user gesture in that extension must grant Jarvis access to a tab; extension-side enforcement is required on every operation. Reject restricted URLs/schemes and incognito by default; revoke authorization on tab close, privileged/restricted navigation, and origin change; clear all live grants on extension disconnect or browser restart. Do not assume a browser-reported tab ID is permanent or globally unique.
  • Define scoped MCP authorization for browser-read discovery versus arbitrary script execution; do not accidentally classify arbitrary JS as ReadOnly or as ordinary workspace file access. Reuse local Jarvis permission policy (including trust behavior) but require extension pairing and tab-grant checks regardless of trust mode. Document the Auth0 scope/configuration changes if a new browser scope is chosen, and test denial at both server and client boundaries.
  • Return typed, actionable errors for: bridge disabled, browser not connected, not paired, tab not shared, stale tab handle/origin mismatch, command denied, execution exception, invalid result, timeout, canceled request and oversized payload. Audit operation metadata (device, tab handle/origin, duration, success/error) without storing source JavaScript, DOM content, returned page data, or pairing credentials.

Implementation sequence

  1. Define the protocol, handles, DTOs, permission classifications and stable error contract; document the extension-facing wire contract in docs/.
  2. Implement JarvisClient loopback listener, pairing lifecycle and connection registry, authorization-aware tab catalog, request correlation, bounds, and shutdown handling. Make the transport testable without a browser.
  3. Integrate shared AgentCommand union/capabilities, client dispatch and audit, MCP endpoints, device routing, scope validation, local policy, and user-level browser bridge configuration.
  4. Build an in-process simulated browser-extension WebSocket client for end-to-end tests, including fake DOM/script results and adverse network events. Update README/privacy/security documentation and command catalog.

Acceptance tests

  • With a simulated extension paired and one tab explicitly granted, an MCP-facing browser-list call finds only that tab, and execute-JS returns the exact correlated JSON result through existing server/client routing.
  • Without bridge enablement, pairing, or tab grant, no page data or script execution is possible. A hostile WebSocket Origin, incorrect token, and unauthenticated MCP caller are rejected. A full-trust client does not bypass extension consent.
  • Two concurrent requests/tabs and two Jarvis devices do not leak or swap replies. Out-of-order responses, duplicate request IDs, mid-request disconnect, tab navigation/revocation, restart, timeout, and cancellation fail closed and release resources.
  • Run focused F# client/protocol/server tests and the normal solution build; capture meaningful success/failure evidence in a repository-backed task checkpoint. The headless fixture must cover real local WebSocket I/O, not merely unit-test helper functions.

Out of scope / handoff

The Chrome/Chromium extension, its UI, JavaScript execution implementation, and Chrome permission/userScripts details are a follow-on task. This Jarvis task must provide a documented, versioned interface and mock endpoint sufficient for independent extension development. No deployment, server restart, main-branch merge, CDP support, arbitrary tab enumeration, or unattended all-tabs access is authorized here.
