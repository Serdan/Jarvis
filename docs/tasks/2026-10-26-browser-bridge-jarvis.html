Local browser bridge and MCP command routing

Scope: Jarvis-side foundation in Jarvis::browser-bridge, branch feature/browser-bridge. Implement the .NET client, shared protocol, MCP surface, policy, and test harness. Do not implement a browser extension in this task, merge to main, or deploy.

Goal

Let an authenticated ChatGPT/Jarvis session inspect the tabs that the local user has explicitly shared with Jarvis and execute JavaScript from an ordinary Jarvis project file in one selected shared tab. An agent supplies a project identifier and project-relative script path; files are not registered with Jarvis and can be managed in Git normally. The path is MCP caller → existing authenticated Jarvis server/SignalR routing → selected JarvisClient → local loopback WebSocket → paired browser-extension client. The extension will be implemented separately; complete this task against a realistic simulated extension.

Existing integration points

Follow existing F# conventions: Common/Messages/AgentCommand.fs for command/DTO/capability definitions; Server/McpTools.fs for MCP endpoints, scopes and per-request device routing; Client/SignalR/Client.fs for dispatch/audit and bounded response serialization; Client/Modules/PermissionPolicy.fs for local command approval; Client/Program.fs and runtime for lifecycle; Client/Modules/ClientConfig.fs for OS-user-level settings. Existing server → client routing already handles request correlation. Browser access must be device-local and independent of the project root, while preserving existing device selection and concurrent-agent isolation.

MVP command surface

  • BrowserListTabs(deviceId?): return only currently shared/authorized tabs exposed by the paired extension, with opaque browser-connection/tab handles, title, URL/origin and grant state. Never enumerate or transmit unrelated browser tabs.
  • BrowserExecuteFile(projectName, scriptPath, tabHandle, deviceId?, args?, timeoutMs?): the primary execution tool. Take a project-relative path to a .js file in any normal Jarvis project, including a Git worktree selector (for example Userscripts and browser/chatgpt/sendMessage.js). The client reads the script at invocation time, sends its source plus optional JSON arguments to the paired extension, executes it in the explicitly shared tab, and returns a bounded JSON-compatible result. projectName, scriptPath and tabHandle are the only required inputs; scripts need no separate registration or special directory.
  • BrowserExecuteJs(tabHandle, code, deviceId?, timeoutMs?): optional direct evaluation for diagnostics and exploratory DOM inspection; it uses exactly the same authorization, bounds and result contract as file execution. Default to an isolated execution world, allowing DOM reads/changes; a page-main-world mode requires separate review. Both operations are privileged because they may act on authenticated pages.
  • DOM inspection is possible through either execution operation (e.g. document.documentElement.outerHTML with output limits). Dedicated DOM/screenshot/wait/navigation APIs and extension UI are separate follow-on work.

File resolution: Resolve scriptPath with existing Jarvis workspace/project confinement and symlink checks. Never accept arbitrary machine-absolute paths, URLs, .. escapes, or paths outside the selected project/worktree. Re-read on every invocation so changes and Git commits take effect immediately. Scripts need not already be committed; Git is the user's choice. Reject absent, unreadable, oversized, non-UTF-8, or non-.js files with typed errors. Browser execution must not become a loophole for accessing files without the ordinary Jarvis read permissions. Pass the script text to the extension, not the filesystem path; the extension has no direct filesystem access.

Script contract: Specify one simple file-level entrypoint in the wire protocol, with optional JSON-serializable args. No pre-registration or permanent injection is required. The client sends the source and arguments in an executeJs request; all stored JavaScript remains in normal project files, and a reload/discarded tab does not retain injected functions. Document repeatable execution and maximum JSON argument/result sizes.

A tab handle is scoped to an authenticated client device, a specific paired extension connection, and the tab authorization generation. Do not store a global “selected tab” in server process state. Stale handles must fail, not silently retarget another tab.

Bridge protocol and lifecycle

  • Host a configurable, disabled-by-default loopback-only WebSocket endpoint in JarvisClient (127.0.0.1, never 0.0.0.0; choose a configurable default port with collision diagnostics). Do not expose the bridge from the public Jarvis server.
  • Specify and implement a versioned JSON envelope, with BrowserExecuteFile resolved to source text by JarvisClient before sending: hello/pair, tabs/tabGranted/tabRevoked, executeJs, result, error, cancel and ping/pong as appropriate. Include request ID, protocol version, extension connection ID, tab/grant ID, origin, operation, payload, and structured status/error. Document exact schema and provide runnable mock-extension fixtures.
  • The extension initiates the WebSocket connection to JarvisClient. JarvisClient sends a request frame, correlates the result on that same connection, then returns it over the existing SignalR response path. Handle concurrent calls, duplicate/out-of-order replies, disconnect/reconnect, client shutdown, cancellation, and timeouts without cross-request responses or leaked pending tasks.
  • Use bounded frames, script file/source code size, JSON argument size and returned JSON/text limits; enforce the existing MCP response ceiling. Establish specific defaults in the implementation documentation (suggest 64 KiB input script, 256 KiB result, 15 s default timeout, 30 s hard timeout, and a small in-flight cap), and reject over-limit requests/responses explicitly rather than truncating silently.

Local pairing, tab consent, and authorization

  • Do not trust a localhost WebSocket connection merely because it came from localhost: ordinary websites and local processes may reach loopback. Validate the extension's expected Origin and perform an explicit user-initiated pairing using a high-entropy per-installation secret or one-time challenge. Keep credentials out of URLs, browser page scripts, command responses, persistent activity logs, and source control. Offer a local CLI/TUI pairing/disable/revoke path suitable for the future extension.
  • Pairing only authenticates the extension. A separate explicit user gesture in that extension must grant Jarvis access to a tab; extension-side enforcement is required on every operation. Reject restricted URLs/schemes and incognito by default; revoke authorization on tab close, privileged/restricted navigation, and origin change; clear all live grants on extension disconnect or browser restart. Do not assume a browser-reported tab ID is permanent or globally unique.
  • Define scoped MCP authorization for browser-read discovery versus arbitrary script execution (whether inline or file-backed), and require appropriate workspace-read authorization when loading files; do not accidentally classify arbitrary JS as ReadOnly or as ordinary workspace file access. Reuse local Jarvis permission policy (including trust behavior) but require extension pairing and tab-grant checks regardless of trust mode. Document the Auth0 scope/configuration changes if a new browser scope is chosen, and test denial at both server and client boundaries.
  • Return typed, actionable errors for: bridge disabled, browser not connected, not paired, tab not shared, stale tab handle/origin mismatch, command denied, execution exception, invalid result, timeout, canceled request and oversized payload. Audit operation metadata (device, tab handle/origin, duration, success/error) without storing source JavaScript, DOM content, returned page data, or pairing credentials.

Implementation sequence

  1. Define the protocol, handles, DTOs, file-backed script entrypoint and args, permission classifications and stable error contract; document the extension-facing wire contract in docs/.
  2. Implement JarvisClient loopback listener, pairing lifecycle and connection registry, authorization-aware tab catalog, request correlation, bounds, and shutdown handling. Make the transport testable without a browser.
  3. Integrate shared AgentCommand union/capabilities, client dispatch and audit, MCP endpoints, device routing, scope validation, local policy, existing project/worktree file resolution, and user-level browser bridge configuration.
  4. Build an in-process simulated browser-extension WebSocket client for end-to-end tests, including fake DOM/script results and adverse network events. Update README/privacy/security documentation and command catalog.

Acceptance tests

  • With a simulated extension paired and one tab explicitly granted, an MCP-facing browser-list call finds only that tab, and BrowserExecuteFile loads a JavaScript file from a normal project and returns the exact correlated JSON result through existing server/client routing. The fixture proves the extension receives source plus args, not a local path.
  • Without bridge enablement, pairing, or tab grant, no page data or script execution is possible. A hostile WebSocket Origin, incorrect token, and unauthenticated MCP caller are rejected. A full-trust client does not bypass extension consent.
  • File-backed tests cover an existing ordinary project, a Git-registered worktree, a changed script picked up on its next invocation, missing file, path traversal, symlink escape, invalid encoding, excessive source/args length, and read-permission denial. Two concurrent requests/tabs and two Jarvis devices do not leak or swap replies. Out-of-order responses, duplicate request IDs, mid-request disconnect, tab navigation/revocation, restart, timeout, and cancellation fail closed and release resources.
  • Run focused F# client/protocol/server tests and the normal solution build; capture meaningful success/failure evidence in a repository-backed task checkpoint. The headless fixture must cover real local WebSocket I/O, not merely unit-test helper functions.

Out of scope / handoff

The Chrome/Chromium extension, its UI, JavaScript execution implementation, and Chrome permission/userScripts details are a follow-on task. Jarvis has no ChatGPT-specific knowledge, browser-script registry, script-specific storage, or special browser-automation project. This Jarvis task must provide a documented, versioned interface and mock endpoint sufficient for independent extension development. No deployment, server restart, main-branch merge, CDP support, arbitrary tab enumeration, or unattended all-tabs access is authorized here.
