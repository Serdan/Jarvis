## Storage contract

The existing process-job registry remains authoritative for full requests, receipts and output. The ordinary 100 completed job / 7-day expiration policy and 64 active supervisor limit remain unchanged. A separate bounded compact reservation store under the same client-local registry holds up to 64 creation operations, each covering up to 32 distinct original job IDs. Each record is capped at 256 KiB (16 MiB committed store maximum, plus bounded atomic staging). The compact proof is not returned as a reconstructed ordinary GetJobResult receipt.

All reservation reads, writes, release and production pruning are serialized by the existing stable cross-process admission lock. A reservation is one atomic record keyed by the exact canonical Create operation UUID, with the logical project, initiating actor, project/ledger GUID and epoch. Its request identity includes the original start time and SHA-256 digest of the complete serialized request. Repeating the exact scope and canonicalized set of job IDs is idempotent; conflicting reuse, wrong owner/project, missing evidence, malformed storage and capacity exhaustion fail closed. Multiple conditions for one job share the same reservation within a Create; independent Creates have independent reservations. An exact matching compact proof from another active reservation can satisfy a subsequent acquisition for the same binding, but an absent unreserved original is not reconstructed.

When a reserved terminal job is due for ordinary pruning, the registry derives the same bounded outcome, completion time and SHA-256 of the matching supervisor receipt that the existing job wake uses. It atomically publishes all linked compact records before deleting any ordinary output. Partial failure leaves the ordinary receipt intact; a subsequent retry is idempotent. Reserved unknown jobs do not generate terminal evidence. Corruption or failed compact persistence propagates to admission rather than silently deleting the only proof. The claim fence and existing request/receipt publication remain unchanged. This inherits the existing atomic-file durability assumptions, not a new disk-loss guarantee.
