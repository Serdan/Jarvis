## Compatible registration contract

The legacy Challenge schema has a human/agent owner discriminator but no machine-condition field. A narrow versioned codec uses the existing Description field with **exact** `jarvis:job-terminal:v1:<lowercase 32-hex original job ID>`, e.g. `jarvis:job-terminal:v1:0123456789abcdef0123456789abcdef`. OwnerKind is Agent, OwnerAgentId is the job initiator and Challenge issuer, SuggestedAgentId is empty. This reserved exact form is not natural-language evidence. Ordinary conditions retain their existing semantics and persisted format. Creation of a marked condition with a different issuer/owner is rejected; reassigning or splitting the marked condition and generic agent Resolve (even by owner) are rejected. There is no new remote authority, account/Work state, or second job registry.

Use existing Challenge Create and BlockAttempt with the exact original job ID. The post-commit registration edge must notify the job host. If terminal evidence wins before BlockAttempt, existing canonical logic rejects waiting on an all-satisfied dependency; the caller continues rather than parking on an already-completed job. ## Evidence and reconciliation

The adapter reads the accepted supervisor's registry using DurableJobs.entries/readRequest/observe. It reopens the immutable original request and checks exact job ID, canonical project selector, authenticated original initiating actor, challenge issuer/owner and condition marker. It never uses a notification payload as terminal evidence, never fabricates success from process death, and does not launch or cancel anything. Only the existing observer's Terminal case with a completion timestamp is used, including nonzero exit, cancellation, and failed-to-start; Running, RecoveryUnknown, missing/evicted handle, or foreign identity never satisfy the condition.

The evidence stores the job identity, project, actor, original start/completion timestamps, outcome and SHA-256 of the serialized authoritative terminal receipt. The job's original result is still the place to recover buffered output. A bounded failure-to-start message is only a summary; receipt hash retains the identity of the full receipt.

The resolution operation ID is deterministic over the bound project/ledger/epoch, challenge, condition, exact challenge CAS version and job ID. The internal resolve path calls the same LegacyDirectWriterFence/ChallengeWorkflow transaction (same operation type and canonical event) as ordinary resolution; no side effect outside the ledger is repeated. A retry on unchanged canonical version uses the same operation UUID and evidence; a committed condition is not resolved again. Independent sibling conditions are preserved. The existing transaction performs dependent requeue, assignment generation, eligible-when-occupied behavior and Ready transition; the adapter never directly changes an agent state. A fresh committed receipt is delivered as the existing typed ChallengeWriteCommand / OperationResponse.Presented pair to the same Challenge wake adapter. Duplicates do not emit a second hint. A failed hint cannot undo the canonical requeue.

The optional job host coalesces startup, receipt publication, registration and reconnect hints. It installs per-job watchers before reading receipts, watches the root for directory creation/removal, and rescans on watcher error; a new job directory cannot be missed merely because a recursive watcher was not yet installed. Only failed reconciliation has a bounded-backoff retry deadline; a successful idle host does not poll. The durable request/receipt and Git ledger remain authoritative across a host restart; watches and pulses are ephemeral.
