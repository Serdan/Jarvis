### Fixture definition and what it does *not* prove

`Server.Tests/WorkStatefulRolloutAcceptanceContractTests.fs` creates a disposable SQLite file under the OS temp directory with **two distinct project scopes** (`project-alpha`, `project-beta`) sharing an account with maximum capacity 1. It creates the eight B record kinds for each project, duplicate local Work and Stage IDs across projects, synthetic exact source/review/integration SHA values, a stable source-verification UUID, and separate `Prepared` and `Unknown` external-effect states. It verifies persisted per-project scoping, restart, replay of the **same** UUID as history rather than an added transaction, and rejection of changed payload at that UUID. Pure D/graph cases exercise independent Draft→Proposed→Open gates, pinned spec/Lead authorization, required blocker descendants, and optional containment. The existing `WorkSchedulerSqliteTests` use the same disposable-store pattern to prove cap-one competing reservation, role feasibility, blocking priority/FIFO, STOP and effect fences.

**Crucial limit:** fixture SHA, repository identity, and verification receipt are *synthetic test data*, not proofs of an authenticated original Git producer. Physical B V2 provenance storage is not the complete authenticated B1 ingress contract, and a receipt round-trip is not authorization for a new external effect. No real agent dispatch, Git push, credential, scheduler or client is used.
