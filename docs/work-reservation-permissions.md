# Work reservation permissions: default-off contract

This branch adds a narrow, project-ledger-owned reservation authorization seam. It depends on accepted credential admission 8c306e50 / integration d9f5f02c. It does not touch Worker 12's composition/WQ02 writer, switch on the Scheduler, alter legacy Agent handlers, or deploy live routes.

## Delegation and authority

The client module Client/Modules/WorkQueueReservationPermissions.fs stores a current versioned grant and immutable revision history in the same approved Git ledger as WQ02. A trusted authenticated operator adapter (not a model-selected role) would invoke its INTERNAL reviseAt method (Planning/non-source) or reviseWithSourceAt (source checkout explicitly bound). That method receives an operator actor string for audit attribution, but this string is NOT itself OAuth proof and must never become a public self-granting endpoint. The winning CAS resolves original credentialed project admission, canonical project, pinned credited/claimed Work, its stage generation, current launch and account identity; the grant derives its upper-bound operation families from Work kind, not from the agent label. Future host integration must validate the operator approval and trusted clock before invoking it.

Families are ContextRead, Implementation, Prerequisite, Review, Integration, SchedulingAdmin. SchedulingAdmin is intentionally not grantable through this module. Integration remains gated on canonical IntegrationAuthorized and original source lineage; an ordinary Worker cannot become an integrator by claiming a Lead role. Source Implementation/Integration grants additionally require the trusted host to supply the physically registered, detached, clean WQ03 checkout for the original Work/launch/next-or-current claim generation. Other project IDs can be allowed for CONTEXT READS only. Writes require the exact own project, Work, ref, worktree, granted family and active launch. The immutable grant records revision, expiry, approval, operator actor, stage/launch/account identity, and explicit revocation. A revision updates the current pointer and appends immutable history in a single Git CAS.

The source grant uses schema v2 and distinguishes source ReachableRef (optional on first-generation Implementation), immutable continuation SHA (or first pinned base), lineage/repository ID, exact generation-scoped WQ03 worktree and absolute checkout path from the APPROVED integration TargetRef. The original WQ03 checkout verifier independently checks registered linked/detached checkout, clean status, HEAD SHA, approved repository/remote and continuation ref. A same-name checkout in another clone cannot substitute for the approved physical checkout path. Source operations require authorizeWithSourceAt/checkSourceAt with a real checkout; the string-only checkAt rejects source-stage Implementation/Integration. Revocation and Planning grants do not require a source checkout. Source verification is local and must be repeated by the future trusted host at the point of each source operation; it is not a Git-ledger transaction over mutable filesystem state.

The authorization method compares the bearer SHA256 with the same immutable original credential verifier using constant-time comparison, resolves a registered non-stopped launch, and rejects stale grant revision, launch version, lease generation, Work stage generation, expiry, revocation and foreign source scopes. Denials do not expose credentials.

## Practical blockers

Small directly necessary fixes within assigned engineering scope need no new Work. Significant or outside-delegation prerequisites must be recorded as an immutable evidence-backed proposal by an existing, authenticated Prerequisite-family reservation; its proposal refers to owning Work, launch, grant revision, graph version, suggested new Work ID and evidence digest. Status is ProposedOnlyNotRunnable. It intentionally does NOT publish a work stage, modify graph edges, or make a queue credit available. Lead/operator must route the proposal through canonical Work creation and the independently reviewed WQ04 graph/WQ02 writer to atomically create/link the hard prerequisite before scheduling. This avoids recursively taking unrelated backlog or silently expanding the existing assignment.

## Mechanically enforced vs advisory

Only the opt-in INTERNAL claimFixtureAt, claimSourceFixtureAt and checkpointFixtureAt methods currently use the winning Git transaction's authorization callback, and an INTERNAL evidence-backed prerequisite proposal uses its own Git CAS. checkAt is an authenticated preflight, not authorization for executing an arbitrary process. Production WorkQueueToolFacade transitions remain non-applied RejectedMissingBinding; there is no public Work-native mutation wiring, Scheduler activation, live role elevation route, or source-job authorization. Additional integration of each actual tool family with authenticated credentials and in-CAS checks is required before cutover.

Engineering boundaries and the instruction to propose substantial blockers remain partly advisory. These logical grants do not sandbox files, Git worktrees or unrestricted shell commands at the OS layer. Existing authenticated operator repair/debug actions and old Agent compatibility remain unchanged; no server-local durable permission database is introduced.

## Verification

Focused .NET 11 Release tests live in Client.Tests/WorkQueueReservationPermissionsTests.fs and use two real independent Git clones and a disposable bare remote. They cover pinned approval, lost stale version, read versus edit across projects, disallowed integration/scheduling, credential borrowing, source-worktree mismatch, grant revision and expiry, revoked scope, wrong lease/launch generation, evidence-backed blocker proposal without queue changes, and CAS claim/checkpoint. The new source fixtures exercise real registered WQ03 Implementation checkouts, original source/target differentiation, source claim generation, two-clone valid and foreign clone paths, valid foreign ref and SHA, denial without host-selected checkout, and cross-clone operation validation. A real WQ03 source-yield/re-claim successor fixture asserts ReachableRef and ContinuationSha from immutable WIP rather than TargetRef, plus stale previous-generation credential rejection. An Integration positive source-stage fixture remains dependent on a genuinely admitted canonical Integration stage with approved source lineage, rather than synthesizing authority by setting IntegrationAuthorized in a test. Integration/source jobs and public binding therefore remain NO-GO. Existing credential and Work tests are separate regressions. No hosted Actions, Codex, Scheduler or production deployment.
