# P1: Terminal release accepts unrelated Git OIDs and never binds proof to the original project fence

**Frozen source:** `5e37133d5f1b7e7c6e13c890b662caf14eafa9c8`. **Original acceptance:** duplicate/foreign/**stale** terminal release denied; current project snapshot and original effect/fence provenance required before releasing conservative Unknown occupancy.

**Source trace:** `Client/Modules/NativeSchedulerAccountReservation.fs:328-369` calls the caller-supplied `INativeDisposableTerminalVerifier.VerifyCurrentTerminal(locator)`, then checks dispatch/reservation/effect/terminal UUIDs, project GUID/ledger/epoch, canonical key and optional provider session equality. For `proof.ProjectHead`, `ProjectTerminalOid` and `ProviderTerminalOid`, the only local checks at lines 363-365 are **40-/64-hex syntax**. There is no equality/verified-ancestry check against `NativeDisposableCoverage.ProjectHeads`, no relationship between proof's project terminal and the persisted `record.ProjectFenceOid`, and no durable provider-session terminal object check at this layer. The verifier receives just four UUIDs, not the persisted project fence/head or provider session, so the account implementation delegates all such correctness to an opaque fixture oracle.

**Concrete positive control demonstrating the gap:** In `Client.Tests/NativeSchedulerRosterPolicyTests.fs:751-809` (`UnknownOccupiesExactlyOneSlotUntilOriginalVerifiedTerminal`), the mock verifier always returns `Ok proof`. The proof's `ProjectHead`, `ProjectTerminalOid` and `ProviderTerminalOid` are all assigned `f.InitialSourceHead` (a Git OID obtained from the **account** fixture clone before the **project** fixture remotes were created at lines 90-118). Thus an unrelated, syntactically valid account Git commit is accepted as both project/provider terminal evidence and releases Unknown occupancy. The test establishes that occupancy is retained until a mock says OK, but does not establish independent current project/provider terminal truth or rejection of stale/unrelated OIDs.

**Impact/boundary:** Public production admission remains disabled, and there is no real provider send. This is a test-scoped authority gap, not a claim of an active provider exploit. However, the source and passing fixture cannot be cited as proving a *trusted terminal* invariant; a misconfigured/incorrect verifier (or later promotion of this entrypoint) can free account capacity on unrelated Git OIDs, permitting double dispatch. The original task explicitly required stale/foreign terminal negatives.

**Proportionate remedy:** Keep production disabled. In the disposable proof contract, require a project/provider terminal verifier tied to the original canonical candidate, persisted project-send fence and verified current project lineage, with a source-bound negative returning a syntactically valid but unrelated/stale Git OID even when `VerifyCurrentTerminal` returns `Ok`. Alternatively, explicitly separate trusted terminal verification into a separately bounded prerequisite and report this phase only as *inert accounting*, not as an independently proved release authority. Do not create a production sender or new root as a review shortcut.
