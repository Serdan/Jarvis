## F01 — P1 blocking: arbitrary producer assertions enter project Git CAS without canonical event proof
- `Client/Modules/WorkQueueGitLedger.fs:903-932` handles a caller-provided `WorkMutation.ProduceEvent` by checking only that `event.ProjectId` matches the ledger binding, then invokes `WorkQueueProducers.applyEvent`. At `:1039-1059`, the post-transition source proof verifies *implementation lineage* only. Planning, frozen review, review correction's verdict, accepted integration, challenge follow-up, and policy resolution do not obtain authoritative task/review/challenge source-event proof in that transaction.
- `Server/WorkQueueProducers.fs:157-244` performs mostly shape checks. `FrozenReviewRequested` accepts any syntactically valid SHA/ref; `AcceptedIntegration` only requires a prerequisite of kind `FrozenReview` and checks neither Accepted verdict nor that review ID/SHA/target matches the claimed accepted review. `TaskRequested` and `ChallengeFollowUp` accept arbitrary source IDs. The `SourceId` is caller-supplied and is the identity input for `workId` (`:87-108`).
- This is observable in `Client.Tests/WorkQueueProducerGitTests.fs:93-105`: the Git-CAS fixture successfully publishes a `FrozenReviewRequested` with a made-up review ID `review-1` and an all-`a` SHA, without any canonical review evidence. A successful CAS therefore does **not** mean a canonical frozen review actually exists.
- **Risk:** the queue can contain fictitious/falsely accepted actionable work and multiple planning/follow-up generations for one real source event. An integration stage can become runnable after completion of an unrelated/non-Accepted review; this crosses the very authority boundary the task promises to preserve. The current code is inert, which mitigates immediate production exposure but does not satisfy the accepted canonical-producer contract.
- **Required:** bind every origin to a specific immutable canonical source event + stage generation, verify exact event provenance/acceptance/lineage/target in the same pinned project/source transaction before publication, and reject forged, stale or already-projected events. Do not treat a typed caller assertion as a source witness. Keep an inert fail-closed gate until that verifier exists; add disposable two-clone negative tests for a fabricated review, non-Accepted integration, mismatched review ID/SHA and duplicated task event.

## F02 — P1 blocking: versioned role demand disagrees with the authoritative project admission/claim logic
- `Server/WorkQueueProducers.fs:274-320,355-410` uses `RoleCatalog.Versions`, `RoleConfiguration.QueueSubscriptions` and `Enabled` to choose demand and rematch historical launch versions.
- But `Server/WorkQueueContracts.fs:428-444` defines the actual `compatible` predicate using **only** `project.Subscriptions.[launch.RoleId]`. It ignores `Launch.RoleVersion`, the pinned historical instructions/subscriptions and the `Enabled` bit. `admitProject` (`:644-654`) and `claimNext` (`:757-775`) call that incompatible predicate.
- `RoleCatalog` is pure caller-held state and has no durable project Git-CAS mutation/read path in this patch (`Client/Modules/WorkQueueGitLedger.fs` adds only `ProduceEvent` and `RemoveHardPrerequisite`).
- **Concrete divergence:** after a role switches from `planning` at v1 to `review` at v2, `selectRoleDemand` can choose v2 review demand while project admission rejects it against stale `project.Subscriptions`; conversely a previously admitted v1 launch can be rematched/claimed against the unversioned v2 map. Disabling a role only affects preflight, not the core claim predicate.
- **Required:** one authoritative, versioned role/subscription source must be pinned and consumed by both role-demand selection and CAS admission/credit reconciliation/claim; old launch versions must retain immutable semantics. Test role-v1/v2 mismatches and disablement through **two Git clones**, not just an in-memory selector.

## F03 — P1 blocking: integration-policy successor is not exactly-once
- `Server/WorkQueueProducers.fs:214-229` admits `IntegrationPolicyResolved(task, oldWork, receipt)` whenever the predecessor integration is completed/authorized/clear. It never tests whether an integration-policy successor for that predecessor+resolution has already been emitted.
- `workId` (`:87-108`) incorporates the caller-controlled `SourceId`, and `Contracts.publishStage` (`Server/WorkQueueContracts.fs:569-595`) deduplicates only the resulting ID. Once the old integration is terminal, `SourceId=\"policy-A\"` and `SourceId=\"policy-B\"` with otherwise identical event, receipt and prerequisites both produce distinct actionable planning generations under sequential valid CAS versions.
- **Risk:** violates the task's explicit F06 condition that gate resolution publish *exactly one* integration-policy producer after prerequisite satisfaction or versioned waiver/replan. Different operation IDs do not solve semantic duplication.
- **Required:** a canonical terminal-resolution event key and durable unique projection receipt/index (or equivalent project-CAS check) that rejects the second logical publication, including two-clone replay/new-operation race tests.

## F04 — P1 coverage limitation: high-water witness is not yet tied to verified source/index contents
- `Server/WorkQueueProducers.fs:135-153` only compares caller-supplied `ProducerHighWater=QueueIndexedThrough`, message/source counters and booleans. It does not derive these from a Git snapshot, index or source-event range, or prove that the queue includes every authoritative event. The project Git mutation does not write a canonical producer event index/cursor.

They show rejection when fabricated numbers disagree, **not** detection when missing/unseen source items exist but asserted numbers match.
- **Required:** obtain source/queue/message high-water and exact coverage from trusted, pinned canonical heads/indexes as one proof, or remain explicitly incomplete and suppress scheduling. Add missing-source/index negative case with equal caller-reported counters. This may be resolved jointly with F01's canonical producer adapter, but should not be reported as proven by current tests.
