# F5 — P2 TUI Save uses stale startup machine name after successful connected-loop re-registration

**Frozen source:** `730c6ce74481155f5c1bc26f3345819cfbbf903b`. **Original obligation:** adjudicated F4 (task spec binding GO seq11280) requires the typed shared settings transaction to report the actual current runtime / registry state and truthful pending status, not a stale startup snapshot. This is a source-trace finding, not a claim that I performed a live multi-save registry test.

**Reproducible control-flow trace:**

1. Start a disposable connected client registered as machine `A`. `Program.runClient` captures `effective.MachineName=A`, then installs its initial running context (`Program.fs:174-213`). The TUI `SetSettingsAccess.Save` closure permanently supplies this captured `effective` to `ClientConfig.applySettingsAt` (`Program.fs:207-213`).
2. Save machine name `B` through TUI, successfully persisting config. The connected loop detects it in `refreshRegisteredMachineName`, calls `register` and on success sets `registeredMachineName=B` and updates `ClientConfig.recordRegisteredMachineName B` (`Program.fs:585-595`).
3. While this same client remains connected and registered as `B`, reopen Settings and save another benign field or no-op. The TUI closure still passes startup `effective.MachineName=A`. `ClientConfig.applySettingsAt` then sets `CurrentRuntime=A` and `RegistryRefreshPending=(A <> B)=true` (`ClientConfig.fs:491-505`).
4. `ConsoleTui.saveSettingsUnsafe` displays **"Device registry name awaits the connected-client check."** whenever this flag is true (`ConsoleTui.fs:1409-1427`), though registration already succeeded. Separately, `tryRunningContext` *does* hold the updated registered name; only the TUI adapter ignores it.

**Impact:** A later successful Save reports a nonexistent pending registry action, and its `CurrentRuntime` value is not the actual registered machine name. This is precisely the settings-experience uncertainty F4 required to eliminate. Remote adapter source is outside W24's lease and is not implicated.

**Bounded candidate remedy:** Before each TUI Save, observe the current locally installed running/registered context for machine name (without accepting any remote-supplied approval or mutating unrelated runtime properties). Preserve startup CLI override precedence and existing CAS/confirmation. Add a two-save isolated connected-loop or deterministic service-level regression: save A→B, observe successful registration B, then save another field and assert `RegistryRefreshPending=false`, `CurrentRuntime.MachineName=B`, and no false pending UI message. No live WSL restart or tool/protocol edits.
