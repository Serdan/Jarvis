# P2 — renderer's transport-budget success can exceed actual BrowserRunInNewTab argument budget

**Original requirement:** defined input bounds and an Operator able to inject the rendered prompt unchanged through the existing BrowserRunInNewTab transport. This concerns a valid but oversized render, not a request for new launch infrastructure.

**Source proof:** `RoleInstructions.fs:508–523` permits a 24,000 UTF-16-unit prompt with up to 65,536 UTF-8 bytes and up to 131,072 escaped bytes. `BrowserBridge.fs:21,447,737` rejects argsJson larger than 65,536 bytes, including the wrapper/metadata. The documented minimal `JSON.stringify({ prompt: rendered.Prompt })` already adds 13 bytes. `ReviewWorkflow.fs:649–650` allows a registered 120-byte Unicode agent ID. A disposable registered ID consisting of 40 copies of U+754C (3 UTF-8 bytes each), template consisting of `{{agentId}}` repeated 546 times followed by `{{projectName}}123456789`, and project name `Jarvis`, gives a valid template and a 21,855-code-unit, 65,535-byte prompt. Default .NET escaped string size is 131,057 bytes (within renderer cap). Minimal JS JSON envelope is 65,548 bytes, over the actual 64 KiB bridge cap even with no optional metadata. This is a mathematical/source counterexample, not a live browser test. It is fail-closed at the bridge, but the explicit renderer returns success for an unusable prompt; optional launcher metadata/JSON escaping can only make the envelope larger.

**Candidate remedy for adjudication:** define the minimal launch-argument encoding and reserve its overhead (and document available metadata budget), or validate the exact composed envelope at the shared non-effecting pre-send boundary before reporting transport readiness. Keep generic BrowserRunInNewTab unchanged; don't relax its safety limit. Add a focused negative boundary case with valid Unicode registered ID and minimal envelope, and an adjacent accepted case. No browser effect needed.
