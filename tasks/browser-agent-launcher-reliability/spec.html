Stabilize Jarvis browser-bridge ChatGPT agent bootstraps after live multi-agent test

Observed 2026-11-15: Lead used the existing user-registered Edge window and browser-scripts/chatgpt/launchAgent.js to launch Workers 1–5 and Reviewer 1 with only role/project/inbox bootstrap. All six ultimately read Jarvis and entered Working. Two concrete reliability failures caused repeated manual handling; do not broaden this into a replacement orchestrator.

Failure A: restored stale composer drafts

A fresh https://chatgpt.com/ agent-created tab sometimes contained an exact previously submitted bootstrap prompt from another just-launched agent. The initial launcher refused with notSubmitted/ExistingDraft. The operator clarified that ChatGPT routinely restores unsubmitted text, and the newly Jarvis-created tab is deliberately disposable. Therefore the launcher should replace the composer text directly with the intended bootstrap prompt, verify it matches, and submit once. Do not implement stale-draft provenance matching as a precondition on these new tabs.

On the same selected home Jarvis device, repeated BrowserListWindows/BrowserListTabs calls sometimes showed registered window main Ready and sometimes an unrelated registration agents in needsReauthorization. Previously opened agent-owned tab registrations could temporarily fail TabNotRegistered or an immediate BrowserOpenTab could fail WindowNotRegistered. A BrowserExecuteFile post-injection attempt once returned OutcomeUnknown: IOException while ChatGPT nonetheless created a new conversation and the target worker entered Working. Source inspection has now identified the server-side single-active-connection takeover as a concrete cause; details below. Independently confirm through a dual-extension regression before declaring all symptoms resolved.

Confirmed bridge root cause and bounded design target

Source inspection on 2026-11-15 identified a concrete defect in Client/Modules/BrowserBridge.fs: Service has one mutable active: Connection option. After every authenticated WebSocket connection, handle aborts the previous active socket and fails all its pending operations with an IOException (outcome unknown), then replaces active. ListWindows, ListTabs, OpenTab, CloseTab, Execute and CaptureDom all consult that single pointer. Meanwhile browser-extension/background.js automatically reconnects after socket closure, so two independently paired browser extension/profile instances can continually displace one another. This directly explains the alternating disjoint main and agents registries, intermittent wrong-socket lookup failures and post-dispatch outcome-unknown I/O error. Do not mistake an independently stale agents registration for authority to reauthorize it.

  • Primary fix: Do not evict a healthy authenticated extension when another connects. Keep authenticated connections separately tracked for their lifetimes; make read-only listings include explicitly registered windows/tabs across those connections, and route each action to the exact connection owning its window or tab registration. The selected owner/connection must remain fixed during each side-effecting request and multi-step launch, even when another instance connects. A disconnect affects only its own operations.
  • Identity and ambiguity: Use authenticated connection-specific ownership, unique opaque registration IDs and generation checks. If aliases/IDs collide across connections, fail closed with explicit ambiguity rather than choosing an arbitrary profile. A window marked needsReauthorization remains unavailable; never migrate to another window or silently grant browser access. Preserve extension origin/pairing and host authorization. Consider bounded connection count and duplicate same-profile reconnect only as needed to preserve correctness; do not create a new global agent/session orchestration layer.
  • Regression tests: Simulate two simultaneous authenticated extensions with disjoint window/tab registries, one Ready and the other requiring reauthorization; verify stable union listings, targeted Open/Execute/Close/CaptureDom and no cross-profile routing, and a second connection arriving during an in-flight action without aborting it. Verify disconnect/ambiguous aliases and exact no-resend semantics. Existing single-extension behavior must remain unchanged.
  • Separate ChatGPT composer issue: A fresh agent-created ChatGPT home tab may restore any unsent text. On that new Jarvis-created tab only, simply replace the composer contents through the normal UI with the correct bootstrap text, verify exact match, and click Send once. Existing unrelated user tabs and established conversations are not targets. Do not require stale-prompt recognition or a persistent prompt-store subsystem; no retry after a possibly dispatched Send.

Required investigation and implementation

  • Reproduce each failure with current app/script under real UI conditions; correlate exact device, connection, extension registration and browser window identities without revealing prompt contents or exposing unregistered tabs. Distinguish legitimate revocation from cross-session lookup errors.
  • Correct the minimum responsible path: make one registered-window selection and tab lifecycle stable within a launch, with fail-closed behavior on genuine revocation; make sequential ChatGPT new-chat bootstraps robust by replacing any restored composer text in a fresh Jarvis-created home tab, without editing existing unrelated user tabs or using private ChatGPT APIs.
  • Preserve one-send-only, exact prompt evidence, no blind retry after a possible Send click, and safe close of only Jarvis-created tabs. On uncertainty, return explicit state for operator/Manager reconciliation; never treat an uncertain submission as failed and automatically resend.
  • Use existing browser bridge, registered windows, project script, and task/agent ownership. No generic new agent manager, backend API automation, persistent conversational transcript capture, or unrelated browser scheduling changes. Challenge Lead before a material expansion.
