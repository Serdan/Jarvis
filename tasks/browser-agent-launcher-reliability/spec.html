Stabilize Jarvis browser-bridge ChatGPT agent bootstraps after live multi-agent test

Observed 2026-11-15: Lead used the existing user-registered Edge window and browser-scripts/chatgpt/launchAgent.js to launch Workers 1–5 and Reviewer 1 with only role/project/inbox bootstrap. All six ultimately read Jarvis and entered Working. Two concrete reliability failures caused repeated manual handling; do not broaden this into a replacement orchestrator.

Failure A: restored stale composer drafts

A fresh https://chatgpt.com/ agent-created tab sometimes contained an exact previously submitted bootstrap prompt from another just-launched agent. The script correctly refused with notSubmitted/ExistingDraft. Lead could only continue by verifying exact match with an earlier Jarvis bootstrap and clearing it through normal contenteditable editor commands before executing the existing one-shot script. Root cause and safe resolution need investigation; a fresh tab does not reliably mean an empty composer.

Failure B: inconsistent registered-window visibility

On the same selected home Jarvis device, repeated BrowserListWindows/BrowserListTabs calls sometimes showed registered window main Ready and sometimes an unrelated registration agents in needsReauthorization. Previously opened agent-owned tab registrations could temporarily fail TabNotRegistered or an immediate BrowserOpenTab could fail WindowNotRegistered. A BrowserExecuteFile post-injection attempt once returned OutcomeUnknown: IOException while ChatGPT nonetheless created a new conversation and the target worker entered Working. Treat this as a bridge/extension identity/routing/lifetime defect until evidence establishes otherwise.

Required investigation and implementation

  • Reproduce each failure with current app/script under real UI conditions; correlate exact device, connection, extension registration and browser window identities without revealing prompt contents or exposing unregistered tabs. Distinguish legitimate revocation from cross-session lookup errors.
  • Correct the minimum responsible path: make one registered-window selection and tab lifecycle stable within a launch, with fail-closed behavior on genuine revocation; make sequential ChatGPT new-chat bootstraps robust to the observed restored draft without overwriting arbitrary user text or using private ChatGPT APIs.
  • Preserve one-send-only, exact prompt evidence, no blind retry after a possible Send click, and safe close of only Jarvis-created tabs. On uncertainty, return explicit state for operator/Manager reconciliation; never treat an uncertain submission as failed and automatically resend.
  • Use existing browser bridge, registered windows, project script, and task/agent ownership. No generic new agent manager, backend API automation, persistent conversational transcript capture, or unrelated browser scheduling changes. Challenge Lead before a material expansion.

Acceptance

  1. Repro and root cause documented separately for A and B; negative cases (unknown draft and revoked window) still fail safely.
  2. Regression tests plus a small live Edge sequence of 3 distinct minimal bootstrap messages against one registered window demonstrate reliable distinct submissions, no duplicates, predictable registration and cleanup; test adverse connection/state flips.
  3. Use .NET 11 Release tests for touched Client/extension code; script compatibility and browser lifecycle tests included. Independently frozen review, exact-commit integration by Lead, no deployment or restart without operator authorization.
