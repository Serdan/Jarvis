Operator clarification — quota sizing and recovery (2026-11-20)

The configured limits are not sacred. Inspect the live database and sidecar sizes, telemetry write rate, and useful retention horizon before choosing new limits. A moderate increase, preferably configurable and documented, is authorized where justified by measurements and host capacity. Merely raising a limit is not an acceptable recovery mechanism.

  • Provide an explicit soft/high-water threshold to trigger bounded cleanup/backpressure and a hard ceiling that prevents new expendable writes. Define a lower recovery watermark to avoid repeated oscillation. An exceeded budget must never permanently lock out cleanup and read-only use.
  • Keep recovery and read paths available under saturation: bounded retention of eligible operations and connection_events; safe WAL checkpoint/truncation and physical reclamation (including compaction when actually needed). Reclamation must be crash-safe, bounded in time and disk headroom, and not tie up normal MCP/SignalR dispatch threads. If physical reclamation cannot run safely, return a precise degraded/maintenance-required reason rather than silently staying wedged.
  • GetConnectionDiagnostics should still return the current in-memory session/device state even when persistence is full, corrupt, absent, or slow. Report optional historical event unavailability explicitly rather than failing the whole call. Preserve authentication and isolation.
  • Preserve recorded human feedback and any required audit/security evidence. Never silently purge it to meet quota. If retained feedback alone makes normal write service impossible, expose its precise footprint and a separately authorized archival/export/retention decision. Do not treat optional telemetry as canonical state.
  • Tests must cover both the database-page limit and aggregate WAL/SHM/journal limit, continued reads at/above cap, graceful selective write shedding, successful reclaim below recovery watermark, non-reclaimable protected-data case, restart/recovery, concurrency and failure isolation. Existing quota-exhaustion tests should be updated rather than removed.
