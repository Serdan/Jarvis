[P2][Browser audit] Correct browser bridge deployment and scheduler documentation

Finding

Browser documentation still describes the one-shot scheduler as not supporting recurrence and implies the feature is undeployed; actual Jarvis has recurring client-local schedules, deployed browser bridge, session-bound window registration and different UI retry semantics.

Required work

Audit README and system/design documents against the current implementation and supported deployment. Make a single reliable contract description for recurring and one-shot launches, authorization, suspension/cancel behavior, known platform limitations, uncertain outcomes, tab-close semantics, and release verification. Distinguish current behavior from proposed future design and explicitly label current known defects pending remediation.

Acceptance criteria

  • Update browser-extension/README.md, docs/BrowserOneShotScheduler.md, docs/ChatGPTAgentLauncher.md, docs/BrowserBridgeSystem.md and docs/ExecutionScheduling.md where inaccurate.
  • All public examples use current APIs, including windowRegistration, repeatEverySeconds, closeTabAfterExecution and lifecycle statuses.
  • Documentation does not claim UI incompatibility permanently suspends recurring schedules unless implemented, and matches the approved final suspension fix.
  • Clearly describe installed extension registration versus client/server deployment and user authorization boundaries.
  • Review against actual implementation and a versioned test run, not only historical design notes.

Evidence and starting points

Audit found discrepancies among browser-extension/README.md, docs/BrowserOneShotScheduler.md and code in Client/Modules/BrowserSchedules.fs.

Boundaries

Writing this task does not authorize deployment, changes to live schedules, live prompt sends, or agent launch. Coordinate with existing work and use actual test and runtime evidence before completion.
