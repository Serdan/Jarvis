[P2][Browser audit] Scheduling and launcher documentation reconciliation

Objective: correct documentation against current source and the connected deployed command catalog. Documentation must distinguish implemented behavior, default-off behavior, known defects and operator-gated operations.

Verified facts to reflect

  • The connected deployed catalog now exposes ScheduleExecution, ListScheduledExecutions, GetScheduledExecution and CancelScheduledExecution, plus durable Challenge commands. Do not repeat the older claim that only the legacy ScheduleBrowserExecution family is deployed.
  • Client/Program.fs intentionally supplies an ActivityProofUnavailable error to AfterAgentIdle. The trigger is fail-closed and not operational in the production host.

  • config/manager/Jarvis.json has the Manager heartbeat disabled. The current Jarvis schedule listing contains no active Jarvis Manager heartbeat.
  • scripts/manager-heartbeat.mjs is a deterministic per-project planner with a local journal; it does not itself launch sessions. The model-based Manager still performs the actual browser launch. It is not the required account-wide non-agent Scheduler.
  • BrowserSchedules is a per-client persistent schedule runner, not an account-wide task/agent scheduler. Do not conflate it with the separate default-off Work Queue Scheduler prototypes.
  • Restore behavior for persisted suspended schedules was corrected by commit 9c2ae32e5, included in the audited main history. Do not document an automatic rearm on restore.
  • Two follow-up defects remain open: recurring launches can repeatedly retry WindowUnavailable:needsReauthorization, and suspended schedules cannot currently be canceled through the normal cancel path. Describe them as open until their code tasks are integrated.
