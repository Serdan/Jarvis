[P1][Browser audit] Prevent unauthorized rearming of suspended recurring schedules on restart

Finding

Commit 95c3b89ff reactivates persisted recurring schedules with Status=suspended and Error prefixed UiIncompatible: when the Jarvis client restores its schedule file. This can resume obsolete schedules without a new operator decision; historically, suspended entries were not cancelable. Separate issue from duplicate role ownership, currently being fixed.

Required work

Define durable schedule states and authority to resume. Distinguish failure of one occurrence from active schedule authorization, explicit suspension, cancellation, and retained old records. Preserve operator suspension and cancellation across restart and migrations; make suspended entries explicitly cancelable. Specify retry policy for transient UiIncompatible failures without interpreting legacy suspension as blanket consent. Review upgrade/migration semantics against existing persisted states and the continuing four approved Organon schedules.

Acceptance criteria

  • A suspended schedule remains suspended after upgrade/restart unless an explicit authorized resume or narrowly proven migration rule applies.
  • An operator can cancel any nonterminal scheduled item, including suspended, and canceled items never return to pending on restore.
  • Migration tests cover legacy UiIncompatible suspension, repeated failures, manual suspension, cancellation, pending recurrence, and uncertain prior dispatch.
  • No automatic replay of possibly submitted prompts; retries are new future occurrences only when recurrence remains authorized.
  • No new duplicate Manager or Health schedule IDs are created; coordinate with the already-active project-owned schedule consolidation task.

Evidence and starting points

Commit 95c3b89ff; Client/Modules/BrowserSchedules.fs restore branch and recurring failure mapping; Client.Tests/BrowserSchedulesTests.fs test previouslySuspendedRecurringUiFailureRearmsOnRestore. Overlap with p1-organon-project-owned-browser-schedules-20261119 is coordination, not duplicated implementation.

Boundaries

Writing this task does not authorize deployment, changes to live schedules, live prompt sends, or agent launch. Coordinate with existing work and use actual test and runtime evidence before completion.
