[P1][Browser audit] Suspended schedule cancellation and terminal-state preservation

Objective: make a suspended schedule explicitly cancelable while preserving the existing fail-closed restart behavior. Do not reintroduce automatic rearming.

Corrected source finding

The earlier claim that commit 95c3b89ff reactivated persisted suspended recurring schedules is superseded by later fix commit 9c2ae32e5, which is included in the audited main history. Current restore logic preserves the persisted suspended state; do not change that behavior. The remaining confirmed gap is that the normal cancel path accepts pending/running/waiting-activity entries but rejects suspended as not active.

Required behavior

  • Allow an operator to cancel a suspended schedule and persist terminal canceled state. Repeated cancellation must be idempotent or return a clear terminal result.
  • Preserve suspended and canceled across restart and supported migrations. No implicit resume or rearm.
  • Only a new explicit authorized schedule operation may replace/reconfigure a suspended schedule; do not interpret legacy state as consent to resume.
  • Add regression tests for canceling suspended one-shot and recurring entries, repeated cancel, restart after cancel, restore of suspended entries, and explicit replacement semantics.
  • Do not change recurring UiIncompatible retry policy in this task unless a separate source-backed requirement is established.
