[P1][Challenges] Audit canonical automatic Challenge wake/requeue and residual gaps

Disposition: completed read-only audit. No implementation change and no separate non-agent requeue authority recommended.

Verified source and execution boundary

Audit baseline: clean original Jarvis origin/main 95a471fc565b57fe309c65fc85f371693dbe9067. Assignment generation 2, attempt version 3, no source binding. Applicable task and AGENTS instructions read. No prior lifecycle checkpoint/history surfaced. No tests were executed; this is source inspection only.

Transition and authority contract

  • Waiting → Requeued when owner is already free: ChallengeWorkflow.blockAttempt validates exact task/attempt/agent versions, current attempt, owner and generation; validates dependency identity and rejects duplicates/inaccessible/cancelled/wrong-task dependencies or a nonempty set already entirely Satisfied. Zero/manual or multiple dependencies are allowed. It writes the durable wait and immutable owner/challenge indexes, blocks the attempt, stops/unassigns the owner to NeedsWork, writes audit, and reconciles older Eligible work in the same transaction (ChallengeWorkflow.fs:1656-1795). Zero-dependency waits have no indexes.
  • Waiting → Eligible → Requeued when owner is busy: first transition to Satisfied calls wakeDependents in the same transaction (ChallengeWorkflow.fs:887-990). It validates index/wait identity, all dependencies, current task/attempt/owner/generation and Blocked phase (774-817). If the owner is Stopped, unassigned, NeedsWork and not already claimed in this wake, it requeues immediately; otherwise it persists Eligible (818-884). At most one wait per owner per wake.
  • Eligible → Requeued on owner release: ReviewWorkflow.reconcileEligibleOnRelease checks owner Stopped/unassigned/NeedsWork, wait/index identity, current InProgress task/attempt, exact owner/generation, Blocked phase and all dependencies still Satisfied; at most one wait per release (ReviewWorkflow.fs:792-903).
  • All direct reconciliation call sites found: completeAgentWorkWithSession (ReviewWorkflow.fs:2165-2171); setAgentAdministrativeStateAs to NeedsWork/unpark (2319-2322); clearAdministrativeFocus (2755-2761), called by ParkAttempt/BlockAttempt/AbandonAttempt/CancelTask and TransferOwner (2814, 2916); and ChallengeWorkflow.blockAttempt (1785-1794). No other direct call sites were found in Client F# sources.
  • Manual zero-dependency wait: explicit owner-attributed RequeueAttempt validates exact versions/generation, actor=attempt owner, free NeedsWork slot, Waiting status and all linked dependencies Satisfied (ChallengeWorkflow.fs:1800-1869; OrchestrationApi.fs:2801-2806). Generic ResumeAttempt rejects Waiting/Eligible challenge waits (ReviewWorkflow.fs:2779-2785).

CAS, idempotency, audit and source provenance

  • ChallengeWorkflow.changed uses LegacyDirectWriterFence.transact (625-627), delegating to LedgerStore.transact (LegacyDirectWriterFence.fs:123-128). The ledger re-fetches, checks prior operation UUID, replans against the current snapshot, validates every ExpectedBlobOid, and retries/replans on non-fast-forward publication races (LedgerStore.fs:2300-2334, 2417-2433). If release commits first, satisfaction replans and sees a free owner; if satisfaction commits first, release replans and sees Eligible. Same UUID replay returns the prior receipt before planner execution.
  • Immediate and delayed requeue record the actual operation actor in TaskLifecycleEvent.ActorId and AssignmentIssue.IssuerId (ChallengeWorkflow.fs:843-871; ReviewWorkflow.fs:877-899). The actor is the condition finalizer, authenticated operator, or actor completing/unparking/admin-releasing/blocking the owner's current work. Explicit requeue is owner-only; no Scheduler identity or notification side channel is required.
  • Requeue preserves the same attempt and source provenance (BaseCommit, TargetRef, repository/remotes, SourceRef) while incrementing assignment generation; no new source binding/checkout lease is created (ReviewWorkflow.fs:118-152, 756-773; ChallengeWorkflow.fs:843-855, 1641-1654).
  • No live/current wait can remain Eligible while its exact owner is already stopped, unassigned and NeedsWork: supported transitions into that state invoke reconciliation; satisfaction immediately requeues a free owner or records Eligible for a busy/parked owner; CAS replanning closes concurrent satisfaction/release ordering.
  • A raw Eligible wait may remain after attempt cancellation/abandonment/transfer/supersession as historical data, but it is inert: reconciliation requires task InProgress/current attempt and exact Blocked generation (ReviewWorkflow.fs:820-829); inbox projects waits only for current Blocked attempts (3285-3302). This is hygiene, not a requeue-authority gap.

Existing tests and concrete gaps

Existing Client.Tests/ChallengeWorkflowTests.fs covers All-vs-partial and canceled/already-satisfied dependencies (276-343, 345-380, 840-882); stale Challenge versions/concurrent condition writers (142-187, 247-272); busy-owner completion (690-721); parked-owner explicit unpark (764-790); multiple owners (794-836); zero-dependency explicit owner requeue (383-422); reblock/generation 2→3 and index retention (919-955); and operation replay for create/resolve, blockAttempt, partial resolution and operator response. The fixture uses two independent clones of a shared bare Git remote (40-69), covering cross-client persistence, but no explicit process restart test was found.

  1. No replay of the final Satisfied operation with an actual blocked dependent waiter, asserting one generation increment, one assignment issue and one lifecycle event.
  2. No race test between final dependency satisfaction and owner completion/unpark; current concurrency coverage races condition writers only.
  3. No assertions for ActorId/IssuerId on generated immediate and delayed requeue lifecycle events/assignment issues.
  4. No process restart/reopen test; generation coverage does not actively exercise a stale old locator against the new generation.
  5. No stale Eligible-wait inertness test after terminalization/transfer, although source guards exist.

Conclusion

Challenge-linked automatic requeue already exists via synchronous wake plus owner-release reconciliation, with transactional CAS/replanning and actor attribution. Do not add a non-agent requeue authority or change production logic on this audit. The next proportionate work is tests-only for the idempotency, satisfaction/release race and actor-provenance gaps; add restart/stale-wait coverage if it remains bounded. If a test exposes a production defect, report the exact failing transition and stop before editing implementation.
