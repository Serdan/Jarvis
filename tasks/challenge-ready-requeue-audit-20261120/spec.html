[P1][Challenges] Audit canonical automatic Challenge wake/requeue and identify residual gaps

Objective: produce a source-backed audit of the existing Challenge wait state transitions and authority. This is read-only investigation; no source or ledger mutations.

Verified current baseline

Use the current verified original Jarvis origin/main baseline 95a471fc565b57fe309c65fc85f371693dbe9067, unless a fresh remote check establishes a newer main.

Existing behavior Lead has verified — independently confirm

  • Client/Modules/ChallengeWorkflow.fs:wakeDependents runs in the same ledger transaction when a Challenge first becomes Satisfied. It walks the reverse index, checks every linked dependency from the same snapshot, and validates task, attempt, owner and assignment generation. If the owner has no current assignment, is Stopped, and has UnassignedDisposition=NeedsWork, it requeues the blocked attempt and writes the wait, attempt, agent, assignment and lifecycle audit atomically. If the owner is occupied or parked, it persists the wait as Eligible.
  • Client/Modules/ReviewWorkflow.fs:reconcileEligibleOnRelease consumes eligible waits on canonical owner-release transitions. It verifies the exact wait/attempt/generation/owner and every dependency, then requeues at most one eligible wait when the owner is free and eligible. Parked owners remain eligible until explicit unpark.
  • The helper is called by canonical completion/release paths and by ChallengeWorkflow.blockAttempt. Enumerate every call site and the transition that invokes it; do not assume the grep list is exhaustive if additional modules or admin paths exist.
  • ChallengeWorkflow.requeueAttempt is a separate owner-attributed recovery operation. Its validated attempt requires attempt.OwnerAgentId = actor. Do not call it as a Scheduler, impersonate the blocked owner, or propose an unrestricted service identity.
  • Existing tests include SatisfiedDependenciesRemainEligibleUntilBusyOwnerReleasesTheirSlot, ParkedOwnerKeepsDurableWakeUntilExplicitUnpark, FinalChallengeResolutionRequeuesEveryDistinctDependentOwner, BlockingAnotherAssignmentWakesPreviouslyEligibleWork, and AlreadySatisfiedDependenciesCannotCreateAnUnwakeableWait.

Include exact required conditions, task/attempt/generation/owner identity, source lease implications, CAS/version checks, and actor/audit provenance.
  • Trace Challenge creation, condition satisfaction, operator response, wakeDependents, durable wait record, every reconcileEligibleOnRelease caller, and explicit requeueAttempt. Confirm whether all supported owner-release transitions invoke reconciliation.
  • Inspect current tests for all-satisfied versus partial dependencies, duplicate/repeated wake delivery, operation idempotency, stale attempt generation, stale Challenge versions, owner busy/parked, explicit unpark, restart/persistence and actor attribution. Identify exact missing cases rather than proposing generic test expansion.
  • State clearly whether any real state can remain Eligible while its exact owner is already stopped, unassigned and NeedsWork. If no such gap exists, conclude that a separate non-agent requeue authority is unnecessary for the existing Challenge flow.
  • Only if a concrete release path or state can bypass the existing automatic reconciliation, report the exact file/method/call path, minimal failing scenario and narrow correction to Lead. Do not implement it.
