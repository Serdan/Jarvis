Composable Work Units: Project / System / Feature

Purpose: Introduce a durable, recursive work model in Jarvis. The unit of organization and progress is work, not a persistent agent. This task captures the design decisions agreed with the operator on 2026-11-16 and asks for their implementation as an independently scoped follow-on to the already-running Agent => Work migration.

Boundaries and relationship to existing work

  • Do not reimplement Agent => Work. That migration is already in progress under work-queues-ephemeral-executions. Build on its durable work, claims, scheduler, and execution concepts after examining their actual interfaces.
  • Use the existing canonical, versioned Git-backed Jarvis ledger and proven task/review/integration mechanisms where they fit. Avoid parallel sources of truth and duplicate lifecycle machinery.
  • Related but distinct concern: scope-drift-overengineering addresses runaway scope and architectural drift. The present task is the composable work graph and its semantics.

Decided conceptual model

  • One composable unit of work with common identity, durable state, specification, history, and verifiable outcome. Domain-facing names are Project, System, and Feature; avoid Agile-specific epics, sprints, story points, and organizational hierarchy as foundational terminology.
  • A Feature is a well-scoped implementable outcome; a System groups related work around a coherent functional boundary; a Project is the top-level objective. Systems may contain subsystems recursively. Favor common work-node machinery over three unrelated workflow engines.
  • Every level is first-class, not just a folder: it has its own description, intent/goal, scope, acceptance criteria, constraints, decisions, evidence, history, and (where appropriate) child work. The parent outcome requires independent validation.
  • Child completion does not imply parent acceptance. A completed set of features can still fail system-level acceptance; a collection of completed systems can fail project-level acceptance. A parent may need further corrective children after such a failure.
  • Work carries persistent identity and history; LLM sessions are ephemeral executions of bounded slices. Execution/session identifiers are for provenance and concurrency, not human-like task ownership. Integration and review are schedulable work, not permanent people or singleton offices.

Declarative, lazy, reactive work model (guiding architecture)

Core insight: Treat Jarvis as a lazy, reactive interpreter of engineering objectives. A work unit is a durable, declarative specification of an outcome, not a running process and not a persistent agent. The system should separate describing the computation from executing it. A fully specified System or Feature may remain dormant for weeks without any assigned session or allocated execution resources; when its prerequisite work reaches the specified evidence/acceptance state and capacity becomes available, Jarvis recognizes readiness and starts appropriate execution automatically. Completing that work can transitively unlock other work.

Useful functional model (conceptual, not a purity guarantee):

Evaluate(Spec, DependencyResults, DurableState)
    -> (NextState, Artifacts, Evidence, NewWork)
  • Declarative semantics: Specs state desired outcomes and acceptance criteria; dependency edges state prerequisites; readiness is derived from authoritative durable state. The work unit need not know when to wake, who will run it, or retain a live agent. Runnable work is selected by a scheduler based on readiness, policy, and available capacity.
  • Lazy/reactive activation: Work that cannot run remains inert, rather than consuming an agent slot. Every relevant committed state transition (dependency acceptance/integration, new work, capacity release, changed constraints) can trigger reevaluation. Do not require a human or persistent Lead to notice and restart the work.
  • Recursive/higher-order composition: A work unit can discover and create smaller units of work and their explicit dependencies; those units follow the same readiness/evaluation rules. New work must be justified by parent intent and recorded as an explicit, versioned graph change, not silently added scope.
  • Functional core, imperative shell: Keep graph evaluation, dependency resolution, acceptance/status derivation and scheduling decisions as predictable, testable state-to-decision computations where practical. Put effects (LLM calls, files, command execution, reviews, commits, branch promotion) behind explicit actions whose results become durable evidence and state transitions. Reuse existing Jarvis ledger/queue contracts instead of inventing a second runtime.
  • Do not mistake the analogy for literal purity: LLM calls are not referentially transparent or deterministic, and repository mutations are real side effects. Persist sufficient inputs, decisions, outputs and evidence to make history auditable; use existing version/claim/commit controls for concurrency, while resisting speculative transactional infrastructure. Deterministic readiness does not require deterministic intelligence.
  • Composable autonomy: A dormant specification plus known dependencies is sufficient to drive future execution. The system may scale across many independent features and systems, each activated only when needed, with no persistent agent identity or singleton managerial bottleneck.

Design review question: Does the proposed implementation preserve the separation between a declarative work description, a deterministic/inspectable readiness decision, a bounded ephemeral execution, and the durable recording of its effects? Avoid designs that reintroduce person-like agents as the repository of context, or rely on manually coordinating dependent work.

Composition and relationships

  • Support parent/child composition and meaningful directed dependencies (especially blocks / blocked by) between work units, including across system boundaries; reject dependency cycles.
  • Optionally support non-blocking related to links, kept separate from scheduling dependencies.
  • Explicitly distinguish organizational containment from dependency, shared code ownership, and integration ordering. Do not infer blocking from shared parentage.
  • Start with the simplest coherent containment model; decide whether multi-parent composition is necessary based on real use cases. Cross-system dependencies must not require multi-parent containment.

Readiness, progress and acceptance

  • Jarvis should answer queries such as: 'How far along is the Scheduling system?', 'What is blocking completion?', 'What is ready now?', 'What remains to validate?', and 'What can integrate?'. Traverse dependencies to identify root blockers and active execution/verification states, not permanent agent owners.
  • Derive progress from authoritative child-work states, never manually maintained percentages. Display closed/active/blocked/cancelled distinctions; cancelled scope must not silently distort the denominator. Distinguish execution finished, review accepted, integrated, and parent acceptance (existing CloseTask by itself does not verify review or integration).
  • Each work unit's acceptance criteria must be testable/inspectable with appropriate evidence. Parent acceptance should be an explicit independently verifiable transition; do not assume 100% children closed means done.
  • Keep the enduring identity of a system distinct from a particular accepted target state or release; adding future work should not automatically rewrite history or erase prior acceptance.

Elastic execution and integration

  • The scheduler dispatches ready work based on current need and capacity, including planning, implementation, review, integration, and validation. No fixed '10 workers per system', dedicated permanent Lead, or singleton project integrator.
  • Implementation may occur on per-feature branches; validated changes can flow through optional system/subsystem integration branches and onward to the project branch, according to actual boundaries. Do not force unnecessary branch layers for small units.
  • Multiple integration sessions can prepare and verify promotions concurrently, including promotions toward main. The Git ref update itself is atomic; stale-head conflicts require refresh and appropriate revalidation. Meaningful semantic compatibility must be tested even for textually clean merges.
  • Favor maximizing verified, integrated progress, not raw session count. Avoid speculative complex scheduling heuristics until supported by observable bottlenecks.

Preserving intent and engineering judgment

  • Preserve authoritative objectives, constraints and acceptance criteria across decomposition. Keep assumptions distinguishable from accepted requirements, and record important decisions/revisions with rationale and provenance. An execution checkpoint must not silently promote an assumption into project intent.
  • Fresh verification at parent boundaries should check that the implemented composition fulfills the parent's intended outcome, not merely that children passed their local tests. Surface semantic drift and propose explicit spec changes rather than quietly rewriting goals.
  • Inherit relevant project/system engineering constraints into descendant work. Seek the smallest coherent solution: neither a hardcoded local patch ignoring domain context nor a speculative mega-framework. Favor reuse of actual existing capabilities.
  • For Jarvis specifically, execution sessions are trusted under the user's existing trust policy. Do not invent fictitious per-agent security principals or build elaborate permission frameworks as part of this work. Maintain real user/device and Git correctness boundaries already in place.

Implementation direction / non-decisions

  • First inspect and fit the new model to the ongoing work-queue migration and canonical ledger; record a minimal schema and API plan. Any proposed design choices not described here should be made explicitly, not treated as previous operator decisions.
  • Provide essential operations for creating/updating composite units, attaching/detaching children, maintaining dependency edges, and retrieving a consistent recursive overview with blocker/readiness and completion evidence. Exact MCP names and storage encoding remain implementation decisions.
  • Make changes versioned and auditable using existing ledger conventions. Concurrency protection should safeguard actual invariants, without resurrecting permanent agent ownership or overengineering speculative failure paths.
  • Use coherent bounded implementation slices as required; the parent task should retain the enduring design and completion objective. Do not introduce separate Agile process vocabulary or a full project-management application.

Acceptance criteria

  1. A Project/System/Feature work graph, including nested Systems, can be represented durably and reloaded consistently from canonical Jarvis state; specifications and acceptance criteria exist at all levels.
  2. Containment and cross-unit blocking dependencies can be updated with versioned/auditable operations. Invalid references and dependency cycles are handled clearly.
  3. Queries expose derived status, readiness, blockers, review/integration state and progress at each level without requiring persistent agent ownership.
  4. Closing all children does not automatically accept the parent. Parent acceptance can be evaluated with its own evidence; unfinished or newly discovered corrective work remains visible.
  5. Concurrent execution, review and integration operate through the existing Agent => Work scheduling/claims system without singleton 'Lead' assumptions. Candidate promotions use safe Git semantics and appropriate validation.
  6. Tests cover recursion, cross-system dependencies, lifecycle/progress edge cases, parent acceptance, and concurrent reads/mutations relevant to the chosen design.
  7. Documentation explains the conceptual model, operator queries, and which facts are authoritative versus inferred.
  8. Demonstrate reactive activation end to end: a specified unit with unsatisfied prerequisites consumes no execution slot; completing only one of two prerequisites does not dispatch it; when all required acceptance/integration evidence arrives, it becomes runnable without manual intervention, receives at most the appropriate bounded executions under concurrent scheduler evaluation, and behaves consistently after restart. A unit created by another execution follows the same rules.

Open questions to resolve during design

  • How to represent a system's enduring identity versus versioned accepted target states/releases.
  • Whether a unit can have multiple structural parents or should have one parent plus arbitrary relationship edges.
  • Whether acceptance and integration are explicit work transitions, derived states, or separate verification work units in the new queue contracts.
  • How to choose optional branching/integration boundaries without rigidly coupling them to every work-node nesting level.
  • How much traceability/provenance to encode in the MVP versus build incrementally using existing specs, history and review evidence.
