Objective

Let the operator configure how Jarvis uses available projects, AI accounts, client instances, browser bridges, and machines. Jarvis should route new AI sessions to a viable spawner/account and dispatch queued development jobs to suitable hosts (initially home and kruso) without requiring persistent named agents, an open TUI, or manual machine selection for every operation. Keep the smallest implementation that meets observed needs, extending existing Work scheduling, client routing, browser bridge, and job execution mechanisms.

Candidate requirements to refine

  1. Operator project priorities. Configure project-level priority/pause policy separately from Lead's within-project Work priority; define precedence clearly so a Lead cannot accidentally override operator allocation. Avoid unproven fairness algorithms. No implicit preemption of running work when priorities change.
  2. Shared execution capacity. Set an account-wide maximum for simultaneously active AI sessions across all participating clients/machines, with optional per-account/per-host limits. Admission must be consistent across clients and must not release capacity merely because a launch or termination outcome is uncertain. Reuse the existing/target authoritative Work capacity and claim machinery.
  3. Multiple accounts and spawners. Configure multiple authorized execution-account/profile references and one or more spawner methods (initially existing browser-based launches), including simple preferred-order fallback when an account is unavailable or quota-exhausted. Route only new sessions; do not silently move running sessions. Credentials must remain protected and scope-specific. Observe provider requirements and account terms.
  4. Quota/availability probes. Allow the operator to register a trusted local script/command per account or spawner that reports a small structured status such as available, exhausted, or unknown, plus optional reset time. Use bounded execution, explicit expiry, and transparent diagnostics. Treat a probe as advisory; live launch errors and unknown outcomes must also affect readiness and reconciliation. Do not create a provider-specific quota subsystem by default.
  5. Client daemon mode. Run the existing Jarvis client without an interactive TUI as a long-lived process under OS supervision, maintaining authentication, heartbeats/reconnect, capability advertisement, and authorized session/job handling. Closing the TUI must not terminate daemon-hosted work. Reuse the client implementation; do not invent a separate machine-agent product or service manager. A daemon may still need an active graphical session/bridge for browser work.
  6. Dynamic browser readiness. Discover browser-spawning capability from a connected, responsive browser bridge rather than a redundant static enabled flag. On bridge loss, stop new launch admission through it; reconcile uncertain in-flight launches rather than treating them as definitely failed.
  7. Machine capabilities and queued jobs. Treat participating machine/client instances as eligible job hosts. Support a small operator policy identifying allowed workloads and concurrency per host, with initially simple routing by explicit host or required capability (e.g. Windows/.NET 11, test, benchmark). A session on home may queue an external job on kruso; that job is not another AI-session slot. Reuse existing Jarvis remote job/queue capabilities and stable machine/instance identity rather than building a new execution layer.
  8. Heavy-work isolation. Provide practical queueing and exclusive benchmark access where required to preserve reproducible measurements. A mere max-concurrent-jobs=1 does not prove the machine is otherwise quiet; define what the host can actually guarantee and report external interference/unknowns honestly. Avoid speculative generic resource pools or continuous CPU/RAM/GPU allocation accounting.
  9. Visibility and recovery. Operator-facing state should explain why sessions/jobs are waiting (quota, bridge unavailable, global limit, host down, exclusive resource held, etc.). Reconnect/restart must not duplicate uncertain launches or jobs; preserve existing one-shot journaling, idempotent operation IDs, fencing, and audited results.

Minimal scenarios to validate later

  • Two project queues have different operator priority; eligible work is admitted according to the agreed precedence, subject to the shared session cap.
  • A preferred browser-account quota probe reports exhausted: the next authorized launch uses the second configured account, without duplicating a possibly-submitted first launch.
  • A bridge disconnects/reconnects on home: new-launch readiness changes automatically; unrelated jobs/sessions are not falsely completed.
  • Run the client as a daemon and close the TUI: permitted jobs and connectivity continue, with safe reconnection.
  • A Worker session hosted on home submits a .NET test/build to kruso and receives durable completion evidence; a queued benchmark runs only under a justified isolation condition.
  • Concurrent client instances/machines do not collide in identity, routing, capacity accounting, or uncertain-effect recovery.

Review questions before promotion

  • Which of these requirements are essential for the minimum trustworthy Work cutover versus follow-on improvements? Do not expand G0/G5 by implication.
  • What existing Jarvis Work Scheduler, account-global capacity, client-instance identity, BrowserBridge, job queue, and remote-execution components should be reused or extended?
  • Do we actually need generic resource allocation, host capability discovery, fair sharing, or advanced reservations now? Default answer: no, absent a concrete scenario.
  • How should operator project priority interact with existing (isBlocking, leadAssignedPriority, -availableSequence) ordering? Preserve the current guarantee intentionally, not accidentally.
  • What is the correct deployment/host identity and security boundary for daemon-side quota scripts and spawner credentials?
  • What is the smallest verifiable exclusivity contract for performance benchmarks, including unmanaged host activity?
