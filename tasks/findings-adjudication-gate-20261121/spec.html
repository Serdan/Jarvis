[P1][Process] Implement bounded independent findings adjudication before corrective Work

Human Operator decision, 2026-11-21. This is a governance and workflow correctness feature for Jarvis, not permission to establish a second review subsystem. Effective immediately, Lead and Reviewer role instructions (canonical versions updated 2026-11-21) distinguish an immutable code-review verdict from the separate decision to change task scope. A dedicated Adjudicator role and an idle independent Adjudicator 1 agent exist. Adjudication MUST occur before a reviewer finding becomes an implementation requirement, corrective task, new dependency, expanded threat model or spec amendment, unless the human Operator explicitly overrides. Use the existing canonical review, task, spec, checkpoint and decision mechanisms; do not reinvent reviews, ledgers or a continuously running adjudication scheduler.

Required bounded procedure

  1. Read current Lead/Reviewer/Adjudicator roles; inspect the existing ReviewWorkflow decideReview / ChangesRequested / review findings and task creation/revision flows, existing canonical task metadata and immutable feedback. Before designing any code, assess whether one canonical adjudication task per review decision, referencing each distinct finding, is already sufficient. Avoid schema changes, new API surfaces or separate persistent records if existing canonical task HTML plus checklists/decision document, pinned review ID/finding blob and immutable task/checkpoint can meet the requirements.
  2. Independence: adjudicator must differ from source author, reviewer who raised the finding, and remediation designer; record their identifiers and source/review/task/spec binding. If no independent agent available, mark awaiting adjudication and hold the new requirement, not the immutable review. Roles alone are not security permissions. Adjudicator must neither edit source nor create/assign corrective tasks.
  3. Each individual finding gets one terminal disposition: Accept, Narrow, Defer or Reject. Record demonstrated validity (evidence vs assumptions), original scope/threat model clause and potential net-new objective, real operating prerequisites/impact, proportionality and maintenance cost, existing architectural alternatives, decision and explicitly authorized bounded correction. In Narrow, state accepted subset and excluded remedy; Defer, condition for reconsideration; Reject, evidence/reason. Valid defect does NOT imply reviewer remedy is necessary. If finding needs new product/security objective, require explicit Operator approval; no silent expansion.
  4. Lead may create/revise corrective implementation Work only based on an accepted/narrowed adjudicated finding or explicit Operator override, with reference to disposition and precise allowed scope. A deliberately deferred/rejected finding does not become a blocking implementation requirement. For preexisting ChangesRequested source, keep frozen review status immutable; when all findings rejected/out-of-scope, do NOT edit reviewer decision or claim source Accepted. Describe lawful recovery: new independent review on a valid source if appropriate, or bounded Operator disposition; no automatic override, no meaningless rebases. A source failing an original task requirement still cannot be integrated merely because a proposed extension was rejected.
  5. Adjudication is terminal one-pass human-readable reasoning. No recursive review-of-adjudication, rebuttal cycle, duplicate follow-up adjudication or launching cascades. A genuinely ambiguous policy question escalates ONCE to Operator with precise alternatives, then stops. Reviewers continue to report actual defects and choose source verdict independently; they do not get an implicit veto over adjudicator's work-scope decision. Emergency suspected production-impact findings may cause a conservative temporary HOLD pending adjudication, never automatic scope expansion.

Deliverables and acceptance

Persist concise operational procedure in repository docs and role handoffs; apply it to one historical disputed review as a read-only example (publisher-provenance findings / trust-root proposal are suitable), preserving immutable original reviews and noting that human Operator has already approved the proportionate trusted-writer decision. If an existing canonical task cannot represent the decision without ambiguity, implement only the smallest necessary typed metadata/check at the current review-to-task conversion seam, with source-bound .NET11 Release tests. Do not require LLM consensus, a new Adjudicator service, second database or automated Scheduler. Test at minimum: real valid in-scope finding Accepted; valid defect but overbroad solution Narrowed; unsupported assumed threat model Rejected or Deferred; mixed multi-finding verdicts; attempted correction without disposition rejected by process; independent actor guard; duplicate decision idempotency; zero findings don't create an artificial gate; historical review untouched; explicit Operator override recorded; no recursive adjudication. Separate manual policy and code-enforced guarantees honestly. Record whether the manual-role gate is all that is justified or actual backend changes are required. Produce exact docs/source SHA and independent frozen review for any implementation changes; do not overwrite existing reviewed sources or main.

Safety and priority: Other Worker4/Worker5 integration source, Worker7 Challenge source, Scheduler/Health activation and Git main publication remain independent. No automatic launches, customer/system deployment, retroactive rewrite of immutable reviews, or uncertain effect replay. Continue until task complete, hard blocker or stop. Respect existing task-spec proportionality review: do not underengineer by ignoring current mechanisms or overengineer by building a general adjudication engine.
