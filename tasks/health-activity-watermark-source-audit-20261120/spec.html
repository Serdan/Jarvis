[P0][Health] Trace authoritative cross-device tool-activity watermark

Objective: Remove the concrete evidence blocker for deterministic native Health recovery by establishing whether Jarvis already has an authoritative, durable, cross-device per-agent tool-activity source. This is a bounded read-only source audit and design task, not implementation.

Verified starting evidence

  • Client/Modules/OrchestrationApi.fs builds ObserveAgent.lastSeen from getLocalLastSeen and explicitly labels it LocalClientActivityCache with lastSeenIsCanonical=false.
  • Server/Services/HubService.fs currently makes GetAgentActivity fail with ActivityProofUnavailable, explicitly rejecting the server SQLite watermark as authoritative for AfterAgentIdle.
  • Server/Services/FeedbackStore.fs labels attributed_agent_activity as legacy, nonauthoritative diagnostics. Do not use it as recovery authority.
  • Server/Services/UserService.fs tracks device connection LastSeenAt; connection liveness is not per-agent tool activity.
  • Client/Modules/BrowserSchedules.fs fails closed when there is no trusted cross-device activity watermark. Keep this safety behavior.
  • The Health implementation task jarvis-native-configurable-agent-recovery-20261120 is preserved as Blocked pending this evidence. Its requirements include configurable 600-second default, exact CAS recovery preserving assignment/instructions, restart/reconnect correctness, and no LLM/browser dependency.

Audit requirements

  1. Trace the actual MCP tool-call path end to end: authenticated request entry, project/agent attribution, server-to-client dispatch, canonical Git-ledger access and the point where an accepted tool invocation can be recorded. Cite exact source paths and line ranges.
  2. Search for any existing canonical per-agent activity watermark or durable activity event. Distinguish it from local TUI caches, client connection timestamps, disposable telemetry databases, Work leases and browser schedule state.
  3. If no suitable source exists, propose the smallest viable canonical activity-watermark protocol using the existing Git-backed ledger as authority. Specify identity binding (user/project/agent/device/session), monotonic timestamps/sequences, idempotency, concurrent-device ordering, clock skew, CAS conflicts, restart/reconnect behavior, coalescing/write-rate tradeoffs, retention and fail-closed semantics. Do not assume a missing watermark means inactivity.
  4. Identify exact implementation files and narrow non-overlapping source regions, plus the tests needed. Avoid Worker 11's scheduled RunCommand consumer and Worker 18's BrowserSchedules/BrowserScript ownership; propose explicit separate leases if overlap cannot be avoided.
  5. Produce a dependency-ordered, task-ready implementation and acceptance plan that unblocks the existing Health task without expanding into Telos Work/SQLite migration or a second scheduler framework.

Required negative cases

  • No activity record, reset/lost local cache, server restart or disconnected device must never authorize recovery.
  • Out-of-order or duplicate activity reports must never move the watermark backwards or cause duplicate recovery.
  • Concurrent clients and separate projects/agents must not contaminate one another's watermark.
  • Connection activity alone must not be treated as agent tool activity.
  • Recovery must remain disabled until an authoritative source is implemented, independently reviewed and integrated.

Boundaries

  • Read-only audit and design only. No source edits, commits, ledger writes, schedule creation/cancellation, browser actions, deployment, restart, migration or activation.
  • Do not use FeedbackStore.attributed_agent_activity, local GetAgentLastSeen, connection LastSeenAt, or Work lease heartbeats as authority.
  • Do not weaken ActivityProofUnavailable or any fail-closed path.
  • Return a concise evidence-backed report with exact paths/lines, the recommended minimal protocol, source ownership boundaries, test matrix and the precise next task needed.
