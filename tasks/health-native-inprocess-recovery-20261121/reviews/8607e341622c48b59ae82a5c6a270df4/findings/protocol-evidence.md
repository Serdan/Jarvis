# Required native recovery protocol scenarios are not demonstrated

Severity: P2 (explicit task acceptance evidence). `Client.Tests/NativeHealthTests.fs:266–326` executes the two Git clients sequentially, directly calling `ReviewWorkflow.recoverAgentAssignmentAs` with different IDs, then replaying the winning ID. It neither runs two concurrent `checkOnce`/production `recover` calls with their deterministic identical ID, nor simulates a lost response after publication through `TaskApi.write`, the pending-intent journal, and `NativeHealth.recover`'s status lookup. The staleness test at lines 229–245 injects `None` rather than constructing the indicated Ready/Parked/Blocked canonical states. Source tests do exercise time boundaries, server read failures, changed observations, config, and source preservation, but the named tests cannot establish the remaining required real adapter and race properties.

The task explicitly requires concurrent two-client one-winner, lost-ACK reconciliation, and actual ineligible states under the native Health seams. Add bounded tests through the real adapter/journal and two clients with controlled concurrency and an injected post-commit lost acknowledgement; exercise canonical ineligible states. The independently delivered server implementation is a separate dependency, so this finding does not demand real server integration or a new architecture.
