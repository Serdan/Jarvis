[P0][Automation/Health] Authoritative server SQLite activity timestamps

Explicit human Operator approval, 2026-11-21: Replace the former cross-device Git watermark dependency with server-authoritative SQLite activity for native Health. This is the first of two bounded implementation tasks. Git remains authoritative for assignment/recovery CAS, not heartbeat observation. Never make a Git transaction for every tool call. Do not reactivate legacy Health/Manager browser agents or schedules.

Verified current implementation and minimum scope

  • Server/Services/FeedbackStore.fs already creates attributed_agent_activity(user_id, project_name, agent_id, last_seen_at) with monotonic upsert and read; it is currently explicitly labeled diagnostic/non-authoritative.
  • Server/Services/ClientService.fs lines 325-334 identifies authenticated actor/project and AgentCommandInfo.isAgentActivity before dispatch, but calls RecordAgentActivityForUser which currently only sends droppable cross-device SignalR hints, not the SQLite write.
  • Server/Services/HubService.fs GetAgentActivity currently fails with ActivityProofUnavailable even for a registered client; Common/SignalR/IHubService.fs already declares AgentActivitySnapshot with last-seen/server-now.
  • OptionalFeedbackStore has intentionally droppable, bounded best-effort telemetry writes. Do not blindly declare that pipeline an authoritative heartbeat: silent dropped writes could cause false stale recovery. Reuse existing SQLite/schema as appropriate and implement the smallest bounded, trustworthy activity-status path, not a second database or telemetry architecture.

Acceptance contract

  1. On each authenticated, qualifying Jarvis agent call received by the server, attribute existing user/project/agent and server UTC time; record monotonic last activity in SQLite through the established table and existing authentication context. Never derive identity or liveness from browser tab state, local/client clocks or arbitrary caller timestamps. Non-agent observer/administrative probes must not impersonate target activity.
  2. Expose a trusted read through the existing IHubService.GetAgentActivity for registered client requests scoped to the authenticated user/project/agent. Return the actual server timestamp and server-now; absence means Unknown/NotEnoughEvidence, not idle. No new provider-session identity subsystem.
  3. Define a minimal conservative treatment for persistence failures, busy/locked SQLite, drop/timeout, startup/restart and optional telemetry quota: don't silently treat missed activity as a stale timestamp. Preserve ordinary Jarvis tool execution if telemetry fails, but expose Health verification as unavailable until evidence is trustworthy again. Keep any reliability marker simple and avoid long blocking or unbounded request-side DB work. If existing OptionalFeedbackStore cannot support this property without risk, isolate only the small Health-specific persistence boundary while sharing existing database/schema; explain why.
  4. Retain monotonic timestamp update, bound database growth, bounded labels and safe multi-device aggregation. Do not turn AfterAgentIdle BrowserSchedules into a Health launcher and do not introduce per-tool Git commits.
  5. Source-bound .NET 11 Release tests: correct authenticated attribution; two clients/agents/projects; ordering and duplicate activity; trusted current server time; observer-only exclusion; lost/missing DB row; locked/busy/failed or quota-exhausted SQLite; missing/unregistered caller; server restart; nonactivity must not become a recovery authorization. Test actual integration ingress and HubService, not just a private helper; log commands, exits and counts.
