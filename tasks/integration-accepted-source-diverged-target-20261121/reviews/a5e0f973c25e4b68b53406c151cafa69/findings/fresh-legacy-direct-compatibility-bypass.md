## Verified correction, and remaining failure

The previous I-to-S **post-hoc downgrade** is structurally corrected: `WorkCompositionAcceptanceAdapter.fs:189` unconditionally calls `requireManagedCompletionAt`; `LedgerStore.fs:945-979` discovers a canonical `CompleteIntegration` operation through first-parent path history and `getOperationOriginAt`; `WorkCompositionAcceptanceAdapter.fs:86-94` compares the current full receipt to the immutable receipt in the original introducing commit. The new tests at `Client.Tests/WorkCompositionLedgerTests.fs:481-505` exercise both downgrade variants and completion-less status forgery.

However, `WorkCompositionAcceptanceAdapter.fs:96-112` treats a direct-looking `I=S` receipt with four blank publisher fields as *historical legacy* solely because those fields were blank **at that operation's origin**. Neither this gate nor `findCompletionOperationForPathAt` checks any immutable rollout boundary, authenticated historical version/epoch, or known pre-publisher allowlist. The operation's existence proves when a record was introduced in the canonical Git history, but not that it predates the publisher protocol. In addition, the code never parses `completion.CanonicalRequestJson` to bind the operation's taskId, submissionId and integratedCommit to this exact receipt; it checks the generic operation kind, touched path, actor and sequence.

The new purported positive compatibility test `compositionAcceptanceRetainsAuthenticatedHistoricalDirectCompletion` (`Client.Tests/WorkCompositionLedgerTests.fs:313-380`) is itself a fresh adversarial witness: it initializes a disposable bare remote and two clients **under the current source**, completes the modern managed `SubmitIntegration`, then uses the current generic `LedgerStore.transact` to originate a new operation with `Kind = "CompleteIntegration"`, `IntegratedCommit = S`, publisher fields blank, and a manually backdated `CompletedAtUtc = "2026-11-06T03:16:08Z"`. It publishes S to main outside `ReviewWorkflow.completeIntegration` and `publishIntegrationTarget`. The test then asserts `WorkCompositionAcceptanceAdapter.acceptIntegrated` succeeds. This is a newly manufactured legacy *shape*, not an actual pre-upgrade operation. The timestamps are caller-controlled data, not historical proof.

`ReviewWorkflow.fs:1349-1377` requires current managed completions to use `publishIntegrationTarget`, which performs a verified ordinary non-force target publication. Yet the adapter can accept a freshly originated `CompleteIntegration` that never went through that route. Original-operation immutability does **not** by itself prove authorized publisher execution or genuine legacy-era origin. With a valid canonical-ledger write capability and an external target update, the old-shaped receipt enters the compatibility path. If target history was force-replaced on a permissive host, its current ancestry alone likewise does not attest an original non-force managed push.
