[P0] Integrate exact Accepted source across target advancement without compulsory re-review

Operator-approved architectural change (2026-11-21). Replace the obsolete rule “Accepted source commit must already descend from the current target head” with: source review applies to its immutable reviewed commit; integration verification applies to composition of that commit with the current target; only the final target publication must be a non-force fast-forward. Advancing main independently must NOT invalidate an Accepted verdict or force Workers to rebase, rerun a full independent source review, and resubmit an unchanged implementation.

Current authoritative code and incorrect gate

Client/Modules/ReviewWorkflow.fs:1235+ submitIntegration pins the Accepted review SHA/ref and its target, then incorrectly calls LedgerStore.verifySourceAncestry binding targetHead pinned, denying a diverged Accepted source. completeIntegration incorrectly rejects integratedCommit != submittedCommit and again requires old target to be ancestor of the original reviewed source. Existing LedgerStore.verifyIntegrationOnRemote already proves submitted SHA is ancestor of integrated SHA, which is ancestor of the advertised remote target. Client.Tests/ReviewWorkflowTests.fs contains AcceptedSnapshotCannotBypassAdvancedRemoteTarget asserting the obsolete rejection. Change the contract and tests, not only an Integrator prompt.

Required behavior and trust boundaries

  1. SubmitIntegration: require exact independent Accepted canonical review, pinned immutable remote review ref/commit and target ref, valid source identity and create-only managed integration ref, idempotent publication and CAS as today. Record the observed current target SHA for provenance. Do not require the current target to be an ancestor of the reviewed source. Do not let a mutable source branch substitute for the reviewed immutable SHA. Preserve all source and effect fencing, or strengthen it where needed.
  2. Integrator: fetch the latest target, compose the exact Accepted source into an isolated clean worktree, verify clean conflict-free merge or already-fast-forward case, inspect resulting diff/scope, run appropriate merged-result tests, and publish the target with an ordinary non-force fast-forward. If target races, re-fetch, reconstruct and re-verify the result; never force-push or replay an uncertain publication. A target moving is ordinary concurrency, not a reason to seek a new source review.
  3. CompleteIntegration: accept either (a) direct accepted commit when target advancement is genuinely fast-forward-compatible, or (b) a verified integration merge containing BOTH the current target lineage and the exact immutable reviewed source commit. Record the distinct SubmittedCommit and IntegratedCommit with remote ancestry proof. For the merge case, require suitable verifiable topology/provenance (e.g. first parent is the target snapshot used for composition, second parent the pinned Accepted source; first parent descends from the captured target head) and a clean deterministic merge result. Do not accept arbitrary unreviewed alterations just because the merge has both commits as ancestors: compare merged tree to Git's conflict-free mechanical merge result or an equivalently strong, reproducible integration-delta proof. Reject unrelated/unreviewed changes and fabricated parentage.
  4. Conflicts: when non-mechanical conflict resolution or changes to reviewed behavior are required, obtain a focused independent review of the integration-specific changes before publication. Do not require a completely fresh full source review for a clean merge. Where the current ledger cannot encode this exception safely, fail closed and document the specific missing evidence rather than inventing blanket authority.
  5. Record and verify: retain exact source SHA, original accepted review/ref, target head observed at submission and actual composition, merge/integration SHA, source/target ancestry, merged test evidence, operation IDs and final verified remote target receipt. Preserve already-integrated/idempotency semantics, older legacy integration entries and recovery from uncertain effects.

Tests and acceptance

  1. Replace AcceptedSnapshotCannotBypassAdvancedRemoteTarget with a positive two-clone real-bare-remote test: accepted S from B, independent target advance T from B, submit S after T (must succeed and retain S), produce a clean two-parent integration I, publish non-force, complete with I distinct from S, verify exact receipt and ancestry. Test a second target advance before publication with safe retry/recomposition.
  2. Negative tests: review not Accepted, forged SHA/ref, invalid target ref, missing reviewed source, missing/unrelated parent/target ancestry, arbitrary extra edits in a merge tree, conflict requiring unreviewed resolution, unsafe rewritten remote target, duplicate/replayed operation or uncertain create-only integration ref. Test direct fast-forward path and historical compatible records.
  3. Run the exact affected .NET 11 Release test group and relevant integration suites; provide real OS exit/count/duration, source SHA, diff scope and git diff --check. Independent frozen source review before promotion and exact merged-result verification before non-force publication; no self approval.
