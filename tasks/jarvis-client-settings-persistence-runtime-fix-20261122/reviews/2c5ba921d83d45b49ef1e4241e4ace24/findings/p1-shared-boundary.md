# F4 — Shared typed settings transaction contract not yet implemented

The mandatory Lead cross-path contract requests **one client-local reusable operation** invoked by TUI, CLI and Worker25 selected-device dispatch. It must accept typed setting + Set/Unset, expected revision, authorization provenance and runtime snapshot and return old/new stored values, config source, effective/runtime and override sources, applied/reconnect/restart flags, and typed validation/authorization/IO/CAS outcomes.

The frozen change adds `ClientConfig.applyAt`, `applyKey/applyUnset`, `applyRemoteAt` in `ClientConfig.fs:341-384`. These return only `ClientConfigSnapshot`/`string` error; TUI still directly invokes `ClientConfig.save(snapshot,staged)` in `Program.fs`/the SettingsHarness, with a hard-coded status paragraph (`ConsoleTui.fs:1409-1425`), while CLI separately prints a generic saved revision. Thus the common CAS implementation is useful, but it is not the requested typed service describing effective state and restart/reconnect boundary to all callers; remote transport is not yet integrated in Worker24's frozen source. This is not a demand to edit Worker25's leased protocol files. It is a missing promised Worker24 service/API contract that affects transparent end-to-end settings behavior.

**Remedy:** Agree a minimal typed service and ownership boundary with Worker25/Lead before changing anything. Keep `ClientConfig.save` as low-level persistence, route all caller-visible success/authorization/status through the same higher-level operation, and test explicit effective override/restart flags and error types without touching live WSL.
