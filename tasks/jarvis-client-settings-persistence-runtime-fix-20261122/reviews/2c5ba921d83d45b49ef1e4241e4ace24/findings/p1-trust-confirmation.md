# F3 — Actual trust increase from NoTrust to default PartialTrust bypasses TUI confirmation

**Concrete source path / consequence:** `Client/Modules/ClientConfig.fs:266` defines an unset trust level (`None`) as effective `partial`. `ConsoleTui.fs:2636-2651` shows a local confirmation only when the staged trust value is `Some "full"` and its stored original was not full, or the environment allowlist expands. Starting from stored `Some "none"`, selecting Trust and pressing `u` (unset) changes the effective level to `partial`. Pressing `s` invokes `saveSettingsUnsafe` immediately without confirmation, and next restart runs with expanded privileges. The mandatory shared settings contract explicitly requires local interactive confirmation for **any** trust increase. By contrast, `ClientConfig.applyRemoteAt` correctly ranks `Some "none"` below `None` and rejects this remote transition (`ClientConfig.fs:371-381`); the TUI parity gap is therefore clear.

The CLI `Program.fs:60-70` calls `applyKey/applyUnset` with no trust-elevation confirmation/provenance boundary; whether an explicitly invoked CLI command itself suffices as local authorization must be made explicit and verified against the original task's confirmation requirement, not assumed equivalent to the TUI.

**Suggested bounded repair:** Centralize effective-trust ranking (including unset/default) and local-approval decision in the reusable shared settings service, then exercise a disposable PTY negative (none -> unset/partial must not save without y; n/Esc must leave persisted none), a full-trust case, and remote refusal. Preserve no remote self-approval.
