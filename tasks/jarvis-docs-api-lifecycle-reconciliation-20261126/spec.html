Reconcile Jarvis API, lifecycle and version documentation

Goal: clean up the human-facing documentation so it accurately describes the current Jarvis command surface, lifecycle semantics and client/server protocol state. This is a documentation-only task; code and instruction configuration are owned by separate workstreams.

Scope

Audit the relevant maintained documents, prioritizing docs/AgentCommandSurface.md, docs/OrchestrationMigration.md and docs/ServerUpdates.md. Find stale version statements, duplicated or contradictory lifecycle guidance, retired tool names, misleading command descriptions, and ambiguity between the client transport capability catalog returned by list_commands and the actual public MCP tool schemas generated from MCP method signatures. Do not edit AGENTS.md, launch/role templates, instruction configuration, docs/specs/**, docs/tasks/** or source code; another workstream owns those areas.

Required outcome

  • Document the actual distinction between MCP tool definitions (names, parameter schemas and descriptions exposed by the active MCP server) and the Jarvis client/server list_commands capability catalog. Do not imply that a capability description or missing InputSchemaJson is the authoritative MCP argument schema.
  • Describe lifecycle operations accurately: checkpoint preserves Working; yield transitions the assigned Working session to Ready; completion releases the assignment; a rejected tool call does not transition state; success must be established from the tool result/canonical state.
  • Use exact current public names and required parameter names. Clearly label retired/internal wire actions and historical migration notes so they are not mistaken for current public tools.
  • Reconcile protocol-version documentation against verifiable source and the current observed deployment evidence. The connected server and selected Serdan-Home device reported protocol 3.68 on 2026-11-26; distinguish that observation from repository-supported release facts and avoid timeless claims based on a single observation. Do not claim a deployment occurred as part of this task.
  • Remove duplicated explanations where a canonical section can be referenced. Keep the documents concise and preserve useful historical migration context.
  • Check links, anchors, command names and version references across the scoped documents. If a discrepancy cannot be established, record it as an explicit open question rather than guessing.

Validation

  • Cross-check every normative API statement against current source or actual tool definitions; record source paths/lines in the change or review summary.
  • Run git diff --check and the repository's applicable documentation/link validation. Search the scoped docs for obsolete public method names and stale protocol claims.
  • Commit on a new isolated branch/worktree based on verified current origin/main; bind exact source before editing. Submit the exact candidate for independent review.
  • No MCP implementation changes, instruction/prompt changes, integration, deployment, server restart or protocol cutover.
