Correct MCP catalog descriptions and verify public tool schema parity

Goal: ensure the Jarvis MCP API presents accurate, actionable tool names, descriptions and parameter schemas, and that its separate client/server capability catalog does not misdescribe operations. This task owns MCP implementation and MCP-specific tests only.

Evidence to investigate

The live list_commands response reported protocol 3.68 and advertised CheckpointAttempt, YieldAgent, CompleteAgentWork and StartTasklessWork with the generic description “Creates/assigns/starts tasks and binds immutable review base.” This is misleading. In source, Server/McpTools.fs builds ledgerAliasCapabilities by copying generic wire capability descriptions for public aliases; the actual MCP methods have their own Description attributes and typed signatures. The live MCP tool definitions in the refreshed session expose accurate signatures, while the client capability catalog is a distinct surface.

Scope

Inspect Server/McpTools.fs, AgentProtocol command capability definitions and Server.Tests/ServiceTests.fs catalog/schema tests. Audit representative lifecycle tools plus other aliases inheriting generic descriptions. Verify which schema belongs to which surface and whether the MCP server's actual public method signatures/descriptions are registered as expected. Do not edit docs or instruction-bearing artifacts; the other workstreams own those.

Required outcome

  • Give each advertised client capability alias an accurate, concise description of its own operation. At minimum cover checkpoint, yield, complete, taskless start/yield/recovery, assignment recovery, review claim/decision and other aliases that currently inherit unrelated generic descriptions.
  • Preserve the distinction between the client/server command capability catalog and actual MCP tool schemas. Do not fabricate or blindly copy MCP JSON schemas into InputSchemaJson; first establish the intended contract and source of truth. If the catalog is intentionally only capability negotiation, document that in code comments/tests and ensure its descriptions remain truthful.
  • Ensure actual MCP method descriptions and signatures remain consistent with implementation and that required arguments are discoverable from the registered MCP tool definitions. Do not change public method signatures or protocol version unless a concrete defect requires it and compatibility impact is explicitly justified.
  • Add regression tests that fail if lifecycle aliases are assigned generic unrelated descriptions, if a public MCP lifecycle method disappears from the registered catalog, or if required parameters drift from the intended signature. Include representative tests for CheckpointAttempt and YieldAgent.
  • Review all alias capability families for the same copy/paste defect; fix the root cause rather than only these two entries.

Validation and boundaries

  • Run focused Server Release tests for catalog consistency and MCP method signatures; record exact commands, source SHA, exit code and test counts.
  • Commit on a new isolated branch/worktree based on verified current origin/main; bind exact source before editing. Submit the exact candidate for independent review.
  • No production deployment, server restart, client update, tool catalog refresh operation, protocol cutover or unrelated server behavior changes. Report any operational refresh requirement separately; the Operator will authorize deployment if needed.
