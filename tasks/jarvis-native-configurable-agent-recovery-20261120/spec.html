P1 — Native configurable deterministic stale-agent recovery

Operator decision (2026-11-20): Replace LLM-based Health sweeps with a deterministic Jarvis runtime operation. There is no judgment in “Working and 10 minutes since last Jarvis activity”; no ChatGPT Health turn should be required. Integrate this into the existing client-side activity/schedule infrastructure, agent observation and canonical recovery/correction transitions. Do not invent a second monitoring platform or defer on speculative browser/job activity.

Configurable policy

  • Expose an operator-editable agent inactivity recovery timeout through the existing Jarvis configuration mechanism, surfaced by the existing config show/set commands (and, where straightforward, per-project override). Default 600 seconds for backward-compatible behavior. Choose and document explicit value validation. A documented disabled setting is useful; do not encode “disabled” as an ambiguous negative timeout.
  • Recovery eligibility must be based on the configured duration, not another hidden hard-coded 10-minute value. Configuration updates must actually affect the next eligibility decision; report the effective policy and next due time through ordinary diagnostics. Multi-client execution must not silently use inconsistent/unknown policy without authoritative reconciliation.

Deterministic operation

  1. Enumerate actual registered agent IDs from canonical state—never role labels Worker/Reviewer or invented agent IDs. Reuse current observation and canonical ledger APIs.
  2. For each actual Working agent, compute deadline = last genuine Jarvis tool activity + configured timeout. New activity invalidates/reschedules the previous deadline. When deadline arrives, re-read current state and recover ONLY if still Working and still past deadline.
  3. Perform the existing exact optimistic-concurrency version/generation state transition to Ready, preserving the same focused assignment, original pinned instructions/task/source/review history and checkpoints. Do not inject Health-specific instructions into the recovered agent. A CAS conflict is an ordinary skip/re-evaluate, not a reason for speculative duplicate resets. Reconcile uncertain operations by their exact IDs; never replay uncertain effects.
  4. Use client/runtime scheduling rather than a browser-based Health agent. On restart/reconnect re-evaluate missed deadlines from the best authoritative activity evidence available, without assuming an unknown timestamp means stale. Preserve current multi-project and multi-client correctness. No agent launch, source code effect, review or integration is implied by recovery; Manager continues dispatching Ready agents.
  5. Record a small summary per sweep/transition: eligible count, recovered IDs, skipped CAS races, real errors, effective timeout and last successful check. The mechanism must function without an LLM, browser tab, prompt or standing Health task. Retire the two existing browser Health schedules only after native acceptance, with Operator-aware rollout; preserve Manager schedules.

Acceptance

Deterministic tests: just below threshold no recovery; exactly at threshold eligible; new activity resets deadline; Ready/Parked/Blocked untouched; one recovery only under competing instances/CAS races; recovered instructions unchanged; missing timestamps safe and visible; restart/reconnect due-time reconciliation; invalid config handled predictably; two project rosters and real Worker 5/Reviewer 1 IDs versus nonexistent role aliases. Demonstrate actual native operation end to end and exact unfiltered Release tests. Document operator config command/example, default, validation and disable behavior. Do not claim completion just because an earlier manual Health sweep worked.

Scope: Jarvis Scheduler/Challenges automation critical path, not Telos Work/SQLite migration. Lead owns concrete decomposition/priority, Manager alone assigns and launches Workers, Reviewer independently reviews exact source, Integrator promotes accepted work.
