Jarvis client version, build identity, and protocol display

Priority: P1. Jarvis has exactly two Operator-controlled clients, on Linux and Windows. They are upgraded together. The current default assembly version is not a trustworthy build identifier, while AgentProtocol.version is a separate wire protocol identifier.

Outcome

Each client must clearly report the exact code it runs: a human-readable application version, Git commit/build identity, protocol version, and target platform. The application's version and the protocol must be visible in the client TUI even when disconnected.

Requirements

  • Use existing .NET assembly/informational-version and publish machinery rather than a separate handwritten registry. Embed release version, full source commit, and RID in builds. Mark non-release/dirty builds appropriately; a source change is distinguishable without artificial semver increments.
  • Show both version and protocol in the visible terminal client, preferably a compact status/header/footer. Expose abbreviated commit nearby or in a detail view; present the same information offline with --version. Layout must remain usable in a small terminal and after reconnect.
  • Report the actual running build identity in client registration and server diagnostics; do not substitute the server's build or most recent download. Preserve existing supported-command negotiation. No lock-family admission registry, mixed-version migration framework, minimum-client-version gate, or legacy compatibility test matrix is required.
  • Publish platform binaries with reproducible identity and SHA-256 verification. Use immutable versioned artifacts and an unambiguous current/latest manifest, built on scripts/build.cs, scripts/publish-client-downloads.cs, and docs/ClientDownloads.md. Keep current stable filenames if convenient for the two-client update workflow, but do not implement a special backwards-compatibility layer.
  • Retain existing Linux/macOS self-update behavior and manual Windows update path. Windows self-update is outside scope. Neither client should be restarted or updated without separate Operator authorization.

Acceptance

  • Linux and Windows Release binaries expose correct app version, commit, protocol, and RID in TUI, offline CLI, and server diagnostics. Dirty builds are distinguishable from clean published builds.
  • CLI works without network/authentication; TUI shows both requested version fields while disconnected and on representative small terminals.
  • Release manifest metadata matches embedded binary identity and SHA-256; corrupted or mismatched downloads are rejected. The two clients can be identified and updated from the same approved release.
  • Independent review and Release validation before merge or deployment. No unnecessary protocol-family migration or old-client compatibility platform.
