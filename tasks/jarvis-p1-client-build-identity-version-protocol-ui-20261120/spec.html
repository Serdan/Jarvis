Jarvis client build identity, release provenance and visible version/protocol

Priority: P1 — release correctness and diagnostics. Today the client registers Assembly.GetExecutingAssembly().GetName().Version, which defaults to an undifferentiated 1.0.0, and separately advertises AgentProtocol.version (currently 3.68) plus supported command names. The server records those values and negotiates command intersection; protocol mismatch is diagnostic rather than a universal rejection. Client artifacts use stable platform filenames and SHA256SUMS. This does not reliably tell an Operator whether Linux and Windows run the same source revision, and it complicates safe mixed-client lock migrations.

Outcome

Give every release an independently verifiable application version and Git source/build identity, distinct from the wire protocol version. Surface both the application version and protocol directly and persistently in the client's terminal UI. A versioned, immutable artifact and a current-release channel manifest must make it possible to identify and retrieve the exact recommended binary without losing existing download/update compatibility.

Implementation guidance

  • Use existing .NET assembly/informational-version and build/publish machinery (not a second hand-maintained version constant). Inject a deterministic source commit at publish/build time; distinguish dirty/unverifiable developer builds from clean releases. Preserve explicit human release version, full commit hash and platform/runtime identifier. Make it inspectable locally without needing network access. Do not turn every ordinary build into an automatically incremented semantic release.
  • Client UI: show the human application version and the AgentProtocol.version in the visible main TUI status/header/footer; ideally include abbreviated commit/build identity in the same compact location or accessible detail view. It must appear when disconnected and stay correct across reconnects and self-update. Do not bury these only in startup logs. Add a clear --version or equivalent noninteractive CLI output showing version, commit, protocol and RID, without requiring authentication or server access.
  • Advertise and record honest build identity in client registration and connection diagnostics. Evolve wire fields backward-compatibly for older installed clients and servers; retained ClientVersion should be meaningful. Identify the actual running binary rather than reporting the server release or newest download. Existing supported-command negotiation stays authoritative for command availability; do not equate matching version strings with behavioral compatibility.
  • Extend scripts/build.cs, scripts/publish-client-downloads.cs and existing docs/ClientDownloads.md with immutable platform-specific release artifacts / manifest entries recording version, commit, RID and SHA-256 plus a separate explicitly selected current/latest channel. Continue to support the existing stable JarvisClient-{rid} names and SHA256SUMS during transition, without silent rollback or an ambiguous mixed-artifact upload. The channel manifest must be published atomically after its referenced binaries; clients verify the corresponding hash before activation.
  • Define an explicit compatibility policy at the existing protocol/command-negotiation boundary. Where a behavioral or schema break is known, provide a testable minimum-compatible-protocol/build gate or fail-closed capability marker rather than relying on lexical comparison of semantic version strings or silently assuming old clients are safe. Keep benign protocol skew and supported-command negotiation workable; no gratuitous universal strict equality.
  • Keep the existing Linux/macOS self-updater and .prev rollback behavior; do not make Windows self-update a hidden prerequisite. Windows public artifact identity and manual update path must nonetheless be correct. No deployment, client restart, or updater activation in this task without separate Operator authorization.

Acceptance evidence

  • Clean Release build for Linux and Windows yields an intentional app version, exact commit, platform and protocol that can be read from the binary/CLI, registration diagnostics and visibly from the TUI; a dirty development build is explicitly distinguishable. A commit-only source change produces a distinct build identity without falsely incrementing semver.
  • Test client TUI appearance/fit at representative small terminal sizes, including disconnected state, and verify version/protocol values do not drift on reconnect. Verify CLI output in a no-network environment.
  • Build/release tests verify immutable filename/metadata/checksum correspondence across all published RIDs, repeatability for a frozen source, atomic channel advancement, tamper rejection, and that older clients still find the stable legacy download and checksum. Never ship an artifact whose embedded commit/version disagrees with its manifest.
  • Client registration, server diagnostics and old-client compatibility tests cover mixed application versions, protocol mismatch, missing optional identity fields, actual unsupported commands, and a known unsafe behavioral incompatibility. No silent wrong-binary selection or accidental release downgrade.
  • Independent review and Linux/Windows Release verification are required before any integration/deployment. Coordinate delivery through Lead, Manager, Reviewer and Integrator; avoid parallel standalone version registries or unrelated updater rewrites.

Scope clarification (Operator, 2026-11-20)

Jarvis currently has two controlled client installations, updated together. The separate pending-intent named-mutex cutover does not require an elaborate backward-compatible lock-family registry, admission service, or mixed-client migration mechanism. Preserve the approved application version, Git commit, protocol display, release provenance and ordinary command negotiation deliverables of this task. Coordinate the two client replacements directly under jarvis-p1-safe-pending-lock-migration-20261120; do not turn version display into a prerequisite for an unrelated lock-protocol compatibility platform.
