Switch Jarvis pending-operation locking to exact UUID named mutexes

Operator scope decision (2026-11-20): There are exactly two Jarvis clients, on controlled Linux and Windows machines. They will be updated together in a coordinated stop/update/start. No mixed-generation compatibility machinery, per-client family registry, or online protocol migration is needed. Previous file-lock reclamation branches and their rejected reviews are historical investigation, not acceptance requirements for this direct cutover.

Target behavior

  • Use one OS-managed named cross-process mutex per (ledger binding, operation UUID), with a bounded 60-second acquisition wait. Different UUIDs — even with the same three-character prefix — do not block one another.
  • Do not create per-UUID lock files, stripe files, cleanup workers, admission caps, or persistent lock debt. Validate journal symlink protections as before. Kernel handles are disposed/released on completion and process exit.
  • Correctly handle an abandoned mutex after a crash, without treating that as proof that an uncertain remote Git effect failed. Preserve saved UUID recovery, canonical ledger verification, and never replay an ambiguous operation callback automatically.
  • Test same UUID exclusion across independent processes on Linux and native Windows, unrelated UUID concurrency, owner death, timeout if the lock cannot be acquired, no lock artifacts, and no replay on IOException. Use Release builds.

Rollout (separate explicit authorization)

Stop both existing clients, verify both are stopped with no in-flight remote effects requiring reconciliation, update both controlled binaries from the same approved source, then restart and check registered client/protocol information.
