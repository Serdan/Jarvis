Safe cross-version exact-operation lock protocol

Observed problem: Windows crashed when recursive PendingIntentJournal.acquire exhausted its stack during contended FileShare.None opens. cdc83c0df fixed recursion. 95a471fc5 currently published a shared legacy stripe gate plus exclusive per-UUID lock files; Linux and native Windows cross-process tests passed. But persistent per-UUID files grow without bound and cannot be unlinked safely while another process may hold an old inode.

A second branch, fix/named-uuid-lock-20261120 at 1be1c1cdd, replaces per-UUID files with named cross-process OS mutexes and passes Linux plus Windows native tests. Do not merge/deploy it directly: clients running the short-lived 95a per-UUID file protocol would share the legacy stripe with new named-mutex clients but would not exclude each other for the same UUID.

Outcome

Bounded, exact-UUID, cross-process serialization for pending operations with no false collision between unrelated UUIDs, no long-lived per-operation lock-file leak, and a proven mixed-version migration protocol covering legacy exclusive-stripe clients, the deployed perUUID-file client, and named-mutex clients. Preserve idempotency and non-replay for uncertain Git writes.

Acceptance

  • Design and test a safe migration gate: either coordinate/verify retirement of the perUUID-file protocol before shared-stripe+mutex activation, or implement an automatic backward-compatible exclusion mechanism. Never infer safety from absence of a lock file alone.
  • Two instances with the same UUID serialize throughout journal persistence, remote Git operation and cleanup; unrelated UUIDs in the same legacy stripe progress concurrently in the final mode; old exclusive stripe owners block new operations. Prove across processes and on native Windows and Linux.
  • Retries only on genuine sharing violations, with bounded total wait and operation-safe failure/diagnostics. Crash/abandoned mutex recovery preserves saved UUID verification, not blind remote replay.
  • Prevent unbounded artifact accumulation. Reuse existing lock infrastructure and do not delete lock files unsafely.
  • Ensure rollback/old download behavior is documented and tested; do not silently activate an incompatible client cutover.

Use isolated implementation and independent review. Current public Windows binary is 95a471fc5; branch 1be1c1cdd is a tested experiment, not authorized for unguarded public rollout.
