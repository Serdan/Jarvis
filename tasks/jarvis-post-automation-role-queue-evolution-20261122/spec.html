Operator decisions to preserve

  1. No named or numbered Agent IDs in operator-facing coordination. Work is owned by durable task/work-item identity and a role queue, not Worker N / Reviewer N assignments or session identity. A role is a versioned set of instructions, queue subscriptions, and capabilities; zero or many ephemeral executions may serve it. Minimal launches bootstrap the role/context, then claim canonical work via one bounded operation. Internal opaque launch/execution/lease/operation identifiers remain necessary for audit, idempotency, independent review, effect fencing and crash recovery; they are not persistent Agents or operator-chosen IDs.
  2. Per-role limits. Configurable max concurrent executions for each role, scoped to the project. Role-based admission is not permission; real authority comes from authenticated account and reservation-scoped grants. Distinct roles may share one underlying implementation but a launch has one pinned role and one primary claim.
  3. Per-project limits. Configurable max in-flight executions per project across all roles and machines, including launches reserved/registered/uncertain. Distinguish a hard project cap from scheduler priority/fairness; capacity limit is not an entitlement or guaranteed share.
  4. Per-machine limits. Configurable max in-flight execution slots per registered machine; enforce actual project/worktree availability, role capabilities, browser/tool compatibility, authenticated device binding, and offline status. The scheduler must not assign a local-only source task to a machine without access. Optional future weighted CPU/GPU/memory budgets require measurement; simple count limits first.
  5. Task-attached notifications. Durable messages, warnings, review feedback, blocker evidence, and required decisions attach to canonical task/work-item/incident subjects rather than ephemeral agents. A role's attention view is a projection over tasks it can handle, not a second message authority. Reading is not acknowledgment; separately track Unread, Seen, Handled/Resolved with immutable actor/receipt and explicit handoff. Closed/blocked task attention must not silently create runnable work; system-wide incidents create durable incident work rather than private DMs.

Architecture hypotheses (to validate, not silently mandate)

  • Use an authoritative composable work graph, with a flat indexed projection of eligible work stages, stage generations, hard dependencies, immutable frozen reviews, and versioned claims; no long-lived Manager/Health model loops once native deterministic scheduling and recovery actually pass their acceptance gates.
  • Scheduler ranks eligible work by (blocking downstream work, explicit Lead priority, availability FIFO) within feasible role and machine constraints. Do not add arbitrary aging or quotas without observed starvation evidence. One ephemeral launch reserves one capacity credit and gets at most one primary work claim. Work can wait indefinitely without occupying a model slot.
  • Intersect project, project-scoped role and machine limits at admission, count unregistered/uncertain/stalled effectful sessions until verified terminal/recovery, and use a transaction or explicit fail-closed reservation/reconciliation protocol. Do not claim cross-ledger atomicity where none exists. Match flexible roles to queue demand without stranding narrower role capacity.
  • Keep exact source/ref provenance, Reviewer/author independence based on frozen evidence rather than named Reviewer, once-only external Send, no retry on OutcomeUnknown, STOP/revocation fences, authenticated machine bindings, and idempotent terminal release. Browser tab closure is never evidence of execution termination. Server-authoritative activity and 10-minute stale-agent policy apply only to actual verified executions.
  • Keep Jarvis execution-plane interfaces small and useful by themselves; future Servitor/Telos integration may consume its queue, claim, evidence and task APIs, but must not dictate a premature rewrite or duplication of canonical authority. Reuse accepted Work assets selectively; migrate existing in-flight assignments holistically, with historical read-only continuity and explicit rollback.

Operator decision: scheduling, priority and manual launch

The Scheduler handles ordinary dispatch. Every Work item, including each review request, has a priority. Queue ordering uses priority alongside the previously specified ordering factors, subject to eligibility. To expedite an item, the Operator can ask an interpreter to change its priority; the Scheduler handles dispatch. The Operator can also ask an interpreter to launch a role such as a Reviewer manually. Manual launches bypass Scheduler caps. A manual launch does not require changing persistent capacity settings. This describes the Jarvis operational interface; the interpreter is a caller.

Operator decision: priority inheritance

When ranking eligible work, the Scheduler accounts for the urgency of downstream Work that it currently blocks, including when the blocker is a review request. Preserve the blocker's explicit priority. Derive inherited urgency from current dependencies and priorities so that a priority change, completed review, or removed dependency removes or updates its contribution. Other active dependencies continue to contribute. Keep the existing eligibility and queue-ordering rules.

Operator decision: available inference profiles

For eligible Work, first filter profiles by hard requirements and availability. Soft preferences choose among eligible profiles available now. When the preferred provider is at capacity, dispatch using another available eligible profile without waiting for the preference. A provider explicitly required by the Work is a hard constraint: if no qualifying profile is available, the Work waits. No preference timeout is needed.

Operator decision: project-level metered fallback

Automatic fallback to a metered inference profile requires the project's explicit opt-in and sufficient configured budget. Account-wide availability alone does not authorize spending. If the only otherwise eligible profile would incur unauthorized spending, leave the Work waiting and show the reason. Within the project's authorization and budget, the Scheduler may dispatch without per-launch approval.

Scheduler intent reassessment — 2026-11-26

Status: design analysis. Captured at the user's request to challenge the scheduler's assumptions. Existing commitments remain in force. The proposed Work execution policy below awaits an explicit decision. This record grants no implementation, activation, or publication authority.

Purpose. Turn eligible Work into verified progress with little human intervention. A timer tick, a browser Send, and a started agent are intermediate events. Progress requires an authorized claim, a meaningful Work transition, or a specific blocker that can be acted on. An exact frozen review remains independent of implementation and may advance the queue in its own right.

Observed evidence. The deployed recurring callback uses a 60-second tick and selects at most one Ready episode. It sorts by priority and issuance sequence, counts Working agents for configured limits, and classifies generic send errors as unknown even though a tab-open rejection can occur before any prompt send. The manual reviewer hit the tab limit. Three Ready episodes had an original intent and no durable pre-send proof, and the live schedule presented a generic completed tick while skipping them. A missing durable conversation URL coexisted with confirmed agent tool activity on other launches, while the bridge retained their tabs. These observations do not establish the exact outcome of any of the three held sends. Sources: Client/Modules/ScheduledReadyResume.fs (candidate selection, next-operation proof and execution), Client/Program.fs (registered scheduler mapping), Client/Modules/BrowserBridge.fs (cleanup), automation-recover-dispatch-after-tab-limit and automation-role-aware-reviewer-dispatch.

  • Runnable is a property of Work. An idle execution identity, a standing assignment, a queue label, and an elapsed timer are insufficient eligibility evidence. Ready means a Work stage has a permitted next action. A job wait affects only its dependent stage. Durable terminal success, failure or cancellation wakes the continuation; missing or evicted evidence has its own diagnosable state. Events prompt authoritative re-evaluation; a bounded rescan covers restart, missed notifications and finish-before-registration.
  • Polling cadence and throughput are implementation choices. One minute and one launch per tick are current rollout settings, not scheduling requirements. Measure runnable-to-claim latency, useful concurrency, duplicate effects and wasted inference. Use events where valuable, reconcile periodically, and derive dispatch concurrency from real resource/provider limits and work demand. A browser-tab limit is an adapter resource constraint, independent of Working counts and user-configured caps.
  • Review demand drives review dispatch. Zero eligible review items means zero reviewer launches. Multiple eligible items may progress concurrently under actual limits. A runnable claimed review resumes with its checkpoint; a blocked claim waits. Preserve author/reviewer independence and one canonical owner per review. Dispatch should record in-flight demand so one review does not summon several reviewers; another valid claim or a revoked review can resolve obsolete demand.
  • Priority, fit and capacity answer different questions. Priority ranks genuinely runnable items, blocker importance can propagate, and FIFO is a tie-breaker. A milestone is for scope and priority, never admission. One held item or unavailable provider must leave independent eligible work runnable. Historical strict roster assumptions are not evidence that every project needs a cap or a comprehensive census. Measure starvation and overshoot before adding policy; preserve the current optional Working-count cap semantics for legacy rollout.
  • Distinguish launch, acknowledgement, claim, external effects and cleanup. A positively proven pre-send failure is eligible for bounded retry; a matched turn without a URL is acknowledgement evidence, not an authorized claim; a missing URL or expired timer is not death evidence. Close verified scheduler-owned tabs when requested, independent of send certainty. Keep original launch identity and ensure unpublished or unknown attempts have explicit recovery and diagnostics. An exact correlated claim can settle dispatch progress even when URL capture fails.
  • Guarantee one authorized execution, not an impossible exactly-once provider launch. With best-effort remote inference, a provider may duplicate or fail to report a launch. The existing Operator lease decision supplies a design boundary: finite claims, monotonically fenced generations and rejection of late stale mutations. An old model might still compute. Uncertain browser, Git, review or other external effects already started keep their original effect identity and require independent reconciliation. Claim expiry cannot authorize replay or revoke credentials that bypass the fence. Restrict automatic replacement to effectively fenced paths.
  • Operator visibility is part of liveness. Report empty queue, waiting on dependency, blocked by capacity, launch outcome unknown, claim started and actual progress as distinct states. For an all-held queue, show the exact Work/attempt, evidence, reason, and admissible recovery. No second monitoring inference loop. Provide a visible replacement control for legacy holds without altering assignment history or requiring defer/resume.

Proposed boundary and sequence. Finish automatic review dispatch on the deployed route, with tab cleanup and honest hold diagnostics wherever needed to make it usable. Keep legacy unknown sends fenced and explicitly recoverable. Do not make legacy agent-state cleanup, provider preference, a new storage backend, or a comprehensive legacy scheduler redesign prerequisites to moving into Work. In Work, prove the narrow real path submit → eligible role → launch → fenced claim → yield on job → terminal outcome → same Work resumes → independent review, with a crash/unknown-send branch and another independent item progressing. Reuse existing scheduler and ledger pieces that satisfy the invariants. Preserve the settled cutover policy and historical data.

Open policy decision. If an inference provider cannot prove whether a launch started, may Work automatically launch a replacement once it can enforce that only the replacement can claim or mutate that Work and no uncertain external effect will be replayed? Recommended yes for provably fenced Work, with bounded retry, visible cost and diagnostics. If those protections are absent, keep the launch held for explicit recovery. This is a choice about accepting possible duplicate inference, not duplicate authoritative work.

Operator decision — dispatch on state transitions, 2026-11-26

The Work scheduler is event-driven. Once Jarvis knows a committed transition changed eligibility or capacity, request scheduling immediately. Do not use a recurring dispatch heartbeat or a fixed one-launch-per-minute pace. This supersedes the periodic rescan suggestion in the scheduler reassessment above. The currently deployed timer is rollout infrastructure.

Wake on changes to runnable Work and review queues, claims, dependencies, capacity, project enablement, and provider or device availability. A job's durable terminal result is a transition. For time-based waits, arm a one-shot wake for the next known deadline. Reconcile durable state at startup, reconnect and resubscribe; ensure cross-process commits and missed or coalesced notifications can be caught up through a durable cursor or verified head comparison. A wake requests re-evaluation of canonical state and never authorizes a launch by itself. Drain eligible demand up to actual admission limits and stop when nothing else can start. Reuse the existing reactive wake coordinator where it satisfies these requirements; verify the live producer subscriptions and consumer wiring independently.

Acceptance: idle queues generate no recurring evaluation; a committed transition starts newly eligible Work without waiting for a tick; several independent items can dispatch within capacity; events duplicated, coalesced, or committed during reconciliation yield no missed work or duplicate sends; restart catches up committed transitions and elapsed deadlines.

Operator decision — five-minute launch check-in, 2026-11-26

An agent reads its inbox as its first action. For each scheduled launch that may have reached Send, start a durable five-minute deadline at the send boundary. The first authenticated inbox call or other positively attributed Jarvis activity from that launch confirms it started; a conversation URL is unnecessary. Unrelated activity, including a read about the agent, does not count.

If five minutes elapse with no attributed check-in and Jarvis has authoritative activity evidence, deem the launch failed for scheduling purposes and make a replacement eligible on the same work or assignment. Recheck eligibility, project enablement, STOP and capacity, then authorize the replacement once using the current generation/launch fence. Preserve the original record and never replay an uncertain effect that the original execution already initiated. A confirmed pre-send failure may retry sooner. Unavailable activity evidence is a separate, visible diagnostic and is insufficient to deem a launch failed. Recognize or fence a late check-in so it cannot take authority from a replacement.

Use a one-shot wake at the deadline. Recover recorded deadlines after restart and test 299/300/301-second boundaries, simultaneous check-in and expiry, delayed and duplicate events, wrong launch identity, unavailable evidence, and a late agent after replacement. This supersedes the previous indefinite hold for a missing launch acknowledgement; it does not change the separate timeout for a session that has already checked in.
