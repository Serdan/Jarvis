Post-Automation milestone: Jarvis role queues and bounded ephemeral execution

Status: PLANNING ONLY — explicitly deferred until the Automation milestone has passed its independent acceptance and separate Operator cutover decisions. This durable planning brief is NOT runnable implementation demand, an assignment, a source lease, approval to integrate, or authorization to enable a Scheduler. Do not assign or launch agents for this task without a new explicit Operator implementation GO.

Scope: Continue evolving standalone Jarvis even if Servitor/Telos later supersedes or composes it; prioritize a smaller, correctness-driven, useful local orchestration product and reusable experience. This is distinct from the historical deferred work-queues-ephemeral-executions broader Work/Telos/SQLite migration epic; no implicit reopening, child assignments or SQLite migration.

Operator decisions to preserve

  1. No named or numbered Agent IDs in operator-facing coordination. Work is owned by durable task/work-item identity and a role queue, not Worker N / Reviewer N assignments or session identity. A role is a versioned set of instructions, queue subscriptions, and capabilities; zero or many ephemeral executions may serve it. Minimal launches bootstrap the role/context, then claim canonical work via one bounded operation. Internal opaque launch/execution/lease/operation identifiers remain necessary for audit, idempotency, independent review, effect fencing and crash recovery; they are not persistent Agents or operator-chosen IDs.
  2. Per-role limits. Configurable max concurrent executions for each role, applying account-wide by default. Role-based admission is not permission; real authority comes from authenticated account and reservation-scoped grants. Distinct roles may share one underlying implementation but a launch has one pinned role and one primary claim.
  3. Per-project limits. Configurable max in-flight executions per project across all roles and machines, including launches reserved/registered/uncertain; no project may consume every global slot merely by creating tasks. Distinguish a hard project cap from scheduler priority/fairness; capacity limit is not an entitlement or guaranteed share.
  4. Per-machine limits. Configurable max in-flight execution slots per registered machine; enforce actual project/worktree availability, role capabilities, browser/tool compatibility, authenticated device binding, and offline status. The scheduler must not assign a local-only source task to a machine without access. Optional future weighted CPU/GPU/memory budgets require measurement; simple count limits first.
  5. Task-attached notifications. Durable messages, warnings, review feedback, blocker evidence, and required decisions attach to canonical task/work-item/incident subjects rather than ephemeral agents. A role's attention view is a projection over tasks it can handle, not a second message authority. Reading is not acknowledgment; separately track Unread, Seen, Handled/Resolved with immutable actor/receipt and explicit handoff. Closed/blocked task attention must not silently create runnable work; system-wide incidents create durable incident work rather than private DMs.

Architecture hypotheses (to validate, not silently mandate)

  • Use an authoritative composable work graph, with a flat indexed projection of eligible work stages, stage generations, hard dependencies, immutable frozen reviews, and versioned claims; no long-lived Manager/Health model loops once native deterministic scheduling and recovery actually pass their acceptance gates.
  • Scheduler ranks eligible work by (blocking downstream work, explicit Lead priority, availability FIFO) within feasible role and machine constraints. Do not add arbitrary aging or quotas without observed starvation evidence. One ephemeral launch reserves one capacity credit and gets at most one primary work claim. Work can wait indefinitely without occupying a model slot.
  • Intersect account-global, role, project and machine limits at admission, count unregistered/uncertain/stalled effectful sessions until verified terminal/recovery, and use a transaction or explicit fail-closed reservation/reconciliation protocol. Do not claim cross-ledger atomicity where none exists. Match flexible roles to queue demand without stranding narrower role capacity.
  • Keep exact source/ref provenance, Reviewer/author independence based on frozen evidence rather than named Reviewer, once-only external Send, no retry on OutcomeUnknown, STOP/revocation fences, authenticated machine bindings, and idempotent terminal release. Browser tab closure is never evidence of execution termination. Server-authoritative activity and 10-minute stale-agent policy apply only to actual verified executions.
  • Keep Jarvis execution-plane interfaces small and useful by themselves; future Servitor/Telos integration may consume its queue, claim, evidence and task APIs, but must not dictate a premature rewrite or duplication of canonical authority. Reuse accepted Work assets selectively; migrate existing in-flight assignments holistically, with historical read-only continuity and explicit rollback.
