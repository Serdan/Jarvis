2. Architecture decisions to incorporate

Work and three independent planes

  • Work: durable intent, specifications, acceptance criteria, graph/dependencies, milestone membership, stages, priorities, checkpoints, evidence, attention and history. Work is not owned by an Agent or a client.
  • Inference execution: ephemeral provider session with provider/profile, execution identity, lifecycle and fenced authority. ChatGPT and Codex are the real-provider coverage required for 2.0 release; Claude and other providers are follow-on adapters. Provider choice is independent of resource choice. Conversation IDs/URLs are optional diagnostics, never canonical identity, authority or continuation state.
  • Resources: independently registered/authenticated JarvisClient hosts and their capabilities: repository checkouts/worktrees, filesystem operations, process/build/test execution, browser instances/extensions and later other measured compute. A client is a resource provider, not the execution context or owner of the model session.
  • Server control plane: Jarvis server is authoritative for Work and orchestration. The intended single local SQLite transaction domain (WAL initially preferred) owns Work, executions/launches, claims/generations, capacity, host/resource registry, resource leases, job/Challenge continuation state, idempotent receipts, audit events and queue projections. In-memory projections are disposable. Git remains source-code and immutable source/review/integration provenance plus asynchronous readable backup, not the hot-path coordination authority.
  • Scheduler: deterministic server-side selection of eligible Work, compatible role/queue, available inference profile/provider, and required resources. It enforces authority and capacity; a client availability event is a reason to re-evaluate canonical state, not launch authority.
  • Challenges: durable blockers/continuations for jobs, timers, dependencies and human decisions. A model execution can checkpoint/end while an engineering job continues on a resource host. Job and execution lifecycles are independent.

Client/resource semantics

  • Use the concrete motivating scenario: Serdan-Home supplies repository checkouts and local process/build/test capabilities to a model execution that may be running elsewhere. The model execution does not run on Serdan-Home merely because it uses those resources.
  • Separate stable authenticated host identity from public deviceId routing labels, project/repository names, local paths, provider conversation IDs and model execution IDs. A reconnect updates the same enrolled host; replacing a machine requires explicit enrollment/identity semantics.
  • Clients advertise typed, bounded capabilities and constraints: supported operations, repository/source availability, OS/toolchain, browser/profile/origin support, concurrency/exclusivity, locality and availability. Begin with existing concrete capabilities; no Kubernetes-like fleet manager or generic distributed hardware allocator.
  • Server grants versioned, expiring, fenced resource leases scoped to Work stage/execution, host/resource, project/repository and permitted operations. Lease expiry revokes authority but does not prove that a process, provider session or external effect physically stopped. Stale generations cannot start new operations or mutate Work.
  • Resource operations/jobs have stable identities, bounded inputs/outputs and durable provenance. Client disconnect, process timeout or lost acknowledgement produces explicit unknown/reconciliation state where appropriate; never fabricate success or blindly replay an external effect. A build/test can outlive its initiating inference session and must remain independently observable and reconcilable.
  • Keep four lifecycles distinct: model execution liveness; host connectivity; resource-lease validity; engineering-job lifecycle. Do not reuse one heartbeat or stale threshold for all four. Closing a browser tab is never proof of model execution termination.
  • Initially support repository/worktree, filesystem, process/build/test and browser resources. GPU/weighted CPU/memory allocation and advanced pools are follow-on only if measured need justifies them.

3. Jarvis 1.0 maintenance branch and release strategy

  • Keep Automation stabilization and acceptance as the immediate execution frontier. Do not cut 1.0 from an unverified or non-deployable point.
  • After Automation passes independent acceptance, integration, release validation and uncertain-effect/job reconciliation, record the exact deployable release SHA, tested artifact/configuration and rollback procedure. Only then create stable/1.x from that exact commit and tag it immutably. This task must not create the branch or tag.
  • After the cut, stable/1.x is targeted maintenance/hotfix only; main is the Jarvis 2.0 development line. Never merge the 2.0 development line wholesale into stable.
  • A 1.0 hotfix branches from stable/1.x, receives focused Release/regression tests and independent review, merges back to stable and receives an immutable release tag as appropriate. Forward-port the semantic fix to main deliberately and validate it there; not every 1.0 implementation detail must survive in 2.0.
  • Keep the known-good 1.0 release, deployment procedure and rollback available throughout 2.0 development. Branch creation, release, deployment and hotfix execution are outside this documentation task.

4. Work as the 2.0 transition boundary

  • Resource management is part of Work architecture and execution admission; it is not a separate milestone that Work waits for.
  • Work implementation proceeds by dependency: reconcile architecture and current implementation; reuse/finish the existing SQLite transaction substrate and typed domain interfaces; establish host/resource identity and resource lease contracts; complete Work graph/queue/authority; implement durable Challenge suspension; integrate provider adapters and JarvisClient resource adapters; then event-driven Scheduler and Operator experience. Parallelize only after shared contracts and source ownership are explicit.
  • Do not build a second SQLite database, duplicate an existing accepted subsystem, or create a parallel resource manager. The implementation alignment must say exactly which existing tasks/code are retained, adapted, completed, superseded, deferred or blocked, with evidence.
  • Do not automatically reopen, cancel, assign or rewrite the existing Work SQLite tasks while preparing the document. If their remaining scopes conflict with the new target, record a recommendation and exact dependency for Operator decision.
  • Keep milestones as scope/progress/priority structures, independent of hard scheduling dependencies. Completion counts accepted deliverables / explicitly included milestone deliverables; task splitting or extra review does not silently change the denominator.

5. Planned clean-slate coordination cutover

  • Pause dispatch intentionally; uninterrupted rolling dispatch is not required.
  • Before switching, fence and reconcile every old execution, in-flight job, source writer and external effect that could still act. A missing session/tab or expired lease is not physical termination evidence.
  • Leave the old Git-backed coordination ledger intact as read-only historical evidence. Do not rewrite/delete it and do not dual-write Git and SQLite as concurrent live authorities.
  • Initialize 2.0 projects with blank coordination state. New projects start directly in 2.0. The Operator initiates selective manual migration of chosen Work, source refs and evidence; do not blanket-migrate Agents, task queues, claims or notifications.
  • Source repositories and project code are not blanked or migrated merely because coordination state is. Preserve immutable commits, reviews and integration evidence as references. Reissued Work must be fenced from old sessions and uncertain effects.
  • Cutover, DB activation, deployment and Scheduler enablement each require a separate explicit Operator GO.
