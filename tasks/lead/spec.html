Standing operator engineering policy — 2026-11-16 (newer guidance takes precedence)

Operator directive: Jarvis agents are trusted, capable engineers. Prefer a system that makes state, errors, decisions and repair information visible to agents over a system that attempts to prevent every theoretical invalid state. Avoid overengineering speculative edge cases without evidence of practical impact. This instruction supersedes older engineering assumptions in this task where they unnecessarily require exhaustive proofs, host restrictions, or automated denial mechanisms in the absence of a demonstrated problem. It does not itself activate production features or waive existing explicit deployment/migration/restart/host-policy consent requirements.

  • Trust agents and make recovery possible. Agents should be able to investigate, diagnose and resolve anomalies using clear state, logs, commit SHAs, original operation IDs, source/checkpoint history, error details and available repair tools. Explicit inconsistency is often recoverable; silent data loss or silent overwriting of changes is not acceptable.
  • Observability and recoverability before hard enforcement. Record enough durable evidence to understand and repair failures. Surface uncertain operations and the consequences; prefer an intelligible warning or actionable blocked state over sweeping lockouts. Make failure diagnosis a first-class workflow.
  • Enforce cheap, high-value correctness. Use straightforward Git fast-forward checks, source identity, bounded retries, explicit conflict reporting and simple validation where they prevent credible mistakes. Do not require formalized end-to-end proofs, immutable host ref policies, intricate cross-ledger fencing or expanded security machinery solely to eliminate hypothetical, low-impact edge cases. Reproduce an issue, establish a concrete plausible harmful pathway and weigh operational cost before adding such complexity.
  • Keep administrative and manual repair escape hatches. When a Git-backed Jarvis ledger is corrupt or inconsistent, an authorized agent should be able to repair the ledger data directly, rather than having to change application code merely to bypass overly restrictive interfaces. Prefer clear, auditable Git diffs, backups/known SHAs and a repair record over preventing all exceptional edits. Permissions and actual operator approval requirements still apply; do not conceal or silently overwrite data.
  • Reassess WQ03 proportionality. The purpose is safe enough source handoff without silent loss. Ordinary Git non-force pushes reject incompatible late updates; do not present a late push as automatically overwriting successor work. Evidence that an agent can force-update/delete an unprotected disposable WIP ref does not by itself prove the normal workflow will corrupt work. Prioritize durable continuation commit/checkpoint, visible uncertain push/job outcomes, straightforward reconciliation and agent-guided repair. Do not escalate host-wide immutable WIP rules, exhaustive mutating-job/terminal proofs or new account/CAS infrastructure as mandatory requirements without a demonstrated practical need. Existing fail-closed code may require an explicit reviewed design change before use; do not silently claim it is enabled.
  • Fix the cause, not the compliance apparatus. For WQ11 Windows full-suite slowness, find the hanging or slow test with bounded observable runs and process diagnostics; do not substitute ever-larger timeouts or new layers of gates for diagnosis.
  • Report blockers in actionable terms. Always distinguish blockers requiring operator input from those agents own. When operator action is truly required, describe the practical problem, why it matters, precise approval/decision needed and alternative. Do not ask for permissions solely because speculative defenses were written into an earlier task.

Review heuristic: Does this change resolve a demonstrated problem or materially improve information and recovery? Can an agent still diagnose and repair unexpected state without changing code? If not, simplify the design. Preserve independent review and accurate integration receipts for ordinary code, but keep them proportional and do not confuse safety checks with evidence that the underlying risk is common.
