Required systemic behavior

  • Preserve distinction between delivered/seen and explicitly processed/acknowledged. Never silently acknowledge merely because inbox was fetched, a browser tab closed, a session stopped, a generic tool ran, or an agent was recovered. Preserve unread messages if processing was interrupted.
  • Provide a bounded, transactional recipient-only batch acknowledgment of exact notification IDs, with deterministic idempotency on the original operationId, robust handling of already-acked IDs, stale/cross-agent IDs, partial failure, concurrent client CAS and unknown outcomes. One canonical Git CAS per batch, not one Git push per notice. Keep old single-ID API compatible; do not delete messages or mutate assignment/review state.
  • Prefer folding an explicit list of processed IDs into existing successful checkpoint/yield/complete lifecycle writes atomically where practical, so acknowledging routine work does not require extra separate calls. If this creates unjustified complexity, demonstrate smaller equally durable approach and document exact tradeoff. Never infer acknowledgment of unlisted notifications; explicit ID binding and recipient authorization remain mandatory.
  • Ensure tools and role-facing instructions make expected process unambiguous: act on inbox notices, acknowledge only ones actually handled or intentionally dismissed with clear disposition; leave unresolved notices pending with reason in checkpoint. Do not convert extraordinary Operator decisions to auto-ack. Retain legacy message format and historical ledgers.

Add negative-space tests for batch >1, duplicate IDs, cross-recipient, already-acked, stale snapshot, concurrent CAS, partial-invalid atomicity, crash/retry original UUID, lifecycle + notifications, and missing unread.
