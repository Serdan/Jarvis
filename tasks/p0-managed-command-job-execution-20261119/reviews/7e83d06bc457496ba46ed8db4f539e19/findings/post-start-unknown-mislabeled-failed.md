# P1 — A post-start unknown process outcome is persisted as a definite failure

**Frozen source:** `c344d04604a584ac4cac0f4c2d5788054fa7bf33` against `a83549a6897a4e26aa4834ff81dc38b6e16ee85e`.

**Concrete source path:** `Client/Modules/JobManager.fs:283-292` starts a process, then checks the managed registry after the response window. If that job is no longer available, it deliberately returns `Client.ContextError "Started process job unavailable; process outcome is unknown."` (lines 287-289), since the process may have executed. `Client/Program.fs:211-214` forwards `Error error` as `Error("", sprintf "%A" error)`; this does not contain the contiguous token `OutcomeUnknown`. `Client/Modules/BrowserSchedules.fs:709-715` recognizes uncertain errors only by `reason.Contains("OutcomeUnknown")` and otherwise persists status `failed`. Thus the explicitly modeled post-start unknown is recorded as a known failure, rather than `outcomeUnknown`. For repeating actions `BrowserSchedules.fs:244-252` re-arms even an uncertain outcome; source/recurrence implications must be assessed without replaying the original occurrence.

**Why blocking:** A definite failure and an unknown external effect have different recovery/fencing meaning. An evicted/missing job handle, or another post-start command error, must not be silently classified as a safe failure merely because an error string differs. The task's explicit acceptance is fail-closed unknown handling. This is a conditional source trace, not a claim of a live reproduced registry-eviction race.

**Required correction:** Use a typed or otherwise exhaustive classification of `Client.receiveCommand` errors that may occur after process admission, and mark such outcomes `outcomeUnknown` (without retry/replay). Add a deterministic injected post-start-unknown path through the real scheduled consumer/scheduler to prove the persisted state, and verify recurrence/recovery fencing for uncertainty. Keep unrelated Worker 18 scheduling source and all no-cutover restrictions unchanged.
