# P1 — Scheduled command consumer remains outside the regression boundary

**Frozen source:** `c344d04604a584ac4cac0f4c2d5788054fa7bf33` (base `a83549a6897a4e26aa4834ff81dc38b6e16ee85e`).

**Evidence:** `Client/Program.fs:196-256` is the production `executeScheduledAction` consumer. It deserializes `RunCommandResult`, awaits `JobManager.awaitScheduledCommandTerminal`, maps `Completed 0` to success and other states to `CommandFailed`/`CommandTimedOut`/`CommandCanceled`/UNKNOWN, and hands the result to `BrowserSchedules.Service` (line 313). The new tests in `Client.Tests/JobManagerTests.fs:1234-1314` invoke only `managedStarted` and `awaitScheduledCommandTerminal`; no test calls `executeScheduledAction`, exercises the `Client.receiveCommand` deserialization/permission path, or asserts the scheduler's persisted `completed` vs `failed`/`outcomeUnknown` status.

**Why blocking:** The exact prior defect (program consumer returned `CommandFailed` on initial `Running`/exit=-1) could be reintroduced in `Client/Program.fs` while every new test still passes, since those tests bypass that consumer. The canonical P0 correction acceptance explicitly requires a deterministic >1.2s *scheduled-command* regression proving no premature `CommandFailed` or duplicate execution, including nonzero/UNKNOWN negative outcomes. The helper's positive marker check is useful, but is insufficient end-to-end evidence for that acceptance gate.

**Required correction:** Extract/expose an injectable scheduled-RunCommand consumer (or add a bounded scheduler integration fixture) that invokes the same code `Program.fs` invokes and persists the resulting action state. Test a >1.2s allowed command with a single external marker and terminal `completed` state; nonzero exit -> `failed`; missing/lost job and uncertain response -> `outcomeUnknown` without replay. Keep the separate Worker 18 accepted schedule source, source lease, and no-cutover guard intact. This is an independent frozen-source code/test review, not a live scheduler run.
