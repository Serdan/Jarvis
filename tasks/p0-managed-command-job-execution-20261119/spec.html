[P0] Unify run_command and start_job on managed OS-process jobs

Operator directive 2026-11-19. Owner proposed: Worker 11; Manager alone dispatches. This is immediate integration-blocking reliability work, independent of and not a precondition for rerunning the existing full Linux Client Release suite through start_job.

Reproduced problem and source

On operator Linux client, run_command sleep 8 with timeoutSeconds=3 returned a pollable ToolOperation but killed the subprocess (ToolCompleted, ExitCode=-1, TimedOut=true); timeoutSeconds=20 completed; start_job sleep 9 reached real exit via get_job_result. Current Client/Modules/ClientShell.fs Core.defaultTimeoutSeconds=60 invokes BoundedProcess.run with process lifetime timeout; Client/SignalR/Client.fs sends a ToolOperation after approximately 3 seconds but does not suspend the actual process lifetime; Client/Modules/JobManager.fs already provides managed job lifecycle. The tool-operation handle is not itself proof the OS process finished.

Exclusive bounded source lease and architectural result

Own the command execution path in Client/Modules/ClientShell.fs, Client/SignalR/Client.fs, Client/Modules/JobManager.fs and narrowly necessary command/result types/Client.Tests for this refactor only. Coordinate separate files and exact remote ancestry with active Worker 10 read-only Release gate, Worker 21 original-Git client producer, Worker 22 launcher tab work and Worker 18 schedule work. Do not modify unrelated Work SQLite/migration source. Reuse existing JobManager instead of a second process tracker.

  1. Map the complete run_command, start_job, ToolOperation and get_job_result/cancel_job response paths and permissions. Design ONE canonical job-managed OS process execution: all processes are managed jobs with real process lifetime independent of initial RPC response threshold. Return terminal result when exited quickly, otherwise a pollable process job handle, not only the command transport wrapper handle. Preserve backward-compatible public interfaces when feasible; if contract changes are necessary, specify typed compatibility and no ambiguity between terminal ToolOperation and actual process termination.
  2. Preserve configured project/worktree execution identity, allowed executables and sandbox permissions, bounded output with truncation, stderr/stdout, cancellation, polling, exit code, timeout and unknown outcomes; never turn missing/ambiguous process status into success. Remove hidden default process-kill timeout; only a separately explicit user-requested deadline may kill a process. Distinguish short response threshold from an optional explicit process deadline.
  3. Add deterministic Release regression tests: sleep beyond initial response threshold succeeds after polling; no implicit 60s process kill; prompt exit returns true final exit code; nonzero exit, cancellation and explicit deadline are distinct; output truncation and process-spawn failures are faithfully represented; project/worktree permission denials remain enforced; repeated job poll does not repeat the process. Include negative-space tests for transport timeout and tracked job survivability, and avoid leaked OS processes.
  4. Run focused Linux .NET 11 Client Release build/tests and, if available, the full Client Release suite via real start_job + get_job_result process completion, source-pinned SHA, test counts, final exit code. Do not use run_command with large timeout as proof. Keep operator-directed Worker 10 independent full-suite gate active concurrently; coordinate findings without duplicating ownership.
  5. Push reviewed implementation only to a dedicated feature branch; publish immutable commit and independent frozen shared-queue review, correct ChangesRequested, submit Accepted exact commit to Integrator. No self-review/merge. Report exact source SHA, test results and remaining risks in canonical checkpoint.

Hard gates

Implementation default-off except command execution semantics explicitly requested by operator. Independent Accepted source review and Integrator current-main proof are mandatory before merge. No production deployment/restart, original-Git STOP/release, Work migration, new Scheduler or SQLite cutover without separate operator approval.
