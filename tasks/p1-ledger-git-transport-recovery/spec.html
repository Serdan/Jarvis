P1 — Resilient Git-backed ledger writes after transient transport failure

Goal: A transient DNS/GitHub transport failure during YieldAgent (or other canonical Task/Review writes) either recovers through bounded, safe retries or leaves a clearly recoverable, unambiguous operation. No lost checkpoint, duplicate state transition, unauthorized mutation, indefinite Working solely from a short transient outage, or fake success.

Incident / evidence

  • On 2026-11-15 Jarvis Lead tried YieldAgent under UUID 62f09ed1-e720-451f-88e5-b713533e9b0a repeatedly; error LedgerFailure(RemoteUnavailable), fatal: unable to access https://github.com/Serdan/Jarvis.git/: Could not resolve host: github.com. Verified NotFoundAtVerifiedHead and no local pending journal record; agent remained Working.
  • Same host succeeded ordinary ls-remote, exact refs/heads/jarvis-orchestration dry-run fetch, 16 bounded Git fetch/push-dry-run probes (closed stdin, GIT_TERMINAL_PROMPT=0), and a real no-op push of the existing ledger SHA. A later new shorter yield under UUID 830a0b43-5d12-4b51-9305-23dd189ed001 succeeded at seq3179, Ready/Stopped verified. Both ID and payload changed; cause is unproven.
  • Source paths: Client/Modules/LedgerStore.fs execute/fetchWithRetries/transact; Client/Modules/OrchestrationApi.fs PendingIntentJournal.executeLedgerWrite; Client/Modules/BoundedProcess.fs; contrast Client/Modules/ClientShell.fs ConfigureStart=Some ProcessEnvironment.apply. This environment discrepancy is only a hypothesis, not a proven cause.

Scope / required implementation

  1. Precisely localize the failed Git stage: remote existence/fetch, local preparation, publication push, or confirmation fetch; include bounded sanitized diagnostics with operation UUID, stage, retry count/duration, exit/timed-out/known transport class, never credential-bearing remote URL, command JSON, environment values, or unbounded stderr.
  2. Bounded, deterministic-jitter or exponential backoff for truly transient failures before publication with an explicit deadline and no runaway Git processes; classify nontransient auth/ref/integrity/CAS/validation failures without masking.
  3. After a push may have started, do not blindly publish a new operation or lose the original intent. Re-fetch the verified remote head, reconcile the same UUID+request hash, preserve durable uncertain intent if unconfirmed; uphold cross-process CAS and exact-once original receipt semantics.
  4. Provide a recoverable response even during sustained outage, with operation ID and safe next action. Do not claim canonical state changed until remote verified.
  5. Deterministic .NET11 Release tests for injected DNS/transport failures at pre-push fetch, after push before confirmation, repeated calls/replay, remote contention, failure during reconciliation, and recovery after remote returns. Assert checkpoint/agent state and pending-intent preservation/retirement. Test no duplicate publication; preserve existing 0-cold-allocation/other correctness expectations where practical.
  6. Minimal solution; no replacement of Git ledger, no generalized offline state database, no restart/deploy, no production credentials. Work in isolated worktree; submit immutable exact frozen independent review and yield. Do not invoke Codex through Jarvis.

Acceptance

Fail-closed exactly-once canonical state transitions under fault injection; bounded time/process usage; clean .NET11 Release tests; independent frozen review on exact source SHA. Existing WQ-02 workstream must remain unblocked; coordinate file overlap proactively if ledger internals overlap Worker5.
