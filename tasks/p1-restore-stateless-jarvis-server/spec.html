[P1] Prove stateless-by-contract Jarvis server and remove correctness dependencies on disposable SQLite

Operator clarification (2026-11-15): Keep Jarvis server small, simple and operationally stateless because persistent state scattered across machines is difficult to manage and the server runs on the cheapest viable droplet. The one intentionally durable server filesystem exception is Jarvis-level agent instruction files. All canonical durable project/workflow/session/recovery state belongs to the clients and approved Git-backed ledgers, never to server-local SQLite or other unmanaged volumes.

Do not infer that existing SQLite was unauthorized. The existing FeedbackStore may have been intentionally approved for loss-tolerant diagnostics; its authorization history is uncertain. The user explicitly permits losing nonessential telemetry/feedback without harming project operations. A small, bounded, discardable SQLite file may remain only if deletion/replacement is operationally harmless; do not migrate, delete or replace the production database simply to satisfy aesthetics. New durable server-owned state still needs explicit operator approval.

Read-only source audit

  • Server/Program.fs:33-43,119-123,205-208 requires DatabasePath, constructs FeedbackStore, and initializes SQLite before server readiness. Server/Services/FeedbackStore.fs contains operations, feedback, connection_events, and attributed_agent_activity. Operations and connections have 30-day pruning.
  • Feedback/operation and connection diagnostics can be classified as noncanonical if API consumers agree they are best-effort, losing them is acceptable, and there is no backup or recovery burden.
  • Current correctness hole: ClientService.RecordAgentActivityForUser stores cross-device idle watermarks in server SQLite. HubService.GetAgentActivity returns None when the row is absent. Client/Modules/BrowserSchedules.fs:655-678 merges remote and local observations and may permit a due AfterAgentIdle action without a verified activity watermark. Losing/replacing server DB can therefore change launch eligibility despite no corresponding authoritative agent state change.
  • In-memory connections, response correlation, and bounded transient export caches are appropriate; validate crash/restart semantics and avoid accidental heavy CPU/memory/disk costs.

Required work, in priority order

  1. Audit existing server SQLite data classification and resource usage, with exact confirmed durability consumers. Write a fail-closed server-replacement contract (empty data directory except intentionally retained instruction files): no lost canonical state, duplicate work, false-idle launch, token admission, or irreversible effects. Mark any unknowns honestly.
  2. Move AfterAgentIdle last-seen authority to a trustworthy client/ledger-owned durable or reverified source, or fail closed when no independent watermark exists; handle client reconnect, multiple devices, stale and absent server rows, delayed activity, errors, server restart and a fresh instance. Verify that no absent/empty SQLite file is mistaken for evidence of being idle.
  3. Make optional server telemetry nonessential to startup and operations where practicable. Do not require server DB backups, migrations, volumes, retention management or special redeploy procedures; cap CPU, RAM, disk and telemetry retention for the smallest viable droplet. If a disposable SQLite remains, explicitly document and test that wiping it only loses diagnostics. Removing SQLite entirely is optional, not the acceptance criterion.
  4. Do not delete or migrate existing production data without explicit authorization and a reviewed rollback/export plan. No deployment or runtime migration under this task.
  5. Run focused .NET11 Release + disposable two-client/restart/data-loss negatives. Isolate source changes from WQ03/WQ08 teams. Freeze an exact task-bound independent review and integrate only Accepted source. Production Scheduler remains gated until trustworthy after-idle behavior and other epic dependencies are proven.

Hard limits: no GitHub Actions (runners unavailable), no Codex through Jarvis, no main push without Accepted frozen review, no unauthorised host changes, no production Scheduler/YieldSource activation, migration or deployment. Preserve the current SQLite until replacement/disposability is actually proven.

Operator rule-of-thumb clarified, 2026-11-15

Acceptance test: if existing SQLite service/database fails to start, is missing, full, locked, corrupt, blocked by I/O or becomes unresponsive, authentication, connection routing, supported MCP tool execution, client project operations and canonical Git-CAS work must continue without awaiting its availability or failing as side effect. Loss of telemetry/feedback is acceptable. Use bounded timeouts, isolation and fail-open for best-effort diagnostics. Do not silently suppress a real canonical client operation error or fabricate a successful result.

Exception: AfterAgentIdle may be selectively disabled or return an explicit unavailable/proof-required status when its activity evidence is missing. A reset SQLite must never be mistaken for proof that an agent is idle. The rest of Jarvis must continue to function normally. Verify two-client adversarial scenarios across server restarts and lost activity samples.

Existing SQLite may be grandfathered; deletion is not required. Work is safe-to-review only, no production deploy, migration, data deletion or host setting change without operator authorization.
