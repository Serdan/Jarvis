[P1] Restore strict stateless Jarvis server; move durable feedback and activity off host

Operator architecture rule (confirmed 2026-11-15): Jarvis server must remain simple, stateless, and disposable. The sole allowed server filesystem persistence is Jarvis-level agent instructions. All other durable data must be owned by the clients or the explicitly canonical Git-backed ledger, not by a server-managed local DB, filesystem store or recovery volume. In-memory SignalR connection registration, bounded request correlation, transient export bytes and disposable caches are fine if restart/replacement has no correctness loss. No implementation may create a second exception.

Verified existing violation on integrated main e14173e116dc03b7dbdf261895fde3c893a643ee

  • Server/Program.fs:33-43 requires DatabasePath even for startup. Program.fs:119-123,205-208 adds a singleton FeedbackStore(databasePath) and forces SQLite initialization before readiness.
  • Server/Services/FeedbackStore.fs:105-149,157-228 creates a persistent SQLite database in WAL mode and tables operations, feedback, connection_events, attributed_agent_activity. Stores operation telemetry, user feedback/resolution records, connection diagnostics and user/project/agent last-activity watermarks. Connection/operation telemetry is pruned after 30 days, but the app depends on the DB continuing to exist.
  • Server/Services/ClientService.fs:188-206 writes attributed activity durably before forwarding best-effort notifications; HubService.fs:124-139 reads server SQLite in GetAgentActivity, used to verify AfterAgentIdle scheduled actions. This is correctness-sensitive, not merely logging.
  • The server MCP transport's Stateless=true only configures HTTP transport; it does not make the application stateless while FeedbackStore exists. ExportStore, ClientResponseTracker and UserService are in-memory and can remain ephemeral provided restart behavior fails safely.

Remediation

  1. Document a single ownership boundary. Rehome persistent feedback, user reports, operation history and connection diagnostics on clients, or the approved Git ledger when cross-device durable access is required. Do not retain server-local SQL or invent a replacement server database/filesystem store. Preserve user scoping, OAuth attribution, original operation IDs and query semantics.
  2. Replace attributed_agent_activity durability with an authenticated, client/ledger-owned, replayable activity witness for AfterAgentIdle. On server reboot, missing client, stale snapshots, lost notifications or unknown query outcomes, fail closed rather than launch early or infer idle from a reset server clock. Account for concurrent devices and delayed activity. Keep the server as an authentication/routing relay.
  3. Remove required DatabasePath, FeedbackStore construction/readiness dependency and server SQLite package. Make replacing the server with an empty instance (except allowed instruction files, environment config and secrets) safe. Do not rely on server volume mounts, DB backups or migrations.
  4. Define a deliberate data-preservation path for any already persisted feedback/operation history and attributed watermarks. Do not silently delete/migrate live data without explicit operator approval. A one-time read-only export may be necessary; production cutover requires independently reviewed migration/rollback plan.
  5. Audit all server disk read/write paths beyond the allowed instruction file, and document server restart, new-instance, reconnect and multiple-client behavior. Unit/integration tests must prove that the server owns no durable canonical state, and the client/ledger restores correctness after server loss, including false-idle/duplicate-schedule negatives.

Workflow: P1 independent architecture/code change, isolated source and .NET11 Release tests, exact task-bound frozen independent review, canonical integration by Lead, separate operator-authorized production migration/deployment. Coordinate with WQ08 Scheduler and WQ03 source journal workers but do not overlap their source. Before the server statelessness assertion is restored and verified, block WQ08 production scheduling cutover. No GitHub Actions, Codex, main push without review, production Scheduler activation, deployment, migration, or host data mutation by workers.
