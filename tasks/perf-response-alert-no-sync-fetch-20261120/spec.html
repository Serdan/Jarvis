Eliminate remote Git I/O from ordinary response-alert decoration

Priority: P1 — client responsiveness and autonomous-operation liveness.

Problem and evidence

Client/SignalR/Client.fs: checkResponseAlerts -> LedgerBindingConfig.loadWithSnapshot -> takeResponseAlertsAt currently synchronously fetches the canonical Git ledger on each eligible visible tool response, even with no queued alerts. GetJobResult can do 0 ms of command work while MCP completion waits >20 seconds. Windows FinanceFlow fetches were ~5.2–5.5 seconds each. Commit bea5f4086 removed one duplicate fetch, not the remaining fetch.

Objective

Normal no-alert tool replies (especially GetJobResult, ListJobs and failures) must complete without remote Git network reads caused solely by alert decoration. Preserve prompt STOP alert delivery, at-most-once best-effort consumption, durable canonical authority, cross-client updates, and correct behavior after restart, transport failure and lost notifications. Prefer reusing existing SignalR, ledger events and local state/cache machinery over a separate bespoke notification subsystem. Do not weaken STOP semantics, silently drop alerts, or replay uncertain external effects.

Engineering approach

Inspect existing alert publication, notification/invalidation transport, cache and reconnect capabilities. Design an event- or hint-driven fast path with a reliable reconciliation boundary for missed events. Make the latency-versus-delivery contract explicit; targeted polling may be acceptable if justified, but never a remote fetch on every ordinary no-alert reply. Avoid a new always-polling subsystem. Preserve the current legacy-Writer fencing and no Work/Scheduler cutover.

Acceptance

  • Tests prove zero remote Git fetches attributable to response decoration for repeated no-alert GetJobResult/ListJobs and failed command responses; fetch-count regression covers the entire pipeline.
  • STOP alerts are delivered at visible reply boundaries, with cross-client publication, concurrent consumers, restarting clients, lost/reordered invalidation, disconnected/reconnected transport and failed command/job poll cases covered. Document any bounded fallback delay.
  • Successful consumption remains at-most-once best effort; uncertainty does not silently discard or duplicate alerts.
  • Measure and report before/after end-to-end command latency and remote Git fetch counts on a warm client, with Windows validation where feasible.
  • Independent review before integration; no deployment or restart without Operator authorization.
