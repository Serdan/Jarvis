[P1][Perf] Attribute routine Git-ledger mutation latency and eliminate avoidable work

Parallel performance investigation, independent of TaskOverview batch reader and generic perf harness. Baseline on 2026-11-21 Serdan-Home client: CreateTask 3.7–4.0s, RegisterAgent 3.4–3.6s, AssignTask 3.6–3.7s, CheckpointAttempt 3.3–9s. These are client execution durations; the end-to-end MCP path may add queue, SignalR and server time. Do not assume the whole duration is unnecessary.

Phase 1 measurements, not speculative fixes

  • Inspect canonical LedgerStore mutation flow and existing TransportScope/phase instrumentation, normal non-force remote push proof, retries, trust binding and response-delivery stages. Identify stage costs (lock/queue, Git fetch, object read, verify/encode, local commit, network push, remote postpublication verify, response ack).
  • Make a deterministic disposable bare-repo fixture in .NET11 Release NUnit that runs exact source-bound CreateTask, RegisterAgent, AssignTask and Checkpoint/Yield. Capture Git subprocess and network operation counts, bytes, allocations, cold/warm p50/p95/p99 with 30+ iterations as non-gating diagnostics. Include a slow Git/process/fault-injection case and 2 concurrent clients; respect publication and uncertain-outcome fencing.
  • Locate repeated Git subprocesses or redundant read/fetch/verification within one mutation. Require before/after count evidence and source-exact tests for any change; distinguish necessary network latency from N+1 local process churn.
  • Do not change live ledger, Git publication semantics, trust roots, queue/authorization, task state, deployment, schedules or scheduler activation. Use isolated branch, independent frozen review and checkpoint/yield. Coordinate with Perf 1 to avoid touching the same harness helper; avoid modifying shared LedgerStore production code without a small measured and independently reviewable patch.

Exit criteria

Produce stage-attributed report with baseline process/fetch/remote-push counts and latency distribution, at least one deterministic upper-bound assertion plus negative case, and evidence-based next fixes. Windows parity on KRUSO when connected; never compare cross-machine absolute latency as a regression without same-machine baseline.
