[P1][Perf] Lightweight Jarvis performance regression lane — work counts, tails, Windows parity

Parallel to Automation. Own perf observability and regression detection without BenchmarkDotNet. Does not gate correctness or require scheduler cutover. Initial work is source-only isolated branch plus independent review, not a production deploy or main edit.

Phase A: deterministic, low-overhead perf contracts

  • Inventory existing scoped Git-read counters and command/queue timing instrumentation (LedgerStore, SignalR CommandDispatch, AgentInboxScaling, ProjectBrowser, BoundedProcess). Reuse rather than duplicate.
  • Provide a tiny .NET 11 NUnit fixture/helper that captures per-invocation wall duration, Git subprocess starts by Git verb or phase, remote fetch count, cat-file batch count, blob reads, bytes, managed allocations and relevant cache hit rates. Keep privacy: never log commands, credential values, repository paths or user payloads in reports.
  • Separate first cold load, warm repeat, remote head changed/invalidated, and two-device/concurrent reads. Require exact canonical result equality and stale-cache nonacceptance alongside performance.
  • Strict CI deterministic limits on redundant Git process/fetch and output amplification, resource leaks or unbounded growth; no flaky absolute latency gates on diverse machines. Record p50/p95/p99/max and allocations as informational in stable local JSON and NUnit output with pinned source SHA, runtime, OS, CPU, sample count, fixture cardinality, no sensitive identifiers.
  • Golden workloads: AgentInbox, task overview, dashboard refresh, get_task, reviewer_inbox, challenge list, send preflight, repeated tool result polling; 0/220/2,200 record ledgers with unrelated historical documents; mutate one canonical head between repeats to validate cache invalidation. Use synthetic temporary Git remotes; no production ledger writes.
  • Tail-latency and contention: 32+ cheap status reads during one controlled 1s slow Git/ledger task, collect queue wait and user-visible end-to-end time, assert no serial head-of-line blocking. Fault injection: delayed Git process, bounded network read and cancellations, confirm no retries or leaked child process fanout.
  • Run Release without BenchmarkDotNet. Provide a tiny optional local script/test filter that runs warmups + 30-100 samples and machine-readable JSON outputs; 3 runs or more before comparing distributions. CI deterministic counters and relative scaling; nightly/local-only budgeted latency trends versus same-host baseline.

Phase B: Windows parity & independent performance probes

  • Once KRUSO client is available, run identical source/fixtures on Windows and Linux, pin OS/runtime/CPU and compare call counts first, latency distribution second. Never interpret cross-machine absolute times as code regressions. Investigate >1m tail calls with stage attribution.
  • Independently inspect unexpectedly expensive paths outside Git: JSON/DOM projection, locks, scheduler dispatch queue, repeated serialization and HTTP transport. Prefer evidence-first fixes with before/after source and tests.

Acceptance

At least three reproducible fixtures demonstrate deterministic Git subprocess/fetch bounds, correct cold/warm/mutation responses, explicit p50/p95/p99 report, and 1s stalled-operation concurrency negative test. Document baseline and execution command. No live deploy, scheduler enable or destructive action. Request independent frozen-source review.
