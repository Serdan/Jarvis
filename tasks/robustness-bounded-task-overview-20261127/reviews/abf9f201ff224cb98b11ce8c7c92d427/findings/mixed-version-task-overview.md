# P1 — bounded query contract is not fenced from existing unbounded clients

Exact source: `c572bf698639fa3aaa00c7d6ab35e8bfa548cb7e` (base `914907d14803ddf861e438419147903dcbf8f7f7`). Independent static finding; not a live experiment.

## Reproduction and impact
- Base and candidate both advertise protocol `3.68` (`Common/Messages/AgentCommand.fs`, base line 1733, candidate line 1750) and the existing `ReviewRead` command capability. The base `ReviewReadCommand` record has no `TaskOverview` field. Base `Client/SignalR/Client.fs` deserializes via the default System.Text.Json `JsonSerializer.Deserialize<AgentCommand>(commandJson)`; unknown properties are ignored by default.
- Candidate `Server/McpTools.fs:2343–2358` sends the new typed query as an optional field on the SAME `ReviewReadCommand` and SAME `ListProjectTasks` action. Base `Client/Modules/OrchestrationApi.fs:2494–2496` dispatches that action to the original unbounded `ReviewWorkflow.listProjectTasks`.
- Pair candidate server with an already registered base 3.68 client. Invoke TaskOverview with scope=history, pageSize=1 or a restrictive filter. The command can be negotiated as supported yet the old client ignores the added property and executes full history with no cursor/count contract. For the representative oversized ledger, the old bridge returns OutputTruncated, precisely the failure this task must solve. On smaller ledgers the result can silently violate the requested query and response shape. A server-only deployment or old device selection is thus not a supported bounded route.
- Candidate adds no capability/version fence or explicit transition plan; its full regression directly invokes the candidate authenticated client route, so the mixed-version scenario is untested.

## Original obligation and candidate remedies
The task expressly requires backwards compatibility or an explicit transition, a supported bounded query that succeeds over the live bridge limit, and correct counts/continuation. This is a material gap in that existing contract, not a request for new functionality. Prefer an explicitly negotiated bounded-action capability or equivalent fail-closed routing/upgrade requirement. An explicit coordinated client/server transition with a tested rejection of incompatible peers is an alternative; exact mechanism is for independent adjudication/implementation. Preserve other ReviewRead operations and avoid treating old output as a valid page. Test old client/new server, new client/old server, and matched candidate including actual public MCP route; verify filters/cursor and bridge-limit behavior. No deployment authorized.
