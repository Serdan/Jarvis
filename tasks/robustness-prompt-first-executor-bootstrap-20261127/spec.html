Prompt-first executor bootstrap; simplify or eliminate inbox

Operator direction 2026-11-27: inject all pertinent initial execution context in the prompt, ordered for prefix caching; simplify or remove inbox. This is part of 1.0 context-efficiency work and the intended 2.0 bootstrap architecture. Current template v8 instructs every execution to call agent_inbox then get_agent_instructions; the latter repeats role/agent layers, and task/spec/checkpoint reads often follow. This is avoidable initialization cost. Reuse existing canonical launch renderer and instruction consolidation task jarvis-instructions-consolidation-20261126; prior launch-template spec automation-project-launch-template-20261123 intentionally kept dynamic material in inbox, superseded in design by this direction. Do not edit the live template until new path is independently reviewed, integrated and ready.

Design and delivery

Resolve a single verified launch snapshot and compose exact pertinent instructions and current work before submitting the prompt: stable common and applicable role/project instructions, then task-specific pinned specification and necessary source/work context, latest checkpoint, actionable review feedback/exceptional notices and necessary dependency state; volatile launch/session/assignment/agent IDs and activity-sensitive data as late as semantics permit. Order by stability and shared scope, deterministic serialization, no unnecessary timestamps/random values, no duplicated layers or copied history, no padding, preserve instruction precedence and required evidence. Discover directory-specific guidance when a later source scope changes rather than loading unrelated repository instructions. Reuse stable common prefixes across launches; report measured common-prefix length, not assumed cache hits. Keep dynamic details exact, not a lossy LLM summary of normative spec or review feedback. Provide precise versioned references and explicit retrieval for intentional expansion. Worker, Reviewer, Lead/taskless and resumed/blocked cases need purpose-specific initial context, not identical all-role payloads.

Separate context delivery from canonical activation and authority. Prompt contents are a snapshot, not permission to act on a stale generation. Existing authenticated activation, check-in, lease/fence, assignment/review claim and freshness checks remain enforced at the relevant runtime boundary; if a first call is needed, it should acknowledge/validate launch or return a compact invalidation/action delta, not repeat the injected payload. Decide whether existing first authenticated call can do this or an explicit small activation operation is required. Do not start Working before actual attributed call-home merely because a prompt was rendered or sent. Preserve STOP, late launch fencing, independent reviewer claim semantics, exact owner/role, concurrent changes and no-replay. If relevant material changes before execution, provide an explicit fresh delta or hold/re-render rather than authorize stale work. Use one canonical rendering path for manual and scheduled launches. Existing account authentication and 1.0 authority unchanged; 2.0 uses Jarvis-issued prompt-injected leases, not provider-specific identity infrastructure. Protect lease material from unnecessary persistence/logging. Provider adapters are transport only.

After production rollout, retire routine inbox calls where prompt and canonical ingress already cover their contract. Keep on-demand targeted queries and exceptional actionable updates; no separate broad mailbox for routine context, no duplicate runtime authority, no loss of durable messages or existing audit records. Preserve backward compatibility with old sessions until migration is verified; do not remove a route still needed by Scheduler or internal canonical consumers. Distinguish the existing instruction consolidation (instruction content) from this runtime context assembly/activation/consumer migration; coordinate source leases with W6/W8/W17, lifecycle and registration seams, shared prompt renderer and inbox work. No new provider implementation or Work cutover in 1.0.

Acceptance

Measure actual context and tool calls per launch/continuation/reviewer turn before and after, total across agents, prefix lengths and deterministic byte equality for common sections across launches, changes in role/project/task/generation and freshness. Test pinned spec vs later edit, current checkpoint and relevant feedback, role/taskless reviewer claims, scope/authorization, manual/scheduled parity, old-session compatibility, actual registered ingress, missing/oversize input with explicit safe behavior, late or duplicate launch, STOP, blocked conditions, snapshot change between render/send/check-in, and no secret leakage. Verify no routine redundant context fetch, no loss of mandatory instructions or evidence, and no hidden activation by render. Independent review, exact source integration, live template cutover only with authorized rollout. Lead owns decomposition and coordination; this is a 1.0 completion requirement, not a new blocker for minimum useful rollout unless a concrete safety dependency is demonstrated.
