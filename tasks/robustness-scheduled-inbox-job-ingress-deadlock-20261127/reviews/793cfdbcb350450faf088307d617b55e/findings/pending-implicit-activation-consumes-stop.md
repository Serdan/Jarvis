# P1 — pending implicit-activation response can remove the scheduled STOP fence

Frozen source: `adda755f01222a26b2bab9303da4549a6410f92b`. Source-derived race; not independently executed.

`Client/SignalR/Client.fs:2009–2029` excludes terminal ActivationUnverified and pending AgentInbox from visible response alert consumption, but not a pending ordinary command that can implicitly activate. `executeOrPromoteWith` at 2132–2145 publishes a pending handle with empty Instructions before the command outcome is known, then calls this alert consumer. For a Ready worker with unresolved launch and a queued STOP, delay an ordinary self activity command (e.g. LifecycleHistory, for which activatesAgent at 492–525 returns true) before its activation lookup. The pending envelope passes both checks and consumes STOP through `checkResponseAlerts` (441–455) and the queue CAS (`ReviewWorkflow.fs:2672–2693`). The same command returning quickly after the scheduled activation guard refuses it would instead carry ActivationUnverified and leave STOP queued. The original correlated launch can subsequently check in/activate because `ScheduledReadyResume.stillReadyAt`/`confirmedActivationAt` (563–614) consult the pending STOP queue. An older/unrelated request with the same actor label receiving a STOP is not evidence that the actual scheduled launch received it or terminated. The existing base guard prevented this consumption during unresolved launch; its removal is correct for independent command admission but the replacement response rule is timing-dependent.

Original spec v2 explicitly preserves STOP for actual activation, requires distinction between activation failure and independent admission, and preserves replacement fencing. Do not restore global ingress checks. Candidate narrow remedy: make pending response alert eligibility conservative for commands that can implicitly activate (not only inbox), leaving STOP available for the next eligible terminal action; verify a deterministically delayed ordinary promoted command during unresolved Ready + queued STOP leaves queue unchanged, ordinary dispatch remains permitted, and exact correlated check-in/activation still cannot proceed while STOP is pending. Consider other existing alert-delivery semantics in adjudication; no prescribed net-new scope.
