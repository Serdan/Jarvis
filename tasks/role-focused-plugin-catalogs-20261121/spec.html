Role-focused, overlapping Jarvis plugin catalogs

Type: API architecture / agent ergonomics. Priority: P2, non-blocking; do not preempt Scheduler, Challenges, Health, or ongoing P0 security/integration work. This task creation does not assign a worker.

Problem and evidence

Jarvis currently exposes approximately 130 actions in one discoverable plugin namespace. In a direct check, their names totaled 3,917 characters. Full action schemas were retrievable individually; there is no evidence that all tool names or schemas are preloaded in every model turn. Thus token savings from new plugins must not be assumed.

Primary problem: Agents discovering tools encounter similarly named Worker, Reviewer, Operator and administrative operations. They must infer the correct operation from names or inspect competing schemas, repeatedly reconstructing workflow/authority intent. Role-focused catalogs should make the appropriate tool easy to find while retaining cross-role flexibility.

Decisions already made

  1. Provide multiple role/workflow-focused plugin catalogs backed by the same Jarvis server. Provisional views: Worker (inbox, tasks, assignments, source leases, submissions), Reviewer (review inbox, queue, claims, evidence, verdicts), Operator (agent lifecycle, assignments, intervention, diagnostics), Scheduler (capacity, health, scheduling/dispatch), and Integration (acceptance, receipts, reconciliation, publication). Derive final grouping from actual workflows.
  2. Intentional overlap: The same action may appear in several catalogs, such as agent_inbox. Overlap does not justify duplicate implementations or divergent semantics.
  3. No new security boundary: All agents operate under the same user account. Catalog membership is a discovery convention, NOT per-role access control. Preserve all backend authorization, identity, independence, Git/CAS, and receipt protections.
  4. Role-first, not role-exclusive: Agents normally look in their workflow catalog first but can discover another when genuinely needed. Optional compact role-specific discovery guidance is appropriate.
  5. Compatibility: Retain the original monolithic Jarvis plugin initially. No mass renaming, removal, or disruptive backend refactor just to change the catalog. Any genuine redundant backend operations should be evaluated separately.
  6. No arbitrary target count: Optimize tool-selection clarity, not a number of actions or unverified baseline token saving.

Deliverables and approach

  1. Action inventory: Classify every exposed action by normal workflow, cross-role usage, ambiguous neighbors and genuine redundancy. Include representative Worker/Reviewer/Operator/Scheduler/Integration task journeys.
  2. Platform validation and design: Verify the supported method for publishing multiple focused plugins backed by the same backend. Document exact mappings (including overlaps), naming/description conventions, discovery instructions, limitations and compatibility strategy.
  3. Task-spec architecture assessment before implementation: Review this specification for both over- and under-engineering. Prefer thin compositional views of existing capabilities over new abstractions, authorization systems, databases or service replicas.
  4. Incremental implementation: Add role-focused catalogs and minimal role-specific discovery guidance if feasible. Preserve the existing monolith. Do not alter currently active/frozen source or review branches as a side effect.
  5. Test and evaluate: Verify shared/overlapping tools invoke the same canonical operation and authority. Test old callers, catalog publishing/discovery, and representative agent tool-selection workflows. Measure confusing choices, unnecessary schema inspections and mistaken tool selection before/after; report only measured token effects.
  6. Documentation: Publish mapping table, role-first and cross-role discovery guidance, migration/rollback plan, and explicit distinction between catalog organization and security authorization.

Acceptance criteria

  • All existing actions classified and role-focused catalog boundaries documented, including deliberate overlaps.
  • At least one complete role-focused workflow is usable via a published focused plugin; if impossible, record concrete platform evidence and a minimal alternative rather than pretending success.
  • Overlapping surfaces retain one canonical implementation, identities, receipts and authority.
  • Representative agent discovery tasks show reduced ambiguity, with reproducible before/after evidence.
  • Monolithic plugin remains functional during migration; existing agent/task/review/scheduler state is unaffected.
  • Tests and independent review appropriate to the actual source changes are completed before integration.

Design criterion: Make the correct tool the obvious tool.
