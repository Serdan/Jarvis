Integrate persistent Roslyn LSP formatting and analyzer hooks

Implement repository-configurable code-quality hooks in Jarvis, beginning with C# via the official Roslyn Language Server. Keep the generic hook mechanism language-agnostic, with Roslyn as a project-scoped adapter. This task targets the simplified Jarvis agent lifecycle; do not reintroduce retired begin_attempt or legacy APIs.

Motivation and evidence

Measured in an isolated Wayfold worktree using roslyn-language-server 5.13.0-1.26514.10: LSP initialization about 0.7–1.3 s; warm formatting after in-memory edits around 2–46 ms for 2.2 KB files and 95–131 ms for 123 KB files. dotnet format whitespace took ~1.8–2.1 s per file in folder mode and ~5–6 s with the solution. Project autoload found Wayfold.slnx and loaded its projects, with asynchronous restore. Roslyn LSP formatting closely matched dotnet format whitespace, unlike CSharpier's extensive style changes. Daemon mode was verified: two LSP clients shared one Roslyn daemon, with first initialization ~948 ms and second ~95 ms. Memory use of hundreds of MB is acceptable; prioritize correctness, responsiveness, and simplicity over memory minimization.

Scope

  1. Add a small configurable, repository-local hook mechanism for file modification and optional batched/pre-review checks. Do not couple hook configuration to C# or Roslyn. Choose a minimal clear configuration schema, explicit enablement, and predictable failure reporting; do not build a scheduler/service framework.
  2. Implement a local-client-owned Roslyn LSP adapter over stdio using roslyn-language-server --stdio --daemon-mode --autoLoadProjects (and telemetry off). Maintain independent LSP sessions/workspace contexts for active worktrees, letting the official daemon share the underlying process. A worktree may have its own project files, dependencies, .editorconfig, custom analyzers and compilation state. Do not assume different worktrees share compilation state.
  3. Prewarm the appropriate session asynchronously on the simplified resume_agent workflow once source/worktree context is available. Do not block resume on project loading; ensure initialization is idempotent and handle unknown source context by initializing when it becomes known. Keep sessions across agent yield/completion, and dispose on worktree removal/client shutdown. Avoid aggressive idle eviction.
  4. On configured file modifications, synchronize document contents via LSP, request textDocument/formatting, and apply returned TextEdits atomically only against the expected current file version/hash. Respect formatting settings and applicable .editorconfig, including final newline. Return any modifications and failures to the agent. Do not overwrite concurrent changes or expand edits outside the targeted worktree.
  5. Preserve an extension path for project-aware diagnostics and custom analyzer support. Investigate/report actual Roslyn diagnostic capabilities and analyzer loading; wire diagnostics where feasible without requiring every edit to run full project/solution analysis. Reserve expensive checks for batches/review hooks.
  6. Handle LSP initialization, server-to-client requests, document open/change/close, background project loading, errors, server restart and cancellation robustly but simply. Maintain project opt-in and command validation. Do not expose remote code execution through unsafe hook configurations from untrusted repositories.
  7. Add a repository-configurable pre-commit hook trigger in Jarvis's git_commit workflow. Determine the exact set of paths/content being committed (respect partial staging, selected paths, and the index), not every dirty file in the worktree. Run configured formatting and targeted analyzers against that commit selection before the commit is finalized. If configured auto-fixes are produced, apply them with version/hash checks and include only their intended changes in the commit, without staging or committing unrelated modifications. Define a clear approach for partially staged files (preserve index/worktree separation or stop with a precise diagnostic rather than silently expanding the commit). Expose per-hook advisory vs blocking failure policy, diagnostics and modifications in the tool result. Existing repositories with no hooks must preserve current commit behavior. Consider Git-native hooks as complementary, not a replacement for structured Jarvis hooks.

Acceptance criteria

  • Wayfold can opt in to immediate Roslyn document formatting; existing projects with no hook config behave unchanged.
  • Two distinct worktrees get isolated LSP sessions while sharing the same Roslyn daemon process; project settings and analyzer configuration remain independent. Verify using representative worktree/config differences.
  • Repeated resume calls never duplicate a session; resume latency does not wait on solution loading.
  • Format a small and large Wayfold C# file after real source edits; record cold/warm latencies, correctness against dotnet format, daemon/launcher RSS, and project-load diagnostics. Report differences in formatting results, including final newline.
  • Conflicting file modifications cannot be overwritten by delayed LSP edits, and hook failures are visible to the caller.
  • Review and tests cover session lifecycle, client restart, multi-worktree isolation, and safe handling of missing tools/unavailable server.
  • Do not alter or reformat unrelated Wayfold files, and do not deploy without explicit user approval.
  • A pre-commit hook runs only against the actual commit selection; tests cover path-limited commits, partially staged files, unrelated dirty files, automatic fixes, blocking versus advisory failures, and prevention of accidental extra staging.

Implementation notes
