[P1][Scheduler] Deterministic Jarvis-ledger planner for Ready work and review selection

Phase 1 of the Jarvis Scheduler delivery. Build a default-off, deterministic decision core over the existing Jarvis Git-backed task/agent/review/Challenge state. This is implementation and tests, not a deployment or live dispatcher.

Verified source baseline

  • Original repository: https://github.com/Serdan/Jarvis.git. Current clean main and advertised origin/main are both 95a471fc565b57fe309c65fc85f371693dbe9067. Use that exact baseline unless a fresh verified main supersedes it.
  • scripts/manager-heartbeat.mjs already contains a deterministic per-project planner and durable local launch journal. The model-based Manager still performs actual browser launches. Its 5-worker/3-reviewer limits are project settings, not account-wide capacity.
  • BrowserSchedules is a per-client schedule runner, not an account-wide task/agent scheduler. Work Queue Scheduler prototypes remain default-off and are outside this task.
  • AfterAgentIdle is intentionally fail-closed in Client/Program.fs; the production provider returns ActivityProofUnavailable. Legacy FeedbackStore.attributed_agent_activity is not authoritative proof of inactivity.

Challenge behavior already present — do not duplicate it

Lead's source inspection on current main found that the canonical Challenge workflow already performs automatic, transactional wake/requeue for the normal paths:

  • ChallengeWorkflow.wakeDependents runs when a Challenge first becomes Satisfied. It resolves every linked dependency from the same snapshot and verifies task, attempt, generation and owner identity. If the owner is stopped, unassigned and explicitly NeedsWork, it requeues the blocked attempt and writes the assignment/audit records in the same ledger transaction. If the owner is occupied or parked, it persists the wait as Eligible.
  • ReviewWorkflow.reconcileEligibleOnRelease is called by canonical owner-release transitions and by ChallengeWorkflow.blockAttempt. It checks the same wait/attempt/generation/owner identity and every dependency, then requeues at most one eligible wait after the owner is free. A parked owner remains eligible until explicit unpark.
  • ChallengeWorkflow.requeueAttempt is a separate owner-attributed recovery operation. Do not impersonate the blocked owner, invoke it as a Scheduler, or introduce a duplicate Scheduler requeue path.
  • Existing regression tests include SatisfiedDependenciesRemainEligibleUntilBusyOwnerReleasesTheirSlot, ParkedOwnerKeepsDurableWakeUntilExplicitUnpark, FinalChallengeResolutionRequeuesEveryDistinctDependentOwner, BlockingAnotherAssignmentWakesPreviouslyEligibleWork, and AlreadySatisfiedDependenciesCannotCreateAnUnwakeableWait. Worker 1 is independently auditing the full authority/call-path contract.

Therefore, the planner must treat canonical Challenge transitions as authoritative. It must not emit routine requeue intents for waits that the existing workflow already requeues. Project Challenge state as an eligibility/hold reason. If an Eligible wait is still Blocked while its exact owner is already stopped, unassigned and NeedsWork, emit an explicit invariant/diagnostic Hold, not a mutation. If Worker 1 finds a genuine uncovered release path, stop and report the exact call path and missing regression test to Lead before proposing any additional authority.

Deliverable

Extend or extract the existing pure planning logic where practical; do not build a parallel framework without explaining why. Add a pure planner that accepts a fully materialized, freshness-checked account/project snapshot and emits deterministic decisions for existing Ready work and unclaimed frozen review requests, while explaining Challenge-blocked and other held work.

Snapshot contract

  • Include source commit/ref, observation time, completeness/freshness, all relevant project task/attempt state, source leases, agent state/current assignment/unassigned disposition, review request identity/version/status, and Challenge wait/condition identity/status.
  • Include account-wide and project-level capacity evidence: configured limits, observed active sessions, reservations, and uncertain/in-flight launches across projects. Missing, stale, contradictory or incomplete capacity evidence must fail closed. Unknown/uncertain sessions count against capacity; never treat missing activity data as idle.
  • Do not use local last-seen cache or legacy FeedbackStore.attributed_agent_activity absence as proof that an agent is idle.

Deterministic decisions

  • Emit worker launch candidates only for existing Ready attempts whose task is still Open/InProgress, source lease is valid, owner is available, current assignment/generation matches, and every capacity check passes.
  • Emit reviewer candidates only for exact unclaimed frozen review requests; do not route work to a named reviewer or merge review and implementation authority.
  • Do not emit Challenge requeue mutations or intents for the canonical wake/release paths described above. Represent pending, partially satisfied, Eligible-but-busy, parked, already-Requeued and invariant-violating waits as explicit states/Hold reasons.
  • Use stable idempotency keys derived from project/task/attempt/generation or review ID/version. Identical snapshots must produce identical decisions; repeated polling must not mint new launch identities.
  • Represent Wait/Hold reasons explicitly for stale snapshots, missing capacity, busy/parked owners, source conflicts, unresolved Challenge waits, terminal tasks, uncertain submissions, duplicate reservations and Challenge reconciliation invariant violations.

Boundaries

  • No assignment mutation, Challenge requeue mutation, agent impersonation, browser prompt submission, session launch, live schedule change, deployment, restart, migration or activation.
  • Do not depend on Telos Work, Work Queue SQLite, or the Work Scheduler prototypes. Do not enable the Manager heartbeat or AfterAgentIdle.
  • Do not edit the currently leased BrowserSchedules/BrowserBridge files. Keep the new planner in a narrow, independently testable surface.

Tests and acceptance

  • Test deterministic repeat plans and stable keys; account-wide plus project capacity; unknown/uncertain sessions; stale/incomplete snapshots; source lease conflicts; terminal tasks; unclaimed review selection; pending versus partially satisfied versus fully satisfied Challenge waits; Eligible waits with busy/parked owners; stale attempt generation; and invariant-violating Eligible waits with an already-free owner.
  • Test that canonical Challenge satisfaction/release state is projected without generating a duplicate requeue intent. Preserve the existing owner-release behavior and audit provenance.
  • Provide a runnable test command and a sample snapshot/decision trace showing a Challenge becoming Satisfied, canonical ChallengeWorkflow requeueing the attempt, and the planner then recognizing the resulting Ready assignment as a launch candidate subject to capacity.
  • Document the exact remaining authority/runtime boundary for Phase 2. This phase is accepted only when the planner is independently reviewed and no live side effects have been introduced.
