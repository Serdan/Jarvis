General-purpose browser automation for Jarvis agents

Goal: Deliver a provider-agnostic browser capability that lets Jarvis agents create and manage permitted tabs, run project-owned JavaScript, and capture the live, dynamically rendered DOM once a caller-defined readiness condition is met. Treat ChatGPT automation as an example, not the feature's purpose or acceptance gate.

Existing implementation: Continue and review feature/browser-bridge (baseline 8154aef9aa6e6c462974e3525b80b1ede52cda34) and the existing architecture documents docs/BrowserBridgeSystem.md and docs/BrowserOneShotScheduler.md. Build on the implemented local Chromium/Edge extension, authenticated JarvisClient bridge, window/tab registration, generic JavaScript execution, scheduling, and existing regression tests; do not reimplement them or couple the core to ChatGPT. Check branch drift before starting.

Feature 1: tab creation and lifecycle

  • Expose registered windows and tabs, and create tabs in an explicitly user-registered browser window only with approved destination host permission and new-tab opt-in. Never enumerate or claim unrelated tabs.
  • Return durable-for-that-browser-session opaque tab registration identifiers; support readiness, availability, navigation within authorized scope, and controlled close. Only Jarvis-created tabs may be closed programmatically; preserve manually registered/user-owned tabs and the parent window.
  • Make creation, execution and cleanup results explicit. Handle browser/extension disconnects, navigation/revocation, stale registrations, timeouts, discarded tabs, capacity limits, and uncertain side effects without blind retries. Ensure tab lifecycle behavior is consistent across individual tools and composite operations.

Feature 2: script execution

  • Execute ordinary project/worktree-relative UTF-8 JavaScript files using the existing async function execute(args) contract, with JSON arguments and bounded structured results. Retain an optional exploratory inline-JavaScript tool under the same permissions.
  • Preserve ordinary project path isolation, opt-in host permissions, extension pairing, per-tab authorization, timeouts, output limits, and clear error taxonomy. Provider-specific selectors, login states, and action semantics remain entirely in project scripts, not Jarvis core.
  • Retain generic open → await readiness → execute → optional close and optional durable scheduled execution. For uncertain page effects, preserve the tab and do not blindly repeat the action. For persistent provider UI incompatibility, report actionable diagnostics and suspend recurring executions until explicitly reconfigured.

Feature 3: first-class live DOM snapshot

Motivation: curl often returns an HTML shell while the useful page content appears only after client-side JavaScript, hydration, fetches or user-interface events. An agent should be able to obtain the current DOM after that content appears through the existing authorized browser tab, without website-specific Jarvis changes or arbitrary fixed sleeps.

  • Add an agent-facing BrowserCaptureDom (name illustrative) capability for an authorized tab, using the same bridge/extension permission checks. Return a point-in-time serialization of the live rendered document or a caller-selected DOM subtree; include URL, document title, capture timestamp, the fulfilled wait condition, and useful timing/status metadata. It is a DOM snapshot, not a screenshot or original HTTP response.
  • Support an immediate snapshot and bounded waiting before capture. At minimum support: (a) an explicit delay/timer; (b) a DOM state predicate such as selector exists/appears, becomes visible or contains expected text; and (c) a specified DOM event on document/window or a selected element (including site-specific custom events). For DOM mutations, prefer MutationObserver with an immediate predicate check and cleanup; avoid brittle polling-only implementations. Document that a one-off event fired before listener registration cannot be observed retrospectively.
  • Wait/capture must share an explicit configurable bounded deadline and use cancellation/cleanup correctly. A page navigation, lost registration, revoked permission, browser disconnect or timeout must yield a distinct actionable outcome, never an indefinitely hanging operation. Background tab throttling and wake/activate policy must respect the existing explicit-consent boundaries.
  • Capture actual post-hydration markup (e.g. serialized document.documentElement.outerHTML or the selected subtree) in a documented consistent format, with optional extracted text/metadata where useful. Do not substitute curl, network-response source, or a screenshot. Only inspect DOM accessible to the authorized script; do not bypass cross-origin iframe restrictions or browser security boundaries.
  • Enforce predictable size bounds. Small snapshots may be returned inline; large DOM captures must have a clearly defined explicit bounded file/artifact export path so agents can retrieve the entire authorized snapshot without silently truncating the content at the current bridge response limit. Oversized captures fail transparently when no suitable export is requested. Avoid accidental logs of DOM, credentials, prompts or page contents; treat snapshots as potentially sensitive and avoid automatic Git persistence.
  • The generic snapshot tool must be useful without authoring a custom site script. Advanced site-specific readiness or extraction can still use the existing project-script execution mechanism. Keep wait conditions structured and constrained rather than inventing a general workflow DSL.

Acceptance and verification

  1. A Jarvis agent can target an explicitly registered window, open a tab on an approved origin, inspect its registration/availability, run a project-owned script, capture live DOM, and close only its own tab. Explicitly registered user tabs can be inspected but never closed by the agent tool.
  2. On a local JS-rendered fixture where initial HTML contains no target data, curl/raw response lacks the data but BrowserCaptureDom returns it after a selector/mutation condition. Verify a delay-based capture and custom DOM event-based capture separately, including event registration/timeout semantics.
  3. Both full-document and subtree captures return useful markup plus metadata. Verify large page behavior using inline bounds and the chosen file/export route with exact bytes/round-trip integrity, or an explicit bounded error if export was not requested.
  4. Tests exercise delayed hydration, event-not-fired timeout, navigation during wait, browser disconnection, revoked authorization, browser restarts, concurrent tab operations, retained tabs after uncertain script execution, and cleanup of listeners/timers on completion or error.
  5. Regression tests cover the existing bridge's window/tab consent, script execution, scheduling and error behavior. Run relevant .NET and JavaScript tests; perform at least one live supported Chromium/Edge test using a generic JS-rendered page. ChatGPT-specific launch success is not required for acceptance.
  6. Review and correct discovered defects, update user-facing setup/API docs and examples to lead with generic browser automation, and document any remaining limitations. Prepare branch for normal integration review. Do not merge or deploy without explicit operator approval.

Boundary: Jarvis owns authorization, tab lifecycle, script transport, waiting, snapshot/export and generic outcomes. Ordinary project scripts own website-specific logic. This task does not implement Codex agent continuation, provider routing, an autonomous browser-repair agent, or a general event workflow engine.
