# P2 — Older-client acknowledgement silently destroys typed notification identity

**Frozen source:** `90ec35f124a2ed0e4c8c7b9c3cd3729ddc0ad094`, `Client/Modules/ReviewWorkflow.fs:260-270, 495-510, 690-707, 1609-1627`, `Client/Modules/ChallengeWorkflow.fs:201-230`; compare prior canonical client `b277cd0d1b850b97ad81d889e2278aaef74e74ae:Client/Modules/ReviewWorkflow.fs:254-263, 1603-1621`.

Typed challenge notifications are written as **schemaVersion 2** entities with new `kind="challenge"` / specific `eventType`, while the schema-2 decoder explicitly tolerates missing/extra properties. This permits an older client to read the notification but its old `AgentNotification` record has no `Kind` or `EventType`, and its unchanged `acknowledgeNotification` writes `{ notification with AcknowledgedAtUtc = ... }` through the old record serializer. So an old client acknowledging a new challenge notice permanently removes both type fields from the canonical Git record. On a modern reader that record is subsequently normalized to `kind="message"`, `eventType="direct"`; history misclassifies the original challenge event, even though it was an immutable typed notice. The new runbook (`docs/notification-indicators.md:60-66`) claims older clients are compatible because they ignore unknown properties, which overlooks this destructive write path.

**Required:** Establish a backwards-compatible write barrier for typed challenge notifications (e.g. new entity schema/version with new clients supporting legacy schema-2 messages and older clients failing closed on new typed notices, or an equivalent safe migration gate), or preserve additive fields across old acknowledgement versions using an authoritative immutable event lineage. Test old-client deserialization and acknowledgement of `challenge`/`assigned` followed by new-client history read. Historic direct messages must still default to `message/direct` and remain acknowledgeable.
