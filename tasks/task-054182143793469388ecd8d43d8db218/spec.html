Expose unread notification counts by kind in Jarvis tool responses

Goal

Make pending agent notifications discoverable during ordinary Jarvis tool use, without requiring explicit inbox polling and without repeating notification contents. This must support the forthcoming structured challenges workflow.

Requirements

  • Include an optional, compact notifications summary on agent-attributed tool responses, keyed by notification kind with unread counts, e.g. {"notifications":{"message":2,"challenge":1}}. Omit zero-count kinds and omit the summary entirely when there are no unread notifications.
  • Scope counts to the actual recipient agent (and the appropriate project/ledger), never all agents or the whole project. Cross-project notification routing must count only where the destination recipient receives the notification.
  • Introduce an extensible, well-defined notification-kind model. Separate the kind (broad workflow such as message, challenge) from a more specific event type (e.g. challenge satisfied or blocked). Do not introduce priority semantics. Preserve compatibility with existing agent-to-agent messages.
  • Integrate with challenges so that challenge lifecycle events can be surfaced under challenge when that functionality is present, routing each notification to the agent expected to act next. Do not conflate challenge issuer, owner and satisfier.
  • Implement summary enrichment in a shared response path rather than per-tool boilerplate, but ensure error handling, identity, permissions, serialization and transport layering are correct. Do not make result payloads ambiguous or accidentally add duplicate envelopes.
  • Unacknowledged counts must reflect durable ledger state and existing acknowledgment operations. Avoid redundant payloads or expensive per-response ledger retrieval. Use a sound cache/index or other efficient approach if necessary, with correct invalidation across writes, acknowledgments, devices and restarts.
  • Do not change agent state, auto-acknowledge notifications or require immediate inbox processing. Preserve existing notification content retrieval and acknowledgement behavior.

Design and acceptance

  • Inspect current MCP response envelope, agent attribution and notification ledger implementation first; document the selected schema and compatibility/migration strategy, including whether client/server coordinated deployment is necessary.
  • Cover responses with no unread notifications, mixed kinds, new notification arrival, acknowledgement, agent/project isolation, cross-project messages, challenge events and error paths.
  • Test that ordinary responses remain bounded and do not duplicate AGENTS.md or notification contents. Add focused automated tests and update protocol/schema/docs as appropriate.
  • Keep the design minimal and extensible; kinds should represent actionable workflow categories, not one enum member per individual event.
