[P2] Index operator-owned challenge queue instead of polling historical challenge blobs

Finding: In the staged one-shot operator-feedback integration, ConsoleTui.fs calls startChallengeRefreshUnsafe every 30 seconds whenever operator access is configured, even outside the Challenges panel. OperatorChallengeApi.list iterates all trusted projects, and ChallengeWorkflow.listOperator currently lists and deserializes every canonical historical challenge to find operator conditions (batched in groups of 128). This defeats the independent active-index scaling guarantee established for ordinary agent inboxes, and creates work proportional to permanent historical challenge volume on each periodic TUI poll.

Scope

  • Introduce snapshot-consistent, account-local UI-visible read projections for operator-owned conditions, distinguishing active pending conditions from a bounded recent history of satisfied/cancelled outcomes. Persist/update materialized indexes atomically with the same canonical Git ledger transactions already used for ordinary Challenge active/recent indexes; do not infer ownership from an empty agent ID (explicit OwnerKind=Operator is required). Keep historical evidence in immutable challenge/event records and on-demand getOperatorPage.
  • Read the operator queue by indexed IDs with bounded batched canonical dereferences from one verified snapshot; avoid enumerating all challenges/* blobs merely to render a badge or refresh the panel. Preserve exactly-one authenticated human response, response provenance, explicit operator identity, no new notification transport, no threaded chat, optional task blocking, and ordinary issuer inbox evidence.
  • Keep the 30-second refresh cheap (or reduce it when the panel is inactive, if semantics permit) and fail closed on corrupt or inconsistent index state. Support multi-client CAS races, cancellation, completion, replay/idempotency, and restart without stale actionable conditions or missing newly pending conditions. Avoid rebuilding the index from all history on each read.

Acceptance

  1. More than 4,096 archived non-operator and operator challenges do not make ordinary TUI operator refresh traverse historical canonical challenge blobs; process count and blob bytes scale with current actionable operator work plus bounded recent outcomes, not the entire corpus.
  2. Agent-owned and Unassigned conditions never appear in operator queue; operator-owned pending conditions never leak to agent triage; resolved/cancelled entries cease being actionable and remain retrievable with immutable evidence/provenance.
  3. Creating, responding to, cancelling, and reopening challenge conditions update indexes atomically and deterministically across two clients and after restart; stale read indexes cannot fabricate permission or lose needed operator action.
  4. Run .NET 11 Release focused and integration tests plus independent frozen review. Coordinate with current operator-feedback feature integration; do not merge/deploy without approval.
