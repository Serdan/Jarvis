Constrain HTTPS import origins and redirects with explicit trust policy

Priority: P2. Finding: JRV-2026-11-03. Review: docs/reviews/2026-11-07-deep-review.md (baseline e50c24af).

Problem

ImportFile checks only HTTPS before using a default redirecting HttpClient. PartialTrust permits workspace writes including network import, so an authorized caller might fetch network-local content and import it into a readable workspace. This is an authorized-caller trust-boundary issue, not an unauthenticated exposure.

Relevant code

Client/SignalR/Client.fs:298-368; Client/Modules/PermissionPolicy.fs:135-136,184-198; Client/Runtime.fs:10; Server/McpTools.fs; Client.Tests

Implementation requirements

  1. Separate provider-backed attachment imports from intentionally generic URL fetches in the typed command/validation path; avoid trusting arbitrary caller-provided download_url or MIME metadata as proof of origin.
  2. Identify and validate supported attachment delivery origins, and apply the same trust policy to each HTTP redirect. Fail closed for redirects to forbidden private, loopback, link-local, metadata or otherwise untrusted network targets. Address DNS re-resolution/rebinding and the actual connected address (not hostname text alone).
  3. Generic arbitrary HTTPS import must require explicit local confirmation or a clearly configured opt-in trust policy. Preserve byte and timeout limits; apply safe streaming/atomic destination handling and close HTTP resources correctly.
  4. Own and reuse HttpClient/handlers with a clear lifetime. Preserve successful legitimate provider file imports without hard-coding ephemeral hostnames or weakening path protections.
  5. Document intended threat model, what is allowed under FullTrust/PartialTrust/NoTrust, and any protocol compatibility requirement.

Acceptance / verification

  • Deterministic local HTTP handler tests cover trusted-origin success, rejected direct private/loopback/link-local connections, public-to-private redirects, DNS rebinding, oversized and stalled downloads, and explicit opt-in generic imports.
  • Permission-policy tests establish that PartialTrust never silently grants a generic network fetch, while legitimate supported attachments still work.
  • Focused and full Client Release tests pass; no secret-bearing URL or content is included in logs.

Boundaries

No arbitrary network proxy feature, and no external penetration test as a prerequisite.

Review the design and implementation; correct findings and re-review until accepted. Prefer long-term correctness to quick fixes.
