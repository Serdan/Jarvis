Add measured per-user MCP concurrency and resource limits

Priority: P3. Finding: JRV-2026-11-10. Review: docs/reviews/2026-11-07-deep-review.md (baseline e50c24af).

Problem

The authenticated /mcp endpoint lacks RequireRateLimiting even though /client and /exports use a fixed-window policy. Heavy authenticated operations can occupy long-lived requests and local Git/process work; an unmeasured global IP quota would harm legitimate multi-agent work behind NAT.

Relevant code

Server/Program.fs:139-172,183-187,213-237; Server/McpTools.fs; Server/Services/ClientService.fs; Server.Tests/McpAuthenticationTests.fs; Server.Tests/ServiceTests.fs

Implementation requirements

  1. Establish representative legitimate concurrency/load from multiple Jarvis agents and devices before choosing limits. Separate short MCP discovery reads from long-lived calls when necessary, and avoid coupling independent users through one proxy/NAT IP.
  2. Define an authenticated-subject scoped concurrency budget and request-rate policy appropriate for heavy MCP tool calls. Enforce reasonable queue lengths, timeouts and backpressure; rejected requests should return clear Retry-After semantics where appropriate, not disappear or starve other users.
  3. Preserve OAuth challenges, Authorization, SignalR protocol behavior and device generation/correlation correctness. Make configuration tunable and choose defaults that support normal agent fan-out.
  4. Limit per-user resource consumption without replacing the simple server architecture; consider cancellation behavior and cleanup if callers disconnect.

Acceptance / verification

  • Integration tests show independent users cannot consume each other's concurrency allocations, overload returns controlled responses and bounded queueing, and normal multi-agent throughput is preserved.
  • Measure a realistic burst against the selected limits and document capacity, retry behavior and operational tuning rather than guessing an overly restrictive IP-based threshold.
  • All Server Release tests pass and existing authentication failure semantics remain unchanged.

Boundaries

No distributed limiter/Redis; Jarvis server is deliberately single-instance.

Review the design and implementation; correct findings and re-review until accepted. Prefer long-term correctness to quick fixes.
