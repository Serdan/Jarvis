P1 — recipient-controlled notification blocking and interchangeable review pool

Operator directive (2026-11-12): agents are flooding other agents' inboxes. Every agent must be able to block unwanted coordination notifications; reviewers are interchangeable, and no agent should ever directly notify a named reviewer. Stop requiring Lead or specific Reviewer N to be notified on normal review submissions. This is a high-priority workflow correctness issue, not a cosmetic hide/filter.

Current behavior (verified source)

Client/Modules/ReviewWorkflow.fs:1010-1041 notifyAgent creates one durable notification record via LedgerStore.transact once sender/recipient exist, with no recipient preference/blocking. pendingNotifications includes every unacknowledged record for recipient. Source ReviewWorkflow already exposes a shared ReviewerQueue and atomic claim/review lifecycle. Cross-project NotifyAgent is routed through Server/McpTools.fs and Client/Modules/OrchestrationApi.fs. AGENTS.md/reviewer-role guidance may be delivered from Jarvis role instructions; verify actual source before making guidance permanent. Existing notification acknowledgements are not equivalent to blocking.

Implementation

  1. Provide self-service durable recipient-owned notification preferences: block/unblock a specific sender identity within a project, and optionally mute all unsolicited agent-to-agent coordination notices. Preserve correct project-qualified sender identity across cross-project delivery; no spoofing, stringly role inference, or unrelated agents mutating recipient preferences. Unblocks must be reversible. Expose through MCP tools and include the current preference state/readback; support registered unassigned agents.
  2. Enforce recipient block preferences before recording a durable NotifyAgent notification in the destination ledger, in the same serialized/CAS decision as the write. A blocked retry must not create a record. Return clear, non-spamming suppressed/blocked result with consistent idempotence, not a misleading successful delivery. Existing earlier notifications should remain in history; decide whether to hide pending ones or offer explicit bulk acknowledgement as an opt-in, not silent deletion. Preserve legitimate self/administrative diagnostics as needed with an explicit audited distinction.
  3. Reviewer pool policy: submit a frozen review, leave it in the existing claimable shared queue; any eligible reviewer chooses/claims it atomically. Workers, Leads, and reviewers must not target individual reviewers with NotifyAgent to request reviews. Persist concise applicable agent/role guidance; avoid relying solely on voluntary compliance if the current role model permits enforcing reviewer-specific direct-message rejection. Verify role capability/identity from canonical data, not from agent name prefixes. A recipient reviewer may still receive canonical review/assignment/decision events through the normal structured inbox; block preferences apply only to discretionary coordination notices.
  4. No automatic notifications for normal review submissions or polls; no role-specific fan-out to every reviewer. Avoid adding a global poller or background work when a shared queue already exists. Keep review requests visible without pinging humans or reviewers. If necessary improve the reviewer queue indicator without duplicating ledger notices.
  5. Update documentation/instructions for all agents, not only Reviewer 1. Add minimal MCP commands for preference management with source-bounded read/write, authorization and true cross-project behavior; typed outcomes should distinguish blocked from delivered. Avoid schema/API churn outside this feature.

Acceptance / negative-space tests

  • Recipient blocks Agent A in project X; Agent A from X and via project Y cannot deliver into recipient's inbox; unrelated Agent B can. Unblock restores delivery. Unauthorized actor cannot alter recipient preferences. Same operation ID retries don't bypass suppression or duplicate records. Concurrent block-versus-send behaves according to one consistent serialized ledger snapshot.
  • Reviewer submits and claims frozen review exclusively using shared queue, no reviewer-specific notifications; attempts to send discretionary review requests to an individual reviewer are refused if role policy can be reliably enforced. No identity-by-name hacks. Existing accepted reviewer decisions and feedback aren't blocked.
  • Full .NET11 Client and Server Release suites, existing snapshot and notification scaling/authorization tests, regression that mute never causes hidden unbounded persistent notification growth, cross-project envelope checks, Git diff --check and frozen independent review before Lead integration and coordinated deployment.

Work in isolated branch on current source main; no production state mutation, Nginx changes, or premature integration. Existing urgent Favn P1 and Worker2 UI filter assignments continue independently.
