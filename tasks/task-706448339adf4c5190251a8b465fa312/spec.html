Client-side automatic promotion of slow Jarvis tool calls to jobs

Priority P1. An agent should invoke ordinary Jarvis tools without predicting runtime. A fast operation returns its usual response; once a configurable short threshold (initial default approximately 3 seconds) elapses, the client returns a typed Running job handle, while the same operation continues to completion. Later get_job_result retrieves the exact outcome without executing it again. This must be implemented client-side using normal .NET Task primitives (prefer Task.WhenAny with Task.Delay, or equivalently safe semantics), not a new server-side task store, worker process or scheduler.

Existing architecture and related task

  • Client/Modules/JobManager.fs currently owns in-memory OS process jobs with generated IDs, project binding, bounded stdout/stderr events, cancellation and retention (at most 100 completed). Generalize the abstraction rather than treating in-process tool operations as fake processes. Preserve current process-job tool contracts and behavior.
  • Client/Program.fs registers ReceiveCommand as a task-returning SignalR callback; Client/SignalR/Client.fs runs command preparation, implicit Ready-to-Working activation, typed dispatch and response delivery inside that callback. Server/McpTools.fs forwards commands through ClientService and returns typed tool results. The server remains a router, not the owner of execution tasks.
  • Related but distinct P2 task task-b0e62987fa03497a809a7d1bdd700ae4 investigates intermittent SignalR receive/dispatch head-of-line stalls (BN-047, delayed agent_inbox and get_job_result). Coordinate on the shared ingress/dispatch abstraction and instrumentation; fixing or avoiding client receive-loop blocking is necessary for responsive polling but does not require moving job ownership to the server.

Execution and response contract

  1. After validating authentication, routing, capability, project/worktree and OS permissions as normal, admit the operation into a bounded client-owned task registry with an immutable job ID, original command identity/operation ID, project/device/actor association, start timestamp and final AgentCommandResponse. Admission must happen before execution; ensure execution does not synchronously monopolize SignalR ingress before the timer can start. Use asynchronous bounded dispatch or a carefully constrained worker mechanism, not unlimited Task.Run / unobserved fire-and-forget tasks.
  2. Race the execution task with a deadline task using Task.WhenAny. If execution wins, return the existing regular success/error payload without a job wrapper. If deadline wins, return a clear typed pending handle (jobId, status Running, associated stable operationId where applicable, and suitable provenance). The original execution is not cancelled, restarted or requeued when promotion occurs.
  3. Extend the existing job model/API to support a distinct tool-operation job alongside OS-process jobs (discriminated union or equivalent typed model). Poll through get_job_result or an explicitly coordinated compatible result endpoint; terminal results must reproduce the original typed AgentCommandResponse, including normal serialized payload, errors, instructions, implicit lifecycle activation receipts and agentStateChanges. A pending response must not falsely claim agentStateChanges: [], because mutations may not yet be known. Do not double-deliver or reapply state effects when polled repeatedly.
  4. Keep jobs discoverable by ID and appropriate listing/recovery interface, including when the initial pending-handle response was lost. Bind access to the same authenticated user's project/device and initiating agent/assignment as appropriate. Reject guessed, expired and cross-project/cross-user job IDs. Preserve operation IDs for idempotent ledger writes and handle an uncertain write outcome without blindly repeating it.
  5. Bound concurrently running and queued operations and result retention. Define terminal states Completed, Failed, Canceled and explicit expiry/eviction responses. Ensure completion exceptions are observed, resources disposed, and cancellation semantics distinguish abandoning a wait from cancelling an operation. Existing process-job status/output/cancel behavior must remain intact. Job registry is client-memory scoped; a client restart loses it, so expose a clear unavailable/reconcile path using stable operation IDs for persisted writes.
  6. Ensure get_job_result, list_jobs and other cheap control requests stay responsive while a slow command runs: no SignalR callback head-of-line waits, no reply-on-same-connection deadlock, no starvation or unbounded memory growth. Preserve committed Ready-to-Working transitions once, regardless of when the eventual result is collected. Review server timeout/request-abort behavior so returning a handle is distinct from transport failure; client owns the continued operation lifetime.

Acceptance and tests

  • Quick tool call returns exactly the old response. Deterministically blocked tool call returns a handle near the configured threshold, completes once and can be polled for the identical typed terminal response. Include error and exceptions, source reads and ledger writes.
  • Parallel slow and cheap commands: cheap get_job_result is not delayed by the long-running command. Exercise multiple projects and competing agents, bounded-queue saturation, concurrent state mutations, cancellation and reconnect.
  • Repeated polling is side-effect-free; retries/reconnects do not cause duplicate ledger writes or extra Ready-to-Working transitions; lost initial handle is recoverable where possible. Verify no false empty state-change lists on pending responses and no loss of instructions/error detail on completion.
  • Existing OS-process jobs remain compatible (start/list/status/output cursor/truncation/cancel). Cross-project, cross-device and cross-user access protections continue to hold. Verify eviction/expiry, client restart and incorrect/unknown job IDs.
  • Record pre/post timings with at least a controlled slow-command/cheap-command test. Run Release Client and Server tests; freeze commit, obtain independent review before merge. Protocol changes require a coordinated client/server release with separate operator approval. No production deployment or client update is authorized by this task.
