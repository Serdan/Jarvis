Read-only cross-agent observation

Feedback: bb82fc5d8c184a2daedf8d5759a3dc15; 7fb0f3d49e484dbf89b2b8ad2b139bfb.

Problem

agent_inbox is described as a read but the supplied agentId is treated as the actor. Lead observing another agent accidentally starts Ready assignments and falsifies Working / last-seen signals. This is an API authority and semantics boundary, not a cosmetic dashboard bug.

Required behavior

  • Expose an explicitly observational operation (prefer observe_agent or equivalent) that has distinct acting agentId and targetAgentId; do not perform target-attributed activity as a side effect of observation. Preserve self-agent_inbox activation behavior.
  • Return target assignment, attempt phase, execution/disposition, last-seen provenance, notification/review counts, pending blockers and relevant administrative metadata as available, with explicit unknown/unavailable markers. Distinguish canonical ledger state from transient activity observations.
  • Enforce same-project authorized operator/agent access as appropriate; never accept target identity as proof of actor authority. Observation must not mutate target version, state sequence, active session, assigned slot, checkpoint, or notifications.
  • Make agent_inbox documentation prominent about Ready-to-Working activation, indicate the observation tool, and show any activation before/after state clearly. Maintain API/schema and client/provider compatibility.
  • Coordinate with global operator Agents dashboard task task-6c6d71c8d3ef408eb30886ded9522af3, sharing a canonical read model where possible without creating duplicate lifecycle authority.

Acceptance

  1. Lead observes eight Ready agents: all retain exact state/version/sequence and no synthetic last seen. Repeating from separate sessions is idempotent and read-only.
  2. Self-inbox still starts a genuinely Ready assignment once; second read cannot restart Working clock.
  3. Cross-project/missing/unauthorized targets fail explicitly and without target mutation; stale/cached observation is labeled, never presented as authoritative current state.
  4. Unit and integration tests cover observer-vs-actor identity, concurrent actual activity, and command documentation; Release suites pass.

Do not deploy without explicit operator authorization.
