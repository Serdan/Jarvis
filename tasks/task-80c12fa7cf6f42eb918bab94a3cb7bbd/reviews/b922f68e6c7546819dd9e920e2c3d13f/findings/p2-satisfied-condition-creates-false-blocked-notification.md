# P2 — Satisfying another condition while challenge is Blocked fabricates another blocked notification

**Frozen source:** `1005298d5df1d5b3d836c4e6fdd5a8f03cd8fb8a` (`Client/Modules/ChallengeWorkflow.fs:318–375`). Review `b922f68e6c7546819dd9e920e2c3d13f`.

**Reproduced against the exact frozen source with a disposable independently added NUnit test** (no owner branch edits). The regression created a two-condition challenge issued by Agent 3; Lead blocked its condition with reason “review hold”, correctly emitting one blocked notice. Agent 8 then satisfied its *different still-Pending* condition with evidence `benchmark:pass` and **empty blocked reason** while the overall challenge remained Blocked. Expected only the first blocked notice; actual count was **2**. The second notification wrongly states that Agent 8 blocked the challenge, with empty reason. Isolated job `62a86bf51c224c66812c7f666333ccac` exited 1: NUnit `SatisfyingPendingConditionWhileAnotherIsBlockedMustNotEmitFalseBlockedNotice`, `Expected: 1; But was: 2`, assertion line 525 of injected test in `/tmp/jarvis-reviewer1-challenge-negative-1005298/Client.Tests/ChallengeWorkflowTests.fs`.

**Root cause:** `ChallengeWorkflow.update` independently resolves the target condition as Satisfied (reason empty) or Blocked (reason nonempty), then computes overall `nextStatus = status nextConditions`. At lines 365–372 it emits `blockedNotice` whenever `kind = "ResolveChallengeCondition" && nextStatus = "Blocked"`, even when the **target condition was just Satisfied** and overall Blocked is inherited from *another condition*. Every distinct resolving operation ID creates a distinct durable notification; atomic dedup is behaving correctly for each operation, but cannot prevent this incorrect business event.

**Impact:** Spurious durable issuer notifications, false attribution of blocked action/reason to successful condition owner, duplicated noise while issuer is deciding whether/how to reopen. Violates the contract that a notification reports an actual newly Blocked condition, and that independent success does not fire an unrelated blocked notification. No data corruption, automatic resumption or missed last-condition satisfaction was observed in this reproduction.

**Fix:** Trigger blocked notification based on **newly transitioned target condition to Blocked**, not only aggregate challenge `nextStatus = Blocked`. If multiple conditions legitimately block at separate times, each genuinely blocked condition may deserve its own notice; retain atomic per-operation dedup, immutable evidence and final ALL-satisfied notice. Add the above two-owner regression to permanent challenge tests, plus optionally an additional legitimate second distinct block to prove it *does* notify. The already Blocked + separate Satisfied transition must emit no new blocked notice.

**Severity: P2**, blocking this challenge feature's independent review.
