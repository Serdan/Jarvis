Durable agent challenges

Implement first-class challenges for structured inter-agent coordination. This task has no dependency on hooks, browser control, or automatic agent scheduling.

Behavior

  • An agent issues a challenge containing a title, optional task context, and one or more conditions, each assigned to a specific agentId with a description.
  • Jarvis generates stable challenge and condition IDs, persisting everything in the existing Git ledger, independently of source branches.
  • Initial completion policy is ALL: every condition must be satisfied.
  • Initial onSatisfied policy is notify: when every condition is satisfied, create exactly one existing-format durable notification in the issuing agent's inbox, including condition results and evidence. Do NOT automatically start or resume an agent.
  • Assigned agents can discover outstanding conditions and explicitly resolve their own conditions with evidence. Support Satisfied and Blocked outcomes for conditions. A Blocked condition makes the overall challenge Blocked and creates a normal notification to the issuer with the reason and evidence; it must never count as satisfied or trigger onSatisfied. Distinguish Pending, Blocked, Satisfied and Cancelled challenge states. Blocked is recoverable: the issuer may reopen the blocked condition or cancel the challenge, preserving immutable history and deduplicating notifications.
  • A Blocked challenge is not an automatic completion. It remains visible and needs an explicit issuer decision before proceeding. Reopening transitions it back to Pending, without clearing evidence history.
  • The issuer can cancel an outstanding challenge. Maintain an auditable immutable history of outcomes and cancellation, including timestamps.
  • Enforce authorization, concurrency safety, idempotent retries, and exactly-once notification behavior using existing ledger and notification conventions.

Agent-level blocked work and challenge dependencies

  • Distinguish a blocked challenge condition from an assigned task owner's blocked attempt. Reuse canonical attempt Blocked disposition rather than inventing another agent state if possible. Show reason, dependency, and operator action; preserve Waiting for taskless agents.
  • An agent waiting for a challenge may explicitly block its attempt, releasing execution without losing ownership, reviews or integration. Model zero, one or multiple dependencies and clear ownership of unblocking.
  • Initial onSatisfied remains notification-only. Challenge satisfaction does not launch an agent or silently transition to Working. After resolution, an explicit unblock/requeue produces Ready, not Working, and preserves audit evidence. Partial satisfaction must not unblock an agent awaiting multiple conditions.
  • Specify and test state mapping in client/inbox, authorization, idempotency, cancellation, stale dependencies and concurrent conditions.

Tools

  • create_challenge: define conditions and owners; return generated challenge and condition IDs.
  • list_challenges: show issued and assigned challenges with statuses.
  • get_challenge: inspect conditions, evidence, and history.
  • resolve_challenge_condition: satisfy or block an owned condition with evidence/reason.
  • reopen_challenge_condition: issuer explicitly reopens a blocked condition with a reason, restoring challenge Pending if no blocked conditions remain.
  • cancel_challenge: cancel an issued challenge with a reason.

Acceptance tests

  1. Agent 3 issues a challenge requiring an integration update from Lead and native benchmark results from Agent 8.
  2. Lead and Agent 8 can independently satisfy their conditions with evidence; unauthorized actors cannot.
  3. Satisfying one condition does not finish the challenge. Resolving the final condition creates one notification for Agent 3.
  4. Concurrent updates, duplicate operation retries, and process restarts cannot lose updates or duplicate completion notifications.
  5. Blocking any condition sets the overall challenge Blocked and notifies the issuer once. Reopening is explicit, preserves history, and lets the challenge reach Satisfied only once all conditions are satisfied. Cancelled challenges cannot complete.
  6. Documentation specifies payloads, ownership, ledger semantics, and the deliberate lack of hook or browser dependencies.
  7. Blocked attempt is visible distinctly from Ready, with a reason and challenge link; resolving only one dependency leaves it Blocked, and explicit requeue after complete satisfaction moves to Ready without auto-Working.
  8. Reopening, cancellation, stale links and races do not cause unintended task lifecycle changes.

Do not introduce a generic workflow engine, condition expression language, or agent scheduler. Do not deploy without explicit operator approval.
