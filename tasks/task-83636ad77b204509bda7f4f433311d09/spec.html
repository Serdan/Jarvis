Prevent cross-agent state mutation through self-inbox identity confusion

Priority P1; follow-up to completed task-79b4fe205a86463184e5ff90b743e9d7. The reviewed observe_agent command (protocol 3.63, merged at 4696197c) is side-effect-free, but the agent_inbox tool still accepts any caller-supplied agentId and automatically activates that agent's Ready assignment. A Lead or reviewer can inadvertently change another agent's canonical state simply by asking for its inbox. The self-inbox documentation alone cannot prevent this.

Root cause to address

  • Server/McpTools.fs:AgentInbox constructs TaskReadCommand(Action=AgentInbox, AgentId=agentId) from the tool argument. RequestDeviceRouting.agentArgument derives the transport's acting agent from the same untrusted argument; comparing those two strings is therefore not an independent self-identity check.
  • Client/SignalR/Client.fs:activateReadyOnActivity uses this acting label and may commit Ready-to-Working, reset activity provenance, and claim a Working turn before the inbox read. An out-of-session inspection must not do any of those things.
  • Both currently connected production clients use protocol 3.62, so even the new read-only observation surface is not yet deployed. Do not treat rollout alone as proof that misuse is prevented.

Required behavior

  1. Establish a genuine self-inbox boundary independently from the submitted target/agentId field. Prefer a validated conversation/session-to-agent association backed by the canonical ledger or another explicit bound actor context. Examine initial registration/first-turn semantics and preserve the existing legitimate self-inbox activation workflow without permitting the caller to silently assume another agent's identity merely by changing a parameter.
  2. If the caller asks to inspect a different agent via agent_inbox, reject it with an actionable SelfInboxOnly-equivalent validation error directing them to observe_agent(projectName, agentId, targetAgentId). Perform the check before RecordAgentSeen, implicit activation, Git ledger reads that attribute activity, or other effects. If authentic actor/session context is missing or ambiguous, fail closed for activation; do not invent self identity.
  3. Keep genuine self-inbox behavior: exactly one Ready-to-Working activation on a legitimate self call; repeats must not restart the Working clock; confirmed before/after activation and canonical state-effects remain visible in every response, including an error after a committed transition.
  4. Keep observe_agent explicitly read-only and usable by authorized other agents and operators with separate observer and target labels. Do not undermine ledger ownership, session association, cross-project authorization or actual agent-attributed activity while tightening self-inbox.
  5. Maintain the existing operator workflow for roster inspection and administrative changes through the correct, explicit operations; do not force operators to impersonate a target to observe it. Review compatibility/rollout for protocol 3.62 versus 3.63 and ensure there is no silent behavior regression during migration.

Acceptance / adversarial regressions

  • Two registered Ready agents A and B. Associated session A invoking agent_inbox(B) cannot change B's state, version, sequence, assignment generation, Working clock, notifications, or last-seen; it returns an explicit error pointing to observe_agent. Agent B's genuine self-inbox starts B once.
  • Repeated observation across separate sessions/devices, forged transport agentId, unknown/unassociated session, duplicate display names and cross-project targets never attribute activity to the target or silently bootstrap an unrelated identity.
  • Exact first-session association/legitimate activation and concurrent activity/canonical ledger CAS are tested; activity stays attributed to the real actor, not merely the supplied target. Negative tests confirm rejected calls perform zero ledger writes and no local Seen updates.
  • Full Client/Server Release suites pass; independent reviewer validates frozen source, particularly the difference between OAuth user authorization and agent-session identity. No merge or deployment before review. Coordinated server/client release requires explicit operator approval.
