Make agent inbox and observation semantics unmistakable to agents

Priority P2. This task explicitly does NOT implement actor/session identity enforcement. An agent mistaking agent_inbox for a passive read may inadvertently activate another Ready agent. The relevant issue is discoverability and accurately communicated side effects, not deceptive callers or impersonation. Respect the operator's preference for simple, clear tool contracts over additional security/identity machinery.

Existing behavior to explain and preserve

  • agent_inbox(projectName, agentId) is an activity-producing self-inbox call: reading a Ready assignment can transition that agent to Working and update last-seen. Other agent-attributed tools can also activate the caller. Existing canonical state-change and committed self-inbox activation receipts must remain accurate.
  • observe_agent(projectName, agentId, targetAgentId) is the passive cross-agent read. It does not begin the target's turn or update last-seen. It was implemented in closed task task-79b4fe205a86463184e5ff90b743e9d7, merged into main under protocol 3.63.
  • The current MCP descriptions and capability catalog already attempt to explain this distinction. Audit whether that wording is consistently conspicuous and actionable to agents; do not assume a change is needed where the existing source already conveys it clearly.

Required work

  1. Review actual MCP tool names, one-line descriptions, ReadOnly annotations, capability metadata, relevant AGENTS.md/instructions and examples. Prefer unambiguous, concise, positive guidance: use agent_inbox when starting/continuing your own assignment; use observe_agent to inspect another agent. Clearly say that the former may change lifecycle state and last-seen, and the latter does not.
  2. Where needed, improve discoverability of the safe observation tool (including the ordinary tools the model sees) and ensure they agree with documentation and activity metadata. Consider a clearer alias only if the benefit justifies compatibility cost; do not gratuitously rename or remove existing public tool methods.
  3. Retain explicit canonical state-change/activation reporting in the tool response, including when a read fails after confirmed activation. A pending action or ordinary passive observation must not report fabricated mutations.
  4. Check instructions used by Lead/reviewers to inspect agent status, and replace any examples encouraging agent_inbox(projectName, agentId=otherAgent) with observe_agent or authoritative passive roster views.
  5. Do not implement session-to-agent binding, actor attestation, stricter access control, forged-identity detection, new permission flows, or failure on caller/target label mismatch. This task is about avoiding innocent tool misuse; the operator explicitly rejected identity enforcement.

Acceptance

  • Tool metadata/catalog/instructions clearly distinguish self-inbox activity from read-only observation; no accidental claims of ReadOnly on activating operations. A new agent reading the tool descriptions alone can pick the correct one.
  • Regression tests cover observable metadata, response state-change reporting and read-only observation behavior where current tests do not already cover it. Prefer extending existing tests and avoid duplicating the complete prior feature suite.
  • No changes to lifecycle authorization, agent identity/session binding, ledger semantics or operator workflows. Release suites pass and frozen code/document changes receive independent review before merge. Deployment of protocol 3.63 requires separate explicit authorization.
