[P1] Operator conversations through durable challenges and Jarvis TUI

Purpose: Agents running headlessly need to ask the human operator for decisions, clarifications, screenshots, or test feedback and receive replies through the Jarvis client, without requiring a live ChatGPT tab. The operator must be able to converse with an agent as well as satisfy a dependency that can block it.

Dependencies: Integrate the existing first-class durable challenge workflow (task-80c12fa7cf6f42eb918bab94a3cb7bbd) and versioned role/agent instructions (task-42e64eb74fef43588d8c64f656e12088, already merged). Coordinate with taskless agent execution (task-a03d7e2dc67e4182ae2b5552ed97f67b). This is a separate post-challenges feature: do not change or invalidate Worker 1's existing frozen challenge review.

Model

  • Extend canonical challenges with a distinct, typed Operator participant/condition target, authenticated as the human user and not masquerading as a registered agent ID named "Operator". Preserve the existing agent-owner, issuer, subscription, authorization and CAS rules; avoid privileged treatment of agent names such as "Lead". No implicit escalation from roles.
  • A challenge may contain an operator-input condition with a title/question, task/agent/project context, optional choices or free-form request, and a durable chronological thread of bounded agent/operator messages. Message append is idempotent, version-checked, immutable/auditable, and separate from a condition's terminal Satisfied/Blocked outcome. Replies do not automatically satisfy the condition. A human can reply, ask for clarification, supply feedback, and explicitly mark a condition Satisfied with evidence or Blocked/reopen/cancel where authorized by policy.
  • Creation and replies need not block an agent. If work genuinely cannot proceed, the agent explicitly links its attempt to the challenge with the existing block_on_challenges. The existing dependency engine then requeues it Ready only when all dependencies are Satisfied and ownership is available; never silently enters Working or launches a session. A taskless agent must likewise be able to request feedback without inventing a placeholder task; any taskless waiting semantics must align with the separately reviewed taskless work.
  • Unread/attention state belongs to the operator-facing challenge projection, not a stream of notify_agent records. Keep canonical challenge state readable from any connected client, with bounded pages/cursors and deterministic ordering; do not treat merely opening the TUI screen as a state-changing agent inbox read. Durable acknowledgement/read cursor is desirable to avoid duplicating attention across multiple clients. No implicit alerts for routine challenge transitions.

Client UX

  • Provide an Operator / Challenges screen or equivalent view in the Jarvis terminal UI listing outstanding operator questions across projects with project, issuing agent, linked task, status, age and unread indicator. Do not bury them in the activity log or assume the operator has a ChatGPT session open.
  • Select a challenge to read the full question/thread and the agent's current state. Compose/send a text reply through the client; separately offer explicit Resolve / Needs more information / Block actions as appropriate to canonical challenge permissions. Make it obvious whether the agent is actively Working, Ready, or blocked awaiting the operator.
  • Sending from the client uses the same authenticated durable command path as MCP; support client disconnect/reconnect, exact operation-ID retries and concurrent replies. Fail clearly if stale/revoked/unauthorized or if a challenge was cancelled/resolved elsewhere. Preserve unsent drafts locally if transmission fails; never report delivery before a ledger receipt.
  • Agent agent_inbox exposes bounded, relevant operator replies/challenge outcome information without requiring every agent to poll all conversations; get_challenge supplies full history. The human's reply must be available on the agent's next invocation, even if the original ChatGPT tab was closed. If an already Working agent polls, it sees fresh messages; if blocked, its substantive work remains quiescent until its dependency becomes eligible/Ready, but an independent message-only continuation may respond without reactivating that work. Actual session launching is a separate, explicit orchestration decision.

Agent-side delivery and message-only wakeups

  • On every operator reply, atomically persist the message and a durable per-agent unread/delivery cursor in the verified challenge ledger. A response from agent_inbox includes bounded summaries/IDs for unread operator messages. The corresponding get_challenge and paginated thread endpoint return message contents. The initiating agent may append its reply in the same thread, with operation-ID deduplication and exact authenticated actor identity.
  • Active agent: Every ordinary Jarvis tool response should advertise a small pendingOperatorMessages count/attention flag (plus stable challenge IDs if bounded), without dumping private message contents into unrelated tools or requiring a poll every few seconds. On receiving that signal, the agent reads its own inbox and challenge thread. A model invocation that does not call Jarvis cannot be asynchronously interrupted; the operator UI must distinguish sent/persisted from actually read.
  • Yielded, taskless or blocked agent: If no turn is active, a supported headless runner should observe pending operator communication and start a message-handling continuation for that agent/project, independent of ordinary task activation. This continuation reads the message, can answer or ask follow-up questions, and ends without changing a blocked attempt, occupying/reassigning its task, or claiming it Ready. It must be safe against concurrent runners and duplicate launch, preserve the same authenticated agent identity, and remain available for multiple back-and-forth replies while substantive work is blocked. No special agent-ID privileges.
  • Separate a communication wakeup from a work wakeup. A text reply may trigger only the communication continuation. Explicit satisfaction of all required challenge conditions is what marks the blocked attempt eligible/Ready through the existing dependency engine; running a message-only continuation must not bypass that gate. For an already Working agent, prefer its current invocation rather than starting another concurrent instance.
  • If there is no headless runner, preserve the unread event durably and display that the message is pending delivery; do not imply a push into an inactive model. Define read and reply acknowledgements separately from durable write receipts, support reconnect and cursors, and expose missed/delayed delivery diagnostics.

Acceptance and safety

  1. Wayfold Agent 4 issues "Please evaluate the water effect" as an operator-input challenge, continues nondependent work, and the Jarvis TUI displays it without a ChatGPT tab. Human replies with feedback; agent sees the exact reply and may request clarification in the same thread. Only a deliberate Resolve action satisfies the condition.
  2. Agent 4 explicitly blocks an attempt on an operator decision. Another unrelated condition remains pending. Human's text reply may start a communication-only turn but does not wake the blocked task; final explicit satisfaction of all linked conditions atomically requeues eligible work to Ready, never Working and never preempts a busy owner. No duplicate wakeups on retry/reconnect.
  3. Cross-project operator dashboard shows originating project and agent; operator can address multiple projects independently. A separate authenticated client can read/reply; stale-version updates resolve by rereading, not silently overwriting concurrent content.
  4. Unauthorized agent/condition impersonation, untrusted client, reused operation ID with changed payload, terminal state mutation, concurrent replies and oversized/unbounded content fail closed. Test negative-space privacy: neither private messages nor drafts leak into generic activity logs, notifications, or unrelated project/agent inboxes.
  5. Tests cover persistence across client restart, offline operation and retry, active-agent tool-response attention, blocked-agent communication-only turns preserving Blocked task state, single-instance deduplication, no-runner pending delivery, blocked/reopened/cancelled cases, role-only/taskless agent case, transcript pagination, full Client/Server .NET 11 Release, and TUI interaction. Request independent frozen review and coordinate protocol/connector rollout; do not merge/deploy without explicit operator approval.
