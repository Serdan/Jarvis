[P1] Operator feedback through durable challenges in the Jarvis client

Purpose: A headless agent must be able to request a decision, observation, screenshot reference, test result, or other human feedback without requiring the human to open that agent's ChatGPT tab. The operator answers in the Jarvis client. Each answer is a one-shot resolution of the requested operator-input challenge. If the agent needs additional information, it issues another challenge. Do not build a separate chat/messaging or multi-turn thread system.

Dependencies: First land durable challenges (task-80c12fa7cf6f42eb918bab94a3cb7bbd), with accepted roles already in main. Coordinate with the separate taskless-agent execution work (task-a03d7e2dc67e4182ae2b5552ed97f67b). This task is an extension after the current frozen challenges review; do not rewrite Worker 1's unreviewed branch as part of this specification.

Canonical operator-input condition

  • Add an explicit typed authenticated human operator condition participant to the existing first-class challenge model. Represent the assignee distinctly from an agent assignee (for example Agent(agentId) | Operator), never as an empty or fabricated registered agent ID. An operator-owned condition must not appear among unassigned agent conditions, be claimable/split through subscriber dispatch, or be resolvable through an agent-identity MCP call. The interactive client must derive operator identity and authority from its authenticated local operator action, not from a caller-supplied agentId or role name. Preserve project/ledger trust, actor authorization and exact challenge-version CAS.
  • Agent creates a challenge with one operator-input condition and a short, actionable question (plus optional task/context). On submitting the response in the Jarvis TUI, atomically record the response text as condition evidence, mark that condition Satisfied, and append the immutable resolution event. The human response is sufficient to satisfy the input request, regardless of whether its content is affirmative, negative, or asks the agent to investigate more. No additional explicit "Resolve" step or acknowledgement is required.
  • A normal operator-input challenge has one condition, so submitting the response satisfies the challenge. If operator input is one condition within a broader ALL-policy challenge, only that condition becomes Satisfied until the others are fulfilled. Preserve existing challenge semantics for all other condition owners and results.
  • When the response needs more context or a follow-up question, the agent creates a new challenge. A complete immutable record of the original request and its answer remains readable through existing challenge history; do not implement conversational message append, unread chat threads, message-only continuations, chat typing, or separate per-message resolution states.
  • Submission is a single durable idempotent mutation with a caller-stable operation ID, exact expected version and authorization. Retry is safe; simultaneous responses or stale/terminal challenges fail clearly and do not overwrite evidence. The operator may decline a request by submitting a response explaining the limitation; it still satisfies the request for input.

Scheduling and blocking semantics

  • Blocking is optional. An agent may create a challenge while continuing other work. If it needs to wait, it explicitly calls block_on_challenges with this challenge dependency. That operation itself transitions the attempt to Blocked and releases its execution slot: the agent must not also call yield_agent on the now-blocked attempt. Blocking is a scheduling tool, not a constraint on the agent's future behavior or available work.
  • For a blocked attempt, resolution follows the existing challenge dependency engine: once all linked challenge dependencies are satisfied and the owner can be assigned safely, the attempt becomes Ready without automatically becoming Working. A normal resume then allows the agent to inspect the operator's answer and decide to reply with a new challenge, continue implementation, test, or block again. No special communication-only mode is necessary.
  • For an agent that was not blocked, the resolved challenge and answer are visible through its ordinary agent_inbox (bounded relevant outcomes) and get_challenge (full evidence/history). The inbox must provide stable challenge IDs and an omitted-count/paging path so answers arriving during a long inactive period are discoverable, not silently lost behind a fixed number of recent events. The existing headless runner/agent continuation mechanism may resume it normally; a response does not need to interrupt a currently executing model turn. A taskless registered agent can likewise issue challenges and receive responses without a placeholder task, in coordination with taskless-agent support.
  • Never silently satisfy a different challenge, create duplicate assignments, preempt an already-Working agent, or change task ownership. If no client/runner is connected, keep the resolved challenge durably available until next agent invocation. State clearly in the TUI that the reply was persisted, rather than claiming it was read by the model.

Operator client experience

  • Show pending operator-input challenges across projects in the Jarvis terminal UI, including project, issuing agent, linked task (when present), question, age and status; provide an actionable count/indicator. Avoid flooding the general activity log or reusing agent-notification entities for challenge transitions.
  • Select the pending challenge, read its question and any existing safe reference to evidence (for example a screenshot path/link if supplied through existing file mechanisms), enter a free-text reply, and submit. No new binary attachment or chat transport is required. One submit both records the answer and satisfies the operator condition; there is no second confirmation solely to resolve. Display the durable success or clear stale/failure result; retain unsent text on failure and support reconnect/retry without duplicate resolution.
  • Allow viewing the original question and response later in the same challenge details, including immutable provenance. No threaded back-and-forth is needed: a new question creates a new challenge with its own ID.
