Recover gracefully from transient trust-binding contention in Agents dashboard (cross-platform)

Priority P2. Existing feedback acd4d298ce104c6d8f017c4e72358c9c. New reproduction: 2026-11-11 on Linux KDE Konsole, Agents dashboard displayed Wayfold: ValidationError "Cannot lock trust binding: The process ..." and Wayfold UNAVAILABLE (counts unknown), while other projects remained populated. Manual refresh immediately recovered. This confirms the symptom occurs on Linux, not merely Windows.

Root-cause investigation

Inspect Client/Modules/OrchestrationApi.fs LedgerBindingConfig.withConfigLock: it opens a per-project .lock with FileShare.None, retries any IOException up to 50 times with synchronous 40 ms sleeps, then an outer broad catch maps failures to ValidationError("Cannot lock trust binding: ..."). Inspect all lock and readStored paths and the Agents dashboard asynchronous refresh/snapshot behavior. Classify transient lock/sharing contention separately from actual invalid trust data, permissions, absent files and remote unavailability; do not claim a validated root cause without reproduction.

Required behavior

  • Introduce a typed, recoverable transient contention outcome for relevant Windows/Linux/macOS file-lock conditions, without converting arbitrary I/O errors or malformed bindings into contention.
  • Use bounded, nonblocking contention handling or a safe short deferred re-read on the existing refresh cadence. Do not synchronously stall the entire TUI or a SignalR ingress callback for a 2-second spin. Do not steal locks, ignore trust checks, use stale bindings to authorize new mutations, or rewrite/reset the trusted ledger state.
  • When a single project cannot be read due to contention, retain its last independently verified dashboard data if available and clearly mark it stale/temporarily unavailable; otherwise show unknown counts. Other project rows must stay available and totals must not treat missing data as zero.
  • Automatically reattempt once the lock is free using the existing refresh behavior, without manual g/Enter refresh or additional unbounded polling. Preserve detailed diagnostic information in appropriate telemetry, not a misleading persistent ValidationError banner.
  • Coordinate shared-file behavior with concurrent-client task task-cff673cd81474ccf9b3932bf0ea33109 and global-dashboard task task-6c6d71c8d3ef408eb30886ded9522af3. Reuse current lock/trust authority rather than introducing a competing trust-binding scheme.

Acceptance

  1. Deterministic injected Windows-style sharing violation and Linux-style lock contention produce typed recoverable outcomes and self-recover after release without manual refresh; verify the behavior at the Agents dashboard UI layer.
  2. Concurrent clients/refresher threads cannot corrupt the trust file or silently lower/replace the trusted head. Existing validated snapshots remain visually identifiable as stale during an outage and recover correctly.
  3. Permanent malformed binding, identity mismatch, access denied, lost file, and remote unavailability have distinct explicit error classifications; never bypass trusted binding validation.
  4. Bound time and number of retries; preserve responsive TUI and unrelated project counts; test the original regression and negative cases. Run Release suites, obtain independent frozen-commit review; integration/deployment requires explicit operator authorization.
