Transient trust-binding contention in Agents dashboard

Feedback: acd4d298ce104c6d8f017c4e72358c9c.

Observed issue

The Windows Agents view intermittently presents another project's trust-binding file lock as a persistent ValidationError even though the condition clears on its own. This conflates transient local IO contention with corrupted/invalid trust metadata.

Required behavior

  • Identify lock acquisition and reading paths for trust-binding files. Separate transient sharing/lock contention from true validation failures and from remote unavailability using typed error categories; never silently ignore invalid trust identity or substitute unsafe metadata.
  • Use bounded retry/backoff or safe short-lived deferred refresh for transient contention, without blocking the entire TUI, performing unsafe lock stealing or changing the trusted ledger binding. Keep other project rows and the previous verified snapshot visible with explicit temporarily-unavailable/stale status.
  • Automatically recover on the next existing refresh once contention ends; preserve detailed diagnostics outside the normal status display. A temporary read failure must never become a false zero-agent result or trigger a trust reset.
  • Coordinate shared-file semantics with concurrent-client task task-cff673cd81474ccf9b3932bf0ea33109 and global dashboard task task-6c6d71c8d3ef408eb30886ded9522af3; avoid duplicating a second trust-binding implementation.

Acceptance

  1. Injected Windows-style sharing violations recover under bounded contention and display recoverable status without clearing other projects.
  2. Permanent invalid identity, malformed binding, permission denial and lost file remain distinct explicit failures; no trust bypass or unauthorized rewrite occurs.
  3. Two concurrent refreshes/clients and interleaved file reads do not corrupt trust state; after lock release the Agents screen automatically recovers. Release tests pass.

Do not deploy without operator authorization.
