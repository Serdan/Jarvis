Problem and existing behavior

Jarvis already has LedgerStore.publishReviewRef and ReviewWorkflow.submitBranchReview: these create an immutable, verified remote ref refs/heads/jarvis-review/<taskId>/<reviewId>/r<version> before a review becomes Unclaimed, and reviewers can fetch it with fetchReviewRef. Keep this working mechanism. The remaining integration workflow still requires a source branch and SHA (submitIntegration calls verifySourceCommit), tying a reviewed integration to the contributor's mutable local branch and availability on the integrating device. Operators/agents have been manually pushing source/integration branches to make reviewed commits accessible on other machines. Remove that unnecessary dependency.

Goal

Make Jarvis own the full source-snapshot lifecycle from review submission through integration submission. An agent should need only to commit work and submit a review; after Accepted, the reviewed exact commit must be independently fetchable and usable for integration without manual source-branch pushes or reliance on the contributor's later branch state. Jarvis owns temporary integration branches. Neither review nor integration request automatically merges, deploys or changes production.

Requirements

  1. Review submission: Reuse existing immutable versioned jarvis-review refs, remote CAS create-only and post-push OID verification; the ledger must never advertise a claimable review until the exact committed object is provably remote. Keep explicit headOid support. Where practical, provide a straightforward submitted-worktree flow resolving committed HEAD and its source context without requiring the agent to manually push its development branch; reject dirty/uncommitted or ambiguous worktrees rather than guessing.
  2. Review-source identity: Treat (taskId, reviewId, reviewVersion, reviewRef, reviewedHeadOid) as the authoritative immutable provenance. Always fetch/verify from the Jarvis-owned review ref; the mutable source TaskRef is descriptive only, not execution authority. ChangesRequested creates a new frozen review version/request, never mutates an existing claimed ref. If remote verification is uncertain, surface an actionable pending/uncertain state and reconcile by immutable ref/OID before retrying.
  3. Integration submission: Support submission directly from an Accepted frozen review ID/SHA without requiring verifySourceCommit against the original contributor branch. Validate the reviewer verdict from one canonical ledger snapshot, verify remote review ref and fetch its exact object, pin the reviewed commit, and retain backward compatibility or an explicit migration for existing branch-based submission records. Do not accept a newer contributor-branch HEAD in place of the reviewed SHA.
  4. Managed integration snapshot: Create a uniquely named Jarvis-owned integration ref per submission/review (for example refs/heads/jarvis-integration/<submissionId>) whose initial commit is the accepted reviewed SHA, with remote CAS/create-only and exact verification. Never force-move reviewed refs. Integration agents work on separate isolated branches/worktrees based on the frozen snapshot and target main; conflict-resolution changes produce a new source commit and require a fresh independent frozen review before merging. If integration is a fast-forward, preserve the exact accepted commit and assert the target expected SHA before pushing.
  5. Ownership and permissions: Reserve the jarvis-review/ and jarvis-integration/ remote namespaces from contributors. Enforce real write boundaries via Git hosting repository rules/branch protections and the authorized Jarvis service credential; agent IDs alone are handles, not authorization. Do not claim refs are protected merely because they are named that way. Define an actionable setup/validation path when host protections are unavailable, and fail closed rather than granting contributors mutation ability to managed refs.
  6. Lifecycle and observability: Expose pinned review and integration ref, source/target SHA, publication/verification status and failure reason in canonical APIs. Permit idempotent retry after network uncertainty (never silently create a different ref), clean up orphan/obsolete managed refs only by exact compare-and-swap after a documented retention interval, and preserve ledger historical provenance even if remote refs are pruned. No background daemon or new CI/PR subsystem required.

Negative-space / acceptance tests

  • A review from a local committed branch publishes a remote immutable review ref without any prior push of the contributor branch; a reviewer on another checkout can fetch the exact SHA. A dirty worktree, absent commit and remote-push failure never create a claimable review.
  • An accepted review can be submitted and integrated even if its contributor branch advances, is renamed, or is absent on the integrating machine. Integration uses exactly the frozen review commit and records the pinned ref.
  • Conflicting concurrent submitters and retries cannot move another review/integration ref. Partial remote success with lost acknowledgement reconciles by inspecting the exact ref; mismatch fails closed. A claimed review is never replaced.
  • Submitting a ChangesRequested review, an unpublished/wrong SHA, or a source from another repository must not produce an authorized integration. Target advancement requires revalidation and an independent review of conflict-resolution changes; no implicit unreviewed merge.
  • Existing review and integration records remain readable. Document deployment/protocol compatibility, remote branch-protection configuration and cleanup policy. Exercise at least two independent local checkouts to prove fetchability.
  • Use .NET 11 Release tests, targeted Git remote fixtures and review-specific regression tests; publish a frozen commit and obtain independent review. Do not merge/deploy until Accepted. Do not run Codex through Jarvis.
