Taskless agent activity tracking and client visibility

Feedback: f099e39dbf1a472fa2d64f8b9c7b4a44; clarified by operator on 2026-11-11. Prerequisite: task-42e64eb74fef43588d8c64f656e12088 (shared roles and per-agent instructions, already independently accepted but awaiting integration). Related: observer API task-79b4fe205a86463184e5ff90b743e9d7 and client inactivity indicators task-6245252f294d4caba024d05cf55b19ce.

Purpose

Primary goal: an agent that has no assigned implementation task (for example a reviewer or coordinator with only a role) must be able to be active, have its execution status and activity tracked, and appear correctly in the Jarvis client. Do not manufacture a permanent placeholder task merely to make such an agent show as Working.

Orthogonal concepts: Roles are durable instructions/identity attached to any registered agent, whether task-assigned or taskless. An agent may have multiple roles. Role assignment, task assignment, review claim, and execution activity are separate axes. This task implements taskless execution/activity; it must not restrict role attachment to unassigned agents or move role definitions into task records. Role membership must neither imply active work nor grant extra permissions.

Required behavior

  • Canonical taskless execution: provide explicit agent-attributed start and yield/stop operations for an agent without an implementation assignment; record typed, versioned, auditable transitions and optional current activity/review context. A role-only agent may enter Working without acquiring a task or generating a fake attempt. When idle it may yield to Parked.
  • No implicit activity: registering an agent, attaching/editing/removing a role, resolving instructions, reading an inbox, inspecting an agent, or an arbitrary tool call must not silently start a taskless execution session. In particular, a role is not an execution state. Preserve existing automatic activity semantics for genuinely task-assigned agents independently.
  • Client visibility and tracking: show taskless Working agents alongside task-assigned Working agents in the Agents client view. Display their role labels and current activity/review context without inventing task IDs. Track state transition, last-seen/recent activity and stale/unknown status consistently; do not equate disconnect, missing heartbeat, or unknown last-seen with an explicit yield. Preserve the existing convention of hiding genuinely Parked agents where appropriate.
  • Roles on all agents: task-assigned agents retain their roles and receive the same canonical role/per-agent instructions as unassigned agents. Adding/removing a task, beginning/yielding taskless work, and claiming/completing a review never implicitly attach, detach, delete or transfer roles. Multiple agents may share a role definition.
  • Independent ownership: implementation tasks retain one exclusive active assignee; reviews retain independent exclusive claims. Taskless work cannot silently acquire or release those resources. Claiming or completing a review may update visible activity context but does not create a fake task.
  • State-machine correctness: define behavior for concurrent taskless start/yield, stale versions/generations, role changes during work, conversion to/from assigned task work, multiple devices, disconnect/reconnect, restart, and explicit admin recovery. Prevent phantom Working, forged attribution, lost review claims, and silent overwrites of canonical state.
  • Observer safety: observational tools and dashboard refresh must never mutate an agent's execution state. Where possible reuse current canonical state and TUI primitives rather than maintaining an incompatible parallel presence model.

Acceptance

  1. One registered agent with a role and an assigned implementation task retains that role through start/yield/complete and displays its role in the client; another registered agent with the same role and no task also receives the role instructions. Role attachment is permitted for both.
  2. A taskless role-bearing Reviewer 1 explicitly starts a session, appears as Working with role/activity and last-seen information, claims and decides an independent review, then yields to Parked; it disappears from the active client list without any placeholder task having been created.
  3. Registering or editing roles, calling agent_inbox, or inspecting agents cannot automatically show a taskless agent as Working; role membership and execution remain visibly distinct.
  4. Disconnected/replaced sessions, stale last-seen, and concurrent self/admin operations do not produce a false idle or phantom active state. Restarts preserve canonical transitions and recoverable status.
  5. Task assignment, review claim exclusivity and role persistence are preserved under taskless transition races. Ledger, API, client view and Release integration tests validate both role-only and task-assigned agents.

Implementation and independent frozen review are separate from integration. Do not deploy without operator approval.
