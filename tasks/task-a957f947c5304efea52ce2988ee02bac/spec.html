Make AgentInbox scale with actionable state rather than total history

Priority: P2. Finding: JRV-2026-11-05. Review: docs/reviews/2026-11-07-deep-review.md (baseline e50c24af).

Problem

ReviewWorkflow.getAgentInbox enumerates integration and task trees repeatedly and reads historical task, attempt, review, and notification blobs through many separate Git lookups. Every agent inbox call pays for all historical entities, amplified by multi-agent polling. The canonical Git-ledger snapshot must remain authoritative.

Relevant code

Client/Modules/ReviewWorkflow.fs:2334-2462; Client/Modules/LedgerStore.fs:957-975,1010-1064; Client/Modules/AgentDashboard.fs; Client.Tests/ReviewWorkflowTests.fs

Implementation requirements

  1. Instrument inbox latency, number of local Git subprocesses, remote fetches, bytes read, and allocation on a reproducible ledger fixture spanning many historical tasks/reviews/notifications. Record baseline before optimizing.
  2. Read each inbox from one verified canonical snapshot. Enumerate relevant paths once and batch blob contents using the existing cat-file --batch pattern (or an equally simple proven mechanism). Avoid repeated ls-tree/show for each record.
  3. Make filtering and joins efficient: do not repeatedly scan the entire notification list for every agent or load unrelated large specs. Preserve exact validation of task, attempt, review, agent and notification identities, ordering, and error behavior.
  4. If a derived per-agent index/read model is warranted by measurements, define its invalidation/rebuild guarantees and validate against canonical Git state. Do not add a second authoritative store or a server-side ledger cache.
  5. Preserve idempotent operation boundaries and safe concurrent readers while canonical writers advance.

Acceptance / verification

  • Fixture with at least hundreds of tasks/attempts/reviews and historical notifications shows a measured reduction in subprocess launches and repeated blob reads; record before/after wall time and allocations, not a guessed threshold.
  • Full inbox response (owned, ready, blocked, parked, available reviews, feedback, integrations, pending notifications) is equivalent before and after optimization across single and multi-agent fixtures.
  • Tests cover remote head advancing between separate inbox calls, malformed canonical records, unexpected owner/phase, snapshot consistency and empty inbox; focused and full Client Release tests pass.

Boundaries

No background server indexer or cross-device replicated database.

Review the design and implementation; correct findings and re-review until accepted. Prefer long-term correctness to quick fixes.
