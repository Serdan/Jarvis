# P1 — Old client can prematurely requeue a review-only blocked attempt

**Frozen source:** `da256ddbddb2e9b601edc878f1b4fa05d43e71e4`, `Client/Modules/ReviewWorkflow.fs:349-358, 470-507, 691-709`, `Client/Modules/ChallengeWorkflow.fs:1655-1660, 1761-1780` (review wait), compared with the deployed-compatible baseline `944bca7fa38cb5e973b04ce7829966cca351202b:Client/Modules/ChallengeWorkflow.fs:1796-1836` and its `ReviewWorkflow.fs` schema-2 decoder.

The new `AttemptChallengeWait` still serializes under **schemaVersion 2**, adding `reviewIds` as an optional member. The pre-change client only knows `ChallengeIds`; its decoder checks the schema and required old members but does **not** reject unknown JSON properties. An old client therefore successfully deserializes the new review-only wait (`challengeIds=[]`, `reviewIds=[pendingReview]`) as a manual zero-challenge wait. Its existing `requeueAttempt` validates only `wait.ChallengeIds` (baseline 1823-1836): the loop is empty, so the old client can requeue the blocked attempt to Ready **before** the review becomes terminal, with valid versions and owner slot. It also rewrites the wait using its old record shape, discarding the review dependency. This violates the all-dependencies gate and multi-client durability, despite new-client tests passing.

**Required:** Introduce a compatibility barrier so an old client cannot interpret new review-dependent waits as old schema-2 manual waits. One approach: write review-linked waits with a new schema version, have upgraded clients read both old challenge-only schema-2 and new schema, and ensure old clients fail closed on the newer schema. Alternatively use an explicit version/protocol gate that enforces the same safety. Add a negative-space upgrade test using old-client-compatible deserialization/manual-requeue semantics, including `challengeIds=[]` and a pending `reviewIds` entry. Keep old challenge-only waits readable/replayable and preserve the single canonical CAS wake path.
