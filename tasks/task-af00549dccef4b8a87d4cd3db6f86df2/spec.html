Add bounded in-memory retention for device and conversation routing

Priority: P3. Finding: JRV-2026-11-08. Review: docs/reviews/2026-11-07-deep-review.md (baseline e50c24af).

Problem

UserService retains disconnected device sessions and per-conversation device selections indefinitely, with no pruning of stale records. Server restarts discard all state. This is modest-risk for Jarvis's intentionally single-instance deployment but affects long-running service behavior.

Relevant code

Server/Services/UserService.fs:34-40,72-168,170-192,222-293; Server/Services/ClientService.fs; Server.Tests/ServiceTests.fs

Implementation requirements

  1. Define a simple deterministic policy for expiry of disconnected sessions and stale per-conversation selections while never expiring actively connected registrations. Specify how defaults and overrides fall back when their device disappears, and when the previous device reconnects.
  2. Implement retention/pruning in process memory only (on access or periodic, with minimal allocations). Respect user/device scoping, generation-based response validation and connected-device routing; no storage service or persistent database is warranted.
  3. Handle repeated device registrations, duplicate device IDs, disconnect/reconnect races, current selections, multiple devices per user, and system restarts. Avoid silently routing an explicit device override to a different device.
  4. Document the expected ephemeral nature of default/selection state and operational diagnostics.

Acceptance / verification

  • Clock-controlled tests show stale disconnected sessions and conversation records are reclaimed, active sessions and replies remain valid, and resource counts remain bounded under many synthetic conversations.
  • Explicit selections targeting expired devices produce deterministic error/fallback behavior with no cross-user routing or stale-generation reply acceptance.
  • All Server Release tests pass; no new persistence service or multi-instance coordination is introduced.

Boundaries

Do not distribute Jarvis server state or require a database migration.

Review the design and implementation; correct findings and re-review until accepted. Prefer long-term correctness to quick fixes.
