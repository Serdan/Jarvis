Add repository CI gates and verifiable release artifact provenance

Priority: P3. Finding: JRV-2026-11-11. Review: docs/reviews/2026-11-07-deep-review.md (baseline e50c24af).

Problem

The repository has extensive Client.Tests and Server.Tests but no tracked continuous validation workflow. Deployments rely on manually initiated release verification, and published checksums alone do not establish which reviewed commit produced the artifacts.

Relevant code

Jarvis.slnx; Client.Tests/Client.Tests.fsproj; Server.Tests/Server.Tests.fsproj; scripts/build.cs; scripts/publish-client-downloads.cs; scripts/publish-server-download.cs; scripts/publish-jarvis2-linux.cs; docs/ClientDownloads.md; docs/ServerUpdates.md

Implementation requirements

  1. Add a minimal source-controlled CI workflow on GitHub for relevant pull requests/merges: restore locked dependencies, Release build, Client Release tests and Server Release tests. Use a job matrix for Linux and Windows if supported and useful; avoid requiring private Jarvis server credentials to test code.
  2. Make automated failures visible and avoid merging known failures. Address test determinism rather than increasing timeouts to disguise failures. Respect existing test filter/platform assumptions and cache responsibly.
  3. Encode release provenance in an auditable manifest or binary metadata tying exact source commit/ref, build inputs and SHA-256 checksums to the published Linux/Windows/macOS binaries. Ensure release scripts do not accidentally publish dirty or mismatched artifacts.
  4. Keep publishing and deploying explicit operator actions. Preserve current SHA-256 checks and rollback; do not automatically deploy on every push or introduce a CI/CD orchestration service.

Acceptance / verification

  • Clean PR/branch builds and passes both Release suites; deliberately failing test/build prevents a green check and fails prior to publish.
  • Release outputs can be traced from published checksums and provenance metadata to exact commit; publish scripts reject mixed/dirty builds or clearly require an explicit deliberate override.
  • Documentation provides the lightweight developer workflow and how to reproduce release verification locally. CI runs without private Auth0/DigitalOcean tokens.

Boundaries

No automatic production deployment and no heavyweight build system replacement.

Review the design and implementation; correct findings and re-review until accepted. Prefer long-term correctness to quick fixes.
