## Blocking P2: two dispatchers compose incorrectly

See `findings/p2-double-dispatch-detaches-work-and-drops-recovery.md`.

The exact **live production entrypoint** in `Client/Program.fs:201–257` sends each SignalR command through `CommandDispatchQueue(8 workers, 128 queued)`, whose worker awaits `Client.receiveCommandAndReplyWithTiming`. However merged `Client/SignalR/Client.fs:934–945` immediately submits the actual long-running command/reply work to **a second `BoundedResponseIngress(96)`** and **returns Task.CompletedTask, discarding the actual completion task**. This means the outer eight workers do not bound command execution and drain pending work while up to 96 actual operations are in flight. When inner 96 fills it rejects an already-outer-admitted command before execution; the rejection is thrown back to the outer `OnUnhandled` and incorrectly treated as post-commit **`UncertainOutcome`**, instead of **confirmed not executed**. Conversely an unexpected failure *inside* the detached inner task is only logged via inner `onError`, never observed by outer correlated `replyUnhandled`, so the server waits for a longer timeout rather than prompt error evidence.

These are direct, independently reproduced production-type composition behaviors, **not theoretical guesses**:
- Disposable detached exact frozen checkout `/tmp/jarvis-reviewer1-dispatch-negative-93b2` has reviewer-injected test `combined dispatcher preserves worker limit under stalled operations`. Config scaled to outer 2/8 and inner 4, six calls admitted by outer while work stalled; test **failed** `Expected: 0; But was: 2` premature inner rejections, exit 1.
- Second independent negative `composed dispatcher propagates inner fault to correlated recovery`: inner fault observed by its log callback but outer correlated recovery **never invoked**, test **failed** `Expected: True; But was: False`, exit 1. Both added solely in temporary reviewer checkout; original Lead integration source was untouched.
- Existing frozen full suites test each dispatch implementation largely independently and consequently all pass; they lack a test for the actual Program→Client dual-stage wiring.
- Root cause is the merge integration between main's `BoundedResponseIngress` and Worker5's new `CommandDispatchQueue`; the already-accepted Worker5 feature by itself was not retested/rejected here.

**Fix required before acceptance:** establish **one actual execution/response admission owner**. For example, under Program's existing detached `CommandDispatchQueue`, await real `receiveCommandAndReplyCore` to terminal reply, rather than another detached `BoundedResponseIngress`; or explicitly choose one alternative and implement its correlated overload and failure paths. Maintain limits, ordered execution evidence, client-owned auto-job `PendingJob`, typed uncertain-versus-confirmed status, original operation IDs, no blind retries and cancellation. Add a regression test of the *actual combined wiring*, testing both (a) queued work when workers are busy and (b) prompt correlated error after an unexpected execution exception.
