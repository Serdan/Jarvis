Per-project review queue counts

Feedback: 67ba75c5f73b4a6387f9050adfc2862f; 597168cf862c41618c00c2e0401778dd.

Goal

Show a compact, immediately actionable review count per project, not merely an aggregate. Display unclaimed/total; total means unclaimed plus claimed outstanding review requests, not completed/withdrawn requests.

Implementation

  • Derive counts from canonical independent review records. Group by stable project/ledger identity, not display name alone. Deduplicate repeated ledger visibility across clients and do not double count review snapshots or task review history.
  • In the existing review queue area, show each project with U/T (e.g. Wayfold 3/8) using appropriate space-saving truncation/scroll behavior; optional aggregate Reviews U/T may supplement but not replace project breakdown.
  • Align totals with review-list filters, the existing refresh cycle, and the planned global operator dashboard task-6c6d71c8d3ef408eb30886ded9522af3. Avoid extra polling and distinguish unavailable/stale project counts rather than silently showing zero.
  • Use consistent counts when reviewers claim/release/decide/withdraw requests, including independent reviews in the _reviews namespace.

Acceptance

  1. Fixtures with claimed, unclaimed and completed reviews across multiple projects yield precise per-project U/T and optional aggregate sums.
  2. Two clients exposing the same ledger produce one group; same-named distinct ledgers remain distinct.
  3. Claim/release/completion changes update on existing refresh; no additional network polling, count flicker or double counting.
  4. Empty, filtered, stale, disconnected and long-name cases remain readable on supported terminal sizes; automated tests and Release build pass.

Coordinate integration with global dashboard work. Do not deploy without operator approval.
