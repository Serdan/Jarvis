Git-backed agent-defined hooks

Implement a small event-driven hook facility in Jarvis so agents can attach scripts to well-defined lifecycle and operation events. Hooks run locally without extra LLM tool round trips, and their definitions and scripts are shared across branches through a dedicated orphan Git branch (suggested jarvis/hooks), checked out independently of source worktrees.

Core design

  • Git-versioned manifest and scripts in a dedicated orphan branch, independent of source branches; local isolated checkout for execution. Concurrent updates should use safe Git/ledger-style serialization or compare-and-retry without lost updates. No invented task IDs.
  • Workspace/project-scoped hooks by default, with optional agent/event filters. Worktree and agent context is passed to handlers; source worktree is the script working directory. Avoid executing untrusted branch-local hook definitions implicitly.
  • Manifest defines event, script path, enabled flag, filters, optional priority, timeout, and blocking behavior where supported. Define stable structured JSON event payloads and optional structured diagnostic results.
  • Before hooks execute synchronously and may block an operation; after hooks execute synchronously and add diagnostics but never reverse completed operations; lifecycle/event hooks can run asynchronously with durable outcome logging. Preserve operation error semantics and do not let reporting hook failures corrupt state.
  • Execution safeguards: timeout, recursion/reentrancy protection, bounded output, deterministic ordering, and clear handling of failed scripts. Log event, handler ID, duration, exit code, stderr/stdout summary, and diagnostics. Keep execution state/logs/caches outside Git.
  • Expose list_hooks, register_hook, update_hook, remove_hook, and run_hook (manual testing). APIs should use generated identifiers where needed, not user-invented IDs.

Initial events

  • agent.started, agent.stopped
  • tool.before, tool.after (include execution outcome), command.after
  • file.after_write (only explicitly instrumented Jarvis file tools; document that arbitrary subprocess changes are not detected)
  • git.before_commit, git.after_commit
  • task.assigned, review.requested, integration.completed, worktree.created

Design the dispatcher so further events can be added cheaply (agent state, command.before, file delete, Git push/merge, checkpoints, review decisions, notification events, etc.). Do not implement all of these initially.

Behavioral details

  • A generic tool.before/tool.after hook includes tool name, project, agent, worktree, operation ID, and outcome as available, with secret/sensitive argument redaction.
  • Define whether generic hooks and specialized hooks both fire, and give stable order. Prevent double invocation for internal/nested operations, and disallow recursive self-triggering.
  • Blocking hooks return actionable rejection diagnostics; nonblocking hook failures are visible and recorded without failing the completed operation.
  • Consider command matching/filtering for build/benchmark collection, and a Roslyn daemon start/diagnostics example, without making Roslyn a special case.

Acceptance criteria

  1. Agents can register, list, update, remove, and manually run script hooks using Jarvis tools; definitions persist through agent sessions and source branch switches.
  2. Two agents can update hook configuration without silently losing each other's changes.
  3. Before commit validation can reject a commit; after-write analysis can return diagnostics to the invoking agent; a failed after-hook cannot undo a successful operation.
  4. Hook loops, timeouts, and excessive output are bounded; runtime history can be inspected.
  5. Tests cover event dispatch, filters, ordering, blocking/nonblocking semantics, safe Git storage/concurrency, recursion, and failure handling.
  6. Documentation includes manifest schema, event/payload catalog, examples for Roslyn and benchmark diagnostics, limitations, and guidance for extending the event set.

Keep implementation focused: no generalized workflow engine or dependency graph between hooks, and no special-case .NET feature in the core dispatcher. Do not deploy without explicit operator approval.
