Verify server application readiness and roll back unhealthy deployments

Priority: P2. Finding: JRV-2026-11-07. Review: docs/reviews/2026-11-07-deep-review.md (baseline e50c24af).

Problem

The server updater verifies binary checksum, restarts systemd and declares success after a short delay if systemctl is-active succeeds. A running service can nevertheless be unable to serve auth discovery, MCP or SignalR requests.

Relevant code

scripts/install-server-updater.sh; scripts/publish-server-download.cs; Server/Program.fs; docs/ServerUpdates.md; Server.Tests

Implementation requirements

  1. Define operational readiness distinct from process liveness. Use bounded loopback probes that establish the deployed version is actually serving the expected protocol endpoints and critical configuration dependencies, without exposing sensitive diagnostic details or weakening authorization.
  2. Run readiness probes with strict total timeout/backoff and actionable failure diagnostics. On failure, stop the bad service, restore the previous verified binary, restart, and independently verify recovery. Keep status files written atomically and readable after the updater's own initiating connection drops.
  3. Explicitly handle missing previous binary, rollback failure, interrupted update, manifest checksum mismatch, service restart failure, and transient probe failures. Avoid reporting 'success' until readiness is confirmed.
  4. Preserve the existing simple single-instance systemd deployment, checksum verification, exact binary provenance and noninteractive updater behavior. Do not require a second server or distributed orchestration.

Acceptance / verification

  • An active-but-unhealthy test service triggers automatic rollback and a status that identifies the failed readiness stage; the prior healthy service is available again.
  • Healthy server, delayed startup, and harmless short transients pass within bounded retries; intentionally invalid manifest and failed rollback produce truthful statuses.
  • Integration tests/script harness exercise deployed-path handling and rollback in isolation without risking the production unit; Release Server tests pass; document emergency manual recovery.

Boundaries

Do not deploy test failures to the real server or remove the checksum/rollback safeguards.

Review the design and implementation; correct findings and re-review until accepted. Prefer long-term correctness to quick fixes.
