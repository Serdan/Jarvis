Make workspace file mutations atomic and race-safe

Priority: P1 (correctness / lost updates). Source: docs/reviews/2026-11-07-deep-review.md, JRV-2026-11-01. Baseline: main e50c24af.

Problem

Client/Modules/ProjectBrowser.fs:917-1002 reads and checks expected hashes separately from FileIO.writeAllText/appendAllText. Client/IO/Impl/FileOperations.fs:88-109 writes in place. Two writers can both pass the same expected SHA-256 check and report success after overwriting each other; interrupted writes can truncate a file.

Requirements

  1. Design one typed file-mutation primitive used by WriteFile (Write and Append) and PatchFile. Preserve the existing public precondition semantics, including expectedHash="none" for creation and current response diagnostics.
  2. Make expected-state verification and commit one concurrency-controlled operation. The synchronization must work across concurrent Jarvis client processes on the same filesystem, not merely within one F# process. Recheck file identity/content under the lock and reject stale preconditions rather than silently overwrite.
  3. Stage replacement contents in the same directory/filesystem, flush appropriately and atomically publish or replace without truncating the live file. Define OS-specific behavior for Linux/macOS/Windows and preserve meaningful file permissions and metadata. Append should use the same committed-state semantics.
  4. Maintain source-root containment and symlink/hardlink protections across the entire operation, including parent creation and the interval between validation and replacement. Clean up temporary files and locks after failures.
  5. Avoid introducing a project-wide serialization bottleneck; independent file mutations should proceed concurrently. Keep error reporting typed and actionable.

Acceptance and verification

  • Two simultaneous updates with the same precondition permit at most one successful mutation; the other receives a stale/conflict result. Exercise independent clients/processes, not just async tasks in a single test process.
  • Simulated failures before commit preserve a complete original file; after commit, consumers see the complete new content, never a partially written intermediate.
  • Tests cover Write, Append, Patch, absent-file creation, stale hashes, Unicode content, empty content, permissions, worktree selectors, concurrent readers, parent creation, and cleanup.
  • Review correctness of filesystem primitives and platform fallbacks; run relevant focused tests and full Client Release tests. Add a short design note explaining the chosen locking and durability guarantees.

Non-goals: No redesign of the canonical Git ledger; no change to Git history or the public MCP tool set unless a compelling API need is documented.
