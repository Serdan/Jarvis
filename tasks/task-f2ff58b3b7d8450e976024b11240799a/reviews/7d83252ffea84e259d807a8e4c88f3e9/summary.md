## Findings and architectural decision

- Two separate unbounded caches were found, not one. `AgentDashboard.parsedNotifications` used entire JSON payloads as process-global dictionary keys; `LedgerStore.dashboardBlobCache` retained every historical raw JSON blob OID. Bounding only parsed JSON would not have fixed long-lived memory growth in the Git layer. Both caches are now FIFO keyed by immutable Git object IDs, with **16,384 entries + 16 MiB estimated bytes** (parsed) and **16,384 entries + 32 MiB estimated bytes** (raw). A duplicate key never replaces immutable content. Over-budget entries are delivered to the current read without retention. Entries and bytes are enforced under a short lock; no additional framework, daemon, server cache or persistence.
- Each raw snapshot resolution pins all selected cache hits and fetched blobs into request-local dictionaries and then builds the returned map from those local references. This is an important negative-space invariant: parallel project refreshes can evict **global** cache entries while a request remains in progress without producing incomplete or mixed-Git-head records. The snapshot's tree listing and all objects are still anchored to a single verified Git commit. The public `readDashboardRecordsAt` and `readAgentInboxRecordsAt` return unchanged `Map<string,string>` and retain existing path/type checks and error shape. The additional internal reader exposes OID to the dashboard only.
- The parsed cache's OID key is content-addressed and immutable across project/agent identity, so reuse cannot borrow a notification from another content version or project. Acknowledgement changes JSON and OID, forcing a new parse. Malformed JSON still aborts the dashboard rather than silently clearing notifications; if repaired under a new OID it is read independently. The same current project head uses the unchanged existing derived `cachedProjects` snapshot.
- The old notification view scanned/filter-sorted the complete historical unread list **per agent**. It now enumerates all notifications once, retaining a bounded per-agent dictionary of `count` and `latest`, comparing the exact original tuple `(CreatedAtUtc, NotificationId)` for tie-breaking and rendering the same sender/task/message string. Notifications with no matching agent still require validation but cannot inflate an agent's counts. No API, row output, canonical ledger path or protocol change.
- Existing `cachedProjects` still retains the **latest derived rows per configured project identity**, not historical notification JSON per prior head. Its count is proportional to distinct project identities ever visited, not the number of notification versions; this P3 change intentionally bounds the latter. Extra global control of arbitrary project identity churn is outside the finding.

## Boundaries and risks

- MiB limits are *estimated retained payload* ceilings (2x UTF-16 OID+JSON characters + 128 bytes/entry), not exact total CLR heap occupancy. Queue/dictionary metadata imposes bounded additional overhead. Large current snapshots may temporarily exceed the cache limits in a single request. Evicted historical Git OIDs may cause repeat `cat-file --batch` fetches on subsequent head changes; this is an explicit memory-vs-I/O tradeoff.
- FIFO rather than LRU is deliberate, simple and deterministic. Both cache count and weight are bounded. Single-request local copies and immutable Git OIDs preserve correctness even under eviction and parallel activity.
- No server-owned state, multi-instance coordination, database migration, `AgentRow` output change or deployment is introduced.
