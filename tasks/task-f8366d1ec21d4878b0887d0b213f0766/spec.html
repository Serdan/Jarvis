URGENT: Remove arbitrary per-user MCP tool concurrency admission gate

Priority: P1 urgent / blocking coordination. Incident feedback: b9b12d204bdd4091b720c89042822843 (2026-11-12). Related prior closed task: task-2eded55b3f7a4c1fa772ba8e982c45b0; its historical intent to measure concurrency was not satisfied before selecting fixed numbers. Target branch is current .NET 11 main commit c12d6cbc, not an older .NET 10 feature branch.

Failure and root cause

Server/Program.fs wraps every MCP tool call in McpUserCapacity.Execute, keyed to one authenticated subject shared by many agents and devices. Server/McpUserCapacity.fs defaults to 24 active tools, 16 queued, 5-second queue timeout and 2-second retry. Permits remain held throughout long remote/client operations, allowing routine agent fan-out to yield Jarvis MCP tool capacity is busy even while the connected client is healthy. These thresholds were not grounded in production concurrency/resource measurements. Coordinated retries can amplify the error.

Implementation

  • Remove the per-subject concurrency limiter on MCP tool ingress. Do not just raise the quota/timeout, introduce another arbitrary cap, or convert a rejected operation into a blind retry. All authenticated MCP calls should reach the actual tool handler subject to its own canonical business safety, cancellation, resource protections and result semantics. Keep request metadata/device routing intact.
  • Preserve independently justified HTTP request-rate abuse protection and OAuth/authorization behavior. The existing McpSubjectRate HTTP fixed-window policy can remain; do not accidentally remove its metadata, 429 response, Retry-After, or subject partitioning. Review but do not invent new thresholds. Remove now-obsolete concurrency configuration, error response, and dead code; consider retaining appropriately renamed rate-only settings/module to avoid unrelated churn.
  • Add low-cardinality observability for in-flight tool counts and elapsed time/queue or admission where meaningful, without logging payloads or subject identifiers; use it to establish actual legitimate fan-out and bottlenecks. These counters are *diagnostics*, never authority for dropping work. Avoid shared hot-path lock contention. If scope is larger, deliver the narrow removal first and track optional instrumentation separately.
  • Coordinate with unmerged Worker 3 admin-correction durable SQLite witness changes in Server/McpTools.fs/ClientService and Worker 5 MCP dispatch-stall work. Do not break per-agent liveness, late replies or idempotency; do not merge/deploy unrelated branches.

Acceptance

  1. Deterministic concurrent simulated multi-agent load exceeding former 24+16 caps can invoke MCP handlers without returning synthetic capacity is busy; cancellation and task/agent lifecycle tools are not starved by the ingress gate. Use a bounded test workload; do not assert impossible unbounded throughput.
  2. Server.Tests/McpCapacityTests.fs updated/replaced: verify HTTP rate-limit policy still enforces authenticated subject isolation, HTTP 429 and Retry-After, and auth challenges. Ensure removing old capacity tests does not erase valid abuse-defense tests.
  3. Full .NET 11 Server Release tests pass; no backwards compatibility or route metadata regressions; git diff --check clean. Prefer a small isolated exact branch commit and independent frozen reviewer before integration.
  4. Provide operational note on what changed and observed limitation: external platform-level MCP tool capacity errors cannot be removed by Jarvis source; test that Jarvis itself no longer emits its own message.

No merge, push to main or production deploy without operator authorization.
