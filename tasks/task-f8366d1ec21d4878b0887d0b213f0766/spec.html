Observed problem and mechanism

Every MCP tool call passes through McpUserCapacity.Execute in Server/Program.fs, keyed by the authenticated subject shared by all agents and devices. Configured defaults are 24 concurrent, 16 queued, 5 seconds queue wait, 2 seconds retry; legitimate long-running client calls consume capacity for their whole duration and cause "Jarvis MCP tool capacity is busy" before reaching the tool. An additional HTTP McpSubjectRate policy applies a speculative 240 requests / 10 seconds cap to all authenticated /mcp requests. Neither cap represents measured hardware capacity.

Required implementation

  • Remove the authenticated per-user MCP concurrency gate entirely, its busy/queue/retry synthetic error path, unnecessary DI and dead configuration/implementation. No replacement magic threshold, queue cap, or application-level semaphore. Keep device routing metadata and identity/cancellation semantics unchanged.
  • Remove the fixed-window per-subject rate limit from authenticated /mcp as well; the operator does not want a second arbitrary ceiling that will simply become the next bottleneck. Preserve authentication/authorization, OAuth challenges, tool-scope checks, and existing separate protective policies for /client and /exports unless evidence requires otherwise. Do not accidentally make unauthenticated discovery publicly accessible or remove infrastructure abuse defenses. Allow any appropriate externally enforced abuse protection at the edge to be considered separately, but do not limit successful authenticated MCP calls at guessed rates.
  • Actual resource safety still matters: preserve existing bounded memory/process/job/SignalR payload/response execution and user-request cancellation mechanisms where justified by concrete resources or protocol correctness. Do not conflate removing arbitrary request ingress throttling with infinite worker processes or unlimited command result sizes. Observe CPU, RSS/memory, GC, in-flight requests, request latency and disconnect/timeout behavior as practical. Include low-overhead, low-cardinality telemetry; instrumentation should not be a new blocking ingress gate or expose credentials/payloads.
  • Prioritize the small functional removal and deterministic tests. Coordinate with Worker 3's unmerged durable agent-activity witness work and Worker 5's MCP dispatch-stall fix; preserve exact source-agent attribution, asynchronous dispatch semantics, and durable operation cancellation. Implement on a dedicated .NET 11 worktree; no edits to main.
