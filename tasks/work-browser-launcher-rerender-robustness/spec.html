Observed root and desired behavior

Launching short agent prompts through Jarvis into new https://chatgpt.com/ tabs intermittently returns UiIncompatible:composer:ModeChanged during draftStabilization after the new ChatGPT app re-renders the mode toggle controls. A second execution in the same tab, after definitely no Send happened, usually succeeds. This is unnecessarily brittle in concurrent agent launches. ChatGPT automatically persists unsent composer drafts across tabs. Operator clarified that these drafts have no value: in a newly Jarvis-created zero-submitted-turn ChatGPT home tab, the launch script may clear any existing editor text via ProseMirror; such drafts do not themselves cause a launch block. They are not evidence of an existing submitted conversation. Preserve actual submitted-user-turn exclusion and existing Chat mode selection.

Use a bounded, state-aware re-snapshot of the zero-turn/new-tab UI when React changes button/editor node identity, rather than failing the whole first launch on a harmless re-render. Recheck DOM/mode/editor/URL/turn count after every awaited state stabilization, and before the only Send. Do not assume text or button identity remains stable through hydration, and do not brute-force click across modes. Re-render or draft restoration BEFORE Send may be recovered only when the new-tab precondition is re-proven; once Send could have occurred, outcomeUnknown is terminal, never retried automatically. Keep an overall bounded deadline (existing 27 seconds), no blind long sleeps, no repeated prompt submission, no clearing or sending in an existing conversation with submitted user turns. The host should continue closing Jarvis-created launch tabs promptly after verified successful submission; this implementation does not need any remote tab-lifecycle change.
