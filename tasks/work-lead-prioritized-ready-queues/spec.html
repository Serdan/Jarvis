[P1][Work/WQ04/WQ08] Lead-assigned priority within two Ready queues

Parent: work-queues-ephemeral-executions. Operator decision 2026-11-17: the canonical ready work queue is prioritized, not FIFO-only. The Lead sets explicit work-item priority; the non-agent Scheduler computes eligibility and dispatches. Earlier architecture wording that excludes Lead priority is superseded for this scope.

Contract

  1. Compute hard blocking-prerequisite classification first. Keep exactly two conceptual buckets: ready work blocking another unfinished work stage, and other ready work. Blocked/ineligible work cannot dispatch.
  2. Within each bucket, sort by descending Lead-assigned numeric priority, then the existing server-witnessed ready/available FIFO time and deterministic identity tie-breakers. Represent as a noncolliding tuple (blockingTier, -priority, readyTime, stableId), not a fixed +100 bonus that can be exceeded by ordinary work.
  3. Expose a straightforward canonical version-checked way for Lead/operator to set or change priority on a Work item (including reason/receipt), with readback in Work-facing tooling and sensible default 0 for existing items. Avoid Agent identity persistence, role-based ACLs, or invented server durability; use existing trusted owner and Git CAS.
  4. Role compatibility, account-global capacity, STOP/unknown-send, graph dependency and original producers remain authoritative. A priority change may reorder eligible work but cannot mutate dependency truth or duplicate a claim/launch.

Acceptance

Hermetic tests cover blocker vs much higher-priority ordinary work; within each bucket priorities override FIFO; equal priority FIFO, stable tie, requeue/yield fresh FIFO; concurrent two-clone priority CAS; stale edit rejects; blocked work never becomes eligible by priority; account capacity and role compatibility unchanged; restart/reload preserves explicit priority. Show actual default-off planner/facade behavior on two projects; no live Scheduler.
