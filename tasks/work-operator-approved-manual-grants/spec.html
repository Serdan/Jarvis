[P1][Work] Operator-approved manual grants for ad-hoc sessions

Parent: work-queues-ephemeral-executions. Follow-up to: completed work-reservation-permissions. Prerequisite: work-uuidv4-explicit-credentials accepted and integrated. Build on the existing Work-native permission checks; do not reimplement the scheduled reservation path.

Objective

Let a trusted, operator-supervised LLM session that was not started by Jarvis request operational authority over a project or a coherent project-creation workflow. The agent should be able to create a project, write its spec, configure roles and perform related housekeeping after one explicit operator approval, without a fabricated Work reservation or permanent project ownership.

Request and approval

  1. Expose an unauthenticated-to-the-execution RequestGrant operation via the existing account-authenticated Jarvis tool path. The request names a coherent purpose, resource scope (existing project or prospective named project) and broad operation capability set. This request does not itself authorize work.
  2. Server generates a CSPRNG UUIDv4 bearer credential and returns it once to the requesting model execution for use as an explicit argument on subsequent Jarvis tool calls. Keep only its verifier, pending/approved state and scope in server memory. Do not introduce a Git-backed account/project grant ledger or a persistent server database.
  3. Jarvis client displays the requested scope/capabilities to the operator and permits a trusted approve/deny decision. The requesting model cannot approve its own grant. Approval activates the same credential; the agent continues without another bootstrap or per-operation approval.
  4. When approving creation of a specifically named project, the grant permits project creation and coherent setup (specification, instructions, roles and related initial work) in one approval. After creation, bind further mutations to that project's actual canonical ID. This does not grant generic creation/management authority for unrelated projects or permanent ownership.
  5. Use the same compact capability categories and authorization enforcement as scheduled Work, subject to the approved resource scope. Keep the distinctions clear: scheduled reservations receive durable project-Git-backed credentials; manual grants use ephemeral server-memory approval state. Do not use provider-specific session IDs or assume automatic credential injection.
  6. There is no duration selector, lease renewal, expiration policy, session tracking or explicit revocation workflow for manual grants. Their state remains valid in the running server and disappears on restart. The operator can stop using the conversation; if the server restarts, the agent can simply request a new manual grant. No automatic migration or recovery of manual grant state.

Acceptance

  • Ordinary ad-hoc ChatGPT session requests a grant for project creation; Jarvis client shows the request; operator approves once; execution presents the returned UUIDv4 and creates/initializes the named project, writes a spec and configures roles without repeated authorization.
  • Before approval, the UUIDv4 does not authorize project mutation. A denied request remains unusable; an invalid credential or unrelated project/operation is rejected. Approval by the requesting model is impossible through its tool surface.
  • Manual grant and secret verifier never enter project/account Git history; after server restart the credential no longer works, and requesting a new grant is sufficient. Existing scheduled Work credentials retain their independent durable semantics.
  • Representative small, hermetic .NET 11 Release tests cover pending/approved/denied, prospective-project binding, allowed operations, cross-project denial, server restart, and no fabricated reservation/agent identity. Preserve current authenticated-account behavior and practical operator controls.

Boundaries: Trusted operator-supervised sessions; use broad capabilities with explicit scope, not a per-tool approval dialog or general-purpose ACL framework. Only ephemeral manual grant state may be server-memory authority; no server-local durable execution/work state. Isolated source, independent frozen review, Lead integration after acceptance. No production Scheduler activation, cutover, hosted GitHub Actions, Codex through Jarvis or unrelated live host changes.
