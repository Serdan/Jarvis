## Blocking finding P1C-01 — client/server type and transport boundary is missing

The plan’s §1 and §3 prescribe using `IOriginalGitPublisherAuthority.PublishCas` as the future typed execution boundary in the `Client/Modules/LedgerStore.fs` and `AccountCapacityLedger.fs` publication leaves, with a default-off client port, but never specifies **how that type and the envelope/result travel across the actual Client/Server build and authenticated process boundary**.

**Source evidence:** `Server/Server.fsproj:33` compiles `Server/OriginalGitPublisherAdmission.fs`, which declares `OriginalGitPublisherCas`, `OriginalGitPublisherCasReceipt`, `OriginalGitPublisherFailure`, and `IOriginalGitPublisherAuthority` (`Server/OriginalGitPublisherAdmission.fs:16-93`). `Client/Client.fsproj` compiles the two original client writers but has **no** compile/link of `OriginalGitPublisherAdmission.fs`; its only `<ProjectReference>` is `../Common/Common.fsproj` (`Client/Client.fsproj:150-152`). It cannot directly type-check against a Server-owned interface as written. The existing source-linked `Server/WorkStatefulApiContracts.fs` and `Client/Modules/WorkStatefulTransport.fs` are precedent for an explicit client-facing wire/transport seam, *not* evidence that a Server CLR interface is callable across the network. Linking an F# source file into two assemblies also does not magically make separately compiled CLR type identities equivalent.

**Why blocking at design stage:** The task requires the smallest coherent, typed client compatibility seam and narrowly proposed future edit leases. The current plan leaves an unavoidable shared contract/transport and `.fsproj` ownership change unspecified while implying the two leaf files suffice. An implementer could invent a prohibited Client→Server assembly dependency, accidentally duplicate typed authority into the client as a local permission gate, or broaden source ownership after review. These are material architecture/acceptance ambiguities, not requests to implement transport in this docs-only task.
