# P1b: fence replay does not bind operator decision; required race evidence missing

**Blocking protocol finding.** `OriginalGitPublisherFenceRequest` includes `OperatorDecisionId` (`Server/OriginalGitPublisherAdmission.fs:41-45`), and P0 checks only that it is nonempty (`:173-175`). The P1b gateway (`Server/OriginalGitPublisherExecutor.fs:183-238`) neither authenticates nor includes that decision in its durable fence envelope. `Server/OriginalGitPublisherStore.fs:220-247` stores/checks only `fence_id` and `target_sha`; `:264-307` persists witness/high-water, not operator identity. Consequently, a replay with the same `FenceOperationId` and targets but a **different** `OperatorDecisionId` returns the previously positive in-memory fixture barrier; it is not rejected as reused/mismatched authorization. This is observable with a two-request deterministic test and violates the requested exact durable operation/envelope identity. A positive synthetic test is not production authorization, but it still must not model accepting a changed authorization identity.

**Required correction:** bind the complete canonical fence request identity (including `OperatorDecisionId`) to the persisted fence record and check exact idempotent replay, and in any future positive gateway require independently authenticated operator authority rather than trusting the caller's GUID. Add an explicit same-UUID/different-operator negative regression and a restart/replay case.

**Required acceptance-test gap:** `Server.Tests/OriginalGitPublisherGatewayTests.fs:401-413` races eight CAS requests with one another, but **never** starts a barrier while a CAS is in flight or delays a remote callback across the fence boundary. The sequential lost-response test (`:173-194`) and after-the-fact barrier test (`:341-399`) do not establish the P1b task's explicit **fence linearization** and in-flight/lost-response timing matrix (accepted P1a plan §5.3/§5.4). Add deterministic gates on the remote CAS before/after ref advancement, run barrier concurrently, and assert either a durably accounted pre-fence effect or `RecoveryHold`, never a false positive barrier. Also add a source-effect/ref-classification negative test: the bare fixture's trusted inventory (`:73`) has project/account refs only, no `SourceEffect` target, while complete authenticated source-effect coverage is an explicit future requirement. Keep C3/hosted all-client evidence **HARD NO-GO** regardless of these hermetic fixes.
