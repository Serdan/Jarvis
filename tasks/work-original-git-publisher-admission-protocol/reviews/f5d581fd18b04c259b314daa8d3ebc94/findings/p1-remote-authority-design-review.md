## Positive design findings

1. **Trust boundary:** Section 1 rejects client-issued pre-push permits and requires the publisher itself to own the actual ref mutation; explicitly separates local serialization from independently enforced denial of still-valid stale credentials at the remote. This matches the C3 prerequisite and the P0 accepted negative-only contract.
2. **Source alignment:** Section 2 uses the existing additive `Server/OriginalGitPublisherAdmission.fs` typed contract as non-authoritative input, names the relevant project/account publication seams (`Client/Modules/LedgerStore.fs`, `AccountCapacityLedger.fs`) and fences importer, Scheduler, backup, Recovery, API, and live configuration from edits. The audited original source has independent project/account init/CAS and review/integration source-ref push/delete paths; a planner-only check would miss prior-UUID returns and direct ref effects.
3. **Durable linearization:** Sections 3–4 require trusted physical (repo,ref) inventory, authenticated identity and credential generation, canonical UUID+request digest, durable prepare before remote effect, no check/push unlock gap, FencePending and RecoveryHold for partial or uncertain outcomes, immutable exact receipts, independent reinspection, and explicit denial after barrier. It correctly does not claim a SQLite transaction atomically commits a Git push.
4. **No parallel production state authority:** A disposable SQLite fixture is proposed for P1; subsequent production persistence must be an adapter into the existing target Work SQLite transaction/recovery authority, not an independently authoritative second database. Existing FeedbackStore remains distinct.
5. **Test/proof separation:** Section 5 includes two project remotes plus an account remote, uncooperative previously-writable stale clones, alternate ref creation/deletion, UUID identity collisions, remote-head CAS, barrier races and unknown/delayed effects, restart, missing inventory and journals, same-name distinct devices, and off-path regression; A synthetic-state / B disposable-bare-host / C independently verified hosted authority cannot be conflated.

## Mandatory downstream conditions (not design defects)

- **No positive hosted witness today.** The private hosted rulesets, Git/API/SSH/Actions/admin bypass actors, privileged publisher credential and full original ref/channel inventory remain unverified. Current GitHub.com branch/tag protections and a disposable `pre-receive` hook are not interchangeable. Every ref that could carry an original ledger/source effect, including dynamic, alternate, delete and direct API paths, requires independent remote exclusion proof or HARD NO-GO.
- **No unbounded orphaned effect:** P1 implementation must exercise publisher crash/restart while a Git child process or already-admitted remote push is still able to finish. A mere process-local serialization lock or `RecoveryHold` record is not enough for a positive barrier if a previously issued effect can still advance a remote ref. Reconcile/fence the effect itself, not only its response.
- **No fabricated history high-water:** The new journal cannot retroactively attest all original client pending-intent and source-effect journals. Missing/partial enrollment, inability to enumerate old credentials or unexplained remote effects must remain nonpositive.
- **Approval separation:** Accepting this *design* does not approve code leases, implementation, remotes/credential changes, a live gate, C3 importer, source cutover, or Work Scheduler. P1b/P1c/P2 need independent frozen-source review and actual .NET 11 Release and disposable remote test evidence, with separate operator authorization of hosted provisioning/cutover.

**Disposition:** No blocking design-stage defect found. Recommend **Accepted — DESIGN ONLY**, subject to preserving the hard NO-GO and independent subsequent review gates.
