# S01 — P1 — No defined lease-reclaim terminal path for a stalled launch without a work claim

**Frozen source:** `a54261ba05a08df1525542aea82fd952505e3f12`, `docs/specs/work-queues-and-ephemeral-executions.md` §§3, 7–9, 12, 16; especially lines 56–60, 177–199, 268–286, 372–375 and tests 5, 34, 39–41, 55.

## Observation
The design properly separates launch termination from work-item completion, and a normal taskless Manager/NoWork execution uses `TerminalizeLaunch` followed by verified project receipt and account-token release (§7). The newly introduced automatic stalled-execution recovery, however, defines `RecoverStalledExecution` as a project CAS that checks an **unchanged exclusive work claim**, fences its claim generation, and either returns **its item** to the queue or marks it RecoveryBlocked (§9, line 280). A Manager has no work claim; neither does a submitted Worker/Reviewer that stalls before ClaimNextWork. The only special taskless stalled path is a Manager already in `TerminalPreparedHandoff` (§9, line 284). There is no specified no-claim branch, accepted terminal receipt, or negative-space fixture for ordinary taskless stalled launches.

`TerminalizeLaunch` is not an adequate fallback as written: it says a *reconciler* may call it with positive termination evidence, not merely a timestamp (§7, line 197). The spec does not say that a safely validated `Stalled/StopRequested` lease-recovery CAS constitutes that evidence for a taskless launch, nor how pending Manager child-dispatch journals are fenced/reconciled before freeing that Manager token. §9 says stalled logical sessions of all roles may be reclaimed, but its concrete transition only covers claimed work.

## Counterexample
With `maxConcurrentAgents=1`, scheduler admits Manager M, which registers/submits its project launch and begins planning a child, but stalls before preparing handoff or calling `TerminalizeLaunch(ManagerFinished)`. The project records `Stalled/StopRequested` for M, queues its UUID-targeted STOP alert, and `reclaimAfter` expires without cooperative response. M owns the only global token but **has no claimed work item**. The specified generic reclaim operation has no item/claim generation to validate or transition; the special prepared-handoff reconciliation does not apply. If the reconciler cannot prove a `TerminalizeLaunch`-acceptable terminal outcome, token M remains reserved indefinitely and the scheduler correctly refuses a replacement Manager. Releasing on elapsed time alone would contradict the project's own terminal-proof policy. A pre-claim Worker/Reviewer has the same missing branch.

This is an **architecture liveness gap**, not evidence that deployed Jarvis already behaves this way. A fail-closed token is safer than unsafe release, but prevents the promised unattended recovery and can halt the entire account at cap one.

## Required contract
1. Define an explicit **no-claim stalled-launch recovery** branch (or `RecoverStalledLaunchWithoutClaim`) for registered, submitted/observed taskless Manager and zero-claim role launches, with stable launch/UUID/lease generation and original operation ID. Under one project CAS, verify the Stalled/STOP receipt, lease expiry, absence of a work claim, unchanged launch/dispatch generation, and safe journal/external-effect state; fence further dispatch/claim/launch mutations and record one immutable project `StalledReclaimedNoClaim` terminal receipt.
2. Reconcile any Manager-created children and pending/uncertain browser submissions by original journals before terminalizing parent; do not release child tokens as part of parent release. If external effects remain uncertain, retain the original token in explicit RecoveryNeeded/RecoveryBlocked rather than assume success or failure.
3. Verify the project receipt independently, then release **only the current matching parent launch token** by account CAS exactly once. Duplicate recovery, late cooperative finish, delayed child dispatch and late wakeups must be fenced; if Manager is `TerminalPreparedHandoff`, the already-specified Swapped/Aborted protocol takes precedence.
4. Add negative-space cases for (a) stalled ordinary taskless Manager at cap one, with no child; (b) Manager with a confirmed child token and an uncertain child submit; (c) submitted zero-claim Worker, concurrent NoWork and lease recovery; (d) prior prepared handoff vs generic reclaim, plus lost STOP/delayed replay. Account capacity must neither leak after definitive safe recovery nor be released on ambiguous evidence.

**Disposition:** P1, blocking acceptance of the claimed *all-role automatic stalled recovery* contract. All C01/C02 project/account CAS corrections examined in this snapshot remain otherwise sound; no source edits or rollout requested.
