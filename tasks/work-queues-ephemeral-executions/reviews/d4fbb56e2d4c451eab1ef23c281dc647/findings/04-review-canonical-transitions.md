# F04 — P1 — Review claims and work-activation lifecycle need one unambiguous transition contract

**Frozen source:** lines 33–38, 114–132, 144–172, 210–221, 240–251, 299–305.
**Related existing contract:** docs/specs/orchestration-architecture.md review independence; docs/ManagedReviewIntegration.md exact immutable review SHA and independent integration submission.

**Finding.** The existing review ledger already has its own Unclaimed/Claimed/Accepted/ChangesRequested transitions and claimant/version. The proposed review work item also has Available/Claimed/Completed and an activation claimant. The spec promises transactional coordination but does not say exactly how `ClaimNextWork`, direct `claim_review`, `release_review`, `withdraw_review`, `decide_review`, `YieldWork` and `CompleteWork` interlock. If the queue claim succeeds without simultaneously claiming the canonical review, an existing reviewer_inbox client can claim the same review. Conversely, a review may be decided while its queue item remains Claimed. If the reviewer then calls generic `YieldWork` (Claimed -> Available in lines 149–155), a terminally decided review can reappear as Available, contradicting the intent of test 6. If the reviewer crashes between decision and CompleteWork, the design must preserve the verdict and expose recovery without inventing a new verdict or second review.

**Required design resolution.** Specify a transition table for direct legacy and queue-based review APIs during and after cutover: one canonical review claimant/decision, atomic linked work claim or verified reconciliation, and an item completion rule when the canonical subject is terminal. `CompleteWork` must not decide a review; `decide_review` must not silently infer a task close or Git merge. Define review release/withdraw effects on live activations and precedence for decision vs yield/block/recovery. Accepted review creates *eligible integration demand only under an explicit workflow policy and valid target/source provenance*; independent ad-hoc reviews and non-integration tasks remain possible. Integration work must reference exactly the accepted pinned review/source and existing integration records, not mutable source HEAD. Make the source producer/version key of each idempotent publication explicit.

**Required tests.** Queue-claim vs direct-claim race; direct withdraw/release during an activation; verdict before yield; crash after verdict before CompleteWork; late yield after accepted review never reopens review work; concurrent accepted/changes-requested idempotent replay; independent review with no integration target creates no fabricated integration obligation; accepted review on two distinct source revisions cannot mix evidence.
