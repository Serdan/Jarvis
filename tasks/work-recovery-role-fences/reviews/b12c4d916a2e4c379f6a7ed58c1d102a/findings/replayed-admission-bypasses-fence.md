# P1 — Positive Scheduler replay bypasses the durable Recovery veto

**Locations:** `Server/WorkRecoverySqlite.fs`, `seed` (only mutates project coverage, stage bodies and new Recovery marker; it guards but does not change original launch receipts); existing `Server/WorkSchedulerSqlite.fs` lines 580–644.

**Problem.** `WorkSchedulerSqlite.reserve` and `claim` first call `replayOutcome` and return `Ok original` when a matching *previously committed* operation ID and launch record are found (lines 628–632, 640–643), before `reserveFresh`/`claimFresh` validate current project coverage or stage gates. `replayOutcome` checks the receipt's launch provenance but **does not check the project Recovery marker, coverage, STOP, or the original effect's reconciliation state** (lines 584–619). Since G1a seeding leaves original launch rows/receipts intact, a same-UUID retry can receive a positive reservation/claim after durable Recovery seeding. A caller treating this successful return as permission to (re)dispatch an uncertain launch can bypass the promised cannot-dispatch-until-independent-release fence, without any new SQLite transaction. This is precisely the lost-response/original-operation path the Recovery gate must handle.

**Required correction.** Keep the historical receipt and original identity for reconciliation, but distinguish historical idempotent outcome lookup from current dispatch authority. A post-fence Scheduler reserve/claim retry must return a typed Recovery-blocked result or be mediated by an authenticated fence-aware admission API that cannot return actionable authorization until independent release. Coordinate any necessary E0 change through its owner rather than silently editing another lane. A zero-delta capacity CAS cannot fence a read-only replay branch.

**Negative regressions:** (1) create a successful E0 reserve with stable `operationId` and `launchId`; (2) build source snapshot including original launch and seed G1a Recovery; (3) replay the *same* reserve UUID and assert no actionable success; (4) repeat for a previously successful E0 claim UUID; (5) retain read-only exact receipt reconciliation and ensure changed UUID/launch identities still fail closed. The existing G1a test only retries fresh `Guid.NewGuid()` IDs after fencing and misses this path.
