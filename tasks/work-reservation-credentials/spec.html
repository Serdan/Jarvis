[P1][Work] Secret execution credentials for reservations

Parent: work-queues-ephemeral-executions. Scope: cryptographic execution identity and lifecycle only. This is a prerequisite to work-reservation-permissions, which will define granular authorization policy. The current Work architecture's caller-provided labels and agentUUID are coordination handles, not authentication; this task deliberately updates that assumption without prematurely creating an ACL framework.

Objective

Stop executions from asserting another execution's identity simply by changing a publicly visible agentId, role, or UUID argument. Bind an execution to its particular reservation with an unpredictable bearer secret while retaining stateless server operation and the durable Work/launch model.

Implementation

  1. Use launchId as the stable, nonsecret reservation identity across pre-dispatch, registration, alerts, leases, cancellation, recovery and audit. Issue a CSPRNG 256-bit secret for each new reserved execution; persist only SHA-256(secret), launch scope and lifecycle in the existing canonical Git-backed ledger. Never expose plaintext in Git, task specs, shared lists, diagnostic receipts or ordinary logs.
  2. Deliver the secret privately through the approved launcher/bridge to the actual execution, which retains it during its lifetime and across transient reconnects. The launcher may hold it transiently until delivery, but must not expose a retrieval API that returns a secret for a known launchId. Be explicit about cooperative bearer capabilities: copying a secret copies authority; no provider-specific authenticated session identity is required.
  3. On initial execution-originated connection, validate the credential against the persisted verifier and atomically register that launch using the existing CAS/operation receipt. Lost responses and retries of the same execution are idempotent. Competing invalid credentials or a known launchId without its secret cannot register or claim the launch. Preserve one primary claim and terminal/stalled fences.
  4. Use the same credential for subsequent Work-native execution tool calls and resolve the effective launch on the server, never from a supplied public agent or role label. In this first task, authentication confers the current launch's existing operations only; enforcement of project/worktree/operation scopes is explicitly deferred to the separate permissions task. Explain legacy Agent API compatibility and ensure there is no silent fallback from the Work-native path to a freely chosen caller identity.
  5. Prefer a single launch ID rather than minting a redundant per-execution agentUUID. Adapt new Work-native alert/lease/audit plumbing through a narrow transitional compatibility layer. Reconcile the old sessionKey/InitializeAgent contract without retaining unnecessary third identities. Avoid rewriting immutable historical records.
  6. Verification uses persisted ledger state; Jarvis restarts do not invalidate a delivered secret. If plaintext is lost before delivery, reconcile the original one-shot dispatch/journal and safely abandon the unregistered launch before creating a replacement. Never blindly submit a second browser launch or silently regenerate credentials for an uncertain launch.

Acceptance

  • Successful reservation, bootstrap, first registration, claim, checkpoint, finish, reconnect/restart and same-operation replay through the authenticated Work-native path.
  • Changing a public launch ID, agent label or Worker/Lead role string cannot authenticate another execution. Incorrect bearer secrets fail. Two-client competing registration/claims have one canonical winner.
  • STOP, cancellation, invalidation and terminal state revoke future mutations; authentication is recovered across server restart solely from the Git-backed verifier. No secret appears in shared persisted material or error messages.
  • Focused .NET 11 Release and disposable fake-launch/two-clone tests; transparent migration/compatibility notes. No live Scheduler, migration, production browser dispatch, server restart or deployment as part of implementation.

Integration: Coordinate with WQ02 launch ledger, WQ08 scheduler/bootstrap, Work-native tool facade and WQ10 migration. Reuse existing Git CAS, one-shot journal and project/account ownership; no new server-side durable secret store or generalized authorization system. Isolated source, independent frozen review, Lead integration after acceptance. No hosted GitHub Actions or Codex through Jarvis.
