# P1 — grant source scope is not tied to the WQ03 launch-generation checkout

**Frozen source:** `58d4223c6c5e0ff20e41d61c170a15d2ab668fac` (no main integration/cutover).

**Evidence:**
- `Client/Modules/WorkQueueReservationPermissions.fs:165-166` checks `SourceWorktree` for a safe-looking NAME only. `:221-229` requires a nonempty name for Implementation/Integration, but does not derive it from or verify it against the authenticated launch, Work ID, claim generation, registered Git worktree, or pinned source SHA.
- `:221` sets `SourceRef` to `stage.SourceLineage.TargetRef`. Per `Server/WorkQueueContracts.fs:102-110` and `Client/Modules/WorkQueueGitLedger.fs:411-465`, this is the APPROVED TARGET branch/ref and pinned base; the actual continuation/source is separately represented by `ReachableRef` and `ContinuationSha`. The grant therefore does not identify the source branch/commit it purports to scope.
- `:330-335` only compares operation-supplied strings with the stored grant. Equality to an arbitrary approved string is not proof that the selected checkout is the correct generation-bound worktree. WQ03 already enforces a stronger invariant in `Client/Modules/WorkQueueGitLedger.fs:467-529`: `wq03-{workId}-{launchId}-g{claimGeneration}`, linked/registered/detached, correct HEAD, clean, approved repository identity.
- The four new tests exercise a `Planning` stage with `SourceLineage=None` and `SourceWorktree=None` (`Client.Tests/WorkQueueReservationPermissionsTests.fs:71-110,129-161`); the wrong-worktree negative changes the request string but does not try approving another reservation's tree or a wrong source continuation. There is no real Implementation/Integration source-scope positive fixture.

**Why this blocks acceptance of the source authorization contract:** Before any later host bridge can safely enforce this grant for edit/test/integration, an operator-issued scope must be bound to the original Work's approved source identity and current generation, not merely a syntactically valid checkout label plus the integration destination ref. Otherwise a wrong-tree approval or mismapped source-ref check can pass this authorization layer for operations on a different source checkout (or reject a valid source operation). No live route currently calls it, so this finding is a *pre-cutover correctness/security gap*, not evidence of a current production exploit.

**Requested remediation:** Define explicit, unambiguous source-versus-target authority fields and validate the exact registered source checkout/repo/branch or continuation SHA against original WQ03 provenance and Work/launch generation at the winning CAS boundary; reject cross-reservation tree/branch and stale generation. Add two-clone negatives for wrong-but-valid approved worktree names, mismatched source continuation, and a positive source-stage grant. Do not start source jobs or enable the public route as part of this fix.
