[P1][Work] UUIDv4 bearer credentials with explicit tool arguments

Parent: work-queues-ephemeral-executions. Follow-up to: completed work-reservation-credentials. The original task is Closed with reviewed historical source; this task implements only the subsequent protocol refinement, not a second credential system. Downstream prerequisite: work-operator-approved-manual-grants.

Objective

Standardize ephemeral Work execution credentials on cryptographically generated UUIDv4 values passed directly by the model in ordinary Jarvis tool arguments. Preserve the existing Git-backed launch/claim architecture, credential verification and one-shot delivery/recovery semantics.

Requirements

  1. Format and issuance: For each scheduled Work reservation, generate a random UUIDv4 with the system CSPRNG. Keep public launchId distinct from the secret credential. Persist only a stable cryptographic hash of the canonical UUIDv4 text with launch scope, generation and lifecycle in the existing project Git ledger. Reuse existing accepted credential and reservation implementation where possible.
  2. Explicit use: Provide the credential in the launch bootstrap to the model execution. The model passes the UUIDv4 as an explicit argument to the initial authenticated Jarvis operation and all later execution-originated tool calls. Do not assume any provider-independent session identifier, private transport binding, or automatic credential injection by a Jarvis bridge/client.
  3. Identity: Jarvis resolves the effective launch/Work identity by verifying the credential, never by trusting caller-selected agentId, role, public launch ID or displayed label. A valid credential grants only the active launch's existing authority; granular permissions are owned by work-reservation-permissions and its successors.
  4. Lifecycle: Honor existing registration idempotence, stopped/terminal launch fences, original operation receipts and one-shot browser recovery. An already-delivered credential continues to verify after a server restart using its persisted verifier. If delivery is lost, reconcile or abandon the original unregistered launch using existing journal rules; do not create an undocumented second credential or blind re-dispatch.
  5. Compatibility: Inspect the exact integrated credential implementation before editing. Correct only missing UUIDv4 issuance/validation or explicit model-supplied argument wiring. Preserve old Agent history and provide a narrow migration/compatibility seam for existing MCP calls without making freely chosen old labels an authentication fallback.

Acceptance

  • Disposable fake launch emits a UUIDv4 credential, bootstraps the execution, registers on its first explicit credential-bearing call, claims/checkpoints/completes Work, and reuses the same credential on retry/reconnect.
  • Server restart with persisted Git verifier preserves valid execution authentication. Incorrect/malformed credentials, role swapping, and use of another launch's public ID do not authenticate; stop/completion fences remain effective.
  • Review the original integrated code first and make the smallest necessary change. Run local .NET 11 Release focused tests and two-clone/fake-provider checks; produce an exact frozen independent review, integrate only accepted source.

Boundaries: Do not implement manually approved grants or a permission policy in this task; those belong to the dependent task. No new ledger, server credential database, provider-specific identity scheme or speculative authentication framework. No live Scheduler/cutover, production browser send, deployment/restart, hosted GitHub Actions or Codex through Jarvis.
