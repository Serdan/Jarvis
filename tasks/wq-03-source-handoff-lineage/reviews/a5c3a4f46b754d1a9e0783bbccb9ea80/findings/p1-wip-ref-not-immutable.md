# P1 — WIP continuation is only a mutable remote branch tip, not an enforced immutable ref

**Frozen SHA:** `4f0ac4df3f3f437501c8da054c262706ec3f5e64`.

**Evidence:** `Client/Modules/WorkQueueGitLedger.fs:253-275` uses `git ls-remote --refs` to verify a ref's current SHA. `verifySourceHandoff` computes a generation-scoped `refs/heads/jarvis-wip/<work>/<launch>-g<claim>` name and checks the current tip, but the implementation neither creates/protects that ref with a create-only/non-overwrite guarantee nor verifies a durable protected-ref policy or retention. Its own two-clone test explicitly and successfully runs `git push --force origin <pinned-base>:<remote-ref>` after a successful handoff, then force-restores the WIP SHA (`Client.Tests/WorkQueueGitLedgerTests.fs:1085,1094`). Thus the supposed immutable proof is freely mutable in the tested approved remote.

**Impact:** A later role/session or external process with account Git permissions can rewrite/delete the sole continuation ref after the original YieldSource CAS, losing the checkpoint's independently reachable exact WIP SHA. The new `ClaimNext` verification correctly refuses a drifted ref, but that only detects lost source after the fact: it cannot recover a no-longer-reachable immutable continuation. Immutable source lineage and protected WIP retention are acceptance requirements (§9), not properties of `ls-remote`.

**Required correction:** Specify and enforce remote-level immutability/retention for generation refs (e.g. verified protected namespace or equally strong create-only source service with no overwrite/delete path and immutable content-addressed identity); publish under that contract before the ledger handoff CAS and record the durable proof. Add an adversarial test that attempts overwrite/delete and confirms remote refuses mutation, followed by independent successor verification. Until that protection exists, do not claim protected immutable WIP semantics or activate source-writer handoff.
