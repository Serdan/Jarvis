# P1 — Accepted review/submission identity is not bound to the integration stage

**Source:** `Client/Modules/WorkQueueReviewIntegrationAdapter.fs:26-57, 210-262, 267-279, 307-350`; `Client.Tests/WorkQueueReviewIntegrationAdapterTests.fs:111-130`.

**Observed from exact frozen code:** `bindAcceptedIntegration` validates canonical review/submission fields and returns an `AcceptedIntegrationBinding`. `planAcceptedIntegration` places that binding in `StagePlan.Provenance` but builds a `WorkStage` whose persisted fields contain neither `ReviewId`/`ReviewRef`/`ReviewVersion` nor `SubmissionId`/`IntegrationRef`/`SourceSha`/`TargetRef`. The integration fixture explicitly publishes only `plan.Work`; it does not publish or independently CAS-bind `plan.Provenance`. `WorkQueueGitLedger.PublishStage` persists `WorkStage`, not the surrounding plan.

`startPinnedOriginalPush binding ... project` looks up `integration-<binding.SubmissionId>` and checks kind, subject, claim, gate and nonblank push operation. It does **not** compare the accepted binding against any authoritative immutable binding attached to that existing stage. It passes `binding.SourceSha`/`binding.TargetRef` through to `Contracts.startOriginalPush`, which checks only nonblank values before journaling them. **Code-path counterexample:** with a claimed stage published from accepted binding A, pass binding A updated only in `SourceSha` and/or `TargetRef`, preserving task/submission ID. Nothing in this adapter or the pure contract rejects the altered immutable source at push-intent creation. This is a logical inspection finding, not a claim that a real Git push was performed.

Separately, `isAuthorizedIntegration` checks work ID, task, source SHA, target and observed effect but never compares `ReviewId`, `ReviewRef`, `ReviewVersion`, `IntegrationRef`, `TargetHeadAtSubmission` or the canonical submission status with persisted canonical records. A binding with the same task/submission/SHA/target but substituted review identity can return true for an already authorized work stage.

**Required:** The WQ-04 producer must atomically persist (or canonically hash and verify) exact review/submission/SHA/target/source ref/accepted decision/version with the stage generation, project graph/high-water and current source lineage. The claim/push/reconcile/authorization APIs must recheck this authoritative binding against the same verified head, not merely the caller's record. Until that join exists, these functions must be explicitly uncallable on production paths and cannot be treated as proof of `IntegrationAuthorized`. Include negative tests for same-submission altered SHA/target, review-ID/ref substitution, stale submitted target head, and post-accept source edit/new-review requirement. No WQ04 producer changes are requested inside the isolated WQ05 branch; coordinate the reviewed interface and keep final integration blocked.
