# P1 - Valid sequential work stages are mistaken for duplicate migration

**Frozen source:** `199baf8b99b2fe033d3c654926e0645b12ea028a`
**Location:** `tools/Wq10MigrationPreview/Program.cs:304-309` (`duplicateCount > 1`)

The preflight counts *all* canonical `state.works` entries whose `subjectId` matches a legacy task and raises `MULTIPLE_CANONICAL_STAGES` whenever the count exceeds one. This is not a valid duplicate criterion. In the accepted `Server/WorkQueueContracts.fs:575-601`, `publishStage` allows multiple distinct work IDs/stage generations for the same task. It rejects an identical immutable work ID and concurrent unfinished Implementation stages for the same source-writer lineage, but retains completed predecessor stages and permits successor stages. The accepted workflow explicitly has implementation, review, integration and correction successors. Historical stages remain in `Works`.

**Independent reproduction:** use the existing disposable two-clone fixture; add `records/work-queue/origins/task-T1.json` with `sourceHighWater=7`, set all four coverage flags true, and represent `T1` by two *distinct* work IDs: an Implementation stage at generation 1 in `Completed`, followed by an Implementation stage at generation 2 in `Available`. The account/project migration phases both remain `Frozen`, the original attempt is `Finished`, evidence inventories are explicit empty arrays, and the three external observations are true. The frozen CLI returns `NO_GO`, with the *only blocker* `MULTIPLE_CANONICAL_STAGES Demo/T1`; a historical-alert warning also appears. Reproduced independently against the frozen Release binary without production data or source edits. The same happens with completed Implementation followed by FrozenReview.

**Impact:** a normal task that has completed one stage and progressed to a successor can never receive a clean preflight, even if every project record and owner-supplied proof is otherwise consistent. This defeats the practical already-migrated/duplicate acceptance case and adds an ungrounded gate contrary to the operator's policy.

**Minimal correction:** use immutable work/stage identity and generation (and relevant kind/lineage for semantic duplicates) instead of aggregate `subjectId` count. Treat multiple distinct expected stages as historical state to display, not as a duplicate blocker. Continue to report genuinely conflicting same-stage records and incomplete evidence. Add one regression fixture for completed predecessor + successor sharing `subjectId`; retain the existing true-duplicate negative fixture with an actually duplicate logical stage.
