# P1 — Projected winner survives contradictory account/project authority

**Frozen source:** `5218ff0c1dd6c66698008c9a5efe86f8bc815489`, `Client/Modules/WorkQueueCrossProjectHostPreview.fs:355-417` (especially 374-401), against `Client/Modules/WorkQueueCrossProjectPlanner.fs:313-334`.

`ProjectSetComplete` is computed solely from the supplied project snapshots, source/role coverage and unique IDs. The report computes `SimulatedWinner` whenever that flag is true and the account read returned `Ok`, regardless of authority conflicts that the accepted planner explicitly detects. For example, two valid pinned projects, with a held account token for a known launch in project A whose `ProjectAuthoritySha256` (or ledger ID/epoch) contradicts the supplied approved project binding, produce `Planner.Issues` containing `AccountProjectIdentityMismatch`, yet `ProjectSetComplete = true` and `SimulatedWinner = Some ...`. The CLI also exits zero at lines 491-493. A similarly inconsistent held token with no corresponding pinned launch produces `AccountTokenLaunchUnknown` while the host still presents a global winner.

This is an authoritative-evidence mismatch, not merely a full cap. A simulated winner need not be runnable, but it should not be represented as a valid global, pinned cross-project selection while known account/project identity contradicts the asserted set. Explicitly gate global selection validity on account token/launch identity coherence, retaining inspection diagnostics and preserving the intentional cap-full simulation. Add deterministic tests for mismatched authority/hash, missing held launch, and normal full-cap behavior. **Do not** fix by promoting planner `WouldLaunch` or synthesizing launch/browser IDs.
