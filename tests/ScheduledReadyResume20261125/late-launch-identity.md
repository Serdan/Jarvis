# Late-launch identity correction (2026-11-26)

This correction continues frozen candidate `c36c1c58aeed92b2ea1485e8882d9cc15d75c611` after independently accepted finding `late-launch-identity-bypass` (checkpoint 17765). It deliberately does **not** implement transparent post-send recovery.

## Authority and recovery

- The five-minute deadline and exact launch-correlated inbox receipt remain durable. A prompt's launch ID correlates the actor-authenticated first inbox to a specific intent; it is **not** an authenticated provider-execution credential.
- Verified pre-send non-invocation still authorizes the next deterministic intent. A no-check-in receipt records deadline/actor-activity evidence only; it no longer grants replacement authority. Historical no-check-in receipts are treated as holds, not permission. A new successor requires a separately recorded operator resolution with the original owner, exact Ready identity, positive confirmation that the original execution ended, and rationale. This does not erase the diagnostic receipt. Missing coverage is visible and insufficient for replacement.
- Before activity, activation, or registered project command execution, the client checks the exact current Ready episode for an unresolved intent. Ordinary actor-only commands cannot bypass this hold. The explicit inbox must own the unresolved chain and be timely; both the check-in write and activation transaction revalidate the chain. Manual attributed launch of a held target also fails at its intent transaction. The independent nonconflicting manual path and verified no-send retry are preserved.
- After exact activation, ordinary calls remain compatible with existing actor authentication. Safety of an operator-authorized successor depends on actual, positively verified old-execution termination, not a timer, an empty activity feed, a closed tab, or a model's assertion. If termination cannot be verified, **keep the hold**. An old session that can still act after purported termination would be indistinguishable from the new session on ID-less calls once the new one is Working. The current transport has no proven per-execution binding to make that safe; do not interpret this correction as a general session-identity fence. The original unsafe candidate was not deployed by this task; this is not a migration or recovery plan for an already-live unsafe successor.

## Evidence boundary

The tests call the registered post-journal SignalR command core and exercise the promotion wrapper using that same core; they check unchanged canonical head, activation metadata, and unchanged **client-admitted** last-seen on rejected calls. They do not call a live model provider, send a live prompt, deploy, or certify provider session identity. The server's legacy raw authenticated actor-level ingress/last-seen remains a separate observation (including failed attempts), not an exact launch check-in or accepted execution. A raw ingress hint can still appear in activity telemetry; it must not authorize a replacement. No assertion is made that the server can distinguish an old ID-less caller from a new caller. An unavailable ledger does not authorize admission for an existing bound checkout; ordinary unbound source-project behavior is retained. A fresh ledger observation is intentionally required for bound project ingress rather than trusting a possibly stale Working cache; no latency improvement is claimed.

The registered regression covers omitted/wrong IDs, rejected old ID followed by omitted/non-inbox calls, expiry, restart, conflicting manual target, pending-intent retry route, promoted core, old A before and after B, exact B activation, and ordinary conflict-free manual/Working calls. The after-B omitted call is legitimate B **under the verified-termination precondition**, not a claimed ability to distinguish two live executions. The existing scoped suite covers 299/300/301 seconds, unavailable or unrelated activity, concurrent check-in/expiry, no-send retry, other eligible candidates, cleanup, and other scheduler invariants.
